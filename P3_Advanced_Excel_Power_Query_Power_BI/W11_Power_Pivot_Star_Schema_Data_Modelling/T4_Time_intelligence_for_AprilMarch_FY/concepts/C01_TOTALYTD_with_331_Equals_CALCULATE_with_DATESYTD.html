Key concept

TOTALYTD with "3/31" Equals CALCULATE with DATESYTD

Concept: YTD Actual = TOTALYTD([Actual], 'Date'[Date], "3/31") is equivalent to CALCULATE([Actual], DATESYTD('Date'[Date], "3/31"))

Statement

YTD Actual = TOTALYTD ( [Actual], 'Date'[Date], "3/31" )

YTD Actual = CALCULATE ( [Actual], DATESYTD ( 'Date'[Date], "3/31" ) )

Both return, for each cell, the base measure evaluated over the dates from 1 April of the fiscal year containing the last visible date up to that last visible date:

\[ \text{YTD}(d^{*}) = \sum_{d = \text{FYStart}(d^{*})}^{d^{*}} A(d) \]

where \(d^{*}\) is MAX('Date'[Date]) in the current filter context, \(\text{FYStart}(d^{*})\) is the 1 April on or before \(d^{*}\), and \(A(d)\) is the base measure on day \(d\).

Explanation

TOTALYTD is a convenience wrapper: the engine rewrites it as CALCULATE(expression, DATESYTD(dates, year\_end), filter). DATESYTD is the real workhorse — a table function returning the set of dates from the start of the year to the last date in context. CALCULATE applies that set as a filter on 'Date'[Date], overriding the existing date filter (and, on a marked Date table, removing filters from other Date columns such as month name).

Why prefer the CALCULATE form in production models:

  • Composability. Additional filters are just more arguments: CALCULATE([Actual], DATESYTD(...), CoA[Statement] = "PL", KEEPFILTERS(Branch[Region] = "South")).
  • No positional ambiguity. TOTALYTD's third argument is a filter and its fourth the year end; a string literal in third position is treated as the year end, but mixing them up is a common source of errors.
  • Consistency with other patterns. PY YTD, capped YTD and calculation-group items all use DATESYTD inside CALCULATE, so the code base reads uniformly.

The year-end string's day and month are what count; a year, if supplied, is ignored. The string is parsed using the model's locale (c06), so always confirm behaviour by checking that April YTD = April month.

Conditions for correctness: 'Date'[Date] belongs to a contiguous Date table covering whole FYs, the table is marked (or the relationship is on a Date-typed column), and the base measure is additive over time (a flow). For balances, YTD is not meaningful.

Illustration

Employee benefits expense (₹ lakh), FY26: April 310, May 305, June 318, July 330.

Row [Actual] [YTD Actual]
April 2025 310 310
May 2025 305 615
June 2025 318 933
Q1 FY26 933 933
July 2025 330 1,263

At the Q1 row, the last visible date is 30 June 2025, so YTD = 1 April – 30 June = 933, equal to the quarter total — a quick visual test. Both measure forms produce identical values in every cell; a DAX query evaluating both side by side with SUMMARIZECOLUMNS('Date'[MonthYear], "T", [YTD TOTALYTD], "C", [YTD CALCULATE]) is a useful regression test after refactoring.

Practice Questions

Q1. Rewrite and extend [L1]

Rewrite TOTALYTD([Actual], 'Date'[Date], CoA[FSLine] = "Revenue", "3/31") in the CALCULATE + DATESYTD form, then extend it so it returns YTD revenue only for branches in Maharashtra and Gujarat without overriding a user's branch slicer.

💡 Hint: Think about KEEPFILTERS for the branch condition.

Q2. Regression test [L2]

You refactor 25 TOTALYTD measures into CALCULATE form. Design a DAX query that proves, for every month of FY25 and FY26 and every FS line, that old and new measures return identical values, and state what output means the refactoring passed.

Q3. Explain to an auditor [L1]

An internal auditor asks why the YTD in your dashboard for September 2025 (₹ 1,842 lakh) does not equal the sum of January–September 2025 in the GL export (₹ 2,310 lakh). Explain in three sentences, referencing the year-end argument.
