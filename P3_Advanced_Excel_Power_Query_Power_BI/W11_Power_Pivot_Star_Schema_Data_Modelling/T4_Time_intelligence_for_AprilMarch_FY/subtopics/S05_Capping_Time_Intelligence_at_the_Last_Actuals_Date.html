Subtopic note

Capping Time Intelligence at the Last Actuals Date

Scope: Partial current month/year: capping measures at the last actuals date

Why it matters

A Date table always covers whole fiscal years (topic t2), so in November 2025 it already contains December 2025 to March 2026. Actuals stop at the last posted date — for a monthly close, the last closed month-end; for a daily sales flash, yesterday. Without a cap, time-intelligence measures happily evaluate future dates: YTD shows a flat line from December to March, PY YTD at FY level shows the full prior year against eight months of current year, and YoY % for the year reads −35%. These are the numbers that get screenshotted into WhatsApp groups. Capping is not cosmetic; it is what makes comparatives like-for-like.

Core notes

Step 1: define the last actuals date

Last Actual Date =
CALCULATE ( MAX ( GL[Date] ), REMOVEFILTERS () )

REMOVEFILTERS() with no arguments clears every filter in the model, so the measure returns the latest posting date regardless of the slicer selection. Design choices:

  • Data-driven vs closed-period driven. MAX(GL[Date]) picks up stray future-dated vouchers (a post-dated cheque entered for 5 April, a provision dated 31 March during November). For monthly MIS, a better anchor is the last closed period: CALCULATE(MAX('Date'[Date]), 'Date'[IsClosedPeriod] = TRUE(), REMOVEFILTERS()), where the flag is maintained in a close-calendar table (t2 s08).
  • Global vs per-entity. REMOVEFILTERS() ignores the entity slicer; if Branch A has posted through 30 November and Branch B through 25 November, the global cap is 30 November. Use REMOVEFILTERS('Date') instead if each entity should cap at its own last date — but then a consolidated view caps at the latest entity.
  • Parameter table. Some teams let the controller pick the as-of date in a disconnected "As-of" table — useful for re-running October's pack in December.

Step 2: blank future periods

YTD Actual (capped) =
VAR lastDate = [Last Actual Date]
RETURN
    IF (
        MIN ( 'Date'[Date] ) <= lastDate,
        CALCULATE ( [Actual], DATESYTD ( 'Date'[Date], "3/31" ) )
    )

The test uses MIN('Date'[Date]): a period is shown if any part of it is on or before the last actual date. So November (1–30 November) is shown when actuals run to 18 November, but December is blank.

Step 3: cap the comparative window

Blanking future months is half the job. For a partial period, the PY comparative must also be cut at the same day-of-year, otherwise a partial current month or year is compared with a full prior one.

PY YTD (like-for-like) =
VAR lastDate   = [Last Actual Date]
VAR lastDatePY = EDATE ( lastDate, -12 )
RETURN
    IF (
        MIN ( 'Date'[Date] ) <= lastDate,
        CALCULATE (
            [Actual],
            DATESYTD ( SAMEPERIODLASTYEAR ( 'Date'[Date] ), "3/31" ),
            'Date'[Date] <= lastDatePY
        )
    )

Both filter arguments act on 'Date'[Date]; CALCULATE intersects them, so the result is the PY YTD window cut at the PY equivalent of the last actual date. The variable is essential: storing the measure result in lastDatePY before CALCULATE means the boolean filter compares against a constant.

An alternative uses a Date-table flag IsYTD (date's day-of-fiscal-year ≤ day-of-fiscal-year of the last actual date) and filters both periods with 'Date'[IsYTD] = TRUE(), which also works for PY and PY-1 without EDATE.

Worked illustration

Actuals loaded to 18 November 2025. Revenue (₹ crore): FY26 1 April – 18 November = 268; FY25 1 April – 18 November 2024 = 249; FY25 1 April – 30 November 2024 = 262; FY25 full year = 420.

Row Uncapped YTD Uncapped PY YTD YoY Capped YTD Capped PY YTD YoY
Nov 2025 268 262 +2.3% 268 249 +7.6%
FY26 total 268 420 −36.2% 268 249 +7.6%

The uncapped FY row is the classic "revenue collapsed" headline; the uncapped November row understates growth because the PY month is complete.

Applying the cap consistently

  • Wrap every time-intelligence measure (YTD, PY YTD, R12M, MoM) with the same IF(MIN(...) <= lastDate, ...) guard, or centralise the logic in a calculation group (s07) so it cannot be forgotten.
  • For R12M, also cap the anchor: MIN(MAX('Date'[Date]), [Last Actual Date]).
  • For Budget, do not cap: budget exists for all months; but a "YTD Budget" for a YTD variance must be cut at the same date as YTD Actual (pro-rated for a partial month if the budget is monthly — e.g., 18/30 of November budget, or better, a daily phasing profile).
  • For full-year forecast (Weeks 17–20): FY Forecast = YTD Actual (capped) + Budget for months after the last closed month.

Visual-level alternatives

Report authors sometimes use a relative date filter ("in the last 12 months") or a visual-level filter on 'Date'[IsYTD]. These help on a single page but do not protect measures used elsewhere (exports, Analyze in Excel, other visuals). Measure-level capping is the robust solution.

Edge cases & judgement calls

  • Month-end accruals posted late: if October is closed on 7 November with entries dated 31 October, the last posting date jumps around during close week. Use the closed-period flag for MIS and the data date only for flash reports.
  • Pro-rating PY for partial months: cutting PY at the same calendar day is precise for daily data; for businesses with strong weekday patterns (retail weekends), compare same number of weekdays instead.
  • Leap years: EDATE(29 Feb 2024, 12) returns 28 Feb 2025; acceptable.
  • Future-dated vouchers: a single voucher dated 31 March 2026 sets Last Actual Date to the year-end and disables every cap. Add a data-quality check: count GL rows with date > today.
  • Row-level security: REMOVEFILTERS() does not override RLS; a user restricted to one branch sees that branch's last date — usually what you want.

Key takeaways

  • The Date table must cover whole FYs, so future dates always exist; measures must be capped.
  • Define Last Actual Date deliberately: data-driven for flash, closed-period-driven for MIS.
  • Blank periods that start after the last date; cut PY windows at the same day-of-year for like-for-like growth.
  • Store the cap in a variable before using it as a CALCULATE filter.
  • Cap every time-intelligence measure consistently, ideally centrally.

Practice Questions

Q1. Write the capped measures [L1]

Write Last Actual Date, YTD Actual (capped) and PY YTD (like-for-like) measures for a model where the GL is loaded daily and the FY ends on 31 March.

Q2. Quantify the distortion [L2]

Actuals are posted to 12 December 2025. FY26 revenue 1 April – 12 December 2025 is ₹ 615 crore. FY25 revenue was ₹ 590 crore for 1 April – 12 December 2024, ₹ 640 crore for 1 April – 31 December 2024, and ₹ 905 crore for the full year. Compute the YoY % that an uncapped model shows on the December 2025 row and on the FY26 total row, and the like-for-like YoY % a capped model shows.

Q3. Closed period versus last posting date [L2]

During the November close, entries dated 30 November are posted between 1 and 6 December, while a sales team also posts invoices dated 1–4 December. Explain which anchor each of the following should use and why: (a) the board MIS for November; (b) the daily sales flash on 4 December; (c) a full-year forecast refreshed on 3 December.

💡 Hint: Separate "what has been posted" from "what has been closed and signed off".

Q4. Budget comparison for a partial month [L3]

The November 2025 budget is ₹ 75 crore, phased monthly. Actuals are to 18 November. The sales head wants a YTD variance that is fair. Design the YTD Budget measure (including how you would pro-rate November), state the data you would need for a better phasing than straight-line, and describe the risk of each approach.
