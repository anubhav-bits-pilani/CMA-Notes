Subtopic note

Time-Intelligence Prerequisites: Marked, Contiguous Date Table

Scope: Prerequisites: marked Date table, contiguous dates, filters applied through the Date table

Why it matters

The DAX time-intelligence functions (DATESYTD, SAMEPERIODLASTYEAR, DATEADD, DATESINPERIOD, the opening/closing balance family) make assumptions about the date column they receive. When those assumptions are violated they rarely error — they return blanks, partial sums or totals that look plausible. In audit terms, these are control failures in the model's design rather than in individual measures, so they must be checked once, at the model level, before any measure is trusted.

Core notes

Prerequisite 1: a proper Date table

The dates argument of a time-intelligence function should be the date column of a dedicated Date dimension that:

  1. Has one row per day — unique values, no duplicates.
  2. Is contiguous — every day from the first to the last date, no gaps (weekends and holidays included).
  3. Covers whole fiscal years — 1 April of the first FY to 31 March of the last FY, spanning every date in every fact (GL posting dates, budget dates, due dates) plus a comparative year.
  4. Has a column of Date data type with no time component and no blanks.

Why contiguity matters: functions like DATEADD and SAMEPERIODLASTYEAR shift the visible dates; if the shifted dates are missing from the table they simply drop out. DATESYTD returns the dates that exist between year start and the last visible date; if GL dates are used and no posting occurred on 1–3 April (holidays), they are not missing from the sum — but DATEADD on a gap-filled column can return the wrong set, and PARALLELPERIOD/ OPENINGBALANCEYEAR look for specific boundary dates that might not exist.

Prerequisite 2: Mark as Date Table

In Power BI Desktop: select the table → Table tools → Mark as date table → choose the date column. In Power Pivot (Excel): Design → Mark as Date Table. The engine validates uniqueness and contiguity at that moment and rejects the column if it fails.

Effects of marking:

  • Automatic removal of Date-table filters. When a time-intelligence function (or any CALCULATE filter) sets a filter on the marked date column, the engine adds REMOVEFILTERS('Date') implicitly, so filters on month name, FY label, quarter or any other Date column do not intersect with the new date set. Without this, a matrix with 'Date'[Month Name] on rows would compute YTD for November as "dates in YTD and in November" = November only.
  • Date-key relationships work. If the relationship from the fact is on an integer DateKey (YYYYMMDD) rather than a Date column, the implicit removal described above happens only if the table is marked. A relationship on a column of Date type gets the behaviour even without marking, but marking is still recommended.
  • Auto date/time is disabled for that table's columns, removing hidden per-column date tables (and the [Date].[Year] style hierarchies that confuse users).

Also turn off File → Options → Current file → Data load → Auto date/time so that every date column in the model does not get its own hidden calendar.

Prerequisite 3: filter through the Date table

Time intelligence works on the Date dimension, not on fact columns:

  • Pass 'Date'[Date], not GL[Date]. DATESYTD(GL[Date], "3/31") operates on the dates present in the GL — a non-contiguous list — and filters the fact column directly, bypassing the dimension. It may return correct numbers in simple visuals and wrong ones when another fact (Budget) is in the same visual, because Budget is not filtered by GL[Date].
  • Put Date-table columns on axes and slicers, never the fact's date column. A slicer on GL[Date] filters GL only, so CALCULATE replacing the 'Date' filter does not clear the slicer, and the YTD intersects with the slicer range unexpectedly.
  • Hide fact date columns (and foreign keys generally, see t1 c06) so report builders cannot use them.
  • Single active relationship. For a fact with several dates (posting, document, due), only one relationship is active; time-intelligence follows the active one unless USERELATIONSHIP is added inside the same CALCULATE.

Diagnostic checks

Run these in DAX query view or DAX Studio before signing off a model:

EVALUATE
ROW (
    "Rows",        COUNTROWS ( 'Date' ),
    "Distinct",    DISTINCTCOUNT ( 'Date'[Date] ),
    "Span days",   INT ( MAX ( 'Date'[Date] ) - MIN ( 'Date'[Date] ) ) + 1,
    "First",       MIN ( 'Date'[Date] ),
    "Last",        MAX ( 'Date'[Date] ),
    "GL min",      MIN ( GL[Date] ),
    "GL max",      MAX ( GL[Date] ),
    "Orphan GL",   COUNTROWS ( EXCEPT ( VALUES ( GL[Date] ), VALUES ( 'Date'[Date] ) ) )
)

Expected: Rows = Distinct = Span days; First is a 1 April; Last is a 31 March; GL min/max lie inside; Orphan GL = 0 (an orphan usually means a datetime with a time part or a date outside the range).

Worked illustration

A model built from a Tally export has a Date table generated from distinct GL dates: 1,019 rows for 1 April 2023 – 31 March 2026 (1,096 days). Missing days are mostly Sundays and holidays. Symptoms observed:

Measure Expected (₹ lakh) Returned Cause
PY Actual for Feb 2025 1,840 1,840 Shift maps dates that exist
PY YTD for 2 Apr 2025 52 Blank 2 Apr 2024 was not in the table
Opening Balance Year (FY26) 12,400 Blank 31 Mar 2025 (a Monday holiday) missing

The fix is a generated, contiguous calendar (t2), not more DAX.

Edge cases & judgement calls

  • Multiple Date tables: one per role (posting/due) is an alternative to inactive relationships, but each must be marked and contiguous; it doubles slicer confusion. Prefer one Date table with USERELATIONSHIP.
  • DirectQuery sources: marking works, but generating the Date table in the source (SQL view) is preferable to a calculated table for performance.
  • Budget at month grain: store on the first day (or last day) of the month and relate to 'Date'[Date] (t1 c02); time intelligence then works for Budget as for Actual.
  • Time zone: cloud exports in UTC can shift a 31 March 23:30 IST voucher into 31 March 18:00 UTC — still the same date, but a 1 April 01:00 IST voucher lands on 31 March UTC, in the wrong FY. Convert to IST before truncating.
  • Weeks and 4-4-5 periods: built-in functions assume a Gregorian calendar; non-standard periods need custom logic on fiscal columns (related item in topic overview).

Key takeaways

  • Time intelligence requires a unique, contiguous, whole-FY Date column of Date type.
  • Marking the table validates it and makes the engine remove other Date-table filters when the date filter is replaced.
  • Always pass 'Date'[Date] and use Date-table columns on visuals; hide fact date columns.
  • Turn off Auto date/time for the file.
  • Run a diagnostic query (rows = distinct = span; orphans = 0) before trusting any time-intelligence measure.

Practice Questions

Q1. Diagnose blank YTD [L1]

A model relates GL[DateKey] (integer YYYYMMDD) to 'Date'[DateKey]. The Date table is not marked. With 'Date'[Month Name] on rows, the YTD measure returns the same value as the monthly measure. Explain the mechanism and the fix.

Q2. Write the diagnostic query [L2]

Write a DAX query that returns, for each fact table in a model (GL, Budget, AR Ledger), the minimum date, maximum date and count of dates not present in the Date table, and state the expected result for a model ready for time intelligence.

💡 Hint: Combine ROW or UNION with EXCEPT(VALUES(fact[Date]), VALUES('Date'[Date])) per fact.

Q3. Slicer on the fact date [L2]

A report has a between-dates slicer on GL[PostingDate] set to 1 October – 30 November 2025, and a card showing TOTALYTD([Actual], 'Date'[Date], "3/31"). Explain what the card shows and why, and redesign the page so the slicer and the YTD measure behave as the user expects.

Q4. Audit checklist for a time-intelligence model [L3]

You are reviewing a Power BI model built by a consultant for a listed NBFC's monthly MIS. Draft a ten-point review checklist covering the Date table, relationships, measure arguments and visuals, and for each point state the evidence you would collect (screenshot, query result, model metadata).
