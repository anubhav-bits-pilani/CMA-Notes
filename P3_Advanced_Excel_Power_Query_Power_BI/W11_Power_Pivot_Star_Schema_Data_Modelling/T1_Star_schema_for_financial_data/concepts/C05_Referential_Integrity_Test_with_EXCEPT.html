Key concept

Referential Integrity Test with EXCEPT

Concept: Referential integrity test: COUNTROWS(EXCEPT(VALUES(GL[AccountKey]), VALUES(CoA[AccountKey]))) should be 0

Statement

RI Orphan Accounts =
COUNTROWS (
    EXCEPT (
        VALUES ( GL[AccountKey] ),
        VALUES ( CoA[AccountKey] )
    )
)
  • VALUES(GL[AccountKey]) — distinct account keys present in the fact.
  • VALUES(CoA[AccountKey]) — distinct keys in the dimension.
  • EXCEPT(A, B) — rows of A not in B (set difference).
  • Result: the number of fact keys with no matching dimension row. Expected value: 0 (DAX returns BLANK when the set is empty, which a card shows as "(Blank)"; wrap with + 0 or COALESCE(..., 0) to show 0).

Explanation

Referential integrity (RI) means every foreign key in a fact matches a primary key in its dimension. In SQL databases this is enforced by FOREIGN KEY constraints; in Power BI it is not enforced. Unmatched fact rows are assigned to the virtual blank member of the dimension, and the amounts surface as "(Blank)" — or vanish from FS lines while staying in the grand total.

Points to note:

  • VALUES vs DISTINCT on the dimension. VALUES(CoA[AccountKey]) includes the virtual blank row when orphans exist. EXCEPT still returns the orphan keys because the orphans' actual key values (e.g. 905) are not equal to BLANK. DISTINCT excludes the blank row; either works for this test.
  • Filter context matters. As a measure, the test respects slicers. Put it on a card with no filters, or wrap it in CALCULATE(..., REMOVEFILTERS()) so it always tests the whole model.
  • Listing orphans. In DAX query view: EVALUATE EXCEPT(VALUES(GL[AccountKey]), VALUES(CoA[AccountKey])).
  • Amount at risk. Pair the count with value: CALCULATE([Actual], ISBLANK(CoA[AccountKey])) is one approach; a cleaner one sums GL rows whose key is in the EXCEPT result using TREATAS.
  • Repeat per relationship. Test CostCentre, Branch, Date (any posting date outside the calendar range) and the Budget fact as well.
  • If you implemented the Unmapped member (s06), this test should always return 0 by construction; it then guards against regressions in the Power Query keying logic.
  • Power BI's own relationship diagnostics do not show orphan counts; DAX Studio's VertiPaq Analyzer does report "RI violations" per relationship, a useful cross-check.

Illustration

March 2026 refresh. GL has 640 distinct AccountKeys; CoA has 636 rows. The test returns 6 — not 4 — because two CoA keys have no postings (irrelevant here) and six GL keys are missing from CoA. Listing them shows 905–910, all ledgers created on 20 March for a new subsidiary branch. GL postings on those keys total net ₹38.4 lakh debit, which appeared in the P&L matrix as a "(Blank)" FS line row. After adding the six accounts to the CoA mapping and refreshing, the test returns blank (0).

Practice Questions

Q1. Extend the test [L1]

Write RI test measures for CostCentre and Date relationships to GL, and one for the Budget fact's AccountKey, each independent of report filters.

Q2. Quantify orphans [L2]

Write a measure that returns the net GL amount on account keys that are missing from CoA, without relying on the "(Blank)" member, and explain how it behaves when a user filters FY2025-26.

💡 Hint: Use the EXCEPT result as a filter on the GL key column.

Q3. Zero orphans but a blank row [L2]

The RI test returns 0, yet the P&L matrix shows a "(Blank)" row with ₹12 lakh. Keys are integers. Explain how this can happen (consider what VALUES returns on each side when some GL rows have a null AccountKey) and write an additional test that would catch it.
