Key concept

USERELATIONSHIP to Activate an Inactive Date Relationship

Concept: CALCULATE([Actual], USERELATIONSHIP(GL[DueDate], 'Date'[Date])) activates an inactive relationship

Statement

Actual by Due Date =
CALCULATE (
    [Actual],
    USERELATIONSHIP ( GL[DueDate], 'Date'[Date] )
)
  • [Actual] is the base measure SUM(GL[Amount]).
  • GL[DueDate] is the many-side column; 'Date'[Date] is the one-side key. The two must already be linked by an inactive relationship in the model.
  • USERELATIONSHIP is a CALCULATE modifier: during this evaluation, the named relationship becomes active and the otherwise active relationship between the same tables (GL[PostingDate] → 'Date'[Date]) is ignored.

Explanation

Power BI and Power Pivot allow only one active relationship between two tables, to keep filter paths unambiguous. When a fact has several date roles, the extra relationships are created but left inactive (dashed line). They do nothing until a measure explicitly requests them.

Key rules:

  • Exists first. USERELATIONSHIP cannot invent a relationship. If no relationship (active or inactive) exists between the two columns, the measure errors.
  • Argument order does not matter. Either column can be first; the engine identifies the relationship.
  • Only inside CALCULATE/CALCULATETABLE (or functions that accept CALCULATE modifiers). It cannot be used stand-alone or in a calculated column's RELATED call.
  • Several at once. More than one USERELATIONSHIP can appear in a CALCULATE when they activate relationships between different pairs of tables (Microsoft documents a limit of 10 nested calls).
  • Outer vs inner. An inner CALCULATE's USERELATIONSHIP takes precedence over an outer one for the same pair, so a base measure that already activates DueDate cannot be "switched back" by the caller without editing it.
  • RLS restriction. Per Microsoft documentation, it errors if row-level security is defined on a table involved in the relationship.

Time intelligence inside such a measure follows the activated relationship, because the date set built on 'Date'[Date] now filters GL through DueDate.

Illustration

GL extract for trade receivables of a Bengaluru-based NSE-listed auto-ancillary company:

Voucher PostingDate DueDate Amount (₹)
SI-1101 18-Feb-2026 19-Apr-2026 24,50,000
SI-1145 06-Mar-2026 05-May-2026 31,20,000
SI-1188 28-Mar-2026 27-Apr-2026 18,75,000

With FY2025-26 March selected, [Actual] (posting date) returns ₹49,95,000 (the two March invoices). In a matrix with April 2026 on columns, [Actual by Due Date] returns ₹43,25,000 (SI-1101 and SI-1188 fall due in April), which feeds the April collections forecast. The same Date slicer drives both measures.

Practice Questions

Q1. Payables due next quarter [L1]

Write a measure that returns trade payables due in the selected fiscal quarter, using an inactive relationship from GL[DueDate] to 'Date'[Date] and filtering CoA[FSLine] to "Trade payables".

Q2. Why it returns the same number [L2]

A colleague's measure CALCULATE([Actual], USERELATIONSHIP(GL[DocDate], 'Date'[Date])) returns identical values to [Actual] for every month of FY2025-26. List three possible reasons and how you would confirm each.

💡 Hint: Check the model, the data itself and where the visual's date field comes from.

Q3. Two roles in one measure [L3]

Write a measure that returns the amount of invoices posted in the selected month that are due after the end of the current fiscal year (31 March), and explain how the relationship and column-comparison logic interact.
