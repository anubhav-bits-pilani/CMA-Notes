Key concept

CROSSFILTER for Per-Measure Bidirectional Filtering

Concept: CALCULATE([Actual], CROSSFILTER(GL[AccountKey], CoA[AccountKey], BOTH)) sets bidirectional filtering per measure, not in the model

Statement

Accounts with Postings =
CALCULATE (
    COUNTROWS ( CoA ),
    CROSSFILTER ( GL[AccountKey], CoA[AccountKey], BOTH )
)

CROSSFILTER(column1, column2, direction) is a CALCULATE modifier that changes the cross-filter direction of an existing relationship between the two columns for that evaluation only. Direction values:

Value Effect
BOTH Filters propagate both ways (fact filters dimension too)
ONEWAY Standard one-side-to-many-side filtering
ONEWAY_LEFTFILTERSRIGHT / ONEWAY_RIGHTFILTERSLEFT One-way in the stated column order
NONE Relationship ignored for this evaluation

The brief's form CALCULATE([Actual], CROSSFILTER(GL[AccountKey], CoA[AccountKey], BOTH)) is syntactically the same pattern applied to [Actual]; it matters when [Actual] is evaluated in a context where filters on another table reach CoA only via GL.

Explanation

Model-level bidirectional relationships (s03) cause ambiguity and slower queries across the whole model. CROSSFILTER gives the same behaviour only where needed, keeping the model a clean single-direction star.

Typical finance uses:

  • Counting dimension members with activity: number of accounts, cost centres or vendors that posted in the selected period. Without BOTH, the Date filter reaches GL but not CoA, so COUNTROWS(CoA) returns all 650 accounts.
  • Dimension-to-dimension filtering through a fact: "which branches use cost centre X?" — Branch filtered by CostCentre via GL.
  • Disabling a relationship (NONE) for an allocation measure that must ignore cost centre, e.g. total corporate overhead to be allocated by revenue share.

Rules:

  • The relationship must exist (active or inactive); CROSSFILTER does not create one.
  • Direction of a many-to-one relationship can be set to BOTH; for one-to-one it is already both.
  • Row-level security filters still apply; Microsoft documents restrictions on changing relationship behaviour for tables secured by RLS, so test any CROSSFILTER measure under each role (View as role).
  • Prefer it in measures that return dimension counts or lists; for plain [Actual] it usually changes nothing, because filters on CoA already reach GL.

Illustration

Model: Date → GL ← CoA, all single direction. FY2025-26 April selected.

Measure Result
COUNTROWS(CoA) 650 (Date filter does not reach CoA)
[Accounts with Postings] 412 (Date filters GL; BOTH lets GL filter CoA)
DISTINCTCOUNT(GL[AccountKey]) 412 (alternative without CROSSFILTER)

The alternative in the last row is often simpler and faster; CROSSFILTER becomes necessary when you need CoA attributes (e.g. count of FS lines with postings: CALCULATE(DISTINCTCOUNT(CoA[FSLine]), CROSSFILTER(...))).

Practice Questions

Q1. FS lines with activity [L1]

Write a measure returning the number of distinct FS lines that had postings in the selected month, using CROSSFILTER, and a second version that avoids CROSSFILTER.

Q2. Allocation with NONE [L2]

Corporate overhead is posted to cost centre "HO-CORP". Write a measure that returns total corporate overhead for the period regardless of the cost centre on the matrix row, using CROSSFILTER with NONE, and compare it with an ALL(CostCentre) approach.

💡 Hint: Consider whether other CostCentre attributes on the row would still filter GL.

Q3. Review a model change [L3]

A developer sets CoA–GL and CostCentre–GL to Both at model level "to make slicers show only relevant items". The model also contains Budget related to CoA and CostCentre. Explain the consequences and redesign the requirement using CROSSFILTER and visual-level filters.
