Key concept

Virtual Relationship with TREATAS for Month-Grain Budget

Concept: Virtual relationship: CALCULATE(SUM(Budget[Amount]), TREATAS(VALUES('Date'[MonthEnd]), Budget[MonthEnd]))

Statement

Budget =
CALCULATE (
    SUM ( Budget[Amount] ),
    TREATAS ( VALUES ( 'Date'[MonthEnd] ), Budget[MonthEnd] )
)
  • VALUES('Date'[MonthEnd]) returns the distinct month-end dates visible in the current filter context (one for a month cell, three for a quarter, twelve for a fiscal year).
  • TREATAS(table, column) applies that table of values as if it were a filter on Budget[MonthEnd], even though there is no physical relationship between Date and Budget.
  • CALCULATE adds this filter to the Budget evaluation, so only budget rows for the visible month-ends are summed.

Explanation

A virtual relationship transfers a filter from one table to another inside a measure, without a model relationship. TREATAS is the efficient way to do it (older patterns used INTERSECT or FILTER(..., CONTAINS(...)), which are slower).

When to use it:

  • Budget arrives keyed by MonthEnd or PeriodKey and you cannot or prefer not to add a physical relationship.
  • Budget is at a coarser grain on another dimension too — e.g. TREATAS(VALUES(CoA[FSLine]), Budget[FSLine]) for FS-line-level budgets — so a physical relationship to CoA's account-level key is impossible.
  • Avoiding a many-to-many relationship: 'Date'[MonthEnd] is not unique in Date (≈30 rows per month), so a physical relationship from it to Budget would be many-to-many; TREATAS sidesteps that.

Rules and behaviour:

  • Column lineage: TREATAS ignores the lineage of the source values and maps them positionally to the target columns; data types must be compatible (Date to Date).
  • Multiple columns: TREATAS(SUMMARIZE('Date', 'Date'[FY], 'Date'[FiscalMonthNo]), Budget[FY], Budget[FiscalMonthNo]) maps a two-column combination.
  • Other dimensions still need their own path to Budget. If CostCentre physically relates to Budget, CostCentre filters apply normally; if not, add another TREATAS argument.
  • Time intelligence: TOTALYTD([Budget], 'Date'[Date], "3/31") works because TOTALYTD modifies the Date filter, and the inner VALUES('Date'[MonthEnd]) then reflects the YTD date set.
  • Totals: at grand total with no Date filter, VALUES returns all MonthEnds in Date; budget rows with MonthEnd outside the calendar range are excluded — a silent loss if the calendar is too short.
  • Performance is good for small Budget tables; for very large facts, a physical relationship is faster.

Illustration

Budget table (PeriodKey converted to MonthEnd), Opex, cost centre "DEL-SALES":

MonthEnd Amount (₹ lakh)
30-Apr-2025 18.0
31-May-2025 18.5
30-Jun-2025 19.0

In a matrix with FiscalQuarter on rows filtered to FY2025-26 Q1, VALUES('Date'[MonthEnd]) returns {30-Apr-2025, 31-May-2025, 30-Jun-2025}; TREATAS filters Budget to those three rows; the measure returns ₹55.5 lakh. In the April row it returns ₹18.0 lakh. No relationship line exists in the Model view between Date and Budget.

Practice Questions

Q1. Two-column TREATAS [L2]

Budget is keyed by FY ("FY2025-26"), FiscalMonthNo and FSLine, with no relationships to any dimension. Write a Budget measure that responds to Date and CoA filters, and state what it returns when a user drills from FSLine to account level.

💡 Hint: Think about what VALUES(CoA[FSLine]) returns when a single account is in context.

Q2. Missing months [L2]

The grand total of the TREATAS-based Budget measure is ₹4.2 crore lower than the budget workbook total of ₹96 crore. The Date table runs 1-Apr-2022 to 31-Mar-2026, and the budget workbook includes FY2026-27 months. Explain the difference and how you would detect such losses routinely.

Q3. Choose the approach [L3]

Compare a TREATAS virtual relationship with storing budget on MonthStart and relating it physically, for a model with 3 crore GL rows and 80,000 budget rows, considering performance, readability, RLS by cost centre and time-intelligence behaviour. Recommend one with reasons.
