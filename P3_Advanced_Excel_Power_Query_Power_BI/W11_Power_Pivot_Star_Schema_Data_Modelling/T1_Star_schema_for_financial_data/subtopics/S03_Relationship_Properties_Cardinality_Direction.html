Subtopic note

Relationship Properties: Cardinality, Direction, Active Status

Scope: Relationship properties: cardinality (1:*), cross-filter direction (single vs both), active vs inactive

Why it matters

In Power Pivot and Power BI, relationships are not joins executed at query time in the SQL sense; they are filter-propagation paths. Each relationship has three properties — cardinality, cross-filter direction and active status — and together they decide which tables a slicer reaches and how. Most "wrong totals" reported by finance users trace back to a relationship with the wrong cardinality (many-to-many by accident), a bidirectional filter that creates an ambiguous path, or an inactive relationship that the author assumed was being used.

Core notes

Cardinality

Cardinality Meaning Finance usage
One-to-many (1:*) Key unique on the "one" side (dimension), repeated on the "many" side (fact) CoA → GL, Date → GL, CostCentre → Budget. The default and the goal.
One-to-one (1:1) Unique on both sides Rare; usually means two tables should be merged (e.g. CoA and an "Account extra attributes" table).
Many-to-many (:) Key repeats on both sides Budget by month text to a day-level Date table; bridge-less many-to-many. Avoid unless deliberate.

Power BI auto-detects cardinality from the data at the time you create the relationship. If even one duplicate AccountKey exists in CoA (for example the same code mapped to two FS lines in the mapping sheet), Power BI will either refuse 1:* or propose :. Treat a proposed many-to-many as an error signal, not a setting to accept. Fix the duplicate in Power Query (Table.Distinct on the key, or correct the mapping file) and recreate the relationship.

In Excel Power Pivot (Diagram View), relationships are always one-to-many in the classic engine; Power Pivot will reject a relationship if the "lookup" column has duplicates ("The relationship cannot be created because each column contains duplicate values").

Cross-filter direction

  • Single — filters flow from the one side to the many side only: Date filters GL; GL does not filter Date. This is the default for 1:* and the right choice in a star schema.
  • Both (bidirectional) — filters flow both ways: a filter on GL rows (e.g. via a CostCentre filter) also filters CoA to the accounts that have postings.

Why single is preferred:

  1. Ambiguity. With two facts (GL, Budget) sharing CoA and Date, a bidirectional CoA–GL relationship creates a second path from Date to Budget (Date → GL → CoA → Budget). Power BI either refuses the relationship or deactivates one, and results depend on which path the engine chooses.
  2. Performance. Bidirectional filters force the engine to compute the set of dimension keys that exist in the fact for every query.
  3. Semantics. Users expect a CoA slicer to list all accounts, not only those with postings in the selected cost centre; bidirectional filtering changes slicer contents in surprising ways.

When you do need "accounts with postings only" — say, a slicer listing only cost centres that posted in the period — use a measure-level bidirectional filter with CROSSFILTER(..., BOTH) (concept c04), or a visual-level filter on the slicer such as [Actual] <> 0.

One legitimate model-level bidirectional case: a bridge table in a deliberate many-to-many pattern (e.g. a Branch–Region-Manager bridge where one branch has two managers). Even then, set the bridge-to-dimension side to both and keep facts single-direction.

Active vs inactive

Only one active path may exist between any two tables. When GL has three date columns (PostingDate, DocDate, DueDate) and all three relate to 'Date'[Date], only one relationship can be active (solid line in the Model view); the others are inactive (dashed). Measures use the active relationship by default; an inactive one is used only when a measure calls USERELATIONSHIP inside CALCULATE (concept c01, subtopic s04).

Power BI also deactivates relationships automatically to remove ambiguity — for example if you add Branch → Budget while Branch → CostCentre → Budget already exists. Always inspect dashed lines after editing the model.

Other relationship settings

Setting Notes
Assume referential integrity (DirectQuery only) Allows inner joins in generated SQL; irrelevant for Import mode.
Make this relationship active The toggle discussed above.
Security filter direction (both) Only for RLS across bidirectional relationships.
Data types Both key columns must have the same data type; Integer to Integer is best.

Reading a relationship in the Model view

The "1" and "*" markers show cardinality; the arrowhead shows filter direction (a single arrow from dimension to fact means single; a double arrow means both); a solid line is active, dashed is inactive.

Illustration

Model: CoA (650 rows), CostCentre (90), Date (1,826), GL (1.2 crore), Budget (65,000). All relationships 1:*, single, active, except GL[DueDate] → Date (inactive). A matrix with CostCentre on rows and [Actual], [Budget] works. Now someone sets CoA–GL to Both. Power BI warns of ambiguity when you then try to make Budget–CoA active, because Date can reach Budget via Date → GL → CoA → Budget as well as directly. If it lets you proceed by deactivating Budget–CoA, the [Budget] by account suddenly repeats the grand total on every account row — a classic symptom of a broken path.

Edge cases & judgement calls

  • Limited relationships. Relationships between tables in different source groups (composite models) or : relationships are "limited": no blank-row handling for missing keys, and RELATED does not work across them.
  • Blank member. When fact keys have no match in the dimension, the engine adds a virtual blank row on the one side, displayed as "(Blank)". A 1:* relationship is still valid, but totals land in "(Blank)" (see s06, c05).
  • Weak 1:1. If Power BI proposes 1:1 between CoA and a mapping table, consider merging them in Power Query.
  • Excel Power Pivot vs Power BI. Excel's data model supports bidirectional filtering only via CROSSFILTER in measures, not as a model setting, which nudges you toward correct design.

Key takeaways

  • Relationships are filter paths; design them as 1:*, single direction, dimension to fact.
  • A proposed many-to-many usually means duplicate keys in a dimension — fix the data.
  • Bidirectional filtering creates ambiguity with multiple facts and slows queries; apply it per measure instead.
  • Only one active path between two tables; extra date relationships stay inactive and are invoked by USERELATIONSHIP.
  • Always read the Model view markers: 1/*, arrowheads, solid vs dashed.

Practice Questions

Q1. Read the diagram [L1]

In a Power BI model you see: CoA "1" — "*" GL with a double arrow; Date "1" — "*" GL solid; Date "1" — "*" GL dashed; CostCentre "*" — "*" Budget. Describe each relationship's cardinality, direction and active status, and identify which ones you would change and why.

Q2. Duplicate key fix [L2]

When relating CoA to GL, Power BI proposes many-to-many. The CoA mapping workbook has 612 rows but only 604 distinct AccountCodes. Write the Power Query or DAX checks you would run to find the duplicates, and explain the business reasons such duplicates arise in an Indian company's CoA mapping.

💡 Hint: Group by AccountCode and keep counts greater than 1; look at remapped or re-used ledger codes.

Q3. Ambiguous path [L2]

GL and Budget both relate to CoA, Date and CostCentre. A developer sets CostCentre–GL to Both so that a CostCentre slicer shows only cost centres with postings. Trace the filter paths from Date to Budget before and after the change, and propose an alternative that achieves the slicer requirement without a model-level bidirectional filter.

Q4. Interview: why not both everywhere [L1]

An interviewer asks why you would not simply set every relationship to Both "so that everything filters everything". Give three reasons with a finance-report example for each.

Q5. Excel vs Power BI behaviour [L3]

You are migrating a Power Pivot model from Excel to Power BI. In Excel, a measure uses CROSSFILTER to count accounts with postings. In Power BI, a colleague proposes removing the measure and setting the relationship to Both. Evaluate the proposal considering the Budget fact, RLS by Branch and query performance.
