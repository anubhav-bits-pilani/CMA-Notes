Subtopic note

Avoiding Snowflakes and Flat Tables; Diagram View vs Model View

Scope: Avoiding snowflakes and single flat tables; Power Pivot Diagram View vs Power BI Model view

Why it matters

Two shapes dominate badly built finance models. The first is the single flat table: a giant Excel-style extract with every description repeated on every row, which feels simple until you need Budget alongside Actual. The second is the snowflake: dimensions normalised into chains (Account → SubLine → Line → Statement as four tables; CostCentre → Department → Function), often imported straight from an ERP or a MySQL schema. Both work for a first report and fail as the model grows. The star schema sits between them. The tool you use to see and edit the model — Excel's Power Pivot Diagram View or Power BI's Model view — shapes how easily you spot these problems.

Core notes

Why not a single flat table

A flat table (GL with account name, FS line, cost centre name, branch city, month name … all on each row) has these problems:

  1. No second fact. Budget cannot be appended to the same table without inventing blank columns and mixing grains; joining Budget into GL multiplies rows.
  2. Size. Repeated text in crore-row tables inflates memory and refresh time, even with dictionary encoding.
  3. Time intelligence. DAX time-intelligence functions need a separate, contiguous Date table; dates inside a fact have gaps (no postings on Sundays or holidays).
  4. Slicer semantics. A slicer on a fact column lists only values that have transactions; you cannot show "accounts with zero actual but non-zero budget".
  5. Maintenance. A CoA remap means rewriting the fact instead of editing one dimension row.

Flat tables are acceptable for one-off analysis of a single fact of modest size, or as a staging step in Power Query before splitting into facts and dimensions.

Why not a snowflake

A snowflake normalises a dimension into several related tables:

Snowflake Star equivalent
GL → Account → SubLine → FSLine → Statement GL → CoA (with SubLine, FSLine, Statement as columns)
GL → CostCentre → Department → Function GL → CostCentre (with Department, Function columns)
Budget → Month → Date Budget[MonthStart] → Date

Problems in Power BI and Power Pivot:

  • Longer filter chains. A filter on Statement has to traverse three relationships to reach GL. Each hop costs query time and adds a place for broken keys.
  • Hierarchies span tables. Power BI hierarchies must sit in one table, so a snowflaked CoA cannot have a Statement → Line → SubLine → Account hierarchy without RELATED columns.
  • Shared intermediate tables. If both GL and Budget relate to Account, but Budget is at FSLine level and relates to the FSLine table, the FSLine table now has two paths to the facts — a recipe for ambiguity.
  • User confusion. The field list shows many small tables whose purpose is unclear.

The fix is to denormalise in Power Query: merge SubLine, FSLine and Statement into CoA (Merge Queries → expand the needed columns), and do the same for CostCentre. Dimensions in a star are deliberately redundant — "Revenue from operations" repeats on every revenue account row — because dimensions are small and compression handles the repetition.

Legitimate exceptions: a very large dimension (lakhs of customers) with a small attribute table used rarely; or a dimension shared at a coarser grain by another fact (Budget at FSLine level) where a separate FSLine dimension is cleaner than TREATAS. Even then, keep it to one hop.

Power Pivot Diagram View (Excel)

Open via Power Pivot → Manage → Home → Diagram View.

  • Tables appear as boxes; drag a column from the fact onto the matching dimension column to create a relationship.
  • Relationships are one-to-many; Excel's UI does not expose bidirectional filtering (use CROSSFILTER in measures).
  • Create Hierarchy button on a table header builds hierarchies (CoA: Statement → FSLine → FSSubLine → Account).
  • Mark as Date Table is under Design → Mark as Date Table in Data View.
  • Hide columns from client tools by right-click → Hide from Client Tools.
  • Measures are created in the calculation area of Data View or via Power Pivot → Measures → New Measure from the Excel ribbon.
  • Results are consumed in PivotTables or CUBE formulas (CUBEVALUE, CUBEMEMBER), which suits fixed board-pack layouts.

Power BI Model view

  • Shows tables, relationships with cardinality markers (1 / *), direction arrows and active (solid) vs inactive (dashed) lines.
  • Manage relationships dialog lists every relationship with its properties; double-click a line to edit.
  • Layouts (tabs at the bottom) let you create separate diagrams, e.g. "GL star", "Budget star", "Data quality", so large models stay readable.
  • Properties pane: set data category, format, display folder, Sort by column, Is hidden, synonyms (for Q&A).
  • Model explorer (in the Data pane / Model view) lists tables, relationships, measures, calculation groups, roles and perspectives; calculation groups can be created here in current Power BI Desktop versions.
  • The TMDL view (newer Desktop builds) shows the model as code, useful for bulk edits and source control.

Illustration

A plant-accounting team's model has GL (60 lakh rows) with relationships GL → Ledger → LedgerGroup → PrimaryGroup (Tally's group structure imported as three tables), plus CostCentre → CostCategory. A P&L matrix by PrimaryGroup takes 6 seconds and the hierarchy cannot be built. Flattening LedgerGroup and PrimaryGroup into the Ledger table as columns (and CostCategory into CostCentre) cuts the model to five tables, the matrix refreshes in under a second, and a single CoA hierarchy becomes possible.

Edge cases & judgement calls

  • Tally's multi-level groups. Tally allows nested groups of arbitrary depth; flatten to a fixed number of levels (e.g. Level1–Level4) with a path-flattening step in Power Query, filling lower levels with the parent name.
  • Parent-child hierarchies. If the CoA arrives as parent-child (ParentAccount column), use PATH and PATHITEM in calculated columns, or flatten in Power Query, to create fixed level columns.
  • Junk dimensions. Several low-cardinality flags (VoucherType, IsReversal, Source) can be combined into one small "Transaction attributes" dimension rather than left in the fact or split into many tables.
  • Two facts at different grains sharing a dimension at different levels can justify one extra hop; document it.

Key takeaways

  • Flat tables fail with a second fact, time intelligence and "zero actual, non-zero budget" analysis.
  • Snowflakes lengthen filter chains, break single-table hierarchies and risk ambiguous paths; flatten in Power Query.
  • Star dimensions are intentionally denormalised; repetition in small tables is cheap.
  • Power Pivot Diagram View: single-direction 1:* only, hierarchies, Mark as Date Table, CUBE-formula consumption.
  • Power BI Model view: cardinality/direction/active markers, multiple layouts, model explorer, calculation groups.

Practice Questions

Q1. Flatten the snowflake [L2]

A model imported from a MySQL finance database has tables gl_lines, accounts, account_subgroups, account_groups, statements, cost_centres, departments. Describe the Power Query merges needed to produce a star schema, the final list of tables with their keys, and the relationships to create.

💡 Hint: Each chain of lookup tables collapses into one dimension.

Q2. Defend against a flat file [L2]

A business user exports a flat 25-column file from Tally every month and wants Power BI to "just use this". List four concrete report requirements in a monthly MIS that the flat file cannot meet, explaining the technical reason for each.

Q3. Tool choice [L3]

The CFO wants a fixed-format board pack in Excel with exact cell positions, plus an interactive dashboard for business heads. Compare building the model in Power Pivot versus Power BI (with Analyze in Excel) on features, maintenance and governance, and recommend an architecture.

Q4. Parent-child CoA [L3]

The CoA arrives as AccountCode, ParentCode, Name with up to five levels, and some branches stop at level 3. Design the transformation to fixed level columns suitable for a star-schema hierarchy, and explain how you handle ragged branches.

Q5. Model view reading [L1]

List five things you can verify about a finance model in the Power BI Model view without writing any DAX.
