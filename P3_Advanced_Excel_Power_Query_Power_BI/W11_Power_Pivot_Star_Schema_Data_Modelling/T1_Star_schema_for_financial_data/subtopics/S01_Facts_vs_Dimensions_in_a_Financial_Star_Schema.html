Subtopic note

Facts vs Dimensions in a Financial Star Schema

Scope: Facts vs dimensions: GL Transactions, Budget and TB balances as facts; CoA, Calendar, Cost Centre, Branch as dimensions

Why it matters

Every FP&A dashboard, MIS pack or variance report built on Power Pivot or Power BI rests on one design decision: which tables hold numbers you aggregate (facts) and which hold labels you slice by (dimensions). Get this right and a single [Actual] measure works for revenue by branch, opex by cost centre and EBITDA by quarter. Get it wrong and you end up writing a separate measure per report, totals that double-count, and slicers that silently fail to filter one of your tables. For an auditor moving into FP&A, the analogy is the trial balance working paper: the TB amounts are the facts, and the grouping schedule (account → Schedule III line) is the dimension.

Core notes

What a fact table is

A fact table records measurable events or states at a defined grain. Its columns are of two kinds:

  • Foreign keys pointing to dimensions (AccountKey, CostCentreKey, BranchKey, Date).
  • Numeric measures to be aggregated (Amount, Qty, Balance).

Fact tables are long and narrow: lakhs or crores of rows, few columns. They should contain almost no descriptive text. In a finance model there are typically three facts:

Fact Grain Nature Typical source
GL Transactions (GL) One row per voucher line (journal line) Transaction fact — flows, additive Tally Day Book export, SAP FAGLL03/ACDOCA, Oracle GL lines
Budget (Budget) One row per account × cost centre × month Plan fact — flows, additive Long (unpivoted) budget table from Week 10
TB balances (TB) One row per account × month-end Periodic snapshot fact — balances, semi-additive Month-end trial balance extracts

The GL fact carries PostingDate, DocDate, DueDate, VoucherNo, AccountKey, CostCentreKey, BranchKey and Amount (debits positive, credits negative). The Budget fact carries MonthStart (or MonthEnd), AccountKey, CostCentreKey and Amount. The TB fact carries MonthEnd, AccountKey and Balance. Note that TB balances are not summable across time — a March balance plus a February balance is meaningless — which is why the TB is classed as a snapshot fact and needs semi-additive measures (topic 5 of this week).

What a dimension table is

A dimension describes the who, what, where, when of a fact row. It is short and wide: one row per member, many descriptive attributes, and a unique key.

Dimension Key Attributes
Chart of Accounts (CoA) AccountKey AccountCode, AccountName, FSSubLine, FSLine, Statement, SortOrder, SignFactor, Account type (Asset/Liability/Equity/Income/Expense)
Calendar ('Date') Date FY, FiscalQuarter, FiscalMonthNo, MonthName, MonthEnd, PeriodKey, flags
Cost Centre (CostCentre) CostCentreKey CC code, CC name, Department, Function (Sales, Admin, Plant), Owner
Branch (Branch) BranchKey Branch name, City, State, GSTIN, Region, Zone

Dimensions are where filters originate. When a user picks "FY2024-25" in a slicer, the filter is placed on 'Date'[FY]; it flows across the one-to-many relationship into GL, Budget and TB simultaneously. A conformed dimension is one shared by several facts with identical keys and meaning — CoA and Date are conformed across all three facts here, which is what makes Actual-vs-Budget possible without any lookup gymnastics.

Deciding: fact or dimension?

Use these tests:

  1. Do I sum, count or average it? Then it is a measure in a fact. Amount, Qty, Balance, Headcount.
  2. Do I filter, group or label by it? Then it belongs in a dimension. Account name, State, Department.
  3. Is it repeated across many rows with the same value? Text repeated on every voucher line (e.g. "Salaries & Wages" on 40,000 payroll lines) is a dimension attribute that has leaked into the fact.
  4. Does it change independently of the transaction? Account-to-FS-line mapping changes when you restructure the P&L; that is a dimension property, not an event property.

Some items are borderline. Voucher type (Payment, Receipt, Journal, Sales) can stay as a low-cardinality column in GL ("degenerate dimension") or become a small VoucherType dimension. Voucher number is a classic degenerate dimension: it identifies the document but has no attributes worth a separate table, so it stays in the fact. Narration text is high-cardinality and rarely sliced; keep it only if drill-through needs it.

The resulting shape

Dimension (one side) GL (many) Budget (many) TB (many)
CoA[AccountKey] GL[AccountKey] Budget[AccountKey] TB[AccountKey]
'Date'[Date] GL[PostingDate] Budget[MonthStart] TB[MonthEnd]
CostCentre[CostCentreKey] GL[CostCentreKey] Budget[CostCentreKey] not used
Branch[BranchKey] GL[BranchKey] not used (unless budget is branch-wise) not used

Each fact relates to each dimension it uses through a single-direction, one-to-many relationship from dimension (one side) to fact (many side). Facts never relate directly to each other: GL and Budget are compared through the dimensions they share, inside measures:

Actual   = SUM ( GL[Amount] )
Budget   = SUM ( Budget[Amount] )
Variance = [Actual] - [Budget]

Placed in a matrix with CoA[FSLine] on rows and 'Date'[FY] on columns, all three evaluate correctly because the row and column filters reach both facts via conformed dimensions.

Illustration

A mid-size NSE-listed FMCG company has 4.2 crore GL lines over five years, 600 GL accounts, 85 cost centres, 32 branches. A flat extract with account names, branch city and cost-centre names on every line would carry perhaps 25 text columns × 4.2 crore rows. In a star schema the GL fact keeps 8 columns (mostly integers), and the descriptive text lives once in dimensions of 600, 85, 32 and ~1,826 rows. VertiPaq compresses integer key columns extremely well, so the model shrinks from several GB to a few hundred MB, and refresh time falls accordingly.

Edge cases & judgement calls

  • Branch vs Cost Centre overlap. Many Indian companies encode branch inside the cost-centre code (e.g. "MUM-SALES"). Decide whether Branch is a separate dimension keyed in GL, or an attribute of CostCentre. If a cost centre can post to several branches (shared services), Branch must be its own key on the fact.
  • GSTIN as a dimension. For GST reconciliation views, Branch with GSTIN and State acts as a registration dimension; do not store GSTIN text in GL.
  • TB as a separate fact or derived? If you have a complete GL from inception (including opening balance entries), TB balances can be derived as cumulative GL. Many teams still load month-end TB snapshots because they are the audited reference and the GL history may be incomplete after an ERP migration (e.g. Tally to SAP).
  • Budget at a coarser level. Budget may be at FSLine or cost-centre-group level rather than account level; then it relates to a different granularity of the dimension (see s02).
  • Intercompany partner is a dimension (Entity), not a text column in GL, if consolidation eliminations are in scope.

Key takeaways

  • Facts hold keys and numbers at a declared grain; dimensions hold one row per member with descriptive attributes.
  • GL Transactions and Budget are additive flow facts; TB balances are a periodic snapshot fact that is semi-additive.
  • CoA, Calendar, Cost Centre and Branch are conformed dimensions shared by the facts, enabling Actual vs Budget.
  • Facts never join to each other; comparison happens in measures through shared dimensions.
  • Repeated descriptive text in a fact is a design smell — move it to the dimension.
  • Voucher number is a degenerate dimension and may stay in the fact.

Practice Questions

Q1. Classify the columns [L1]

A Tally Day Book export has the columns: Date, VoucherType, VoucherNo, LedgerName, LedgerGroup, ParentGroup, CostCentre, CostCategory, BranchName, BranchState, Narration, Debit, Credit. Classify each as fact key, fact measure, degenerate dimension, or dimension attribute, and state which dimension table each attribute should move to.

Q2. Design three facts [L2]

A company has: (a) 1.8 crore GL lines from FY2020-21 to date; (b) an annual budget by account, cost centre and month for FY2025-26; (c) month-end TB extracts for 60 months. List the tables you would create, the keys on each fact, the measures, and which dimensions are conformed across which facts. Draw the relationships with cardinality.

💡 Hint: Check whether every fact uses every dimension — TB, for instance, may not carry cost centre.

Q3. Size argument for a CFO [L2]

The finance controller wants "one big table" because "it is easier for users". The flat file has 3.5 crore rows and 22 columns, of which 14 are text descriptions. Write a 150-word argument, with a rough estimate of what moves out of the fact, for adopting a star schema instead.

Q4. Branch as attribute or dimension [L3]

Shared-services cost centre "HO-FIN" posts expenses that are allocated to branches through journals carrying a branch tag. Decide whether Branch should be a separate dimension with its own key on GL or an attribute of CostCentre, and explain the reporting consequences of each choice for a branch-wise P&L.

Q5. Interview: conformed dimensions [L1]

In an interview you are asked, "Why can you put Actual and Budget side by side in a matrix if there is no relationship between the GL and Budget tables?" Give a precise answer using the terms filter propagation and conformed dimension.
