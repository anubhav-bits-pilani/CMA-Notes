Subtopic note

Role-Playing Dates via Inactive Relationships

Scope: Role-playing dates (posting vs document vs due date) through inactive relationships

Why it matters

A single finance transaction carries several dates, each answering a different business question. Posting date drives the P&L period and the TB; document (invoice) date drives GST return periods and contractual terms; due date drives receivable and payable ageing, cash-flow forecasting and MSME 45-day compliance under Sec 43B(h) of the Income-tax Act. One Date dimension "plays" each of these roles. Modelling them correctly lets a single report show "revenue booked in Q1" next to "receipts due in Q1" without duplicating tables or measures unnecessarily.

Core notes

The role-playing problem

GL has PostingDate, DocDate and DueDate. You want each to be filterable by the same fiscal calendar. Power BI allows only one active relationship between GL and 'Date', because two active paths between the same tables would be ambiguous. The design options:

Option How Pros Cons
A. One Date table, one active + inactive relationships Relate all three date columns to 'Date'[Date]; PostingDate active, others inactive; use USERELATIONSHIP in measures One calendar, one set of slicers, small model Each alternate-date measure must be written explicitly
B. Multiple Date tables (role-playing copies) Create 'Due Date' and 'Doc Date' as calculated or Power Query copies, each with an active relationship Users can slice by both dates simultaneously ("posted in April, due in June") More tables, duplicated slicers, user confusion over which date slicer to use
C. Unpivot dates Store one row per transaction per date role Rarely appropriate for finance Multiplies fact rows; breaks additivity

For most FP&A models, Option A is correct: posting date is the primary role (it ties to the TB and the statutory books), and due date or doc date analyses are delivered through specific measures.

Writing role-specific measures

Actual = SUM ( GL[Amount] )

Actual by Due Date =
CALCULATE (
    [Actual],
    USERELATIONSHIP ( GL[DueDate], 'Date'[Date] )
)

Actual by Doc Date =
CALCULATE (
    [Actual],
    USERELATIONSHIP ( GL[DocDate], 'Date'[Date] )
)

USERELATIONSHIP activates the named inactive relationship for the duration of that CALCULATE and, because only one path may be active, implicitly deactivates the PostingDate relationship for that evaluation. Filters from 'Date' (FY slicer, month on columns) now land on GL[DueDate]. The relationship must already exist in the model (dashed line); USERELATIONSHIP cannot create one.

Typical finance uses

  • Receivables due profile: customer-invoice debit amounts on trade-receivable accounts, by due month, to build a collections forecast.
  • MSME payables compliance: payables to MSME vendors where due date (or 45 days from acceptance) falls before 31 March and payment has not been made — relevant for the Sec 43B(h) disallowance and Schedule III MSME disclosure.
  • GST period vs books period: document-date revenue by month compared with posting-date revenue to explain timing differences in GSTR-1 vs books reconciliation.
  • Cut-off testing (audit): vouchers whose document date is in March but posting date is in April — computable by comparing the two roles.

Combining roles in one visual

Option A cannot show "posting month on rows, due month on columns" because both axes would come from the same 'Date' table. If that cross-tab is needed (e.g. a receivables vintage matrix), add a small second calendar for the alternate role:

'Due Date' =
SELECTCOLUMNS (
    'Date',
    "Due Date", 'Date'[Date],
    "Due FY", 'Date'[FY],
    "Due Month", 'Date'[MonthName],
    "Due FiscalMonthNo", 'Date'[FiscalMonthNo]
)

Relate 'Due Date'[Due Date] to GL[DueDate] as an active relationship. Better still, generate the copy in Power Query by referencing the Date query so it inherits the same logic. Remember to set Sort by Column on the copy too.

Time intelligence with alternate roles

Time-intelligence functions work through whichever relationship is active in that evaluation:

YTD by Due Date =
CALCULATE (
    TOTALYTD ( [Actual], 'Date'[Date], "3/31" ),
    USERELATIONSHIP ( GL[DueDate], 'Date'[Date] )
)

The outer CALCULATE switches the relationship; TOTALYTD then builds a fiscal-YTD date set on 'Date'[Date], and that set filters GL[DueDate].

Illustration

Invoice INV-0457 to a Pune dealer: document date 25 March 2025, posted 2 April 2025 (late entry), credit terms 60 days so due date 24 May 2025, amount ₹11,80,000 including GST. With PostingDate active, [Actual] on the debtors account shows the debit in April 2025 (FY2025-26). [Actual by Doc Date] shows it in March 2025 (FY2024-25) — a cut-off exception for the FY2024-25 audit. [Actual by Due Date] places it in May 2025 in the collections forecast.

Edge cases & judgement calls

  • Blank due dates. Journals and payroll lines have no due date. With USERELATIONSHIP active, those rows match the Date table's blank member and drop out of any date-filtered result; that is usually desired, but confirm totals.
  • Due dates beyond the calendar. Long-dated retention money or deferred consideration may fall years ahead; the Date table must extend to cover them or those rows fall into "(Blank)".
  • Row-level security. Microsoft documents that USERELATIONSHIP cannot be used when RLS is defined on a table involved in the relationship it activates (it raises an error). If you secure the Date or GL tables, test alternate-date measures under each role, or switch to a dedicated role-playing Date table.
  • RELATED follows the active relationship. A calculated column such as RELATED('Date'[FY]) on GL returns the posting-date FY. For an alternate-date attribute (due-date FY), use LOOKUPVALUE('Date'[FY], 'Date'[Date], GL[DueDate]) or a role-playing copy — explicit and easy to review.
  • Too many copies. Do not create a Date copy for every role "just in case"; each adds slicers and confusion.

Key takeaways

  • One Date dimension plays several roles; only one GL–Date relationship can be active at a time.
  • Make PostingDate active (it ties to books and TB) and keep DocDate and DueDate inactive.
  • Activate an alternate role per measure with CALCULATE([Actual], USERELATIONSHIP(GL[DueDate], 'Date'[Date])).
  • Use a role-playing Date copy only when two date roles must appear on different axes of the same visual.
  • Extend the calendar to cover all due dates; handle blanks deliberately.

Practice Questions

Q1. Write the measures [L1]

Write DAX measures for (a) receivables by due month, (b) FY-to-date sales by invoice (document) date with an April– March year, using the GL table with inactive DocDate and DueDate relationships to 'Date'.

Q2. Cut-off exceptions [L2]

Design a measure that returns the total value of vouchers with a document date in FY2024-25 but a posting date in FY2025-26. State which relationships are used, and explain why a simple USERELATIONSHIP measure alone is not enough.

💡 Hint: You need one date role to filter via the relationship and the other compared as a column condition.

Q3. Vintage matrix [L3]

Credit control wants a matrix with invoice posting month on rows and due month on columns, showing outstanding receivable amounts for FY2025-26. Specify the model changes (tables, relationships, sort columns) and the measure, and list two checks that totals reconcile to the receivables ledger.

Q4. MSME 45-day report [L3]

For the 31 March 2026 tax computation, the tax team needs the list of MSME vendor bills (vendor flag in a Vendor dimension) where the due date per Sec 43B(h) has passed and the amount remains unpaid at year-end. Describe the data you need in GL or AP facts, the date roles involved and the measures, noting any assumptions about how due date is computed when there is no written agreement.

Q5. Debug [L2]

A measure CALCULATE([Actual], USERELATIONSHIP('Date'[Date], GL[DueDate])) returns the same numbers as [Actual]. List the possible causes and how you would check each in the Model view or DAX query view.
