Row Context, Filter Context and Context Transition

Scope: Row context vs filter context, and context transition when an iterator wraps a measure or CALCULATE

Why it matters

Almost every surprising DAX result in a finance model — a variance that totals wrongly, a calculated column showing the grand total on every row, an FX-converted revenue twenty times too large — comes from misunderstanding evaluation context. Excel formulas refer to cells; DAX expressions are evaluated "in a context" that is set by the visual, the slicers, CALCULATE and iterators. If you can say, for any expression, which rows are visible (filter context) and which row is current (row context), you can predict its result. Context transition — the conversion of row context into filter context — is the single concept that separates people who debug DAX by trial and error from those who reason about it.

Core notes

Filter context

The filter context is the set of filters active on the model's columns when an expression is evaluated. It comes from:

  • visual coordinates — the row and column headers of a matrix cell (e.g. CoA[FSLine] = "Revenue from operations", 'Date'[FY] = "FY2025-26");
  • slicers, page, report and visual filters;
  • CALCULATE / CALCULATETABLE filter arguments and modifiers;
  • RLS roles.

Filters on dimension columns propagate through relationships (one → many) to facts. SUM(GL[Amount]) then sums only GL rows that survive all filters. In SQL terms, filter context is the WHERE clause plus the GROUP BY values of the current cell.

Row context

A row context exists when DAX iterates a table row by row and an expression refers to "the current row". It is created by:

  • calculated columns (each row of the table being computed);
  • iterator functions: SUMX, AVERAGEX, MINX, MAXX, COUNTX, FILTER, ADDCOLUMNS, SELECTCOLUMNS, GENERATE, RANKX …

In a row context, GL[Amount] means "the Amount of the current row". Crucially, row context does not filter anything. It does not propagate through relationships (use RELATED to reach the one side) and it does not affect aggregations: inside a calculated column on CoA, SUM(GL[Amount]) returns the total of the entire GL on every row, because no filter context exists in a calculated column.

Filter context Row context
Created by Visuals, slicers, CALCULATE Calculated columns, iterators
Meaning Which rows are visible Which row is current
Propagates through relationships Yes (one → many, or both if set) No (use RELATED / RELATEDTABLE)
Affects SUM, COUNTROWS Yes No

Context transition

Context transition is the transformation of every row context active at that point into an equivalent filter context. It happens:

  1. whenever CALCULATE (or CALCULATETABLE) is invoked inside a row context; and
  2. whenever a measure reference is evaluated inside a row context — because every measure is implicitly wrapped in CALCULATE.

The current row's values on all columns of the iterated table become filters (for a table with a unique key, effectively a filter on that row), and those filters then propagate through relationships.

Example, a calculated column on CoA:

-- Calculated column on CoA
Total GL (wrong)   = SUM ( GL[Amount] )               -- same grand total on every row
Total GL (correct) = CALCULATE ( SUM ( GL[Amount] ) ) -- context transition: this account only
Total GL (measure) = [Actual]                         -- same as above; measure implies CALCULATE

In an iterator:

Sales by Customer (correct) = SUMX ( Customers, [Sales] )
Sales by Customer (wrong)   = SUMX ( Customers, SUM ( Sales[Amount] ) )

In the first, [Sales] triggers context transition for each customer row, so it returns that customer's sales; the SUMX adds them, giving the correct total (and the same result as [Sales] itself when customers are unique). In the second, SUM(Sales[Amount]) ignores the row context and returns the total sales in the current filter context for every customer; SUMX then multiplies the total by the number of customers.

Costs and traps of context transition

  • Duplicate rows. If the iterated table has duplicate rows (no unique key, e.g. iterating a fact table with identical lines), context transition filters on all column values, so each duplicate's evaluation sees all the identical rows — the result is multiplied. Iterate dimension tables or VALUES(column), not raw facts, when calling measures.
  • Performance. Context transition over crore-row facts is expensive; iterate the smallest table that gives the needed granularity (VALUES('Date'[MonthEnd]), VALUES(CoA[AccountKey])).
  • Calculated columns referencing measures in fact tables can create circular dependencies and are slow at refresh.
  • Transition removes nothing. Context transition adds filters; existing filters from the visual remain unless overridden on the same columns.

Illustration

Data: three customers in the current filter (FY2025-26, Branch = Pune) with sales ₹40 lakh, ₹25 lakh and ₹15 lakh (total ₹80 lakh).

Expression Result Why
[Sales] ₹80 lakh Filter context: Pune, FY2025-26
SUMX(Customers, [Sales]) ₹80 lakh Context transition per customer: 40 + 25 + 15
SUMX(Customers, SUM(Sales[Amount])) ₹240 lakh 80 evaluated three times (row context ignored)
AVERAGEX(Customers, [Sales]) ₹26.67 lakh Average sales per customer

(Strictly, Customers inside SUMX here means the customers visible in the filter context; if the Customers table is not filtered by the Branch slicer — e.g. Branch filters Sales but not Customers — SUMX iterates all customers, but customers without Pune sales contribute zero to the correct version and ₹80 lakh each to the wrong one.)

Edge cases & judgement calls

  • Nested row contexts. In SUMX(CoA, SUMX(RELATEDTABLE(GL), ...)) two row contexts exist; EARLIER or, better, VAR captures the outer value.
  • ALLSELECTED and iterators. ALLSELECTED reads the "shadow" filter context left by visual filters; inside iterators with context transition, its result can surprise — test carefully (s05).
  • Measures in calculated columns of the Date table are fine for small tables (e.g. IsYTD flags), but avoid them on GL.
  • Blank rows from relationships. Iterating VALUES(CoA[AccountKey]) includes the blank member if orphans exist; DISTINCT excludes it.

Key takeaways

  • Filter context decides which rows are visible; row context decides which row is current.
  • Row context does not filter and does not follow relationships; aggregations ignore it.
  • CALCULATE and every measure reference convert row context into filter context (context transition).
  • SUMX(Customers, [Sales]) sums per-customer sales; SUMX(Customers, SUM(Sales[Amount])) repeats the total.
  • Iterate small, unique-keyed tables when calling measures to avoid duplication and slow queries.

Practice Questions

Q1. Predict the column [L1]

On the CoA table (650 accounts), you add three calculated columns: A = SUM(GL[Amount]), B = CALCULATE(SUM(GL[Amount])) and C = [Actual]. GL total is ₹0 (balanced) and account 400100 has −₹12 crore. State the value of A, B and C on the 400100 row and explain why.

Q2. Explain the inflated total [L2]

A measure Revenue INR = SUMX(Sales, SUM(Sales[AmountFC]) * RELATED(FX[Rate])) returns ₹3,400 crore for April 2025 while the expected figure is about ₹42 crore. Explain the cause using context terminology and correct the measure.

💡 Hint: Decide which part of the expression should be row-level.

Q3. Duplicates and context transition [L2]

GL has two identical rows (same voucher, account, date, cost centre, amount ₹50,000). SUMX(GL, [Actual]) returns ₹2,00,000 for them instead of ₹1,00,000. Explain why and propose two ways to avoid the problem.

Q4. Interview: SUMX vs SUM [L1]

In an interview, explain the difference between SUMX(Customers, [Sales]) and SUMX(Customers, SUM(Sales[Amount])) in under 100 words, using the phrase "context transition".

Q5. Choose the iteration grain [L3]

You need average monthly opex per cost centre for FY2025-26 (sum of opex per month, averaged over 12 months, then shown by cost centre with a total row). Write the measure, state which table you iterate and why, and describe how the total row is computed.
