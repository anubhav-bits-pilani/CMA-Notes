Subtopic note

RELATED and RELATEDTABLE in Columns and Iterators

Scope: RELATED (many → one) and RELATEDTABLE (one → many) in calculated columns and iterators

Why it matters

Row context does not follow relationships (s01). When a GL row needs its account's sign factor, its cost centre's function or the exchange rate for its currency-month, or when a CoA row needs the count of its postings, you must explicitly navigate the relationship. RELATED walks from the many side to the one side and returns a single value; RELATEDTABLE walks from the one side to the many side and returns a table. These two functions power sign-aware P&L measures, FX conversion, mapping-completeness checks and dimension-level flags — and they are frequently misused in ways that bloat the model or fail silently.

Core notes

RELATED — many → one

RELATED ( <column on the one side> )

Requires a row context on the many-side table (a calculated column on GL, or an iterator over GL) and an active relationship path (one or more many-to-one hops) to the target table. Returns the value of the column for the related row.

In an iterator (preferred for aggregations):

Actual Signed = SUMX ( GL, GL[Amount] * RELATED ( CoA[SignFactor] ) )
Revenue INR   = SUMX ( Sales, Sales[AmountFC] * RELATED ( FX[Rate] ) )

In a calculated column (only when the attribute is needed for slicing on the fact or for a further row-level calculation that must be stored):

-- Calculated column on GL (generally avoid; shown for illustration)
GL[FSLine] = RELATED ( CoA[FSLine] )

Storing dimension attributes on the fact duplicates them across crores of rows — exactly the "descriptions in the fact" anti-pattern (topic 1). Use the dimension column directly in visuals instead.

Rules:

  • Chain of relationships: RELATED can traverse multiple many-to-one hops (GL → CostCentre → Department if snowflaked).
  • Active relationship by default. RELATED follows the active relationship. Rather than relying on USERELATIONSHIP wrappers to steer it through an inactive one, use LOOKUPVALUE (or a role-playing dimension copy) for alternate keys such as due date — it is explicit and easy to review.
  • Limited relationships (many-to-many, cross-source-group) do not support RELATED.
  • Orphans: for fact rows with no matching dimension row, RELATED returns BLANK — e.g. blank SignFactor → GL[Amount] * BLANK() = blank → amount drops out of Actual Signed. Protect with the Unmapped member (topic 1 s06) or COALESCE(RELATED(CoA[SignFactor]), 1) plus a data-quality alert.

RELATEDTABLE — one → many

RELATEDTABLE ( <table on the many side> )

Requires a row context on the one-side table; returns the rows of the many-side table related to the current row. It is equivalent to CALCULATETABLE(<table>) — i.e. it performs context transition — so it respects the current filter context too when used inside measures.

Calculated columns on dimensions (small tables — acceptable):

CoA[PostingCount]   = COUNTROWS ( RELATEDTABLE ( GL ) )
CoA[HasPostings]    = NOT ISEMPTY ( RELATEDTABLE ( GL ) )
CoA[LifetimeActual] = SUMX ( RELATEDTABLE ( GL ), GL[Amount] )

These are static (computed at refresh) and ignore report filters — useful for data hygiene (accounts never posted to, dormant cost centres) but not for period-specific reporting.

In iterators (measures):

Accounts Over 1 Cr =
COUNTROWS (
    FILTER ( CoA, SUMX ( RELATEDTABLE ( GL ), GL[Amount] ) > 10000000 )
)

Each CoA row's RELATEDTABLE(GL) is filtered by the current filter context (period, cost centre) plus the current account, so the count reflects the selected period. [Actual] > 10000000 gives the same result more readably.

RELATED vs LOOKUPVALUE vs measures

Need Use
Attribute of the related one-side row inside a fact iterator RELATED
Value from a table with no (or an inactive) relationship LOOKUPVALUE(result, searchCol, value, …)
Aggregate of many-side rows per dimension row, responsive to filters A measure (context transition)
Static per-dimension-row aggregate for hygiene RELATEDTABLE in a calculated column

Illustration

GL extract (April 2025) with CoA sign factors:

Voucher Account FSLine Amount (₹) SignFactor Amount × SignFactor
SV-01 400100 Revenue from operations −18,00,000 −1 18,00,000
SV-02 400900 Revenue from operations −50,000 −1 50,000
PV-11 510100 Employee benefits expense 4,20,000 +1 4,20,000
JV-07 999999 (no CoA row) 75,000 blank blank

[Actual Signed] for April = ₹22,70,000 and silently omits JV-07's ₹75,000. CoA[PostingCount] for 400100 shows the lifetime count of postings, unchanged by any slicer.

Edge cases & judgement calls

  • RELATED in a measure without an iterator errors: "RELATED requires a row context". Wrap in SUMX/FILTER.
  • Performance. RELATED inside SUMX over a large fact is generally fast (the storage engine resolves the join), but complex expressions per row fall back to the formula engine. Consider applying the sign factor in Power Query if it never changes (but then never again in DAX — topic 6 pitfall).
  • Bidirectional alternatives. Do not set relationships to Both just to make RELATED "work backwards"; use RELATEDTABLE or a measure.
  • Calculated column on a fact with RELATED prevents some incremental-refresh optimisations and adds memory — measure-time RELATED is preferred.
  • Multiple paths. If two active paths exist (should not in a star), RELATED's path is ambiguous and errors.

Key takeaways

  • RELATED: from a many-side row to its one-side attribute; needs row context and an active relationship.
  • RELATEDTABLE: from a one-side row to its many-side rows; performs context transition.
  • Use RELATED inside iterators (SUMX) for row-level maths such as sign factors and FX rates.
  • RELATEDTABLE in dimension calculated columns gives static hygiene metrics; use measures for period-specific counts.
  • Orphan keys make RELATED return blank and silently drop amounts — guard with an Unmapped member.

Practice Questions

Q1. Choose the function [L1]

For each requirement, choose RELATED, RELATEDTABLE, LOOKUPVALUE or a measure: (a) sign factor in an Actual Signed measure; (b) flag on CostCentre for "no postings in five years"; (c) FX rate from a table keyed on Currency and MonthEnd with no relationship; (d) number of vouchers per account in the selected month.

Q2. Silent drop [L2]

[Actual Signed] for FY2025-26 is ₹3.2 crore lower than [Actual] adjusted manually for signs. Explain how orphan keys cause this through RELATED, and write a measure that quantifies the dropped amount.

💡 Hint: Iterate GL rows where the related sign factor is blank.

Q3. Dormant accounts [L2]

Write calculated columns on CoA for (a) last posting date and (b) a flag "Dormant" if no posting in the last 24 months from the last actuals date, and explain why these are computed as columns rather than measures.

Q4. Snowflake traversal [L3]

In a snowflaked model GL → CostCentre → Department → Function, RELATED(Function[FunctionName]) works in a GL iterator. Explain why it works, its cost, and how you would flatten the model while keeping existing measures valid.
