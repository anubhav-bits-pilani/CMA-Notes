Subtopic note

Iterators SUMX and AVERAGEX for Row-Level Maths

Scope: Iterators SUMX and AVERAGEX for row-level maths (qty × rate, FX conversion)

Why it matters

Many finance numbers are not stored; they are computed per row and then aggregated: invoice value = quantity × rate, INR revenue = foreign-currency amount × that month's exchange rate, standard cost of sales = quantity × standard cost, GST = taxable value × rate. The order matters: \(\sum (q \times r) \neq (\sum q) \times (\sum r)\) and usually \(\neq (\sum q) \times \bar{r}\). Iterators perform the row-level multiplication first and aggregate second, inside a measure, so the result responds to every filter without bloating the model with calculated columns. AVERAGEX adds correct averaging at a chosen grain — average monthly sales, average daily cash — which simple AVERAGE over a fact column cannot do.

Core notes

Syntax and semantics

SUMX ( <table>, <expression> )
AVERAGEX ( <table>, <expression> )
  1. Evaluate <table> in the current filter context.
  2. For each row, create a row context and evaluate <expression>.
  3. Aggregate the per-row results: SUMX adds them; AVERAGEX averages them, ignoring blanks (blank results are not counted in the denominator; zeros are).

Family: SUMX, AVERAGEX, MINX, MAXX, COUNTX, COUNTAX, PRODUCTX, CONCATENATEX, RANKX. SUM(col) is syntactic sugar for SUMX(table, col).

Qty × rate

Sales Value = SUMX ( Sales, Sales[Qty] * Sales[Rate] )

Row-level multiplication, then sum. Contrast:

  • SUM(Sales[Qty]) * SUM(Sales[Rate]) — multiplies total quantity by the sum of rates: meaningless.
  • SUM(Sales[Qty]) * AVERAGE(Sales[Rate]) — simple average rate, ignores the quantity mix; wrong whenever rates vary across lines.

FX conversion

Foreign-currency revenue must be converted at the rate applicable to each transaction (Ind AS 21.21: spot rate at the date of transaction, or an average rate for a period if rates do not fluctuate significantly — Ind AS 21.22). With a rate table FX (one row per currency × month, related many-to-one from Sales via a composite key or a CurrencyMonthKey):

Revenue INR = SUMX ( Sales, Sales[AmountFC] * RELATED ( FX[Rate] ) )

RELATED fetches the rate from the one side for the current Sales row (concept c04). If the rate table is daily and related through Date, the same pattern applies.

Without a relationship (e.g. rates keyed by currency and MonthEnd), use LOOKUPVALUE inside the iterator — slower but flexible:

Revenue INR (lookup) =
SUMX (
    Sales,
    Sales[AmountFC]
        * LOOKUPVALUE ( FX[Rate], FX[Currency], Sales[Currency], FX[MonthEnd], EOMONTH ( Sales[InvoiceDate], 0 ) )
)

A faster pattern iterates at a coarser grain — currency × month — and converts aggregated FC amounts:

Revenue INR (grouped) =
SUMX (
    SUMMARIZE ( Sales, FX[Currency], FX[MonthEnd] ),
    CALCULATE ( SUM ( Sales[AmountFC] ) ) * CALCULATE ( MAX ( FX[Rate] ) )
)

Valid when one rate applies per currency-month (average-rate policy). Context transition (CALCULATE) turns each group into filters on FX[Currency] and FX[MonthEnd]: those filters select exactly one FX row (its rate) and propagate to Sales, giving the group's FC total. Grouping by 'Date'[MonthEnd] instead would be a subtle bug — the Date filter reaches Sales but not FX (FX sits on the one side of Sales), so MAX(FX[Rate]) would return the highest rate of any month for that currency.

AVERAGEX at the right grain

Avg Monthly Revenue = AVERAGEX ( VALUES ( 'Date'[MonthEnd] ), [Revenue] )
Avg Daily Cash      = AVERAGEX ( VALUES ( 'Date'[Date] ), [Closing Cash] )
Avg Invoice Value   = AVERAGEX ( VALUES ( Sales[InvoiceNo] ), [Sales Value] )

The table argument defines the averaging grain. AVERAGE(GL[Amount]) averages voucher lines, which is almost never the business question. In AVERAGEX, months with blank [Revenue] are excluded; if a month with no sales should count as zero, use [Revenue] + 0 (but then future months in the calendar also count — combine with an IsYTD filter).

Calculated column vs iterator

Approach Model size Responds to filters Refresh cost When
Calculated column Sales[Value] = [Qty] * [Rate], then SUM Adds a column (high cardinality) Yes (aggregated by SUM) At refresh Very large models where query speed matters and the column compresses well
SUMX(Sales, Sales[Qty] * Sales[Rate]) No extra storage Yes At query Default; storage engine handles simple row maths efficiently

For simple arithmetic between columns of the same table, VertiPaq's storage engine computes SUMX very quickly; prefer the measure. If the computation needs RELATED or LOOKUPVALUE across a crore rows, test both.

Illustration

Invoice Currency AmountFC Month Rate (₹) INR
E-101 USD 50,000 Apr-25 85.50 42,75,000
E-102 USD 20,000 May-25 85.20 17,04,000
E-103 EUR 30,000 May-25 95.80 28,74,000

[Revenue INR] for Q1 = ₹88,53,000. SUM(Sales[AmountFC]) * AVERAGE(FX[Rate]) would add USD and EUR amounts (1,00,000 "FC") and multiply by an average rate (≈ 88.83) — ₹88.83 lakh, coincidentally close but conceptually wrong because it mixes currencies; change the mix and the error grows.

Edge cases & judgement calls

  • Blank rates. If FX has no row for a currency-month, RELATED returns blank and the line contributes blank — revenue silently drops. Add a data-quality measure counting Sales rows with blank RELATED(FX[Rate]).
  • INR rows. Domestic sales in INR need a rate of 1 in FX (currency "INR") or COALESCE(RELATED(FX[Rate]), 1) only for INR — never default all missing rates to 1.
  • Monetary items at closing rate. Receivables in FC at year-end are translated at the closing rate (Ind AS 21.23); that is a balance-sheet measure using the closing rate, not the transaction rate.
  • Precision. Multiply then round at presentation, not per row, unless the ERP rounds per invoice (then match the ERP to tie out).
  • PRODUCTX for compounding: PRODUCTX(VALUES('Date'[MonthEnd]), 1 + [Monthly Return]) - 1 gives a compounded return.

Key takeaways

  • Iterators evaluate an expression per row, then aggregate — essential for qty × rate and FX conversion.
  • SUMX(Sales, Sales[AmountFC] * RELATED(FX[Rate])) converts at each transaction's rate per Ind AS 21.
  • AVERAGEX's table argument defines the averaging grain (months, days, invoices).
  • Prefer measures over calculated columns for simple row maths; test when lookups are heavy.
  • Monitor blank rates — they silently drop revenue.

Practice Questions

Q1. Correct the measure [L1]

Explain why Sales Value = SUM(Sales[Qty]) * AVERAGE(Sales[Rate]) is wrong for an invoice table where rates vary by customer, and write the correct measure.

Q2. FX conversion build [L2]

Sales has InvoiceDate, Currency (USD, EUR, AED, INR) and AmountFC. FX has Currency, MonthEnd and AvgRate. Describe the key you would create to relate Sales to FX, write the INR revenue measure, and write a data-quality measure that counts Sales rows lacking a rate.

💡 Hint: A composite key such as Currency & MonthEnd can be built in Power Query on both tables.

Q3. Average monthly opex [L2]

FY2025-26 opex by month (₹ crore): Apr 8.2, May 8.6, Jun 9.0, Jul 8.8, Aug 9.4, Sep 9.1; no actuals yet for Oct–Mar. Write a measure for average monthly opex for the FY that returns the average of the posted months only, and explain what AVERAGEX(VALUES('Date'[MonthEnd]), [Opex] + 0) would return instead.

Q4. Grouped iteration [L3]

Sales has 2 crore rows across 6 currencies and 60 months. Compare the row-by-row SUMX with RELATED and the grouped SUMMARIZE-based conversion on performance and correctness, and state the accounting policy condition under which the grouped version is valid.
