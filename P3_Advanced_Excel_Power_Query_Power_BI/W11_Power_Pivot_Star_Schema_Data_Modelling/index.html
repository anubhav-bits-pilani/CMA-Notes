How this week fits

This is the core modelling week of Phase 3 (Advanced Excel, Power Query & Power BI Automation). Week 10 gave you clean inputs from Power Query: a typed GL fact, an unpivoted long budget, and a CoA mapping with FS lines and sign factors. This week turns those tables into a semantic model — a star schema with a marked Indian fiscal Date table — and writes the DAX that finance users consume: Actual, Budget, variances, YTD and prior-year comparisons, closing balances that do not sum across months, and a formatted P&L with GP, EBITDA and EBIT subtotals and margins.

The six topics form a sequence. Topic 1 designs the star schema (facts, dimensions, grain, relationships, role-playing dates, CoA hierarchy, Unmapped member). Topic 2 builds the April–March calendar. Topic 3 teaches the core DAX functions and evaluation context. Topic 4 applies them to time intelligence for an FY ending 31 March. Topic 5 handles semi-additive balance-sheet measures. Topic 6 renders the P&L layout with subtotals and sign-flip.

Prerequisites: Week 10 outputs; Weeks 1–4 knowledge of Schedule III, normal balances and the year-end close; SQL joins and keys from your MySQL work. What comes next: Week 12 extends to Excel cube formulas and board-pack automation on the same model; Week 14 builds the 3-statement model whose balance-sheet schedules mirror topic 5; Weeks 17–20 (FP&A) add forecast facts and variance analysis on the conformed dimensions designed here.

SQL keys and Java control flow mapped to DAX

SQL keys, joins and cardinality; Java variables and conditionals map to DAX VAR/RETURN and SWITCH

Primary key = the unique column on the dimension ("one" side); foreign key = the fact column ("many" side). A Power BI relationship is like a predefined LEFT JOIN from fact to dimension used for filter propagation; cardinality 1:* corresponds to a unique key joined to a repeating one. Anti-joins (LEFT JOIN … WHERE key IS NULL) become the EXCEPT-based referential-integrity test. Java habits transfer: double diff = actual - budget; becomes VAR Diff = [Actual] - [Budget]; return becomes RETURN; a switch or if-else if chain becomes SWITCH(TRUE(), cond1, result1, cond2, result2, else). Unlike Java, DAX variables are immutable and evaluated once in the context where they are defined.

P&L vs BS accounts and the closing entry

P&L vs BS accounts, normal balances, closing entries to retained earnings → Week 1–4

P&L accounts (income, expenses) are flows: they reset each year, and their year-end balances are closed to retained earnings (Schedule III "Other equity — Retained earnings"); in a cumulative GL model, the P&L for all prior years must be rolled into reserves or the balance sheet will not balance. BS accounts (assets, liabilities, equity) are balances carried forward. Normal balances: assets and expenses debit; liabilities, equity and income credit. In a GL with debits positive and credits negative, a balanced TB sums to zero, profit appears as a negative number (net credit), and every voucher nets to nil — which is why "% of all accounts" denominators are zero.

Cross-cutting concepts

Evaluation context drives most DAX bugs

Evaluation context (filter vs row context, context transition) is behind most DAX bugs

Every DAX expression is evaluated in a filter context (the filters from visual coordinates, slicers, CALCULATE and RLS that decide which rows are visible) and possibly a row context (the current row inside a calculated column or iterator). Row context does not filter aggregations and does not follow relationships; that is why a CoA calculated column SUM(GL[Amount]) returns the GL grand total on every row and why RELATED is needed inside SUMX. Context transition — performed by CALCULATE and by every measure reference inside a row context — converts the current row into filters, which then flow through relationships. Most bugs this week trace to one of these: an aggregation that ignores row context (SUMX(Customers, SUM(Sales[Amount]))), an unexpected transition over duplicate rows, a boolean filter that overwrote the matrix row's filter, or a removed filter whose sort-by column still filtered. When a number looks wrong, write down the filter context of that cell first.

Star schema plus marked fiscal Date table

A star schema plus a marked fiscal Date table is required for all time intelligence

Time-intelligence functions (DATESYTD, TOTALYTD with "3/31", SAMEPERIODLASTYEAR, DATEADD, DATESINPERIOD, CLOSINGBALANCEYEAR) operate on a column of a Date dimension that is contiguous, unique, covers whole fiscal years (1 April to 31 March) and filters every fact through one-to-many, single-direction relationships. Marking the table validates those properties and ensures date filters are replaced cleanly; turning off Auto date/time removes hidden calendar-year tables that would otherwise tempt authors into January-based YTD. The star shape matters equally: if Budget relates to Date through month text (many-to-many) or TB is filtered by a fact date column, the same time function gives right answers for GL and wrong ones for Budget or TB. So design order is fixed: star schema → Date table → marked → measures. Never pass GL[PostingDate] to a time function.

Measure branching

Measure branching: base measures (Actual, Budget) → derived (Variance ₹, Variance %, YTD, PY YTD)

Write aggregation logic once in base measures — Actual = SUM(GL[Amount]), Budget = SUM(Budget[Amount]), optionally Actual Signed with sign factors — and build every other measure by referencing them: Variance ₹ = [Actual] - [Budget], Variance % = DIVIDE([Variance ₹], ABS([Budget])), YTD Actual = TOTALYTD([Actual], 'Date'[Date], "3/31"), PY YTD = CALCULATE([YTD Actual], SAMEPERIODLASTYEAR('Date'[Date])). Benefits: a change to the base (exclude reversal vouchers, add an entity filter) flows to all derived measures; testing is layered (verify base against TB, then verify each transformation); names document intent. Branching also prepares for calculation groups, which apply YTD/PY/YoY transformations to any base measure via SELECTEDMEASURE(). Organise branches into display folders mirroring the hierarchy (Base → Variance → Time Intelligence → P&L lines → Ratios).

Additivity decides the measure pattern

Classifying additivity (flow vs balance vs ratio) decides the measure pattern

Before writing a measure, classify the quantity. Additive (flows) — revenue, expenses, cash movements — sum across every dimension including time: a plain SUM with time intelligence works. Semi-additive (balances) — cash, receivables, debt, TB balances — sum across accounts, branches and cost centres but not across time: a quarter's receivables are the closing balance at quarter-end, not the sum of three month-ends; use LASTDATE/LASTNONBLANK, CLOSINGBALANCE functions or a cumulative-from-inception pattern. Non-additive (ratios, distinct counts) — margins, DSO, ROCE, active customers — never sum; every total is recomputed from its components (total GM % = total GP ÷ total revenue). Choosing the wrong pattern produces the classic errors: a YTD sum of month-end balances, or a total margin equal to the sum of branch margins. Record the additivity class in the measure description.

The exercise pattern

Exercise pattern: GL and Budget facts sharing CoA and Date; Budget at month grain; Variance ₹ = [Actual] - [Budget] with a sign-aware Variance %

The hands-on build follows one pattern. GL (voucher-line grain, daily) and Budget (account × cost centre × month) are separate facts that never relate to each other; both relate one-to-many to the conformed CoA and Date dimensions (and CostCentre). Budget's month grain is bridged by storing each budget row on MonthStart — a real date — and relating it to 'Date'[Date] like actuals (or by a TREATAS virtual relationship on MonthEnd). Then Variance ₹ is simple subtraction of base measures, valid in every cell because both facts respond to the same dimension filters. Variance % divides by ABS([Budget]) so that negative budgets (credit-negative revenue or loss budgets) do not invert the sign, and a favourable/adverse flag uses line type (expense lines reversed). Both facts must share the same sign convention, applied once.

Hands-on exercise brief

Roadmap exercise (verbatim): Build a Power Pivot data model combining Actual GL postings, Annual Budget, and Chart of Accounts. Write DAX measures for Actual, Budget, Variance ₹, Variance %, YTD Actual, and PY YTD.

Scenario and inputs

You are the FP&A analyst for Sahyadri Agro Foods Ltd, an unlisted Pune-based food processor with three branches (Pune, Nashik, Indore) and eight cost centres. FY ends 31 March.

  3. Relationships (Diagram View): CoA → GL, CoA → Budget, Date → GL[PostingDate] (active), Date → GL[DueDate] (inactive), Date → Budget[MonthStart], CostCentre → GL and Budget. All one-to-many, single direction.
  4. CoA hierarchy: Statement → FSLine → FSSubLine → LedgerName; sort columns applied.
  5. Measures (in a _Measures table, with format strings): - Actual, Budget (base, raw signs) and Actual Signed, Budget Signed (with SignFactor). - Variance ₹, Variance % (sign-aware, ABS denominator, blank for budgets under ₹1 lakh), Fav/Adv. - YTD Actual with "3/31", YTD Budget, PY YTD, YTD Growth %. - Data quality: Unmapped Amount, RI Orphans, TB Check (sum of all GL = 0).

Saturday assessment paper

Roadmap assessment (verbatim): Saturday 3-Hour Practical Test: Debug a broken many-to-many financial model and write DAX measures for Rolling 12-Month (R12M) Revenue and EBITDA Margin %.

Instructions

  • Time: 3 hours. Total: 100 marks. Open-book for function syntax (dax.guide); no external help.
  • You receive Broken_Model.pbix (or .xlsx with Power Pivot) for Vindhya Retail Ltd (FY ends 31 March) and Source_TB.xlsx with audited monthly TBs.
  • Submit the fixed file plus a Word/Markdown answer sheet. Show DAX for every measure. Explain reasoning where asked.

Q1. Diagnose the model [L3] (20 marks)

The model contains: GL (32 lakh rows), Budget (keyed by MonthText such as "Apr-25"), CoA, Date (1-Jan-2023 to 31-Dec-2025, not marked), CostCentre, Branch. Relationships: Budget[MonthText] ↔ Date[MonthYear] many-to-many; CoA ↔ GL both directions; Branch ↔ CostCentre ↔ GL plus Branch ↔ GL (one inactive, Power BI-chosen); Date ↔ GL[PostingDateTime] (datetime). Symptoms: budget FY2024-25 shows ₹1,946 crore against an approved ₹642 crore; a "(Blank)" FSLine row holds ₹3.8 crore; Branch slicer gives different Actuals depending on the visual; March 2025 YTD is blank. List every defect, the symptom it causes and the fix, in the order you would apply them.

💡 Hint: Separate grain/relationship defects from data-type and calendar-range defects.

Q2. Repair and prove [L2] (15 marks)

Implement the fixes from Q1. Then show, with DAX query view results or a PivotTable, that (a) total GL = 0, (b) FY2024-25 revenue equals the audited ₹1,284.6 crore, (c) budget FY2024-25 equals ₹642 crore, (d) the RI test returns 0.

Q3. R12M Revenue [L2] (15 marks)

Write R12M Revenue (sign-adjusted, positive) using DATESINPERIOD on the Date table so that each month shows revenue for the 12 months ending that month-end. It must return blank for months after the last actuals date (31-Oct-2025) and for months with fewer than 12 months of history (data begins April 2023). Show the values for October 2025 and March 2024 behaviour.

Q4. EBITDA and EBITDA Margin % [L2] (15 marks)

Using the CoA FSLines (Revenue from operations, Other income, Cost of materials consumed, Purchases of stock-in-trade, Changes in inventories, Employee benefits expense, Other expenses, Depreciation and amortisation expense, Finance costs, Tax expense), define EBITDA as revenue from operations less operating expenses (exclude other income, D&A, finance costs and tax). Write EBITDA, EBITDA Margin % and R12M EBITDA Margin %, using DIVIDE and VAR/RETURN, and state the margin's behaviour at Branch total and FY total.

Q5. Context reasoning [L2] (10 marks)

Explain, with numbers from the model, why SUMX(Branch, SUM(GL[Amount])) and SUMX(Branch, [Actual]) differ for FY2024-25 revenue, and why CALCULATE([Actual], FILTER(GL, RELATED(CoA[FSLine]) = "Revenue from operations")) runs slower than the boolean-filter version and shows different values in a matrix by FSLine.

Q6. Closing balance [L2] (10 marks)

Write Closing Trade Receivables from the cumulative GL (including opening balance entries dated 1-Apr-2023) that shows the 31-Mar balance at FY level, not the sum of monthly balances, and reconciles to the audited TB of 31-Mar-2025 (₹96.2 crore).

Q7. Formatted output [L3] (15 marks)

Build a matrix P&L for FY2024-25 vs FY2023-24 with rows Revenue, Gross Profit, EBITDA, EBIT, PBT, PAT and margin % rows for GM %, EBITDA % and EBIT %; amounts in ₹ crore to one decimal; percentages to one decimal; subtotals in bold; no meaningless grand total. Describe the layout table and the dispatch measure you used, and include a screenshot.
