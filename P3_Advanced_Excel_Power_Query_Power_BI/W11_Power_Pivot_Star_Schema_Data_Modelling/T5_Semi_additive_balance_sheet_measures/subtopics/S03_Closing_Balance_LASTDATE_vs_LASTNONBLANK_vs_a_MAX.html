Subtopic note

Closing Balance: LASTDATE vs LASTNONBLANK vs a MAX-Date Filter

Scope: Closing balance with LASTDATE vs LASTNONBLANK (last date with data) vs a MAX-date filter

Why it matters

On a snapshot fact, the closing balance is "the balance on the last date of the period". The question is which last date: the last date of the calendar period, the last date that actually has data, or an explicitly computed date. The three DAX patterns give the same answer for closed months and different answers for the current partial period, for quarters and years that are not complete, and for accounts that stopped having snapshots. The wrong choice shows as a blank FY26 balance sheet, or as a "total" that silently drops accounts.

Core notes

Pattern 1 — LASTDATE (last calendar date)

Closing Bal = CALCULATE ( SUM ( TB[Balance] ), LASTDATE ( 'Date'[Date] ) )

LASTDATE('Date'[Date]) returns a one-row table with the latest date visible in the Date table in the current filter context — the calendar end of the period, whether or not data exists there. For a month row it is the month-end; for Q3 FY26 it is 31 December 2025; for the FY26 row it is 31 March 2026.

  • Correct when snapshots exist for every period-end displayed.
  • Returns blank if the period-end has no snapshot: the current month before close, the FY26 row in November, or a quarter whose last month is unloaded.
  • Fast: a single-date filter.

Pattern 2 — LASTNONBLANK (last date that has data)

Closing Bal LNB =
CALCULATE (
    SUM ( TB[Balance] ),
    LASTNONBLANK ( 'Date'[Date], CALCULATE ( SUM ( TB[Balance] ) ) )
)

LASTNONBLANK(column, expression) iterates the visible dates and returns the latest one for which the expression is not blank. The inner CALCULATE forces context transition so the expression is evaluated for each date; without it, SUM(TB[Balance]) would be evaluated in the outer context (the whole period) for every date and always be non-blank, so the function would return the calendar last date — exactly like LASTDATE.

  • At FY26 in November, returns the 31 October snapshot date — the latest available balance.
  • The "last date with data" is determined for the current filter context as a whole. At a total over several accounts, it is the latest date on which any account has data. If account A has snapshots to 31 October and account B only to 30 September (e.g., a dormant subsidiary that stopped sending TBs), the total uses 31 October and B contributes nothing.
  • Slower: it evaluates the expression for each visible date (acceptable for a month-end snapshot of a few years).
  • LASTNONBLANKVALUE('Date'[Date], SUM(TB[Balance])) is a newer shorthand returning the value directly.

Pattern 3 — explicit MAX-date filter

Closing Bal MAX =
VAR lastDataDate =
    CALCULATE ( MAX ( TB[Date] ) )            -- last snapshot date within the visible period
RETURN
    CALCULATE ( SUM ( TB[Balance] ), 'Date'[Date] = lastDataDate )

MAX(TB[Date]) in the current context returns the latest snapshot date within the visible period (because the period filter flows from Date to TB). The balance is then filtered to that date. Variants:

  • lastDataDate = MIN(MAX('Date'[Date]), [Last Actual Date]) — calendar end capped at the global last actuals date, so every account uses the same as-of date and future periods resolve to the latest close.
  • Using REMOVEFILTERS(CoA) inside the MAX to choose one date for all accounts, then applying it per account.

This pattern is the most transparent (the date is explicit and can be displayed in a tooltip: "Balance as at 31 October 2025"), and with a global cap it gives one consistent as-of date for the whole balance sheet.

Per-account last date

If each account (or entity) must use its own last date, iterate:

Closing Bal per Account =
SUMX ( VALUES ( CoA[AccountKey] ), [Closing Bal LNB] )

Context transition evaluates LASTNONBLANK per account, then sums. This is right for "latest known balance per subsidiary" in an incomplete consolidation but wrong for a balance sheet that must be as at one date — mixing dates in a balance sheet breaks the accounting equation.

Comparison at a glance

Snapshots loaded to 31 October 2025; Account B (a dormant entity) last snapshot 30 September 2025. Balances (₹ lakh): A = 1,480 at 31 October (1,450 at 30 September); B = 300 at 30 September.

Row LASTDATE LASTNONBLANK MAX-date (capped) Per-account LNB
Sep 2025, total 1,750 1,750 1,750 1,750
Oct 2025, total 1,480 (B blank) 1,480 1,480 1,480 (B has no October data)
Q3 FY26 (Oct–Dec), total blank 1,480 1,480 1,480
FY26, total blank 1,480 1,480 1,780 (A at 31 Oct + B at 30 Sep)

Which is "right" depends on the question: a balance sheet as at 31 October should show 1,480 and flag that B is missing; an "exposure" report may prefer 1,780 at the FY level with B's as-of date shown. Note how the per-account version changes with the width of the period on the row — another reason to prefer an explicit, global as-of date for financial statements.

Edge cases & judgement calls

  • Zero vs blank: an account with a genuine zero balance must have a row with 0 (or the closing logic treats it as missing). Power Query loads that drop zero rows make LASTNONBLANK skip to an older date with a non-zero balance — the balance appears to "resurrect". Keep zeros or use the global MAX-date pattern.
  • Daily snapshots with weekends: bank balance snapshots may not exist for Sundays; LASTDATE on a weekly or monthly row ending on a Sunday returns blank, LASTNONBLANK returns Saturday.
  • Snapshots dated on the first of the month: if the TB export is stamped 1 November for "closing October", every pattern is off by a month. Fix in Power Query: re-date to month-end.
  • Visual totals across time: none of the patterns sum across months; but a grand total across months in a column-less table should be suppressed or labelled "as at".
  • Performance: for large daily snapshots prefer the MAX-date pattern over LASTNONBLANK with an expensive inner expression.

Key takeaways

  • LASTDATE = calendar end of the period; blank if no snapshot exists there.
  • LASTNONBLANK = last date with data in the current context; needs CALCULATE inside for context transition.
  • The MAX-date filter makes the as-of date explicit and, with a global cap, consistent across the balance sheet.
  • Per-account last dates (SUMX over accounts) answer a different question and can mix dates.
  • Keep zero-balance rows in snapshots; decide and document which as-of rule the report uses.

Practice Questions

Q1. Predict the outputs [L1]

Snapshots exist for every month-end to 30 November 2025. For the rows November 2025, December 2025, Q3 FY26 and FY26, state what LASTDATE, LASTNONBLANK and the capped MAX-date pattern each return as the as-of date.

Q2. Missing context transition [L2]

A colleague writes CALCULATE(SUM(TB[Balance]), LASTNONBLANK('Date'[Date], SUM(TB[Balance]))) and finds it behaves exactly like LASTDATE. Explain why, step by step, and correct it.

💡 Hint: Ask in which filter context SUM(TB[Balance]) is evaluated for each date of the iteration.

Q3. Dormant subsidiary [L2]

A group of four entities sends month-end TBs; Entity D stopped at 31 August 2025 pending liquidation. Cash balances at 31 October 2025 (₹ lakh): A 620, B 410, C 180; D's last cash balance 75 at 31 August. Compute the group cash shown on the October row and the FY26 row under each pattern in this note, and recommend what the treasury dashboard should show with what disclosure.

Q4. Zero balances dropped [L3]

A Power Query step filters out TB rows where Balance = 0 "to save space". An overdraft account was −₹ 540 lakh at 31 August 2025 and fully repaid (0) at 30 September and 31 October. Explain what each closing-balance pattern shows for this account at September and October, the impact on Net Debt, and how you would fix the pipeline and add a test.
