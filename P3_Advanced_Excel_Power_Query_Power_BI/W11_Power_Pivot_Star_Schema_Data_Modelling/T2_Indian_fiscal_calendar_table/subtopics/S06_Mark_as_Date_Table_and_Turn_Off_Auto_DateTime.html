Mark as Date Table and Turn Off Auto Date/Time

Scope: Mark as Date Table and turn off Auto date/time

Why it matters

Power BI ships with a convenience feature, Auto date/time, that silently creates a hidden calendar-year date table for every date column in the model. For an Indian finance model it is worse than useless: its hierarchy is Year (January–December) → Quarter (Q1 = Jan–Mar) → Month → Day, it bloats the model, and it tempts report authors into building visuals on GL[PostingDate] hierarchies that ignore your fiscal calendar and Budget. Marking your own Date table tells the engine "this is the calendar", which validates it and makes time intelligence behave predictably. Together these two settings are the first things a reviewer checks in a finance PBIX.

Core notes

Auto date/time — what it does

When enabled, for each date or datetime column (in imported tables, excluding the marked Date table and calculated columns in some cases), Power BI creates a hidden LocalDateTable_<guid> with columns Year, Quarter, Month, Day and a hierarchy. The original column shows an expandable "Date Hierarchy" in the field list. Problems:

  • Calendar-year logic: Quarter 1 is January–March; Year is the calendar year. Indian FY reporting cannot use it.
  • Model bloat: a separate hidden table per date column, spanning whole calendar years for the column's range. GL with PostingDate, DocDate and DueDate gets three hidden tables; a placeholder 01-01-1900 in DueDate creates a table with 125+ years of days.
  • Wrong filtering: a visual using GL[PostingDate].[Month] filters GL only; Budget and TB ignore it.
  • Inconsistent DAX: measures referencing GL[PostingDate].[Date] (variation syntax) work only with the auto table and break when it is turned off.

Turning it off

  • Current file: File → Options and settings → Options → Current File → Data Load → Time intelligence → uncheck Auto date/time. This deletes the hidden tables on the next save/refresh.
  • Global default for new files: Global → Data Load → Time intelligence → Auto date/time for new files — uncheck so every new model starts clean.
  • Excel Power Pivot does not create auto date tables in the same way, but Excel PivotTables have their own date grouping (Years/Quarters/Months) when a date field is placed on rows; it is also calendar-based. Use the fiscal Date table's columns instead; automatic grouping can be disabled in Excel options (File → Options → Advanced → Data → Disable automatic grouping of Date/Time columns in PivotTables).

After turning it off, check for visuals or measures that used auto hierarchies; they break and must be repointed to the 'Date' table's columns.

Mark as Date Table — requirements and steps

Power BI: select the Date table → Table tools → Mark as date table → choose the date column ('Date'[Date]). Power Pivot: Design → Mark as Date Table.

Requirements enforced on marking:

  1. The column is of Date (or Date/Time) data type.
  2. Values are unique.
  3. No blanks.
  4. Contiguous — no missing dates between min and max.

If the column is Date/Time, all values must have the same time (normally 00:00:00). Microsoft also recommends the table spans full years (for us, full fiscal years — s02).

What marking changes

  • Disables auto date/time for that table and its column is recognised as the model calendar.
  • Time-intelligence functions (DATESYTD, SAMEPERIODLASTYEAR, DATEADD, DATESINPERIOD) work reliably even when the relationship from Date to facts uses a non-date key (e.g. an integer DateKey 20250401). Without marking, a CALCULATE that filters the date column through such a key does not automatically remove other filters on the Date table.
  • Automatic ALL on the Date table: when a CALCULATE filter argument filters the marked date column, DAX implicitly adds REMOVEFILTERS('Date'), so filters from MonthName, FiscalQuarter or FY slicers do not intersect with the YTD date set. (The same behaviour applies without marking when the relationship is on a Date-typed column — marking guarantees it regardless of key type.)
  • Q&A and Analyze in Excel recognise the table as time-related; Excel PivotTables over the model show date filters correctly.
  • Enables the date table to be used in calculation groups with time-intelligence items robustly.

Recommended setup sequence

  1. Build the Date table (s01) with whole fiscal years (s02) and all columns (s03).
  2. Set data types: Date as Date (not Date/Time), integers as Whole number.
  3. Sort label columns (s04).
  4. Mark as date table on 'Date'[Date].
  5. Turn off Auto date/time (current file and global).
  6. Relate 'Date'[Date] (1) to each fact date column (*), single direction; set non-primary roles inactive.
  7. Hide fact date columns (topic 1 c06) so users use only 'Date' fields.
  8. Verify: VertiPaq Analyzer in DAX Studio shows no LocalDateTable_ tables.

Illustration

Before: a 640 MB PBIX for a Chennai logistics company with seven date columns across GL, AP and Fixed Assets. VertiPaq Analyzer lists seven LocalDateTables, one spanning 1900–2099 because of a placeholder "01-01-1900" in the asset disposal date, totalling about 35 MB and 1.3 lakh rows. A YTD matrix built on GL[PostingDate] hierarchy shows calendar-year YTD resetting in January. After: Auto date/time off, 'Date' (1,826 rows) marked, visuals repointed to 'Date'[FY], 'Date'[MonthName]; YTD with "3/31" resets in April and Budget responds to every date slicer.

Edge cases & judgement calls

  • Marking fails with "duplicate values" when the table has a time component on some rows or overlapping ranges appended; with "missing dates" if built from GL distinct dates. Rebuild from CALENDAR/List.Dates.
  • Multiple date tables (role-playing copies) can each be marked.
  • DateKey integer relationships (common in SQL warehouses, e.g. 20250401) are fine if the table is marked on the real Date column.
  • Composite / DirectQuery models: marking works, but contiguity must hold in the source.
  • Quick measures and visual "Show as YTD" features may assume auto date/time; prefer explicit measures.
  • Personal preference vs standard: some analysts like auto hierarchies for ad hoc work; in shared finance models the standard should be off.

Key takeaways

  • Auto date/time creates hidden calendar-year tables per date column — wrong for April–March and bloats the model.
  • Turn it off in Current File and Global options; repoint any visuals that used it.
  • Mark the custom Date table on a Date-typed, unique, non-blank, contiguous column.
  • Marking ensures time intelligence works and Date filters are cleared correctly even with integer keys.
  • Verify with VertiPaq Analyzer that no LocalDateTable remains.

Practice Questions

Q1. Why marking failed [L1]

Marking 'Date'[Date] fails. The table was built by taking distinct GL posting dates and appending budget dates. List every requirement that may be violated and how you would rebuild the table.

Q2. Hidden tables [L2]

A model has date columns GL[PostingDate], GL[DocDate], GL[DueDate], FA[CapitalisationDate], FA[DisposalDate] and Employee[DOB]. Auto date/time is on. Estimate how many hidden tables exist, what drives their size, and describe the steps to remove them safely without breaking existing reports.

💡 Hint: Some reports may reference the auto hierarchies; find them before switching off.

Q3. Integer DateKey [L2]

A warehouse Date dimension relates to GL via DateKey (integer YYYYMMDD). The Date table is not marked. A YTD measure using DATESYTD('Date'[Date], "3/31") gives wrong results when a MonthName slicer is applied. Explain why and fix it.

Q4. Review checklist [L3]

Write a ten-point review checklist for the Date-related setup of a finance PBIX received from a junior analyst, covering Auto date/time, marking, range, types, relationships, sorting and visual usage.
