Subtopic note

Contiguous Whole-Fiscal-Year Date Range Covering All Facts

Scope: A contiguous range covering whole fiscal years, 1 April to 31 March, across all fact dates

Why it matters

Time-intelligence functions assume the Date table is contiguous (no missing days) and covers complete years as defined by your year-end. If the calendar starts on the first posting date (say 3 April 2022) or ends on the last posting date (say 18 November 2025), measures such as TOTALYTD with "3/31", SAMEPERIODLASTYEAR, DATEADD(..., -1, YEAR) and CLOSINGBALANCEYEAR return blanks or partial results at the edges. The same failures appear for budget (which runs to 31 March 2026) and due dates (which can run months ahead). Getting the range right is a five-minute task that prevents hours of "why is March PY blank?" debugging.

Core notes

The three requirements

  1. Contiguous: every calendar day between the first and last date appears exactly once. No gaps for Sundays, holidays or days without postings — the Date table is a calendar, not a list of posting dates.
  2. Whole fiscal years: the first date is 1 April and the last date is 31 March of the respective years.
  3. Covers every date in every fact: GL posting, document and due dates; Budget MonthStart/MonthEnd; TB MonthEnd; forecast months; any date used in an inactive relationship.

Determining the range

Compute the earliest and latest relevant dates, then round outward to fiscal-year boundaries:

\[ \text{Start} = \text{DATE}(\text{FYStartYear}(d_{\min}), 4, 1), \qquad \text{End} = \text{DATE}(\text{FYEndYear}(d_{\max}), 3, 31) \]

where \(d_{\min}\) and \(d_{\max}\) are the earliest and latest dates across all fact date columns, \(\text{FYStartYear}(d) = \text{YEAR}(d)\) if \(\text{MONTH}(d) \ge 4\), otherwise \(\text{YEAR}(d) - 1\), and \(\text{FYEndYear}(d) = \text{FYStartYear}(d) + 1\).

DAX implementation with model-driven bounds:

Date =
VAR MinFact =
    MINX ( { MIN ( GL[PostingDate] ), MIN ( Budget[MonthStart] ), MIN ( TB[MonthEnd] ) }, [Value] )
VAR MaxFact =
    MAXX ( { MAX ( GL[PostingDate] ), MAX ( GL[DueDate] ), MAX ( Budget[MonthStart] ), MAX ( TB[MonthEnd] ) }, [Value] )
VAR StartYr = IF ( MONTH ( MinFact ) >= 4, YEAR ( MinFact ), YEAR ( MinFact ) - 1 )
VAR EndYr   = IF ( MONTH ( MaxFact ) >= 4, YEAR ( MaxFact ) + 1, YEAR ( MaxFact ) )
RETURN
    CALENDAR ( DATE ( StartYr, 4, 1 ), DATE ( EndYr, 3, 31 ) )

CALENDARAUTO(3) does the same rounding automatically across all date columns in the model (concept c02) but includes every date column, which can be dangerous (see edge cases).

In Power Query, use the same logic with List.Min / List.Max over the fact queries, or (preferred for governance) fixed parameters reviewed once a year — e.g. Start = 1-Apr-2019 (oldest year in scope for five-year trend plus comparatives), End = 31-Mar of the year after the current budget/forecast horizon.

Why whole years matter — mechanics

  • TOTALYTD / DATESYTD build the set of dates from the start of the fiscal year to the last date in context, limited to dates that exist in the Date table. A calendar starting on the first posting date (3 April) usually gives correct YTD actuals, but any fact row dated before the calendar start — an opening-balance journal on 31 March, a budget row on 1 April — has no matching date, falls into the "(Blank)" member and is excluded from every date-filtered measure. The more visible failures come from the functions below.
  • SAMEPERIODLASTYEAR / DATEADD shift the dates in context by a year and return only dates that exist in the Date table. If the current selection is March 2026 and the calendar starts 1 April 2025, the shifted dates (March 2025) are not in the table, so PY returns blank. That is correct only if you have no PY data.
  • PARALLELPERIOD / PREVIOUSYEAR / NEXTYEAR return whole periods; missing days at the edges produce partial totals.
  • CLOSINGBALANCEYEAR(…, "3/31") evaluates at 31 March; if the calendar ends 18 November, the FY2025-26 closing balance is blank.
  • Mark as Date Table requires contiguous unique dates; it does not strictly require whole years, but Microsoft's guidance and DAX time-intelligence semantics assume them.
  • Fiscal week and offsets: week 1 must start on 1 April; offset columns assume every month is present.

Covering future dates

Budgets and forecasts usually run to the end of the current FY (or beyond, for a three-year plan). Due dates on long-credit or retention invoices can extend a year or more. Extend the calendar to the end of the latest fiscal year containing such dates. Future dates do no harm if measures cap at the last actuals date (s08 and topic 4).

Illustration

GL posting dates: 2-Apr-2022 to 18-Nov-2025. Due dates up to 14-Jun-2026. Budget FY2025-26 (MonthStart up to 1-Mar-2026). TB month-ends from 30-Apr-2022. Range:

Item Value
Earliest date 2-Apr-2022 → FY2022-23 → start 1-Apr-2022
Latest date 14-Jun-2026 → FY2026-27 → end 31-Mar-2027
Rows 1,826 (five fiscal years including leap day 29-Feb-2024)

Had the calendar run 2-Apr-2022 to 18-Nov-2025, the November 2025 YTD would be correct, but PY YTD comparisons for April 2022 months and closing balances for FY2025-26 would fail, and receivables due in 2026 would fall into "(Blank)" for due-date measures.

Edge cases & judgement calls

  • Junk dates. Placeholder dates like 01-01-1900 (Tally/ERP default for blank) or 31-12-9999 in a contract end column will stretch a model-driven range to centuries. Clean these to null in Power Query, or use fixed bounds.
  • Birth dates and joining dates in an HR dimension are model date columns; CALENDARAUTO will include them.
  • Multiple year-ends. If one subsidiary has a December year-end (foreign parent), keep the Date table contiguous and covering both; add separate calendar-year and fiscal-year attributes rather than two tables.
  • Very long history. Twenty years of daily dates is only ~7,300 rows; size is never the reason to truncate.
  • Opening balance entries dated 31-Mar of the year before the first full year (e.g. 31-Mar-2022 for a GL starting FY2022-23) require the calendar to include FY2021-22, or the entry to be redated to 1-Apr-2022.

Key takeaways

  • The Date table must be contiguous, start on 1 April and end on 31 March, and cover every fact date.
  • Round the earliest and latest fact dates outward to fiscal-year boundaries.
  • PY, DATEADD and closing-balance functions return blanks or partials when the range is cut short.
  • Include future budget, forecast and due dates; cap measures at the last actuals date instead of truncating.
  • Clean placeholder dates before using a model-driven range; prefer reviewed fixed bounds for governance.

Practice Questions

Q1. Compute the range [L1]

Fact dates: GL 15-Jun-2021 to 28-Feb-2026; Budget MonthStart 1-Apr-2025 to 1-Mar-2027 (two-year plan); TB month-ends 30-Jun-2021 onwards; AP due dates up to 30-Sep-2026. State the start and end dates of the fiscal calendar and the number of fiscal years.

Q2. Diagnose blank PY [L2]

A matrix shows FY2025-26 months with [PY Actual] = CALCULATE([Actual], SAMEPERIODLASTYEAR('Date'[Date])). April to June 2025 show PY values, but July 2025 to March 2026 show blank. The Date table was built with CALENDAR(MIN(GL[PostingDate]), MAX(GL[PostingDate])) and GL starts 1-Jul-2024. Explain the result fully and fix it.

💡 Hint: Consider both what is in the Date table and what is in GL for the shifted dates.

Q3. Write the bounded DAX [L2]

Write a DAX calculated table whose range is derived from GL posting dates and Budget MonthStart, rounded to whole fiscal years, ignoring any GL date before 1-Apr-2000 as a placeholder.

Q4. Opening entry date [L3]

A company migrated from Tally to SAP on 1-Apr-2024 and loaded opening balances as a journal dated 31-Mar-2024 in the new GL. The Date table starts 1-Apr-2024. Describe what happens to the cumulative balance sheet measures and the TB tie-out, and evaluate two alternative fixes.
