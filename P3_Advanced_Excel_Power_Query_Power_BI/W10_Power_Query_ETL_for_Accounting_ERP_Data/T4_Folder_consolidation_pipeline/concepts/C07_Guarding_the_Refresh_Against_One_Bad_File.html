Key concept

Guarding the Refresh Against One Bad File

Concept: Guard against one bad file failing the whole refresh: each try fxCleanTB([Content]) otherwise null, then log the failures

Statement

WithData = Table.AddColumn(InScope, "Data", each try fxCleanTB([Content]) otherwise null),
Good     = Table.SelectRows(WithData, each [Data] <> null),
Failed   = Table.SelectRows(WithData, each [Data] = null),
Combined = Table.Combine(Good[Data])
  • try x otherwise y evaluates x; if x raises an error, the expression returns y instead.
  • try x on its own returns a record [HasError = logical, Value = ..., Error = record], where the error record has Reason, Message and Detail.
  • Newer M versions also support try x catch (e) => ..., giving access to the error inside the handler.

Explanation

Without a guard, one corrupt, wrongly formatted or half-uploaded file raises an error inside the nested Data column; Table.Combine propagates it and the entire refresh fails, often with a message that does not name the file. With the guard, failing files become null, are excluded from the combine and are listed separately, so 15 good branches still consolidate and the 16th is visibly missing.

Two refinements make the log useful:

  1. Keep the error message. otherwise null discards why the file failed. Use the record form instead:
WithTry  = Table.AddColumn(InScope, "Attempt", each try fxCleanTB([Content])),
Good     = Table.SelectRows(WithTry, each not [Attempt][HasError]),
Combined = Table.Combine(List.Transform(Good[Attempt], each [Value])),
Errors   = Table.AddColumn(Table.SelectRows(WithTry, each [Attempt][HasError]),
               "Message", each [Attempt][Error][Message], type text)

Load Errors (Name, Message) to the Controls sheet.

  1. Raise meaningful errors inside the function. error "Header 'Particulars' not found" or error Error.Record("BadLayout", "No header row", [File = name]) makes the log actionable.

Judgement: a guard trades availability for completeness. A consolidated TB missing one branch is wrong. The guard is therefore paired with a completeness check: expected branches (from the branch master) versus branches consolidated. For final reporting runs, many teams switch to fail-closed — if Errors has any rows, the output query raises an error — and use the tolerant mode only for interim refreshes.

Note that try catches errors raised while evaluating the expression. Because M is lazy, errors in cells of a returned table (for example a type conversion error in row 900) may not surface until those cells are read. Force evaluation inside the guard where needed, e.g. try Table.Buffer(fxCleanTB([Content])), or check cell-level errors with Table.RowCount(Table.SelectRowsWithErrors(t)).

Illustration

Sixteen April branch files: 15 clean, and GUW_2025-04.csv was saved from Excel as UTF-16 with a semicolon delimiter. Unguarded: the refresh fails ("The column 'Particulars' of the table wasn't found"), and no output is produced. Guarded with the record form: Combined contains 15 branches (38,914 rows); Errors shows GUW_2025-04.csv | Header 'Particulars' not found; the completeness check shows "Expected 16, consolidated 15, missing GUW". The preparer re-requests the file instead of discovering the gap at review.

Practice Questions

Q1. Record form of try [L1]

State the fields of the record returned by try fxCleanTB([Content]) for a successful call and for a failing call, and write the expression that extracts the error message.

Q2. Completeness check [L2]

Using BranchMaster[Code] (18 codes) and the parsed Branch column of successfully consolidated files, write a query that lists missing branches for the report period, and explain how it complements the Errors list.

💡 Hint: List.Difference returns items in the first list not found in the second.

Q3. Lazy cell errors [L3]

A file passes the try guard, but the consolidated table later shows Error cells in the Debit column for 12 rows, and loading to the sheet reports 12 errors. Explain why the guard did not catch them, and design two alternative ways to surface such rows in the exception log.
