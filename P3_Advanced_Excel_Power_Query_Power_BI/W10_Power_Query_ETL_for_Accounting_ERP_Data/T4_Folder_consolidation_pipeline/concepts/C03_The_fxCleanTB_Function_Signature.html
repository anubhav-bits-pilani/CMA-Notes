Key concept

The fxCleanTB Function Signature

Concept: fxCleanTB = (file as binary) as table => let s = Csv.Document(file, [Delimiter=","]), ... in result

Statement

fxCleanTB = (file as binary) as table =>
let
    s        = Csv.Document(file, [Delimiter = ",", Encoding = 65001, QuoteStyle = QuoteStyle.Csv]),
    skipped  = Table.Skip(s, each [Column1] <> "Particulars"),
    promoted = Table.PromoteHeaders(skipped, [PromoteAllScalars = true]),
    rows     = Table.SelectRows(promoted, each [Particulars] <> null and [Particulars] <> ""
                   and not Text.StartsWith([Particulars], "Grand Total")),
    typed    = Table.TransformColumnTypes(rows, {{"Debit", type number}, {"Credit", type number}}, "en-IN"),
    result   = Table.SelectColumns(typed, {"Particulars", "Debit", "Credit"}, MissingField.UseNull)
in
    result
  • fxCleanTB is the query name; the query's value is a function.
  • (file as binary) declares one parameter named file, which must be a binary value (a file's bytes, such as [Content] from Folder.Files).
  • as table declares that the function returns a table.
  • => separates the signature from the body; the body is a let ... in expression whose steps can reference file.
  • Csv.Document(file, ...) parses the binary directly; there is no File.Contents because the bytes are already supplied.

Explanation

The signature encodes the contract "bytes in, clean table out". Taking a binary rather than a path is deliberate: Folder.Files and SharePoint.Files both provide binaries, so the same function works for local, network and SharePoint folders, and for a single file tested via File.Contents(path).

Type annotations do three jobs: they document intent, they give immediate errors on misuse (passing text raises "We cannot convert the value ... to type Binary"), and they tell Power Query the shape for the Invoke dialog. They check only the primitive kind; as table does not check column names, which is why the body ends with Table.SelectColumns(..., MissingField.UseNull) to enforce the output schema.

Inside the body, every step must be condition-based rather than positional (conditional Table.Skip, value-based filters), because the function will run against every branch's file, not only the one you built it on. Optional arguments extend the contract without breaking callers: (file as binary, optional header as nullable text) as table =>, with header ?? "Particulars" inside.

Testing pattern: create a scratch query Test = fxCleanTB(File.Contents("D:\Close\TB\DEL_2025-04.csv")) and inspect the result for each tricky file; delete or disable load when done.

Illustration

DEL_2025-04.csv has 7 caption rows, a header row beginning "Particulars", 1,642 ledger rows, 11 group subtotal rows starting "Total" and a final "Grand Total" row. The function above skips 7 rows, promotes the header, removes the Grand Total and blank rows, but leaves the 11 "Total ..." subtotal rows in — the output has 1,653 rows and double counts groups. Changing the filter to not Text.StartsWith([Particulars], "Total") and not Text.StartsWith([Particulars], "Grand Total") yields 1,642 rows; a Dr = Cr check on the output confirms the fix.
