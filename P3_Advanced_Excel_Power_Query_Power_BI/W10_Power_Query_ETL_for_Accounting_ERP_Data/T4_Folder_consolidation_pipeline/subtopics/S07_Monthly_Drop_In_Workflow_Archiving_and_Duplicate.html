Monthly Drop-In Workflow, Archiving and Duplicate-File Detection

Scope: Monthly drop-in workflow: new file in folder → Refresh All; archiving and duplicate-file detection

Why it matters

The promise of a folder pipeline is operational: next month, someone saves the new files into the folder, opens the workbook and clicks Refresh All, and the consolidated TB or bank feed updates with no query edits. That promise only holds if the workflow around the folder is designed as carefully as the M — who drops files, what names they use, what happens to last month's files, how duplicates and re-exports are caught, and what the preparer checks before using the output. This is close-process design, familiar from audit work on IT general controls and spreadsheet controls.

Core notes

The target workflow

  1. Drop. Branch accountants or treasury save files into the inbox folder (ideally a SharePoint library with restricted write access), using the agreed naming convention.
  2. Refresh. The preparer opens the consolidator and runs Data > Refresh All (Excel) or Refresh (Power BI Desktop). In the Service, scheduled refresh does this automatically.
  3. Review controls. The preparer reviews the FileLog (files, rows, Dr/Cr totals), the RejectedFiles list, the Errors list and the duplicate check — all loaded to a "Controls" sheet.
  4. Sign-off and archive. After sign-off, the period's files are either left in place (if the pipeline is cumulative) or moved to an archive folder (if it processes the current period only).

Cumulative vs current-period design

Design Folder contents Pipeline behaviour When to use
Cumulative All months of the FY stay in the folder Every refresh reprocesses all files; output has all periods FY-to-date TBs, trend reports, data models
Current-period Only the open month's files Output has one period; prior months are archived Monthly BRS where prior months are closed
Hybrid All files, but a ReportPeriod parameter Filter the file inventory by parsed period before invoking Large histories where reprocessing is slow

For a 12-month FY with 16 branches, cumulative means 192 files by March — usually fine for CSVs. For years of daily bank files, filter the inventory early on the parsed period so old files are never opened.

Archiving

Folder.Files is recursive, so an Archive subfolder inside the drop folder is still read unless you exclude it:

Active = Table.SelectRows(Source, each not Text.Contains([Folder Path], "\Archive\"))

Safer still: keep the archive outside the drop folder (Close\Inbox\ and Close\Archive\FY2025-26\). Archived files should be read-only and never edited; if a closed period must be reopened, the revised file is a new version with its own name and an approval trail.

Duplicate-file detection

Duplicates arise from re-exports, "(1)" copies from browser downloads, "final"/"v2" naming, and OneDrive conflict copies. Detect at file level on the parsed keys, not on the raw name:

Keys = Table.AddColumn(Parsed, "Key", each [Branch] & "|" & Text.From([PeriodEnd]), type text),
DupFiles = Table.SelectRows(
    Table.Group(Keys, {"Key"}, {{"Files", each Table.RowCount(_), Int64.Type},
                                {"Names", each Text.Combine([Name], "; "), type text}}),
    each [Files] > 1)

Load DupFiles to the Controls sheet. Two policies are possible:

  • Fail closed. If DupFiles has rows, raise an error in the Combined query so nothing is consolidated until a human removes one file: if Table.RowCount(DupFiles) > 0 then error "Duplicate period files: " & Text.Combine(DupFiles[Names], " / ") else Combined.
  • Latest wins. Keep the most recent version per key using Date modified as a tie-breaker only: group by Key, Table.Max(_, "Date modified"). This is convenient but should be paired with a visible log of which files were superseded.

Fail-closed is the better default for financial outputs, because "latest" is not necessarily "approved".

Row-level duplicate detection

Even with one file per branch-month, overlapping export date ranges can include the same voucher twice (e.g. a 1-Apr to 5-May export followed by a 1-May to 31-May export). Group the combined data on Branch + VoucherType + VoucherNo + Date + Amount and flag counts above one. For bank feeds, use Bank + AccountNo + TxnDate + Ref + Amount; genuine repeated transactions (two identical ₹500 bank charges on a day) are exactly why the key must include as much identifying detail as the source provides.

Refresh settings that support the workflow

  • In Excel, Query Properties: enable "Refresh data when opening the file" only if users will not be confused by changing numbers; disable "Enable background refresh" so Refresh All completes before the user reviews.
  • Keep staging and helper queries connection-only; load only the output and controls.
  • In Power BI, the same pipeline refreshes in the Service on a schedule — through a gateway for local folders, directly for SharePoint/OneDrive.

Worked illustration

On 4 May, the folder contains 16 April files. Refresh: FileLog shows 16 files, 41,208 rows, debits ₹311.4 crore, credits ₹311.4 crore. On 9 May, Jaipur re-exports April after a ₹6.2 lakh provision and drops JAI_2025-04_rev.csv without deleting the original. If the name filter is strict (CODE_YYYY-MM.csv), the rev file fails the pattern and lands in RejectedFiles with "Bad name", prompting the preparer to replace the original properly. If the parser is tolerant and reads both as Jaipur April, fail-closed duplicate detection stops the refresh with "Duplicate period files" listing both names. Either way, the problem is visible before anyone uses the numbers. Without these controls, Jaipur's April balances would be included twice and consolidated debits and credits would each rise by roughly the size of Jaipur's TB.

Edge cases & judgement calls

  • Partially uploaded files. A file being copied over a slow VPN may be read half-written; schedule refreshes after the upload cut-off and check row counts against the source footer.
  • Locked files. If a source file is open in Excel, Folder.Files may still read it but the lock file appears; the ~$ filter handles the latter.
  • Reopened periods. Decide who may replace an archived file and how the change is evidenced (version history in SharePoint helps).
  • Clock-based logic. Do not derive "current month" from DateTime.LocalNow(); drive it from a ReportPeriod parameter so refreshes are reproducible.
  • User discipline. The best convention fails if users rename freely; a rejected-files list visible to them is the feedback loop.

Key takeaways

  • The workflow is drop → Refresh All → review controls → sign-off → archive; design it explicitly.
  • Choose cumulative, current-period or hybrid folders deliberately, and exclude archive folders because Folder.Files is recursive.
  • Detect duplicates on parsed Branch + Period keys; prefer fail-closed over "latest wins" for financial data.
  • Add row-level duplicate checks for overlapping exports, with keys detailed enough to keep genuine repeats.
  • Load FileLog, RejectedFiles, Errors and duplicate checks to a Controls sheet reviewed every refresh.

Practice Questions

Q1. Pick the folder design [L1]

For each feed choose cumulative, current-period or hybrid, with a reason: (a) FY-to-date branch TBs for a Power BI P&L; (b) daily bank CSVs for six accounts over three years; (c) monthly BRS where prior months are signed off and frozen.

Q2. Fail-closed duplicate guard [L2]

Write the M for a Combined query that returns the appended branch data only when no Branch + Period key appears more than once, and otherwise raises an error listing the conflicting file names.

💡 Hint: Group the parsed inventory, filter counts above one, then use if ... then error ... else ....

Q3. Overlapping exports [L2]

Branch Lucknow exported its Day Book for 1-Apr-2025 to 5-May-2025 as LKO_2025-04.csv and then 1-May-2025 to 31-May-2025 as LKO_2025-05.csv. Explain the effect on May and April figures in a cumulative pipeline, how a row-level duplicate check would detect it, and the process fix you would propose.

Q4. Controls sheet for sign-off [L3]

Design the Controls sheet that a financial controller reviews before using the consolidated TB: list every table on it, the columns of each, the expected "clean" state, and the action required for each kind of exception.
