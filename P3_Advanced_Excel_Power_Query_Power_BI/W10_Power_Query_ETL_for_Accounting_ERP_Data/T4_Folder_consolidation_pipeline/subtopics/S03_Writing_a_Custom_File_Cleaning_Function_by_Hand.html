Writing a Custom File-Cleaning Function by Hand

Scope: Writing a custom function by hand, (file as binary) as table => ..., and calling it with Table.AddColumn

Why it matters

A hand-written function is the single most valuable M skill for consolidation work. It replaces four generated helper queries with one readable query, enforces an output schema you define, can be reused by several pipelines, and can be tested in isolation on any file. Interviewers for FP&A automation roles frequently ask candidates to "write a function that cleans one file and apply it to a folder" in the Advanced Editor without the UI. It is also how you build the week's exercise: one function per bank, invoked over Folder.Files.

Core notes

Function syntax

An M function is a value written as a parameter list, an optional return type, =>, and a body expression:

(file as binary) as table =>
let
    Source   = Csv.Document(file, [Delimiter = ",", Encoding = 65001, QuoteStyle = QuoteStyle.Csv]),
    Skipped  = Table.Skip(Source, each [Column1] <> "Particulars"),
    Promoted = Table.PromoteHeaders(Skipped, [PromoteAllScalars = true]),
    Rows     = Table.SelectRows(Promoted, each [Particulars] <> null and [Particulars] <> ""
                   and not Text.StartsWith([Particulars], "Grand Total")),
    Typed    = Table.TransformColumnTypes(Rows,
                   {{"Debit", type number}, {"Credit", type number}}, "en-IN"),
    Result   = Table.SelectColumns(Typed, {"Particulars", "Debit", "Credit"}, MissingField.UseNull)
in
    Result

Saved as a query named fxCleanTB, this appears with an fx icon. Elements:

  • Parameter list (file as binary): the name is local to the body; as binary declares the type and causes an immediate, clear error if someone passes text.
  • Optional parameters use optional, e.g. (file as binary, optional skipCaption as nullable text); inside, default them with skipCaption ?? "Particulars".
  • Return type as table documents and checks the output.
  • Body is any expression, usually a let ... in block.

Type checks in M are on primitive kinds only (table, binary, text); as table does not verify column names. Schema must be enforced inside the body (the final Table.SelectColumns above).

Creating it in the editor

Home > New Source > Blank Query > Advanced Editor, paste the code, rename the query fxCleanTB. Alternatively, build a normal query against one file, then edit the first line: change Source = Csv.Document(File.Contents(FilePath), ...) into the function header and replace the file reference with the parameter. Power Query offers an Invoke pane for any function: choose a file binary and test.

Calling it with Table.AddColumn

let
    Files   = Folder.Files(FolderPath),
    InScope = Table.SelectRows(Files, each Text.Lower([Extension]) = ".csv"
                  and not Text.StartsWith([Name], "~$")),
    Keep    = Table.SelectColumns(InScope, {"Name", "Content"}),
    WithData = Table.AddColumn(Keep, "Data", each fxCleanTB([Content]), type table),
    Combined = Table.Combine(WithData[Data])
in
    Combined

each fxCleanTB([Content]) is (_) => fxCleanTB(_[Content]): for every file row, pass that row's binary. The result column holds a nested table per file. WithData[Data] extracts the column as a list of tables and Table.Combine appends them, aligning columns by name.

To keep provenance, add the file name inside each nested table before combining, or expand rather than combine:

WithData = Table.AddColumn(Keep, "Data", each
    Table.AddColumn(fxCleanTB([Content]), "SourceFile", (r) => [Name], type text)),

Note the explicit (r) => lambda: inside a nested each, _ would refer to the inner row, so [Name] written as each [Name] would look for a Name column in the TB, not the file row. Naming the inner parameter avoids that shadowing bug. Alternatively, Table.ExpandTableColumn(WithData, "Data", {"Particulars", "Debit", "Credit"}) keeps the Name column automatically, at the cost of a fixed column list.

Passing more than the binary

Functions can take the whole row or several values:

fxCleanTB2 = (file as binary, fileName as text) as table =>
    let t = fxCleanTB(file)
    in  Table.AddColumn(t, "Branch", each Text.BeforeDelimiter(fileName, "_"), type text)

WithData = Table.AddColumn(Keep, "Data", each fxCleanTB2([Content], [Name]))

Worked illustration

Twelve monthly CSVs for the Kolkata branch, each 2,400 rows with 6 caption rows and 3 subtotal rows. fxCleanTB returns 2,391 data rows per file with three columns. Table.AddColumn produces 12 rows with nested tables; Table.Combine produces \(12 \times 2{,}391 = 28{,}692\) rows. A per-file log built from the nested column — Table.AddColumn(WithData, "Rows", each Table.RowCount([Data])) — shows 2,391 for each file; any file showing 0 or a different Dr total is investigated before the output is used.

Documenting the function

Metadata can be attached so the Invoke dialog shows a description:

let
    fn = (file as binary) as table => ... ,
    fnType = type function (file as binary) as table
        meta [Documentation.Name = "fxCleanTB",
              Documentation.LongDescription = "Cleans one Tally TB CSV into Particulars, Debit, Credit"]
in
    Value.ReplaceType(fn, fnType)

This is optional but helps when the workbook is handed over.

Edge cases & judgement calls

  • Functions do not fold. Calling a custom function per row prevents folding; this is irrelevant for files (which never fold) but matters if you apply a function to a SQL source.
  • Formula.Firewall. If the function references another query that accesses a different source (e.g. a mapping table from SharePoint), refresh can fail with a firewall error; keep functions self-contained or align privacy levels.
  • Shadowed _. Nested each inside each is the most common hand-written bug; name inner parameters.
  • Errors inside nested tables are lazy. A broken file may show "Table" in the column but error only when combined; wrap calls in try and log.
  • Column type after AddColumn. Declare type table (or a full table type) on the invoked column so downstream steps know the shape.
  • Parameters vs functions. A parameter is a single value; a function is reusable logic. Do not create a parameter per file.

Key takeaways

  • A function is (params) as type => body; save it as its own query, named with an fx prefix.
  • Test the function on one file via Invoke before applying it to the folder.
  • Table.AddColumn(Files, "Data", each fx([Content])) invokes per file; Table.Combine(Files[Data]) appends by name.
  • Enforce output schema inside the function, because as table checks only the kind.
  • Use named lambdas in nested contexts to avoid _ shadowing.

Practice Questions

Q1. Write the function [L2]

Write fxCleanBank = (file as binary) as table => ... for an HDFC CSV with columns Date, Narration, Chq./Ref.No., Value Dt, Withdrawal Amt., Deposit Amt., Closing Balance, 20 caption rows above the header and a footer starting with "STATEMENT SUMMARY". Output columns: TxnDate (date, dd/MM/yy), Narration, Ref, Withdrawal, Deposit — all typed.

💡 Hint: Skip until the first column equals "Date", then filter out rows from the footer marker onwards.

Q2. Shadowing bug [L2]

A colleague wrote Table.AddColumn(Files, "Data", each Table.AddColumn(fxCleanTB([Content]), "File", each [Name])). The refresh errors with "The field 'Name' of the record wasn't found". Explain why and rewrite it correctly in two different ways.

Q3. Optional parameter [L2]

Extend fxCleanTB with an optional parameter headerText that defaults to "Particulars", so Oracle exports with the header "Account" can use the same function. Show the function header, the defaulting line and two example calls.

Q4. Function vs generated helpers [L3]

Your manager prefers the Combine Files UI because "the team can click through it". Prepare a short argument for a hand-written function, covering schema enforcement, testing, reuse across pipelines and error logging, and propose how non-technical colleagues can still maintain it.
