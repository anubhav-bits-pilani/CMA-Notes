Subtopic note

Error Handling: Remove Errors, Keep Errors and try ... otherwise

Scope: Error handling: Remove Errors, Keep Errors for an exception log, try ... otherwise

Why it matters

In a finance pipeline, an error cell is a transaction that could not be read: an amount with a stray character, a date in the wrong format, a ledger code that failed conversion. The tempting fix — Remove Errors — makes the query run and quietly drops those rows, so the consolidated TB no longer balances, or a bank receipt disappears from the reconciliation. Auditors would call this an incompleteness risk. The professional approach is: catch errors deliberately, route them into an exception log that someone reviews, and make the main output either complete or visibly flagged.

Core notes

Two kinds of error

Kind Scope Example Effect
Step-level (query) error The whole step fails Column not found, file missing, syntax error, Formula.Firewall Query fails to refresh; yellow banner in editor
Cell-level (row) error Individual cells DataFormat.Error converting "12,5OO.00" (letter O) to number; Date.FromText on "31/02/2026" Refresh succeeds; error cells load as blanks (Excel) or errors are reported per table (Power BI: "x rows contained errors")

Cell errors are the dangerous ones: the query succeeds, and the loaded value is empty.

Remove Errors

Right-click column → Remove Errors generates:

NoErr = Table.RemoveRowsWithErrors(t, {"Amount"})

It removes the entire row if the listed column(s) contain an error. Use only when you have first captured those rows elsewhere and the business rule says such rows are invalid (e.g. a page footer that slipped through and fails conversion).

Keep Errors for an exception log

Home → Keep Rows → Keep Errors generates Table.SelectRowsWithErrors(t, {"Amount"}). Build the log as a separate referenced query, so the main query and the log share upstream logic:

// Query: TB_Typed (connection only) — conversion step
// Query: TB_Clean
= Table.RemoveRowsWithErrors(TB_Typed, {"Amount", "Date"})
// Query: log_TB_Errors (loaded to an Exceptions sheet)
= Table.SelectRowsWithErrors(TB_Typed, {"Amount", "Date"})

Errors themselves do not load nicely; in the log, convert them into readable text. Replace errors in the log with a message, and keep the original raw text column so the reviewer sees the bad value:

WithRaw  = Table.AddColumn(Raw, "AmountTyped", each try Number.FromText([AmountText], "en-IN") otherwise null, type nullable number),
Problems = Table.SelectRows(WithRaw, each [AmountText] <> null and [AmountTyped] = null)

That pattern — keep the raw text, try the conversion into a new column, compare — is the cleanest exception log because it contains no error values at all.

try ... otherwise

try expression returns a record: [HasError = false, Value = ...] on success, or [HasError = true, Error = [Reason, Message, Detail]] on failure. try x otherwise y returns x, or y if x errors.

SafeAmt  = Table.AddColumn(t, "Amt", each try Number.From([Debit]) otherwise 0, type number)

Caution: otherwise 0 makes an unreadable amount look like a genuine zero. Prefer otherwise null plus a log, or capture the message:

Attempt  = Table.AddColumn(t, "Parse", each try Date.FromText([Txn Date], [Format="dd/MM/yyyy", Culture="en-IN"])),
Parsed   = Table.AddColumn(Attempt, "Date", each if [Parse][HasError] then null else [Parse][Value], type nullable date),
ErrMsg   = Table.AddColumn(Parsed, "DateError", each if [Parse][HasError] then [Parse][Error][Message] else null, type nullable text),
Final    = Table.RemoveColumns(ErrMsg, {"Parse"})

In newer Power Query versions, try ... catch (e) => ... is also available, passing the error record to a function: try Number.From(x) catch (e) => error Error.Record("Parse", e[Message], x).

Replacing errors

Transform → Replace Errors (Table.ReplaceErrorValues(t, {{"Amount", null}})) swaps error cells for a fixed value. Same caution as otherwise 0: it hides problems unless logged first.

Raising your own errors

Use error to stop a refresh when a control fails — better a failed refresh than a wrong TB:

Check  = if Number.Abs(List.Sum(Clean[Amount])) > 1
         then error Error.Record("TB.Imbalance", "TB does not net to zero", List.Sum(Clean[Amount]))
         else Clean

Counting errors as a control

A validation query can report errors per file and column:

ErrCount = Table.RowCount(Table.SelectRowsWithErrors(TB_Typed))

Add it to the control-totals table (Week 10 cross-cutting item) with row counts and Dr/Cr sums per file.

Illustration

A 9,800-row Tally Day Book; conversion of Amount gives 14 errors: 11 are "Closing Balance c/f" lines with text in the amount column (should have been filtered), 2 have "1,23,4S6.00" (typo in a manual export edit), 1 is "—" (em-dash for nil). Remove Errors would have deleted all 14 silently, including two real vouchers worth ₹2,46,912. The exception log shows all 14 with raw values; the fix is to filter the c/f lines by condition, treat "—" as zero by rule, and send the 2 typos back for re-export.

Edge cases & judgement calls

  • Errors propagate: a cell error in a column used by a later custom column makes that column's cell an error too; log at the earliest step.
  • Remove Errors without column list (Table.RemoveRowsWithErrors(t)) checks all columns — a single error in an irrelevant column drops a valid amount row.
  • try around a whole table (try fxClean([Content]) otherwise null) protects a folder refresh from one bad file (Topic 4), but you must then list the files that returned null.
  • Lazy evaluation: errors in columns you later remove never surface; errors in columns you keep surface only at load time.
  • Excel load shows error cells as blank with an "x errors" link in the Queries pane; Power BI shows "x rows had errors" after load — both are easy to miss in an unattended refresh.
  • Materiality judgement: some errors are acceptable to drop (blank spacer lines failing conversion) — document the rule, do not decide case by case each month.

Key takeaways

  • Cell-level errors let refresh succeed while losing data; treat each as an unread transaction.
  • Never Remove Errors or Replace Errors without first logging the affected rows.
  • Best pattern: keep raw text, try the conversion into a new column, and log rows where conversion returned null.
  • try returns a record with HasError/Value/Error; use the message for the log; prefer otherwise null over otherwise 0.
  • Raise explicit errors when a control total fails so a wrong result never loads.

Practice Questions

Q1. Build an exception log [L2]

A bank CSV has columns TxnDate (text), Narration, Withdrawal (text), Deposit (text). Write the M for a clean query and a separate exception-log query that lists rows where either date or amounts fail conversion, showing the raw values and the error message.

Q2. otherwise 0 review [L1]

A colleague wrote each try Number.FromText([Debit], "en-IN") otherwise 0 across a 12-branch TB consolidation. Explain the risk with an example, and rewrite the logic so that failures are visible.

💡 Hint: Consider how a reviewer would distinguish a zero-balance ledger from an unreadable one.

Q3. Fail the refresh [L2]

Write M that stops the refresh with a meaningful error if the cleaned TB's signed amounts do not net to zero within ₹1, quoting the difference and the number of rows, and explain why this is preferable to loading the data with a warning column.

Q4. Classify errors [L1]

Classify each as step-level or cell-level and state the first thing you would check: (a) "The column 'Vch No.' of the table wasn't found"; (b) DataFormat.Error: "We couldn't convert to Number" on 3 rows; (c) "DataSource.NotFound: Could not find file"; (d) Expression.Error: "We cannot convert the value null to type Text" on 12 rows.

Q5. Policy design [L3]

Draft an error-handling policy for a month-end Power Query pipeline covering: where errors are caught, which may be dropped by rule, how logs are reviewed and signed off, which conditions fail the refresh, and how this evidence is kept for internal audit.
