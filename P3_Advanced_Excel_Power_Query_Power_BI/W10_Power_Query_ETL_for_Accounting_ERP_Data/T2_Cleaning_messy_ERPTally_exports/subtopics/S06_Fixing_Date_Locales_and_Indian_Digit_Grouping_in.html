Fixing Date Locales and Indian Digit Grouping in Text Amounts

Scope: Fixing date locales (dd-mm-yyyy vs mm/dd/yyyy) and Indian digit grouping in text amounts (1,23,456.00)

Why it matters

Indian exports write dates day-first (03-04-2026 = 3 April 2026) and amounts in lakh/crore grouping (1,23,456.00 and 4,82,36,190.00). Many laptops — and almost every Power BI Service tenant by default — run with an en-US locale, which reads dates month-first and expects thousand grouping. The result is the most dangerous kind of error: silent. 03-04-2026 becomes 4 March, 13-04-2026 becomes an error (there is no month 13) or is left as text, and the cut-off for a 31 March year-end moves by weeks. For days 1–12 the swap is invisible in a preview. Any bank recon with a date window, any ageing, and any FY/quarter derivation depends on getting this right.

Core notes

Where the locale comes from

When converting text to date or number, Power Query uses (in order) the culture argument you pass, otherwise the file/workbook locale setting (Query Options → Current Workbook → Regional Settings → Locale; Power BI: Options → Current File → Regional Settings), otherwise the machine's regional settings. In the Power BI Service, the dataset's culture applies. Relying on the default means the same file gives different results on different machines.

Always pass a culture explicitly for text dates and formatted numbers.

Converting dates with a culture

Three tools, from simplest to most precise:

  1. Change Type → Using Locale… (right-click column header) in the UI, which generates:
Typed = Table.TransformColumnTypes(t, {{"Txn Date", type date}}, "en-IN")
  1. Date.FromText with a format — exact control when the pattern is known:
D = Table.TransformColumns(t, {{"Txn Date", each Date.FromText(_, [Format="dd-MM-yyyy", Culture="en-IN"]), type date}})

Format strings follow .NET: dd day, MM month number, MMM abbreviated month name, yy/yyyy year. Note mm is minutes — a classic mistake.

  1. Parse components manually when separators vary (/, -, .):
D = each let p = Text.SplitAny(_, "/-.") in #date(Number.From(p{2}), Number.From(p{1}), Number.From(p{0}))

Two-digit years need a rule (+2000).

Mixed formats in one column

Some bank CSVs mix "02/04/25" and "2025-04-02" (ISO) after a format change mid-year, or SAP exports in user-specific formats. Use try with fallbacks:

each try Date.FromText(_, [Format="dd/MM/yy", Culture="en-IN"])
     otherwise try Date.FromText(_, [Format="yyyy-MM-dd"])
     otherwise null

Then count nulls in a check query.

Excel serial numbers

Excel sources may deliver real dates (already typed), serial numbers (45748 = 1 April 2025) or text. Date.From(45748) handles serials; text needs culture parsing. Detect with Value.Is(_, type number).

Detecting a swapped locale

Swaps are silent for days 1–12, so test the data:

  • Any parsed date outside the statement period (e.g. a March 2026 statement producing dates in December) indicates a swap.
  • The distribution of day numbers: under a swap, no day exceeds 12 and failed rows appear only for days 13–31.
  • Errors only on days above 12 after conversion are the signature of a dd/mm vs mm/dd mismatch.
  • Compare the closing balance date in the statement header with the max parsed date.

Indian digit grouping in text amounts

"1,23,456.00" has commas after the lakh and thousand positions. With culture "en-IN", Number.FromText("1,23,456.00", "en-IN") and typing with "en-IN" parse it correctly. With "en-US", parsing usually also succeeds because group separators are generally tolerated, but do not rely on that — some cultures (e.g. de-DE) treat "," as the decimal separator, turning 1,23,456.00 into an error or a wrong value. Robust approaches:

// 1. Explicit culture
Typed = Table.TransformColumnTypes(t, {{"Amount", type number}}, "en-IN")

// 2. Strip grouping entirely, then parse with an invariant pattern
Amt = Table.TransformColumns(t, {{"Amount", each
        if _ = null or Text.Trim(_) = "" then null
        else Number.FromText(Text.Remove(Text.Trim(_), {",", " ", "₹"}), "en-US"), type number}})

Watch for: "(1,23,456.00)" brackets for negatives, trailing "-" ("1,23,456.00-" in SAP), "Dr/Cr" suffixes (s04), char 160 as a group separator (s05), and "-" or "0.00" meaning nil.

Displaying in lakh/crore

Display formatting is separate from parsing. In Excel use a custom number format; in Power BI set the model's culture or use format strings. Power Query should hold the number; never store "₹1.23 lakh" text in a fact table.

Illustration

HDFC CSV dates: 01/04/25, 02/04/25, 13/04/25, 30/04/25. Converted with en-US: 4 January 2025, 4 February 2025, error, error. Converted with [Format="dd/MM/yy", Culture="en-IN"]: 1 April 2025, 2 April 2025, 13 April 2025, 30 April 2025. A recon with a ±3-day date window would match nothing against the Tally ledger in the first case and report two spurious errors that someone might "fix" by removing errors — losing two transactions.

Edge cases & judgement calls

  • Datetime text ("02/04/2025 14:35:10") — parse as type datetime with culture, then DateTime.Date if only the date is needed.
  • Month names ("02-Apr-2025") are unambiguous once a culture with English month names is used; preferable when you control the export.
  • Power BI Service culture: a dataset published from a machine with en-IN may refresh in the Service with a different culture if conversions are not explicit — another reason for culture arguments.
  • Merges on dates: type both sides as date (not datetime) before joining; a time component of 00:00:00 vs a date does not match.
  • Removing errors after a bad conversion hides a locale problem; keep errors in an exception log first (s07).
  • Fiscal attributes (FY, quarter) derived from swapped dates are wrong in a way that is hard to spot in summaries — validate date ranges per file.

Key takeaways

  • Pass an explicit culture ("en-IN") or an explicit format to every text-to-date and text-to-number conversion.
  • MM is month, mm is minutes in format strings.
  • Day/month swaps are silent for days 1–12; detect via out-of-period dates and errors only on days above 12.
  • Strip grouping commas, spaces and ₹ and handle brackets/suffixes before parsing amounts if culture alone is not enough.
  • Keep values numeric in Power Query; lakh/crore display is a formatting concern.

Practice Questions

Q1. Choose the conversion [L1]

Write the M to convert each text column to the right type: (a) "05-04-2025" day-first; (b) "2025-04-05"; (c) "05-Apr-25"; (d) "05/04/2025 18:22:01" to a date only; (e) "4,82,36,190.00" to a number.

Q2. Detect the swap [L2]

A recon of the March 2026 SBI statement shows 41 transactions dated between 3 January and 12 December 2026 and 37 conversion errors. Explain what happened, how you would confirm it from the data alone, and the fix.

💡 Hint: Look at which day numbers produced errors.

Q3. Mixed formats [L2]

A bank changed its CSV format on 15 October: before, dates are "dd/MM/yy"; after, "yyyy-MM-dd". Write a conversion that handles both, logs rows that match neither, and explain why you would not simply use Table.TransformColumnTypes with a culture.

Q4. SAP amounts [L2]

An SAP export has amounts like "1,23,456.00-" (trailing minus for credits), "45.000,00" (from a user with German settings) and "12,500.00". Design a parsing rule and the checks you would add, and state what you would ask the SAP team to change at source.

Q5. Service refresh discrepancy [L3]

A Power BI report shows FY2025-26 revenue of ₹412 crore in Desktop and ₹389 crore after refresh in the Service, with no errors reported. Outline your investigation plan focusing on locale issues, and the permanent design changes.
