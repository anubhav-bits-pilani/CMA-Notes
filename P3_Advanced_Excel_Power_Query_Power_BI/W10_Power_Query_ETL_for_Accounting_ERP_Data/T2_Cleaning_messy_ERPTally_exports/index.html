Roadmap topic: Cleaning Messy ERP/Tally Exports: Removing blank/subtotal rows, filling down cost center headers, splitting ledger codes, trimming whitespace, and fixing date locales

Overview

ERP and accounting systems export reports, not tables. A Tally Trial Balance in Excel is laid out for printing: company name and period at the top, a two-line caption, group headers, indented ledgers, subtotals, a Grand Total and sometimes page breaks. SAP list outputs repeat page headers and mark totals with asterisks; Oracle BI Publisher outputs add parameter blocks; bank CSVs carry 15–20 lines of account metadata. Before any consolidation, reconciliation or modelling can happen, these reports must become tidy tables — one header row, one row per ledger or transaction, one column per attribute, correct types, Dr-positive signed amounts.

The guiding principle is condition over position. Every manual Excel habit — "delete the first 6 rows", "delete the last 3", "fill the blanks with the cell above after sorting" — breaks when next month's file has one more line. Power Query lets you express the rule ("skip until the row whose first cell is Particulars", "keep rows that have a voucher number", "fill the cost centre down before any sort") so the same query works for every month and every branch. The second principle is nothing disappears silently: totals removed from the data are kept as control totals, rows that fail conversion go to an exception log, and the cleaned TB must still net to zero.

Learning sequence: start by recognising source layouts (s08) so you know what you are cleaning; skip report headers by condition and promote headers (s01); remove blank, subtotal, total and page-break rows (s02); fill down cost-centre and group headers (s03); split ledger code/name and parse Tally Dr/Cr amounts (s04); clean invisible characters (s05); convert dates and amounts with the right locale (s06); and handle errors with exception logs instead of deleting them (s07). The concept notes give the canonical M for each step (c01–c07). Together they form the cleaning function you will apply to every file in the Topic 4 folder pipeline and the bank files in the week's exercise.

For roles in reporting, audit analytics and FP&A, this is where most real-world time goes. Interviewers routinely hand over a messy Tally export and ask candidates to clean it live; the habits here — named steps, conditional logic, control totals, exception logs — are what distinguish a robust pipeline from a one-off clean-up.

Related concepts to study

Data profiling on the entire data set

Data profiling: column quality, distribution and profile; switch to "profiling based on entire data set"

View → Column quality shows Valid/Error/Empty percentages; Column distribution shows distinct and unique counts; Column profile shows statistics and a value distribution for the selected column. By default these are computed on the top 1,000 rows; the status bar toggle "Column profiling based on top 1000 rows" can be switched to entire data set. For a 40,000-line Day Book, errors on row 32,000 or a date swap in the second half of the year are invisible on the default. Use full profiling during build and review (it is slower), and confirm: zero errors in amount and date columns, expected distinct counts for ledger and cost centre, and no unexpected empties in key columns.

Text parsing functions

Text parsing with Text.BetweenDelimiters, Text.AfterDelimiter, Text.PositionOf

Beyond splitting columns, M offers non-destructive extraction. Text.BeforeDelimiter(x, " - ") and Text.AfterDelimiter(x, " - ") return the text before/after a delimiter (with an optional occurrence index and direction). Text.BetweenDelimiters(x, "/", "/") extracts a UTR from an SBI narration such as "NEFT/SBIN526012345678/ABC TRADERS". Text.PositionOf(x, "UTR", Occurrence.First) returns the zero-based position (or −1 if absent), combined with Text.Middle(x, pos, len) for fixed-length tokens like 22-character RTGS UTRs. These functions build match keys for Topic 5 and parse branch/period from file names in Topic 4.

TB integrity after cleaning (Weeks 1–4)

→ Week 1–4: TB integrity checks (Dr = Cr) after cleaning

Cleaning is only complete when the result proves itself. From Weeks 1–4, a TB must satisfy: total debits equal total credits (or signed amounts net to zero); the cleaned total equals the report's Grand Total; the closing balance of each ledger equals opening plus movements; and the P&L balance equals the profit transferred to reserves. In Power Query, compute these in a check query per file — row counts, Dr sum, Cr sum, net, difference to the Grand Total captured before removal — and load it visibly. A non-zero net after cleaning usually points to a subtotal kept, a ledger removed, a Dr/Cr sign misparse, or a failed conversion silently removed.

Excel equivalents (Week 9)

→ Week 9: Excel equivalents TRIM, CLEAN, TEXTSPLIT

Week 9's formula toolkit has direct counterparts. TRIM collapses internal spaces and trims ends (code 32 only); CLEAN removes codes 0–31; SUBSTITUTE(A2, CHAR(160), " ") handles non-breaking spaces; TEXTSPLIT(A2, " - ") splits into columns (all occurrences); TEXTBEFORE/TEXTAFTER mirror Text.BeforeDelimiter/Text.AfterDelimiter; DATEVALUE depends on system locale just like untyped Power Query conversions. Formulas are recalculated live and visible cell-by-cell, which helps ad-hoc checks, but they must be copied down and adjusted for each new file; Power Query applies the logic once per refresh to any number of rows and files.

Tally ODBC server

Tally ODBC server (default port 9000) as a direct connection instead of exported files

Instead of exporting reports, Tally Prime can act as an ODBC (and XML/HTTP) server, by default on port 9000, while the company is open. With a DSN configured, Power Query reads ledgers, groups and vouchers through Odbc.DataSource or Odbc.Query — no report headers, no subtotals, no Dr/Cr suffix text in many fields, so most of this topic's cleaning disappears. Trade-offs: Tally must be running with the right company loaded at refresh time; a gateway is needed for Service refresh; sign conventions of closing balances must be verified; and SQL support is limited, so filtering happens mostly locally. For branch environments where Tally runs on a local PC, exported files to a shared folder are often more reliable.

Common pitfalls

Remove Bottom Rows on a variable footer

Removing total rows with Remove Bottom Rows when the row count changes each month

"Remove Bottom Rows: 2" (Table.RemoveLastN(t, 2)) assumes the footer always has two lines. Tally adds "Difference in opening balances" when openings do not tally; bank CSVs add summary lines for cheque returns; SAP page footers depend on row counts. One extra line keeps a total in the data (double counting); one fewer deletes a real ledger. People use it because the UI offers it and it works on the sample. Correct treatment: remove footer rows by condition (Table.SelectRows with exact text or structural tests), and reconcile cleaned totals to the captured Grand Total. Review detection: search M for RemoveLastN/RemoveFirstN with numeric arguments; any positional removal on a report export needs justification.

Fill Down after a sort or filter

Running Fill Down after a sort or filter, which pulls the wrong header into rows

Fill Down uses physical row order at that step. If rows were sorted (e.g. by ledger name to tidy up) or filtered (header-only rows removed) before the fill, each detail row inherits the wrong cost centre or none at all. People reorder steps casually because most transformations are order-independent. Correct treatment: create the header column, convert blanks to null, Fill Down immediately after promotion and header-flagging, and only then filter and sort. Review detection: in Applied Steps, check that no Sorted Rows, Merged Queries or header-removal filter precedes Filled Down; test by reconciling cost-centre totals to the report's block totals.

Wrong-locale date conversion

Converting dates in the wrong locale, which silently swaps day and month for days 1–12

Converting "03-04-2026" on an en-US machine yields 4 March 2026 without error; only days 13–31 fail. The query appears to work in April testing (when many errors might be noticed) or gives plausible but wrong dates, shifting cut-off, ageing and FY/quarter attributes. It happens because the default culture is invisible and differs between laptops and the Power BI Service. Correct treatment: pass "en-IN" (or an explicit format) to every conversion from text, or set the file's locale, and type in source-specific staging queries. Review detection: per-file min/max dates against the statement period, errors concentrated on days above 12, and a distribution of day numbers.

Profiling only the top 1,000 rows

Profiling only the top 1000 rows by default, which hides errors deeper in the file

Column quality and distribution default to the first 1,000 rows. A Day Book of 40,000 lines can show "100% valid" while rows 18,000–40,000 contain conversion errors, a second date format or a stray page header. People trust the green bar because they do not notice the status-bar note. Correct treatment: switch to "Column profiling based on entire data set" when building and reviewing, and in production rely on explicit checks — error counts, null counts and control totals per file — rather than the preview. Review detection: check the status bar setting; compare full-refresh error counts reported after load with what the preview showed.

Practice Questions

Q1. Clean a Tally TB end to end [L3]

You receive TB_Hyderabad_Mar26.xlsx from Tally Prime, Detailed mode, with: 6 report-header lines (company, address 2 lines, GSTIN, "Trial Balance", "1-Apr-25 to 31-Mar-26"); a two-line caption "Particulars | Closing Balance" over " | Debit | Credit"; groups (e.g. "Current Assets") followed by indented ledgers like "130105 - Sundry Debtors - Rao & Sons"; group lines that carry group totals; zero-balance ledgers with both amounts blank; a "Grand Total" row; amounts as text with Indian grouping, some cells containing char 160. (a) Write the full M query (named steps) producing Group, Code, Name, Debit, Credit, Amount (Dr positive). (b) Add a control-totals query comparing cleaned Dr/Cr with the Grand Total. (c) Add an exception log for unparseable amounts and ledgers without codes. (d) List three ways the query could still fail next month and how you would detect each.

Q2. Bank statement CSV cleaning [L2]

An HDFC statement CSV contains 19 header lines (account number on line 4 as "Account No :50100123456789"), then columns Date, Narration, Chq./Ref.No., Value Dt, Withdrawal Amt., Deposit Amt., Closing Balance; dates "dd/MM/yy"; narrations with quoted commas and line breaks; and a footer block "STATEMENT SUMMARY" of variable length. (a) Write the source and cleaning steps up to a typed table with an Account column. (b) Explain how your query behaves if the footer grows by four lines or the header by two. (c) Design checks that would detect a locale problem and lost rows.

💡 Hint: Capture metadata before skipping, and stop the data at the footer marker by condition.

Q3. Day Book to voucher lines [L2]

A Tally Day Book export (detailed) shows the Date, Vch Type and Vch No. only on the first line of each voucher, ledger lines below with Particulars and Debit/Credit, narration lines in italics as separate rows with no amounts, and blank lines between vouchers. Describe and write the M to produce one row per ledger line with Date, VchType, VchNo, Ledger, Amount and Narration. State the sequence constraints between Fill Down and filters.

Q4. Review a cleaning query [L2]

A colleague's SAP FBL3N cleaning query: Source → Promoted Headers → Changed Type (auto, en-US machine) → Removed Top Rows (3) → Removed Bottom Rows (2) → Split "G/L Account Text" by "-" at each occurrence → Replaced Errors with 0 → Trimmed Text. Write a review memo identifying every problem, its likely consequence on a consolidated TB, and the corrected step list.

Q5. Interview case: why condition-based cleaning [L1]

Prepare a 3-minute explanation for an FP&A hiring manager of why condition-based steps, control totals and exception logs matter when cleaning ERP exports, using one example each from Tally, SAP and a bank statement.
