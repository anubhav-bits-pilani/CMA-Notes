Subtopic note

Column From Examples, Custom Column and Conditional Column

Scope: Column From Examples vs Custom Column vs Conditional Column, and reading the M each one generates

Why it matters

Power Query offers three dialogs under Add Column for creating a new column, and each writes a Table.AddColumn step with different M inside. Finance users often use whichever dialog they found first, accept the result because the preview looks right, and move on. The risk is not the dialog but the unread M: Column From Examples may infer a rule that fits your five examples but not row 3,000; a Conditional Column may compare text with numbers; a Custom Column usually leaves the type as any. Reading the generated formula bar is how you catch these before they reach the model, and it is also how you learn M quickly — the dialogs are a code generator.

Core notes

Column From Examples

You type the desired output for a few rows; Power Query searches for a transformation that reproduces them and shows the formula it found at the top of the dialog. Options: From All Columns or From Selection.

Typical uses: extracting a code ("400100" from "400100 - Sales Domestic"), combining text ("MUM-2025-04"), reformatting dates ("Apr-25" from a date), and range bucketing of numbers (type "0-30" next to 12 and "31-60" next to 45, and it proposes bins).

Generated M examples:

Table.AddColumn(Source, "Code", each Text.BeforeDelimiter([Ledger], " - "), type text)
Table.AddColumn(Source, "Period", each Date.ToText([Date], "MMM-yy"), type text)
Table.AddColumn(Source, "Range", each
    if [Days] >= 0 and [Days] <= 30 then "0-30"
    else if [Days] >= 31 and [Days] <= 60 then "31-60"
    else null, type text)

Strengths: quick, and it usually adds a type. Weaknesses: the inferred rule is only as good as your examples; it may choose Text.Middle([Ledger], 0, 6) (positional, fails for 5-digit codes) instead of Text.BeforeDelimiter; range bins may leave gaps or return null outside the example range; and date-format outputs are culture-dependent. Always provide examples that cover edge cases (short codes, missing delimiters), then read and, if needed, edit the formula.

Custom Column

You write an M expression in a dialog that shows available columns. The step generated is:

Table.AddColumn(#"Previous Step", "FYEnd", each Date.Year([Date]) + (if Date.Month([Date]) >= 4 then 1 else 0))

The expression is wrapped in each, so [Date] refers to the current row. Strengths: full M power — let ... in blocks, function calls, references to parameters (AsOfDate) and other queries. Weaknesses: the dialog in many versions has no type selector, so the column is any (ABC/123 icon). Newer builds include a data-type drop-down; if yours does not, add the type argument by editing the formula bar:

Table.AddColumn(#"Previous Step", "FYEnd", each Date.Year([Date]) + (if Date.Month([Date]) >= 4 then 1 else 0), Int64.Type)

Conditional Column

A rule builder: column, operator, value, output, with Else If clauses and an Else value. Values and outputs can be literals, columns or parameters (choose via the ABC/123 drop-down). Generated M:

Table.AddColumn(#"Added Days", "Bucket", each
    if [Days] <= 30 then "0-30"
    else if [Days] <= 60 then "31-60"
    else if [Days] <= 90 then "61-90"
    else ">90")

Strengths: readable rules for non-coders, easy to edit through the gear icon. Weaknesses: one column per condition (no and across columns in older versions; you need a Custom Column for compound tests), no null handling unless you add a rule for it, and type may be left as any depending on version. Nulls behave differently by operator: null = 30 is simply false, so an equality rule lets a null row fall through to the Else output (a silent misclassification), whereas null <= 30 returns null, and if null then ... raises an error, so a range rule turns the row into an Error cell that surfaces only at load.

Reading and editing the generated M

Each dialog produces one Table.AddColumn(table, newColumnName, columnGenerator, optional columnType) step. After using a dialog:

  1. Click the step and read the formula bar.
  2. Check the generator logic for positional operations, uncovered ranges and null behaviour.
  3. Check the fourth argument (type); add it if missing.
  4. Rename the step meaningfully ("Added FY label" rather than "Added Custom2").

Once comfortable, you can write the step directly in the formula bar or Advanced Editor, which is faster and less error-prone than reopening dialogs.

Choosing between them

Need Best route
Text pattern you can show but not easily describe Column From Examples, then verify the formula
Rule chain on one column with literal outputs Conditional Column
Compound logic, parameters, functions, let blocks Custom Column (or formula bar)
Anything going into a data model Any of them, but confirm the type argument

Worked illustration

Ledger values: "400100 - Sales Domestic", "40020 - Sales Export", "Misc Income". Column From Examples given the first row's "400100" may infer Text.Start([Ledger], 6) and return "40020 " (with a trailing space and hyphen issues) for the second row and "Misc I" for the third. Supplying "40020" as a second example pushes it towards Text.BeforeDelimiter([Ledger], " - "), which returns "Misc Income" (whole text) for the third — still wrong for a ledger without a code. A Custom Column with if Text.Contains([Ledger], " - ") then Text.BeforeDelimiter([Ledger], " - ") else null, typed type text, is the robust version.

Edge cases & judgement calls

  • Culture in examples. Typing "01/04/2025" as an example output is read in the current locale; prefer unambiguous outputs.
  • Editing via the gear icon. Re-opening a Conditional Column dialog after hand-editing its M may fail or discard edits; once edited by hand, keep editing by hand.
  • Column references with spaces. Custom Column writes [Invoice Date]; names with special characters use [#"Inv. Date"].
  • Parameters in Conditional Column. Comparing with a parameter (e.g. MSME threshold days) is supported and keeps rules configurable.
  • Performance. All three produce row-by-row expressions that do not fold on file sources; on SQL sources simple expressions may fold, Column From Examples outputs often do not.

Key takeaways

  • All three dialogs generate a Table.AddColumn step; the difference is how the generator expression is produced.
  • Column From Examples infers a rule from your examples — verify it for positional logic and uncovered ranges.
  • Custom Column gives full M but often leaves the column as any; add the type argument.
  • Conditional Column suits single-column rule chains; handle nulls explicitly, or they fall through to Else (equality rules) or error (range rules).
  • Read every generated formula, fix the type and rename the step before loading.

Practice Questions

Q1. Identify the generator [L1]

For each formula, say which dialog most likely produced it and what is missing for a data-model load: (a) Table.AddColumn(t, "Custom", each [Debit] - [Credit]); (b) Table.AddColumn(t, "Bucket", each if [Days] <= 30 then "0-30" else ">30"); (c) Table.AddColumn(t, "Code", each Text.Start([Ledger], 6), type text).

Q2. Null fall-through [L2]

An ageing Conditional Column is if [Days] <= 30 then "0-30" else if [Days] <= 60 then "31-60" else if [Days] <= 90 then "61-90" else ">90". Fourteen invoices have a null InvoiceDate, so Days is null. State what the column shows for those rows and why, what happens when the query loads, and rewrite the formula to put them in a "No date" bucket with a proper type.

💡 Hint: Work out what null <= 30 evaluates to in M, and what if does with a condition that is not a logical value; then test [Days] = null first.

Q3. Repair an inferred rule [L2]

Column From Examples produced Text.Middle([Narration], 9, 16) to extract a UTR from narrations like "NEFT CR-HDFCN52025040112345-ACME". Explain why this is fragile and write a delimiter-based replacement that returns null when the pattern is absent.

Q4. Choose the route [L1]

Which dialog would you use for: (a) a column showing "Domestic" or "Export" from the ledger code range; (b) a period label "Apr-25" from a date; (c) ageing bucket using the AsOfDate parameter and InvoiceDate; (d) an MSME flag that depends on both MSMEStatus and DaysOverdue?
