Subtopic note

Conditional Logic in M: if/then/else, and/or, and Null Coalescing

Scope: if ... then ... else, nested conditions, and/or, null coalescing with ??

Why it matters

Almost every finance attribute built in Power Query is a condition: the FY end year depends on whether the month is April or later; an ageing bucket depends on a range of days; an MSME breach depends on both the vendor's status and the days outstanding; a net amount depends on which of Debit or Credit is populated. M's conditional syntax is small, but its rules on null differ from Excel and SQL, and most silent errors in custom columns come from nulls: a null Debit makes the net amount null, a null date makes a range test raise an error, a null text makes a concatenated label null. Knowing exactly how M treats null in comparisons, logic and arithmetic is the difference between a column that is right and one that is right except for 2% of rows.

Core notes

if ... then ... else

if Date.Month([Date]) >= 4 then 1 else 0
  • else is mandatory; there is no implicit null. Use else null explicitly if needed.
  • The condition must evaluate to a logical (true/false). If it evaluates to null or any non-logical value, M raises an error ("We cannot convert the value null to type Logical").
  • if is an expression and returns a value, so it can appear inside arithmetic: Date.Year([Date]) + (if Date.Month([Date]) >= 4 then 1 else 0). The parentheses are needed because if ... else extends as far right as possible.

Nested conditions

if d <= 30 then "0-30"
else if d <= 60 then "31-60"
else if d <= 90 then "61-90"
else ">90"

Conditions are tested in order and the first true branch wins, so each test only needs the upper bound. Put the most specific or exceptional cases first (null checks, disputed items) and the general fall-through last. For long mappings of discrete values (ledger group code to Schedule III line), a lookup is cleaner than a long chain: merge with a mapping table, or use a record:

Map = [#"10" = "Revenue", #"20" = "Other income", #"30" = "Cost of materials"],
Line = Record.FieldOrDefault(Map, [GroupCode], "Unmapped")

and, or, not

  • and, or and not are lowercase keywords (not functions, not &&).
  • Precedence: not binds tightest, then and, then or. a or b and c means a or (b and c). Use parentheses whenever you mix them.
  • and and or short-circuit: in [Days] <> null and [Days] > 45, the second test is not evaluated when Days is null, so no error is raised. This is the idiomatic null guard.
  • Membership tests use List.Contains({"Micro", "Small"}, [MSMEStatus]), the equivalent of SQL IN.

Example — MSME breach flag:

Table.AddColumn(AP, "MSMEBreach", each
    List.Contains({"Micro", "Small"}, [MSMEStatus])
    and [DaysFromAcceptance] <> null
    and [DaysFromAcceptance] > 45, type logical)

How null behaves

Operation Result with null Example
Equality =, <> Logical; null = null is true, null = 5 is false [Ref] = null is the null test
Relational <, <=, >, >= null null <= 30 → null (then if raises an error)
Arithmetic + - * / null null - 500 → null
Text concatenation & null "FY" & null → null
and / or Short-circuit; false and null → false, true or null → true
List functions Usually ignore nulls List.Sum({100, null, 50}) → 150

The practical consequences: test for null before range comparisons; coalesce before arithmetic; coalesce before concatenation.

Null coalescing with ??

x ?? y returns x if x is not null, otherwise y. It replaces the verbose if x = null then y else x.

Net    = ([Debit] ?? 0) - ([Credit] ?? 0)
Party  = [PartyName] ?? [LedgerName] ?? "Unknown"
Header = optionalHeader ?? "Particulars"

?? has lower precedence than arithmetic, so parentheses are essential: [Debit] ?? 0 - [Credit] ?? 0 is parsed as [Debit] ?? ((0 - [Credit]) ?? 0), which returns Debit unchanged whenever Debit is not null — the Credit is silently ignored. ?? chains right-to-left, so a ?? b ?? c returns the first non-null.

Note that ?? tests only for null, not for empty text or zero. An empty string "" from a CSV is not null; convert blanks to null first (Table.ReplaceValue(t, "", null, Replacer.ReplaceValue, {"Party"})) or test if x = null or x = "" then ....

Errors vs nulls

A condition that errors produces an Error cell, not a null. To convert errors into a default inside a column: try <expr> otherwise <default>. Use sparingly: hiding errors with otherwise can mask bad data; log them instead where they matter.

Worked illustration

Row values: Debit = null, Credit = 25,000, Days = null, MSMEStatus = "Micro".

  • [Debit] - [Credit] → null (row disappears from sums later).
  • ([Debit] ?? 0) - ([Credit] ?? 0) → −25,000.
  • [Debit] ?? 0 - [Credit] ?? 0 → null ?? ((0 − 25,000) ?? 0) → −25,000 here by coincidence; with Debit = 10,000 it returns 10,000 instead of −15,000.
  • if [Days] > 45 then "Breach" else "OK" → error (condition is null).
  • if [Days] <> null and [Days] > 45 then "Breach" else if [Days] = null then "No date" else "OK" → "No date".

Edge cases & judgement calls

  • Type mixing in comparisons. "45" > 30 raises an error (text vs number); type columns before building conditions.
  • Case sensitivity. [Status] = "micro" is false for "Micro"; normalise with Text.Upper or compare with Comparer.OrdinalIgnoreCase via Comparer.Equals.
  • Floating-point equality. 0.1 + 0.2 = 0.3 is false; round before equality tests on amounts.
  • Booleans as numbers. Unlike Excel, true + 1 is an error; use if b then 1 else 0 or Number.From(b).
  • Readable logic. For long chains, compute intermediate values in a let inside the each (e.g. let d = ... in ...) to avoid repeating expressions.

Key takeaways

  • if ... then ... else always needs else; its condition must be a logical, or M raises an error.
  • and/or/not are keywords with precedence not > and > or; they short-circuit, which makes x <> null and x > 45 safe.
  • Null propagates through relational, arithmetic and concatenation operators; equality with null returns a logical.
  • ?? returns the first non-null value; it has lower precedence than arithmetic, so parenthesise.
  • ?? does not treat "" or 0 as null; clean blanks to null first.

Practice Questions

Q1. Evaluate the expressions [L1]

Give the result (value or error) of each: (a) null = null; (b) null > 0; (c) if null > 0 then 1 else 0; (d) "FY" & null; (e) 5 ?? 0 - 3; (f) (null ?? 0) - 3; (g) List.Sum({10, null, 5}).

Q2. Write a robust net-amount and side column [L2]

A TB has Debit and Credit columns as numbers with nulls and occasional zeros. Write M adding Net (Debit minus Credit, nulls as zero) and Side ("Dr", "Cr" or "Nil" based on Net), both typed.

💡 Hint: Compute Net first, then derive Side from Net rather than from Debit and Credit separately.

Q3. MSME and disputed logic [L2]

Write a single Custom Column that returns "Disputed" if DisputeFlag is true, otherwise "MSME overdue" if the vendor is Micro or Small and DaysFromAcceptance exceeds 45, otherwise "Within terms" — handling nulls in DisputeFlag and DaysFromAcceptance without errors.

Q4. Precedence bug hunt [L2]

The formula each [Opening] ?? 0 + [Debit] ?? 0 - [Credit] ?? 0 is used to compute Closing. For a row with Opening = 50,000, Debit = 20,000, Credit = 5,000, state what it returns and why, then correct it.
