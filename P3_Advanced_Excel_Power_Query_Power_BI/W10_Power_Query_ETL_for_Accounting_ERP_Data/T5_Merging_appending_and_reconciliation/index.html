Roadmap topic: Merging & Appending Queries: Left Outer, Inner, and Anti-Joins (e.g., matching Bank Statement vs Book Ledger in Power Query to isolate unreconciled items)

Overview

Most finance reconciliations are join problems. A bank reconciliation statement asks which bank transactions have a matching book entry and which do not; a GSTR-2B reconciliation asks which supplier invoices appear in both the portal and the purchase register; an intercompany reconciliation asks whether entity A's receivable from B equals B's payable to A. In Excel these are typically done with VLOOKUP/XLOOKUP and COUNTIFS columns, filtered for #N/A. Power Query expresses the same logic as merges (joins) and appends (unions), with two advantages: the logic is repeatable on next month's data with one refresh, and anti-joins return the unreconciled items directly as tables.

The topic builds in this order. First, the distinction between Append (Table.Combine, stacking rows like SQL UNION ALL) and Merge (Table.NestedJoin, matching rows like SQL JOIN) (s01). Then the six join kinds and what each returns in a reconciliation — LeftOuter for an annotated bank list, Inner for matched pairs, FullOuter for a complete recon view, and LeftAnti/RightAnti for the exceptions (s02). Next comes the hard part, which is not M syntax but matching design: choosing the key (amount, UTR or cheque number, date window) (s03), normalising keys so that "000123" matches 123 and "acme ltd " matches "ACME LTD" (s04), using fuzzy merge where names rather than codes are the key (s05), and handling repeated identical amounts with sequence numbers so one-to-many matches do not multiply rows (s06). Finally, the same toolkit applied to other reconciliations: GSTR-2B vs purchase register, AR sub-ledger vs GL control, and intercompany balances (s07).

For FP&A and controllership roles, this is where Power Query directly shortens the close: the BRS, the ITC reconciliation and the intercompany confirmation can each be reduced to "drop the files, refresh, review exceptions". The key concepts give the exact M: anti-joins for bank-only and book-only items, the expand step with prefixed names, the fuzzy-join options, the duplicate-safe sequence key and sign alignment between bank and book.

Related concepts to study

SQL anti-join pattern

SQL LEFT JOIN ... WHERE b.key IS NULL as the anti-join pattern in MySQL

In MySQL, there is no ANTI JOIN keyword; the idiom is SELECT k.* FROM bank k LEFT JOIN book b ON k.ref = b.ref AND k.amount = b.amount WHERE b.ref IS NULL. The left join keeps every bank row and puts NULLs in the book columns where nothing matched; the WHERE clause keeps only those. NOT EXISTS (SELECT 1 FROM book b WHERE ...) is the equivalent correlated form and is often faster. Power Query's JoinKind.LeftAnti does both steps in one, and when the source is a SQL database the merge can fold into exactly this SQL. One semantic difference: SQL's NULL = NULL is unknown, so null keys never match, whereas M treats null equal to null, so blank references on both sides can match each other unless you filter them out first.

BRS and control-account reconciliations (Weeks 1–4)

→ Week 1–4: BRS preparation and control-account reconciliations in month-end close

The accounting logic does not change when the tool does. A BRS starts from the balance per bank or per books and adjusts for timing items (cheques issued but not presented, deposits in transit) and for errors or omissions (bank charges, interest, direct credits, dishonoured cheques not yet booked). The anti-join outputs map directly: bank-only items are mostly entries the books must pass (charges, interest, NACH debits, unidentified receipts); book-only items are mostly timing differences awaiting the bank. Control-account reconciliations (debtors, creditors, GST input) follow the same pattern at a summarised level: sub-ledger totals by party vs the GL control balance, with differences explained by direct GL postings, cut-off and unallocated items.

Forensic tests with merge and group (Weeks 5–8)

→ Week 5–8: forensic tests (duplicate payments, split invoices) with merge/group

Forensic analytics on payables uses the same building blocks. Duplicate payments: self-merge the payment register on Vendor + Amount (and optionally invoice number normalised), keep pairs where the voucher numbers differ and dates are within, say, 30 days. Split invoices: group by Vendor + Date, count invoices just below the approval limit (e.g. ₹4.9–4.99 lakh where the limit is ₹5 lakh), flag groups with more than one. Vendor master overlaps: fuzzy-merge vendor names or match bank account and PAN across vendor codes. Power Query makes these tests repeatable each quarter, which internal audit values over one-off spreadsheet analysis.

Formula-based reconciliation (Week 9)

→ Week 9: XLOOKUP/COUNTIFS reconciliations as the formula alternative

In Excel, a typical recon adds =COUNTIFS(Book[Ref],[@Ref],Book[Amount],[@Amount]) to the bank table and filters for zero, or =XLOOKUP([@Ref]&"|"&[@Amount], Book[Ref]&"|"&Book[Amount], Book[Date], "Not found"). Formulas are visible and quick for a few thousand rows, and reviewers understand them. They become fragile with repeated amounts (COUNTIFS shows 2 but does not pair rows), heavy for 100,000-row statements, and must be re-extended every month. Power Query anti-joins scale, pair rows explicitly with sequence keys and refresh in one click; formulas remain useful for spot checks of the query's output.

Common pitfalls

Text keys vs number keys

Merging text keys with number keys returns zero matches and no error.

If the bank's cheque number column is text ("000456") and the book's is a whole number (456), or if the Amount is decimal on one side and text on the other, Table.NestedJoin compares values of different types as unequal: every row goes to the anti-join, and nothing errors. People miss it because the columns look identical in the preview. Correct treatment: normalise both sides to the same type and format before merging (text with leading zeros stripped, or numbers rounded to two decimals). Detect it by checking the matched count: an Inner join returning zero or a suspiciously low number of rows is the alarm; also inspect column type icons on both key columns.

No tolerance for charges and TDS

Exact-amount matching when bank charges or TDS create partial differences, with no tolerance rule.

A customer pays ₹1,00,000 less 10% TDS under Sec 194J, so the bank receipt is ₹90,000 against a ₹1,00,000 invoice; an inward remittance arrives net of ₹590 bank charges. Exact amount matching sends both sides to exceptions. People rely on exact matching because it is the default merge. Correct treatment: match first on reference (UTR, invoice number) without amount, then compute the difference and classify it against tolerance rules (e.g. difference equals 1%, 2% or 10% of the base, or is under ₹1,000 and narration contains "CHG"). Detect it in review when the exceptions list contains many pairs of near-equal amounts with the same reference.

Many-to-many row multiplication

Many-to-many matches that multiply rows after expanding.

If three bank rows of ₹25,000 and two book rows of ₹25,000 share the same key, the merge gives each bank row a nested table with two book rows; expanding produces six rows. Totals inflate and the same book entry appears "matched" three times. People miss it because the merge dialog's "matches X of Y rows" statistic looks good. Correct treatment: ensure keys are unique on at least one side, or add sequence numbers within each duplicate group (Group By + Index) so that pairing is one-to-one. Detect by comparing row counts before and after expanding, and by checking key uniqueness with a Group By count.

Repeated merges without buffering

Repeated merges on non-folding sources without Table.Buffer, which makes refresh slow.

A recon query that merges the bank table against the book table four times (tier 1 exact, tier 2 date window, tier 3 fuzzy, final check) may re-read and re-clean the source CSVs for each merge, because Power Query's evaluation does not cache intermediate results reliably across steps and queries. With 2 lakh rows the refresh can take many minutes. Correct treatment: after cleaning and before the merges, Table.Buffer the smaller lookup table (or both) so it is held in memory, and disable load on staging queries. Detect with Query Diagnostics or simply by timing refresh before and after; do not buffer foldable SQL sources early, as buffering stops folding.

Practice Questions

Q1. End-to-end BRS in Power Query [L3]

The books' bank ledger for HDFC current account (April 2025) has 1,940 entries with columns VchDate, VchNo, Narration, ChequeNo (text, e.g. "000417"), Debit, Credit. The bank CSV has 2,015 rows with Date, Narration, Chq./Ref.No. (number), Withdrawal Amt., Deposit Amt. Balance per bank on 30-Apr-2025 is ₹84,26,310.00; balance per books is ₹71,58,940.00. (a) Design the full query chain from source to exceptions, including normalisation, sign alignment and sequence keys. (b) State which join kinds produce each list in the BRS. (c) List the BRS line items you expect each list to contain and how you would prove the BRS arithmetic closes.

💡 Hint: Separate tier-1 (reference + amount) and tier-2 (amount + date window) matching, removing tier-1 matches before tier 2.

Q2. GSTR-2B reconciliation design [L3]

For September 2025, GSTR-2B (downloaded as Excel) has 3,482 invoice lines; the purchase register has 3,610 lines. Invoice numbers differ in format ("INV/25-26/0042" vs "42", "inv-0042"). Design the normalised key, the merge sequence and the output categories (matched, value mismatch, in 2B only, in books only). Explain the Sec 16(2)(aa) CGST Act consequence of each book-only item and how the output would feed the ITC claim in GSTR-3B.

Q3. Intercompany matching with signs and currency [L2]

Entity A (India, INR) shows a receivable from Entity B (Singapore) of ₹4,15,00,000; B shows a payable to A of SGD 6,48,000 at 31-Mar-2026. Closing rate is ₹64.20 per SGD. Design the Power Query steps (key, sign alignment, currency conversion, tolerance) that produce a matched/unmatched intercompany report, and identify what the residual difference may represent.

Q4. Interview: why did the recon find nothing? [L2]

A junior's recon query reports 100% of bank rows as "not in books". Give five possible technical causes in Power Query, how you would test each in under two minutes, and the fix for each.

Q5. Duplicate payment test [L3]

The AP payment register for FY2025-26 has 48,600 rows (Vendor Code, Vendor Name, Invoice No, Invoice Date, Amount, Payment Date, Voucher No). Design a Power Query forensic test that flags potential duplicate payments, handling repeated amounts, normalised invoice numbers and fuzzy vendor names. Specify outputs and how you would control false positives.
