Subtopic note

Repeated Identical Amounts: Sequence Keys for One-to-One Matching

Scope: Repeated identical amounts (one-to-many): sequence numbers via Group By + Index before joining

Why it matters

Bank and book data are full of repeated amounts: monthly rent of ₹1,50,000 to the same landlord, ten salary-advance recoveries of ₹5,000, three customer cheques of ₹25,000 deposited the same day, identical bank charges of ₹590. When a merge key is not unique, Power Query pairs every left row with every right row that shares the key. Expanding then multiplies rows, inflates totals and marks a single book entry as matched to several bank lines. A reconciliation must pair items one-to-one: the first ₹25,000 to the first ₹25,000, the second to the second, and any surplus becomes an exception. Sequence numbers within each duplicate group achieve exactly that.

Core notes

The multiplication problem

Bank has three rows of ₹25,000 on 12-Apr; Book has two rows of ₹25,000 dated 11-Apr and 12-Apr. Merging on Amount alone:

  • Each of the three bank rows gets a nested table with two book rows.
  • Expanding gives \(3 \times 2 = 6\) rows.
  • A LeftAnti returns nothing (every bank row found a match), although one bank deposit has no book counterpart.

So many-to-many keys break both the matched register and the anti-joins.

The sequence-key technique

Within each group of identical keys, number the rows 1, 2, 3 in a defined order, on both sides; then join on Key + Seq.

SortedBank = Table.Sort(Bank, {{"AmtPaise", Order.Ascending}, {"TxnDate", Order.Ascending}, {"BankRowID", Order.Ascending}}),
GroupedBank = Table.Group(SortedBank, {"AmtPaise"},
    {{"Rows", each Table.AddIndexColumn(_, "Seq", 1, 1, Int64.Type), type table}}),
BankSeq = Table.ExpandTableColumn(GroupedBank, "Rows",
    {"BankRowID", "TxnDate", "Narration", "Ref", "Seq"}),

Repeat for the book side (grouped on the same key, sorted by voucher date and voucher number), then:

Matched  = Table.NestedJoin(BankSeq, {"AmtPaise", "Seq"}, BookSeq, {"AmtPaise", "Seq"}, "Bk", JoinKind.Inner),
BankOnly = Table.NestedJoin(BankSeq, {"AmtPaise", "Seq"}, BookSeq, {"AmtPaise", "Seq"}, "Bk", JoinKind.LeftAnti),
BookOnly = Table.NestedJoin(BookSeq, {"AmtPaise", "Seq"}, BankSeq, {"AmtPaise", "Seq"}, "Bk", JoinKind.LeftAnti)

With three bank rows (Seq 1–3) and two book rows (Seq 1–2): Matched has 2 rows, BankOnly has 1 row (Seq 3), BookOnly is empty.

Why sorting matters

Table.AddIndexColumn numbers rows in their current order inside each group. Without an explicit sort, the order is whatever the source produced, which can differ between refreshes; the same bank row might be "Seq 1" this month and "Seq 3" after a re-download. Sort deterministically — by date, then by a stable row ID — before grouping. Note that Table.Group preserves the incoming order within groups in practice, but if in doubt, sort inside the group: each Table.AddIndexColumn(Table.Sort(_, {"TxnDate", "BankRowID"}), "Seq", 1, 1).

Sorting by date means the earliest bank item pairs with the earliest book item — a FIFO assumption that mirrors how most people tick a BRS manually. It is a convention, not truth: if the second ₹25,000 cheque in the books bounced, FIFO pairing may attribute the unmatched item to the wrong cheque. For cheques, prefer cheque-number keys; use sequence keys for amounts without references.

Combining with date windows

Sequence keys can be scoped more narrowly by including a date bucket in the group key: group on AmtPaise + Week or AmtPaise + TxnDate (exact day) so that a ₹590 charge in April does not pair with one in May. The trade-off: narrower groups reduce wrong pairings but miss matches that cross the bucket boundary (a deposit on 30-Apr cleared on 2-May). A common pattern: first sequence-match within the same day, then sequence-match the leftovers within the window.

Checking uniqueness

Before any merge in a recon, test key uniqueness on both sides:

DupCheck = Table.SelectRows(Table.Group(BankSeq, {"AmtPaise", "Seq"},
    {{"n", each Table.RowCount(_), Int64.Type}}), each [n] > 1)

DupCheck must be empty. Table.IsDistinct(Table.SelectColumns(BankSeq, {"AmtPaise", "Seq"})) is a one-line alternative that returns true or false.

Worked illustration

Bank (April), amount ₹590 (charges): 7 rows. Book: 5 rows of ₹590. After sequencing: Seq 1–5 match, bank Seq 6–7 are bank-only — two charges (₹1,180 in total) not yet booked. Without sequencing, merging on amount would have produced \(7 \times 5 = 35\) expanded rows and a LeftAnti showing zero unbooked charges.

Edge cases & judgement calls

  • Grouping key must equal the join key minus Seq. If you group on Amount but join on Ref + Amount + Seq, sequences are meaningless.
  • Sign alignment first. Sequence after flipping signs; otherwise receipts and payments of equal magnitude share groups on one side but not the other.
  • Bulk vs individual. A ₹75,000 single bank credit versus three ₹25,000 book entries is a many-to-one aggregation problem, not a sequence problem; sequencing will not find it — aggregate by date first.
  • Stability across months. Recompute sequences on the current month's open items, including carried-forward unmatched items from prior months, so numbering stays consistent.
  • Performance. Group By with nested tables is in-memory; buffer inputs if the recon runs several sequence stages.

Key takeaways

  • Non-unique keys make merges many-to-many: expanded rows multiply and anti-joins miss exceptions.
  • Number rows within each key group with Group By + Table.AddIndexColumn, on both sides, then join on Key + Seq.
  • Sort deterministically before numbering, so pairing is reproducible and FIFO by date.
  • Narrow groups with a date bucket where appropriate, and run a second pass for cross-bucket items.
  • Prove uniqueness of the final key on both sides before merging.

Practice Questions

Q1. Predict the counts [L1]

Bank has four rows of ₹12,000 and book has six rows of ₹12,000 for the same account and month. State the number of rows after expanding a merge on Amount only, and the matched, bank-only and book-only counts with Amount + Seq keys.

Q2. Write the sequencing step [L2]

Write M that adds a Seq column to the Book table, numbering rows within each AmtPaise group in order of VchDate then VchNo, and returns a flat table with all original columns plus Seq.

💡 Hint: Sort inside the each before Table.AddIndexColumn, then expand with Table.ColumnNames(Book) plus "Seq".

Q3. FIFO pairing risk [L2]

Three cheques of ₹40,000 were deposited on 7, 9 and 14 April and booked on those dates; the bank credited two of them on 9 and 11 April, and the 9-April cheque was returned unpaid. Explain how FIFO sequence matching on amount would pair these items, why the result could misidentify which cheque is outstanding, and what key would avoid this.

Q4. Many-to-one detection [L3]

A payment gateway settles daily: one bank credit per day equals the sum of 150–400 book receipts (net of 1.8% MDR plus GST). Design the Power Query logic to match settlements to receipts, explain why sequence keys are not suitable here, and state the tolerance rule for the MDR.
