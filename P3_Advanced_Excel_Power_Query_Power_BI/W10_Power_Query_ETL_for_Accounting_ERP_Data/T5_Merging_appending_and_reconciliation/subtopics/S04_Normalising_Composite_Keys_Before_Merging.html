Normalising Composite Keys Before Merging

Scope: Normalising composite keys before merging (trim, upper case, strip leading zeros, matching types)

Why it matters

Power Query merges use exact, type-sensitive, case-sensitive equality. "000417" and 417, "ACME LTD" and "Acme Ltd ", 125000 and 125000.0000001 all fail to match — silently. In real exports, these differences are the rule rather than the exception: Tally exports cheque numbers as text with leading zeros, the bank CSV exports them as numbers; SAP pads document numbers to 10 digits; amounts arrive as floating-point values with tiny binary residues. Normalising both sides of every key to one canonical form, before the merge, is the single biggest driver of match rate.

Core notes

The canonical-key principle

For each key component, define one canonical representation and convert both sides to it, in a dedicated step or function. Do not normalise only one side; do not rely on "it looks the same in the preview".

fxNormRef = (r as any) as nullable text =>
    let t = if r = null then null else Text.From(r),
        c = if t = null then null else Text.Upper(Text.Trim(Text.Clean(Text.Replace(t, Character.FromNumber(160), " ")))),
        d = if c = null then null else Text.Select(c, {"0".."9", "A".."Z"}),
        z = if d = null then null else Text.TrimStart(d, "0")
    in  if z = null or z = "" then null else z

Component by component

Whitespace and non-printables. Text.Trim removes leading/trailing spaces; Text.Clean removes control characters; non-breaking spaces (character 160) should be replaced with ordinary spaces explicitly before trimming: an embedded NBSP is never touched by Text.Trim, and relying on its default handling of edge NBSPs is not refresh-proof.

Case. M comparisons are case-sensitive by default. Convert both sides with Text.Upper (or Text.Lower). Table.NestedJoin accepts an optional key-equality comparer argument (e.g. Comparer.OrdinalIgnoreCase) in recent versions, but explicit normalisation is clearer, visible in the data and works everywhere.

Punctuation and separators. Invoice and reference numbers appear as "INV/25-26/0042", "INV-25-26-0042", "INV 2526 42". Text.Select(t, {"0".."9", "A".."Z"}) keeps only letters and digits after upper-casing. Be careful: stripping separators can merge distinct numbers ("1-23" and "12-3" both become "123"); test for new collisions with a Group By count after normalisation.

Leading zeros. Cheque numbers ("000417"), SAP document numbers ("0090001234") and account numbers are padded differently by different systems. Text.TrimStart(t, "0") removes leading zeros. Alternatively pad both sides to a fixed width with Text.PadStart(t, 6, "0"). Never convert an account number to a number type to strip zeros: long account numbers exceed precision and lose digits.

Types. Both key columns must have the same type. For references, text is canonical (it preserves letters and length). For amounts, use a fixed-decimal number rounded to two places: Number.Round([Amount], 2) and type Currency.Type (fixed decimal), or convert to integer paise (Number.Round([Amount] * 100, 0)) to avoid floating-point mismatches such as 0.1 + 0.2 ≠ 0.3.

Dates. If a date is part of the key, convert datetime to date with Date.From on both sides; a book datetime of 01-04-2025 00:00 does not equal a date 01-04-2025.

Nulls and blanks. Convert empty strings to null and exclude null keys from exact matching: in M, null equals null, so blank references would match each other.

Building composite keys

Either merge on several normalised columns ({"RefN", "AmtP"}) or concatenate into one key text:

WithKey = Table.AddColumn(t, "Key", each
    if [RefN] = null then null else [RefN] & "|" & Text.From([AmtPaise]), type text)

A concatenated key is easy to inspect and to use in multiple merges; include a separator that cannot appear in the components to avoid "12|345" vs "123|45" collisions.

Checking the effect

Measure match rate before and after normalisation with an Inner join count. Then check uniqueness on each side (Table.Group(t, {"Key"}, {{"n", each Table.RowCount(_)}}) filtered to n > 1). A good normalisation raises match rate without creating new duplicate keys.

Worked illustration

Raw bank ref Raw book ref After normalisation Match?
417 (number) "000417" "417" / "417" Yes
"UTIB0001234 " "utib0001234" "UTIB0001234" both Yes
"INV/25-26/0042" "INV-25-26-42" "INV25260042" / "INV252642" No — padding inside the number differs

The third case shows the limit of generic normalisation; a domain-specific parser (extract the trailing invoice serial, Text.AfterDelimiter(t, "/", {0, RelativePosition.FromEnd}), strip zeros, recombine with the FY) is needed for invoice keys.

On amounts: a bank deposit of ₹1,25,000.00 and a book entry computed as ₹1,05,932.20 + ₹19,067.80 (taxable value plus GST, summed in floating point) can differ in the 10th decimal place. Rounding both to paise makes them match.

Edge cases & judgement calls

  • Over-normalisation. Removing all non-digits from a narration-derived UTR may merge distinct references; normalise only the extracted reference, not whole narrations.
  • Culture-sensitive upper-casing. Use plain Text.Upper for ASCII references; culture effects are rare in Indian finance data but matter for some names.
  • Mixed instrument types. A cheque "417" and an internal transfer reference "417" in the same account can collide; include an instrument type in the key if both exist.
  • Normalise once, reuse. Put the logic in a function (fxNormRef) used by every recon, so improvements apply everywhere.
  • Keep raw values. Keep the original columns alongside normalised keys so exceptions are reported as the users know them.

Key takeaways

  • Merges compare exactly: type, case, whitespace and padding all matter, and mismatches fail silently.
  • Normalise both sides to one canonical form: trim and clean, replace char 160, upper-case, strip separators and leading zeros, align types.
  • Round amounts to paise (or use fixed decimal) before using them as keys.
  • Exclude null keys from exact matching because null equals null in M.
  • Measure match rate and key uniqueness before and after normalisation.

Practice Questions

Q1. Normalise these keys [L1]

Give the canonical form under the fxNormRef function in the notes for: (a) " 000958 "; (b) 958; (c) "hdfc n 5250 4011"; (d) "" (empty string); (e) null.

Q2. Write the amount key [L2]

Bank amounts arrive as text "1,25,000.00" (Indian grouping) and book amounts as decimal numbers with floating residues. Write M to create an integer-paise key AmtPaise on both sides and explain why the text must be converted with an explicit culture.

💡 Hint: Convert with Number.FromText(t, "en-IN"), multiply by 100, then round to 0 decimals.

Q3. Collision test [L2]

After stripping separators from invoice numbers, the purchase register shows 14 keys that occur more than once, whereas before normalisation there were 2. Explain what this indicates, how you would list the colliding raw values, and how you would redesign the key.

Q4. Silent zero matches [L2]

A merge on ChequeNo returns no matches. Bank ChequeNo shows the 123 icon; book ChequeNo shows ABC and values like "000123". Explain two different fixes, and the risk of converting the book column to a number.
