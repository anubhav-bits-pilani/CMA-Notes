Subtopic note

Append vs Merge: Union vs Join with SQL Analogies

Scope: Append (Table.Combine) vs Merge (Table.NestedJoin): union vs join, with SQL analogies

Why it matters

Append and Merge are the two ways to bring tables together, and confusing them is a classic beginner error with real financial consequences: appending a bank statement under a ledger double counts cash, while merging twelve monthly TBs on Ledger produces a wide, unusable table. Append stacks more rows of the same thing (months, branches, banks, scenarios). Merge matches rows of different things on a key (bank lines to book lines, invoices to a vendor master, ledgers to a Chart of Accounts mapping). Every reconciliation and every consolidation uses both, in a particular order.

Core notes

Append: Table.Combine

AllBanks = Table.Combine({HDFC, ICICI, SBI})

Append returns the rows of every input table, one after another. The UI (Home > Append Queries, or Append Queries as New) offers "Two tables" or "Three or more tables" and generates Table.Combine.

  • Columns align by name, not position. A column missing in one table is filled with null for that table's rows. Column order follows the first table, with new names appended at the end.
  • Duplicates are kept: it behaves like UNION ALL, not UNION. For distinct rows, follow with Table.Distinct.
  • Types: if the same column has different types across inputs, the result type is broadened (often to any); retype after appending.
  • Folding: appending two tables from the same SQL database can fold to UNION ALL; file sources never fold.

SQL analogy:

SELECT Date, Ref, Amount FROM hdfc
UNION ALL
SELECT Date, Ref, Amount FROM icici;

The key difference: SQL matches columns by position and requires equal column counts; M matches by name and tolerates different column sets.

Merge: Table.NestedJoin

Merged = Table.NestedJoin(Bank, {"Ref", "Amount"}, Book, {"Ref", "Amount"}, "Book", JoinKind.LeftOuter)

Merge (Home > Merge Queries) matches rows of the first (left) table to rows of the second (right) table where the key columns are equal, and adds one new column containing a nested table of the matching right rows for each left row. You then expand that column (choose which right-side columns to bring in) or aggregate it (count, sum).

  • Keys can be one or several columns; the UI selects them with Ctrl-click, and the order of selection pairs the columns.
  • Join kind is the sixth argument: JoinKind.LeftOuter (default in the UI), RightOuter, FullOuter, Inner, LeftAnti, RightAnti.
  • Equality is exact and type-sensitive: text "123" ≠ number 123; "ACME" ≠ "Acme"; null matches null.
  • Nested result: a left row with three matches gets a nested table of three rows; expanding produces three output rows.

Table.Join is the flat alternative: it returns the joined columns directly (no nested column), but fails if both tables have a column with the same name, so it suits joins where you control names. Table.NestedJoin is what the UI generates and what most recon queries use.

SQL analogy:

SELECT k.*, b.VchNo, b.Narration
FROM bank k
LEFT JOIN book b ON k.Ref = b.Ref AND k.Amount = b.Amount;

Choosing between them

Question Use
Are the inputs the same kind of record from different files, periods or entities? Append
Do I need attributes from another table for each row (lookup)? Merge, LeftOuter, expand
Do I need to know which rows have no counterpart? Merge, LeftAnti / RightAnti
Do I need Actual and Budget side by side for variance? Append with a Scenario column (long), then pivot or measure — or Merge on the dimension keys after grouping to the same grain

The last row matters for FP&A: appending Actual and Budget with a Scenario column produces a long fact table that a data model handles well; merging them requires both to be at exactly the same grain first.

Typical sequence in a reconciliation

  1. Append the monthly or multi-bank statement files into one Bank table (folder pipeline).
  2. Append book extracts for the same accounts into one Book table.
  3. Normalise keys and signs on both.
  4. Merge Bank to Book with anti-joins to produce exceptions; Inner to produce matched pairs.
  5. Append the exception lists (with a Side column: "Bank only" / "Book only") into one exceptions table loaded to a sheet.

Worked illustration

Bank (April) has 1,500 rows, Book has 1,460. Appending them gives 2,960 rows — meaningless for reconciliation, but exactly right if the goal is a combined "all cash movements" table with a Source column. Merging Bank to Book (Inner on Ref + Amount) gives 1,380 matched rows; LeftAnti gives 120 bank-only rows; RightAnti gives 80 book-only rows. Check: \(1{,}380 + 120 = 1{,}500\) bank rows and \(1{,}380 + 80 = 1{,}460\) book rows — the identity holds only if keys are unique on each side, which is the subject of the sequence-key subtopic.

Edge cases & judgement calls

  • Append with renamed columns. "Amount" in one table and "Amt" in another append as two separate half-null columns; standardise names first.
  • Merge direction. Left and right are not symmetric: LeftOuter keeps all left rows; choose the table whose completeness you care about as the left table.
  • Merging on calculated keys. Create the key as a column on both sides before merging; the merge dialog cannot use expressions.
  • Self-merge. Merging a table with itself (e.g. for duplicate-payment tests) is valid and common; use Reference queries to avoid recursion.
  • Performance. Merges on file sources are performed in memory; buffer the lookup table for repeated merges.

Key takeaways

  • Append = stack rows (Table.Combine, like UNION ALL but matched by column name).
  • Merge = match rows on keys (Table.NestedJoin, like JOIN), producing a nested table column to expand or aggregate.
  • Merge equality is exact and type-sensitive; null matches null in M.
  • Recons typically append within each side, then merge across sides, then append the exception lists.
  • For FP&A, append Actual and Budget with a Scenario column rather than merging them side by side.

Practice Questions

Q1. Append or merge? [L1]

For each task, state Append or Merge and the join kind if relevant: (a) combine Apr–Mar branch TBs; (b) add the Schedule III line item to each TB ledger from a mapping table; (c) list vendors in the payment file not present in the vendor master; (d) stack Actual and Budget fact tables for a variance model.

Q2. Predict the append [L2]

Table Actual has Date, Account, Dept, Amount (24,000 rows). Table Budget has Account, Dept, Date, Amount, Scenario (6,000 rows). Describe the result of Table.Combine({Actual, Budget}): columns, order, row count and nulls. Then write the steps to make the result a clean long fact table.

💡 Hint: Add the missing Scenario column to Actual before appending.

Q3. SQL to M [L2]

Translate into M: SELECT k.*, b.VchNo FROM bank k INNER JOIN book b ON k.Ref = b.Ref AND k.Amount = b.Amount; Name each step and explain why the M result needs an expand step that the SQL does not.

Q4. Reconciliation identity [L2]

After merging, Inner returns 2,410 rows, LeftAnti 165 rows and RightAnti 97 rows. The bank table has 2,560 rows and the book table 2,470. Explain what the mismatch between these counts tells you and how you would locate the cause.
