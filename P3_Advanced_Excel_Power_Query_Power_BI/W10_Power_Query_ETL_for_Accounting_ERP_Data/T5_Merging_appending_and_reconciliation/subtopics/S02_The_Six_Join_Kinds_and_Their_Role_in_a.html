The Six Join Kinds and Their Role in a Reconciliation

Scope: Join kinds LeftOuter, RightOuter, FullOuter, Inner, LeftAnti, RightAnti, and what each does in a recon

Why it matters

The join kind decides which rows survive a merge. In a reconciliation, each join kind answers a different control question: "what matched?", "what is in the bank but not in the books?", "show me everything side by side". Choosing the wrong one either hides exceptions (Inner drops them silently) or buries them among thousands of matched rows (LeftOuter without a filter). Interviewers often ask candidates to name the join that gives "unpresented cheques" — the expected answer is an anti-join, with the correct direction.

Core notes

Definitions

For Table.NestedJoin(Left, keys, Right, keys, "R", kind):

JoinKind Rows returned SQL equivalent
LeftOuter All left rows; nested R holds matches (empty table if none) LEFT JOIN
RightOuter All right rows; left columns null where no left match RIGHT JOIN
FullOuter All rows from both; nulls on the side without a match FULL OUTER JOIN (not in MySQL; emulate with UNION)
Inner Only rows with a match on both sides INNER JOIN
LeftAnti Left rows with no match; nested R is empty LEFT JOIN ... WHERE r.key IS NULL
RightAnti Right rows with no match RIGHT JOIN ... WHERE l.key IS NULL

The numeric enum values (Inner 0, LeftOuter 1, RightOuter 2, FullOuter 3, LeftAnti 4, RightAnti 5) sometimes appear in generated code.

How the nested result looks

Table.NestedJoin always returns the left table's columns plus the nested column. For kinds that return right-only rows (RightOuter, FullOuter, RightAnti), those rows have null in every left column and carry the right row inside the nested column. You must expand the nested column to see the right side's data. This catches people out with RightAnti: the result looks like a table of nulls until you expand. A clearer alternative for "right rows with no left match" is to swap the inputs and use LeftAnti.

What each does in a bank reconciliation

Take Bank as left and Book as right, keyed on normalised Ref + aligned Amount:

JoinKind Recon use Typical contents
Inner Matched pairs register Cleared cheques, NEFT/RTGS receipts and payments booked correctly
LeftOuter Bank statement annotated with book voucher numbers All bank lines; blanks are exceptions
LeftAnti Bank-only items (entries not in books) Bank charges, interest credited, NACH/ECS debits, direct customer credits, dishonoured cheques, GST on charges
RightAnti Book-only items (entries not in bank) Cheques issued not presented, deposits in transit, wrong postings in books
FullOuter One complete recon view All lines from both sides, with match status
RightOuter Book ledger annotated with bank dates Clearing-date analysis for issued cheques

A common deliverable is a single exceptions table:

BankOnly = Table.AddColumn(Table.NestedJoin(Bank, {"Key"}, Book, {"Key"}, "B", JoinKind.LeftAnti),
              "Side", each "In bank, not in books", type text),
BookOnly = Table.AddColumn(Table.NestedJoin(Book, {"Key"}, Bank, {"Key"}, "K", JoinKind.LeftAnti),
              "Side", each "In books, not in bank", type text),
Exceptions = Table.Combine({Table.RemoveColumns(BankOnly, {"B"}), Table.RemoveColumns(BookOnly, {"K"})})

Using LeftAnti in both directions (with inputs swapped) avoids the null-left-columns behaviour of RightAnti and gives each list its own columns.

Building the BRS from the outputs

Starting from balance per books:

\[ \text{Balance per bank} = \text{Balance per books} + \text{Unpresented cheques} - \text{Deposits in transit} + \text{Bank-only credits} - \text{Bank-only debits} \]

where unpresented cheques and deposits in transit come from the book-only list, and bank-only credits/debits from the bank-only list (before they are booked). After the month's adjusting entries are passed for bank-only items, only timing items should remain.

Worked illustration

April, HDFC current account. Balance per books ₹52,40,000. Book-only list: cheques issued not presented ₹6,80,000; deposit in transit ₹2,10,000. Bank-only list: bank charges ₹4,720 debit; interest ₹18,300 credit; NACH insurance debit ₹45,000; direct customer NEFT credit ₹3,25,000.

\[ 52{,}40{,}000 + 6{,}80{,}000 - 2{,}10{,}000 + (18{,}300 + 3{,}25{,}000) - (4{,}720 + 45{,}000) = 60{,}03{,}580 \]

If the bank statement closing balance is ₹60,03,580, the recon closes; any difference means a missed or mis-keyed item.

Edge cases & judgement calls

  • Inner hides exceptions. Never use Inner alone in a recon; always produce both anti-joins.
  • FullOuter for small data, anti-joins for review. FullOuter is a convenient single table but harder to review; reviewers prefer two short exception lists.
  • Null keys. M matches null to null; rows with blank Ref on both sides can pair arbitrarily. Exclude null-key rows from reference matching and route them to the amount + date tier.
  • Partial matches. A row matching on Ref but not Amount lands in both anti-joins; detect these by a second merge on Ref alone and classify as "amount difference".
  • Folding. On SQL sources, anti-joins can fold to LEFT JOIN ... IS NULL; on CSVs they run in memory.

Key takeaways

  • LeftOuter keeps all left rows; Inner keeps matches; FullOuter keeps everything; the anti-joins keep non-matches.
  • Table.NestedJoin returns left columns plus a nested column; right-only rows show nulls in left columns.
  • For bank-not-in-books and books-not-in-bank, LeftAnti in both directions with swapped inputs is clearest.
  • Map bank-only items to adjusting entries and book-only items to timing differences in the BRS.
  • Prove the BRS arithmetic closes using totals from the exception lists.

Practice Questions

Q1. Name the join [L1]

Which join kind (and which table on the left) returns: (a) cheques issued but not yet presented; (b) bank charges not yet booked; (c) all book entries with their bank clearing date where available; (d) only matched items for a cleared-items register?

Q2. Prove the BRS closes [L2]

Balance per books on 31-Mar-2026: ₹1,18,62,450 (debit). Book-only items: unpresented cheques ₹14,26,000; deposits in transit ₹9,80,500. Bank-only items: interest ₹42,600 credit; TDS on interest ₹4,260 debit; NACH loan EMI ₹2,85,000 debit; unidentified NEFT credit ₹1,60,000. Bank statement closing balance: ₹1,22,21,790 (credit). Determine whether the BRS closes and, if not, the unexplained difference.

💡 Hint: Use the identity in the notes and keep careful track of which side each item increases.

Q3. RightAnti puzzle [L2]

A colleague's RightAnti merge shows 64 rows where every visible column is null. Explain why, show the expand step that reveals the data, and rewrite the query using LeftAnti with swapped inputs.

Q4. Exceptions table design [L3]

Design a single exceptions table for a six-account bank reconciliation that a controller reviews monthly: columns, the Side and Category classification logic, how amount-only differences are flagged, and how prior-month unresolved items are carried forward.
