Fuzzy Merge for Vendor and Customer Names

Scope: Fuzzy merge for vendor/customer names: similarity threshold, ignore case, transformation table

Why it matters

Codes are the ideal join key, but many finance matches have only names: bank narrations show "ACME INDS PVT LT" while the customer master says "Acme Industries Private Limited"; GSTR-2B shows the supplier's legal name while the vendor master holds a trade name; a newly acquired subsidiary's vendor list must be mapped to the group master. Exact merges fail on every spelling, abbreviation and truncation. Fuzzy merge scores how similar two text values are and accepts pairs above a threshold, which turns weeks of manual mapping into a reviewable suggestion list. Used carelessly, it also creates confident-looking wrong matches — so threshold choice and review discipline matter.

Core notes

Where it lives

In the Merge dialog, tick Use fuzzy matching to perform the merge and expand Fuzzy matching options. The generated M is Table.FuzzyNestedJoin (or Table.FuzzyJoin for the flat version):

Matched = Table.FuzzyNestedJoin(BankParties, {"Party"}, CustMaster, {"Party"}, "M", JoinKind.LeftOuter,
    [Threshold = 0.85, IgnoreCase = true, IgnoreSpace = true, NumberOfMatches = 1,
     TransformationTable = Synonyms])

Fuzzy matching works only on text columns, does not fold to any source, and is computed in memory.

The options

Option UI label Effect Default
Threshold Similarity threshold Minimum similarity score (0.00–1.00) for a pair to match; 1.00 means exact 0.80
IgnoreCase Ignore case Compares without regard to case true
IgnoreSpace Match by combining text parts Ignores spaces, so "Tata Steel" matches "TataSteel" true
NumberOfMatches Maximum number of matches Caps the number of right rows returned per left row all
TransformationTable Transformation table A table with columns From and To; values are mapped before scoring none
Culture — Culture for comparisons —

Power Query's algorithm is based on Jaccard-type similarity over the text's characters/tokens. You do not need the formula; you need to know that short strings are unstable (a one-letter change moves the score a lot), common words ("PRIVATE", "LIMITED", "INDIA") inflate similarity between unrelated companies, and the score is symmetric.

The transformation table

A transformation table maps known variants to a canonical form before scoring:

From To
PVT PRIVATE
LTD LIMITED
INDS INDUSTRIES
CO COMPANY
M/S (blank)

It must have exactly the columns From and To. It is ideal for abbreviations and legal-form suffixes that would otherwise depress similarity between true matches. A complementary approach is to pre-clean names yourself: upper-case, remove punctuation, and strip legal-form words entirely ("PRIVATE", "LIMITED", "LLP", "PVT", "LTD") on both sides, so that similarity is driven by the distinctive part of the name.

Choosing the threshold

  • High (0.90–0.95): few false matches, many misses; suitable for auto-accepting.
  • Medium (0.80–0.85): a good suggestion list for human review.
  • Low (below 0.70): many false matches; useful only for exploratory mapping.

Calibrate on a labelled sample: take 200 known pairs, run the fuzzy merge at several thresholds, and count true and false matches. Choose the threshold and accept rule (e.g. auto-accept at 0.92+, review 0.80–0.92) from evidence, and document it.

Review workflow

  1. Run exact merge first on normalised names or, better, on codes (GSTIN, PAN, bank account) where available.
  2. Fuzzy-merge only the exact-merge leftovers (LeftAnti output), with NumberOfMatches = 1 for a suggestion, or 3 to show alternatives.
  3. Expand the suggested match and, where your version supports it, a similarity score column.
  4. Load the suggestions to a sheet for review; reviewers confirm or correct, and confirmed pairs go into a mapping table (BankName → CustomerCode).
  5. Next month, the mapping table is merged exactly first; fuzzy matching is only needed for new names.

This converts a fuzzy, non-deterministic step into a growing, deterministic mapping — which auditors prefer.

Worked illustration

Bank narration parties after extraction and customer master names:

Bank party Best master candidate Indicative score (no transform) With transform + suffix stripping
ACME INDS PVT LT Acme Industries Private Limited Low High
SHREE GANESH TRADERS Shree Ganesh Traders 1.00 with IgnoreCase 1.00
GANESH TRADING CO Shree Ganesh Traders Medium Medium — likely a different firm
RELIANCE RETAIL LTD Reliance Retail Limited High 1.00

The third row is the risk case: plausible, wrong. If the bank credit is ₹6,40,000 and it is auto-accepted against the wrong customer, the AR ledger and the ECL ageing are both misstated. A GSTIN or bank-account cross-check would have rejected it.

Edge cases & judgement calls

  • Do not fuzzy-match amounts or references. Fuzzy merge is for names and descriptions; references need exact matching after normalisation.
  • Common-word inflation. "INDIA PRIVATE LIMITED" dominates short names; strip such words before scoring.
  • Performance. Fuzzy merges compare many pairs; run them only on leftovers and on distinct names (group first, then fuzzy-merge the distinct list, then merge back exactly).
  • Determinism. Results can change when the master changes; persist confirmed pairs in a mapping table rather than re-deriving them each refresh.
  • Related parties and group companies. Similar names within a group (e.g. "XYZ Infra Ltd" and "XYZ Infra Projects Ltd") are exactly where fuzzy matching misleads; require a code match.

Key takeaways

  • Fuzzy merge (Table.FuzzyNestedJoin) scores text similarity and matches pairs above a threshold; it works only on text and never folds.
  • Key options: Threshold (default 0.80), IgnoreCase, IgnoreSpace, NumberOfMatches, TransformationTable (From/To).
  • Pre-clean names and use a transformation table for abbreviations and legal-form suffixes.
  • Calibrate the threshold on known pairs; auto-accept only at high scores and review the middle band.
  • Persist reviewed matches in a mapping table so next month's match is exact and auditable.

Q2. Build the vendor-mapping pipeline [L3]

An acquired subsidiary has 1,850 vendor names to map to the group vendor master of 12,400 names. Both have PAN for about 60% of records. Design the full Power Query approach — exact PAN match, normalisation, fuzzy match, review sheet, mapping table — and the controls that prevent wrong mappings from flowing into consolidated AP.

💡 Hint: Fuzzy-match only what the exact PAN match leaves behind, on distinct cleaned names.

Q3. Threshold calibration [L2]

On 300 labelled pairs, results were: at 0.95 — 180 true matches, 2 false; at 0.85 — 255 true, 14 false; at 0.75 — 281 true, 49 false. Recommend an accept/review policy and justify it with these figures, considering that a false match misposts customer receipts.
