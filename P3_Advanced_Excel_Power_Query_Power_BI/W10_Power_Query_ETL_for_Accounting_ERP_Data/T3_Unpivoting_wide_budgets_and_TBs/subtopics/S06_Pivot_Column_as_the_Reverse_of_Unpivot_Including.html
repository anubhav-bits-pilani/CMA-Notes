Subtopic note

Pivot Column as the Reverse of Unpivot, Including Don't Aggregate

Scope: Pivot Column as the reverse operation, including the "Don't Aggregate" option

Why it matters

Unpivot turns columns into rows; Pivot turns rows back into columns. Finance pipelines need both: unpivot to store and model, pivot to produce a wide output for a board pack, to rebuild a check table (Opening/Debit/Credit/Closing side by side for a roll-forward test), to spread a "Measure" column into proper columns after loading key-value data, or to compare scenarios side by side (Actual vs Budget columns for variance). The aggregation choice in the Pivot dialog decides whether duplicates are summed, counted or treated as an error — and "Don't Aggregate" is the setting most likely to produce surprising errors.

Core notes

The operation

Select the column whose values will become new column headers (the attribute, e.g. Month or Scenario), then Transform → Pivot Column, choose the Values Column (e.g. Amount) and, under Advanced options, the Aggregate Value Function: Sum, Count (All), Count (Not Blank), Minimum, Maximum, Median, Average, or Don't Aggregate.

M generated:

// With aggregation
Wide = Table.Pivot(Long, List.Distinct(Long[Scenario]), "Scenario", "Amount", List.Sum)

// Don't Aggregate
Wide = Table.Pivot(Long, List.Distinct(Long[Scenario]), "Scenario", "Amount")

Arguments: the table; the list of values that become columns (the UI hard-codes this list, e.g. {"Actual", "Budget"}; replace with List.Distinct(t[Col]) for refresh safety); the attribute column; the value column; an optional aggregation function.

All columns other than the attribute and value columns act as row keys — every distinct combination of them becomes one output row.

How each aggregation behaves

Aggregation Duplicate key rows (same row keys + same attribute) Typical use
Sum (List.Sum) Added Budget by month from line-level detail
Count (List.Count) Counted Number of vouchers per month per ledger
Min / Max Smallest/largest Earliest/latest date per party
Don't Aggregate Error in the cell: "Expression.Error: There were too many elements in the enumeration to complete the operation." Reshaping data that is unique per key (e.g. key-value pairs)

Don't Aggregate is for genuinely unique data — for example, rebuilding a record per ledger from Measure/Value pairs. If any key has two values, the cell errors (often noticed only at load, or in Excel as blank cells with an error count). That is a feature: it reveals duplicates you did not know about. Sum would silently add them.

Unpivot–pivot round trip

Unpivot followed by pivot with Sum returns the original wide table only if:

  • no duplicate row keys existed (otherwise values are summed),
  • nulls dropped by the unpivot are acceptable as nulls in the output,
  • the pivot's column list includes all attribute values in the right order,
  • extra columns added in between (Scenario, Date conversions) are accounted for as row keys.

This makes the round trip a useful losslessness test: unpivot, pivot back, compare totals per row.

Ordering the new columns

List.Distinct(t[Month]) gives columns in order of first appearance, which may not be chronological. Sort first, or supply an explicit sorted list:

Months = List.Sort(List.Distinct(t[Month])),          // dates sort chronologically
Text   = Table.TransformColumns(t, {{"Month", each Date.ToText(_, [Format="MMM-yy", Culture="en-IN"]), type text}}),
Wide   = Table.Pivot(Text, List.Transform(Months, each Date.ToText(_, [Format="MMM-yy", Culture="en-IN"])), "Month", "Amount", List.Sum)

Pivot column names must be text — convert dates to labels for the pivot.

Pivot vs reporting tools

For presentation, a PivotTable on the Data Model or a Power BI matrix does the same job without changing the stored shape. Use Table.Pivot in Power Query when the output itself must be a wide table (export to a template, a check query, an input to another system), or when the source arrives as key-value pairs that need spreading into columns.

Illustration: Actual vs Budget variance table

Long fact rows (Date, Account, Scenario, Amount): (30-Apr-25, 610100, Actual, 12,40,000), (30-Apr-25, 610100, Budget, 12,00,000), (30-Apr-25, 620300, Actual, 1,62,000), (30-Apr-25, 620300, Budget, 1,50,000). Pivot Scenario with Sum → columns Actual, Budget; add Variance = Actual − Budget: 610100 → 40,000; 620300 → 12,000. If the actuals came from line-level GL (several rows per account-month), Sum is required; Don't Aggregate would error.

Edge cases & judgement calls

  • Hard-coded column list: a new Scenario ("Forecast") or month is ignored by the UI-generated list; use List.Distinct but be aware that column names then vary, which can break downstream steps that reference them by name.
  • Null attribute values cause errors ("cannot convert null to Text" for the column name) — replace nulls with a label such as "(blank)" first.
  • Attribute values with characters like leading spaces create near-duplicate columns ("Budget" vs "Budget "); clean before pivoting.
  • Large pivots (thousands of distinct values) create unwieldy tables; pivot only low-cardinality attributes.
  • Pivot does not fold on most file sources; on SQL sources it can fold to PIVOT in some cases, but expect local evaluation.
  • Error cells from Don't Aggregate — investigate duplicates with Group By (Count Rows) on the row keys plus attribute.

Key takeaways

  • Table.Pivot is the inverse of unpivot: attribute values become columns, the value column fills them.
  • All other columns are row keys; duplicates on keys are aggregated by the chosen function.
  • "Don't Aggregate" errors on duplicates — use it to assert uniqueness, use Sum when detail rows must be added.
  • Replace the UI's hard-coded value list with a sorted dynamic list, converting dates to text labels.
  • Pivot in Power Query for wide outputs and checks; otherwise let PivotTables/matrices present wide.

Practice Questions

Q1. Choose the aggregation [L1]

For each, choose the aggregation and explain: (a) spreading Measure ∈ {Opening, Debit, Credit, Closing} into columns for a TB with one row per ledger per measure; (b) a monthly expense matrix from GL line items; (c) number of invoices per customer per month; (d) last payment date per vendor per quarter.

Q2. Diagnose the error [L2]

A Don't Aggregate pivot of Scenario on a budget fact shows errors in 23 cells: "There were too many elements in the enumeration to complete the operation." Explain what this means and how you would find the offending rows.

💡 Hint: Group on the row keys plus the attribute and count rows.

Q3. Chronological wide output [L2]

Write M that pivots a long budget (Date as month-end, Account, Department, Amount) into a wide table with months as columns in Apr → Mar order, labelled "Apr-25" style, summing duplicates, and adds an FY Total column.

Q4. Round-trip test [L2]

Design a check that unpivots a budget template, pivots it back and compares each row's month values and total with the original, and list three reasons the round trip might not reproduce the original exactly.

Q5. Variance table [L3]

Build the specification for a Power Query output that shows, per Account and Department, Actual, Budget, Variance and Variance % for a selected month (parameter), from a long fact containing both scenarios at month grain. Address missing budget or actual rows and division by zero.
