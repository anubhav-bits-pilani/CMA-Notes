Key concept

Table.UnpivotOtherColumns with Fixed Identifier Columns

Concept: Table.UnpivotOtherColumns(t, {"Account", "Department"}, "Month", "Amount")

Statement

Table.UnpivotOtherColumns(table as table, pivotColumns as list, attributeColumn as text, valueColumn as text) as table keeps the columns named in pivotColumns as identifiers and turns every other column into attribute–value pairs:

  • each original row produces one output row per non-identifier column whose value is not null;
  • attributeColumn ("Month") holds the former column header (text);
  • valueColumn ("Amount") holds the cell value.

If the input has \(r\) rows and \(k\) non-identifier columns, the output has at most \(r \times k\) rows.

Explanation

The function hard-codes only the identifiers, so it adapts automatically when value columns are added, removed or renamed — the property that makes it the default choice for monthly budgets and rolling forecasts. The UI commands "Unpivot Other Columns" and "Unpivot Columns" both generate it (s02).

Its weakness is the mirror image of its strength: any column that is not an identifier is unpivoted. FY Total, H1/H2 totals, "Remarks", "Prior Year", or a new identifier column ("Cost Centre") added to the template are all swept into Amount. Two defences:

  1. Remove known derived columns before the step with Table.RemoveColumns(t, {...}, MissingField.Ignore), so their absence in a future file does not error.
  2. Validate the Month column after the step: every value must parse as a month (s03); route the rest to an exceptions query and fail if any appear.

Other behaviours:

  • Identifier names must exist — if "Department" is renamed to "Dept" in the template, the step errors ("column not found"). Normalise headers first if templates vary.
  • Null values are dropped (c06); zeros and empty strings are kept.
  • The Amount column inherits types loosely — after unpivoting mixed-type columns it is any; type it explicitly with culture.
  • Column order of output: identifiers first, then attribute, then value.
  • On SQL Server sources, it can fold into an UNPIVOT clause; on Excel/CSV sources, it runs locally (no folding).

Illustration

Account Department Apr-25 May-25 FY Total
610100 Sales 12,00,000 null 12,00,000
620300 Sales 1,50,000 1,20,000 2,70,000

Direct Table.UnpivotOtherColumns(t, {"Account","Department"}, "Month", "Amount") gives 5 rows (the null May value for 610100 is dropped): 610100/Apr-25/12,00,000; 610100/FY Total/12,00,000; 620300/Apr-25/1,50,000; 620300/May-25/1,20,000; 620300/FY Total/2,70,000. Sum = ₹29,40,000, of which ₹14,70,000 is FY Total — exactly double the true budget. After removing FY Total first: 3 rows summing to ₹14,70,000, which agrees with the sum of the FY Total column (12,00,000 + 2,70,000) — the control check that proves the unpivot is complete and free of double counting.

Connections

Implements s02 (which unpivot survives new months) and s01 (wide to long). Followed by c02 (month text to dates) and c06 (nulls). The pitfalls on fixed month columns and on totals in the unpivot are about this function's selection logic. In Week 11 the output becomes the Budget fact.

Practice Questions

Q1. Row count [L1]

A budget has 260 rows, identifiers Account, Department and Cost Centre, 12 month columns and an FY Total. 74 month cells and 3 FY Total cells are null. How many rows does Table.UnpivotOtherColumns with the three identifiers return, and how many after removing FY Total first?

Q2. Template change [L2]

Next year the template adds a "Region" identifier column after Department and renames "Department" to "Dept". Describe what happens to the current query at refresh and write a version that tolerates both changes.

💡 Hint: Normalise header names first and validate the Month values after unpivoting.

Q3. Validation query [L2]

Write M that, after the unpivot, separates rows whose Month value parses as "MMM-yy" from those that do not, loads the latter as an exceptions table, and raises an error if any non-month attribute carries a non-zero amount.
