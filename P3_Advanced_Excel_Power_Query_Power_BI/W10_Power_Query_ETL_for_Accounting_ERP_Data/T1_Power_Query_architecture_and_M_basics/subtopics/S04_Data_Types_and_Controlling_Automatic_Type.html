Data Types and Controlling Automatic Type Detection

Scope: Data types and type detection, including turning off automatic type detection on import

Why it matters

Types decide whether a ₹1,23,456.00 balance is summable, whether 03-04-2026 is 3 April or 4 March, whether account code 00400100 keeps its leading zeros, and whether a merge between the bank file and the ledger finds any matches at all. Power Query's automatic type detection is convenient on a one-off import, but in a recurring pipeline it is a liability: it inserts a Changed Type step that hard-codes every column name from the sample file and guesses types from the first 200 rows. The professional pattern is to turn auto-detection off, then type deliberately, once, at a known point, with an explicit locale.

Core notes

Two kinds of typing exist in M. Conversion (Table.TransformColumnTypes) changes values — "125000" becomes 125000 — and produces cell errors where conversion fails. Ascription (the type argument of Table.AddColumn, or Value.ReplaceType) only labels a column without converting; if the values do not conform, errors surface later in the model. Use conversion on imported columns and ascription on columns you compute.

Why codes must be text

Account codes, cost-centre codes, PAN, GSTIN, IFSC, UTR and cheque numbers are identifiers, not quantities. Typed as numbers they lose leading zeros (000123 → 123), long UTRs can lose precision beyond 15 significant digits, and a merge with a text-typed key on the other side returns zero matches without any error. Rule: anything you would never add up is text.

Automatic type detection

On import of CSV/Excel, Power Query adds Promoted Headers and Changed Type steps:

#"Changed Type" = Table.TransformColumnTypes(#"Promoted Headers",
    {{"Date", type date}, {"Narration", type text}, {"Chq./Ref.No.", Int64.Type},
     {"Withdrawal Amt.", type number}, {"Deposit Amt.", type number}})

Problems in a recurring pipeline:

  1. Hard-coded column names: if next month's file names the column Withdrawal Amount, refresh fails with Expression.Error: The column 'Withdrawal Amt.' of the table wasn't found.
  2. Sample-based guesses: types are inferred from the top 200 rows; a cheque number column that is numeric for 200 rows becomes Int64.Type and errors on "NEFT-HDFCR520..." later.
  3. Locale of the machine: the conversion uses the current machine/file locale. On a laptop set to en-US, "03/04/2026" becomes 4 March; on en-IN, 3 April.
  4. Typing before cleaning: report headers and subtotal rows still present make columns any or produce errors.

Turning it off

  • Excel: Data → Get Data → Query Options → Current Workbook → Data Load → Type Detection: "Never detect column types and headers for unstructured sources". There is also a Global setting for new workbooks.
  • Power BI Desktop: File → Options and settings → Options → Current File → Data Load → Type detection → uncheck "Detect column types and headers for unstructured sources" (Global offers three choices: always, per-file setting, never).

After turning it off, imports land with Column1, Column2 … as any; you skip report headers, promote headers and type explicitly. Alternatively, simply delete the auto Changed Type step and add your own at the end of cleaning.

Typing deliberately with locale

Type once, after cleaning and before output, with the locale stated:

Typed = Table.TransformColumnTypes(Cleaned,
    {{"Voucher Date", type date}, {"Debit", Currency.Type}, {"Credit", Currency.Type},
     {"Ledger Code", type text}}, "en-IN")

The third argument (culture) controls parsing of dates and number formats. "en-IN" reads dd-mm-yyyy dates and Indian digit grouping. For a mix of sources, type each source with its own culture in its own staging query. To avoid hard-coding the column list for typing, build it dynamically:

AmountCols = List.Select(Table.ColumnNames(t), each Text.EndsWith(_, "Amt")),
Typed = Table.TransformColumnTypes(t, List.Transform(AmountCols, each {_, Currency.Type}), "en-IN")

Decimal vs fixed decimal

type number is a 64-bit float: summing a million amounts with paise can leave residues like 0.0000000003, so a Dr = Cr check written as = fails. Either use Currency.Type (fixed to four decimals) for amounts, or test with a tolerance: Number.Abs(Dr - Cr) < 0.01.

Illustration

A Tally Day Book export: Date "01-04-2025", Voucher No "00045", Amount "1,23,456.00 Dr". With auto-detection on an en-US machine: Date becomes 4 January 2025 (wrong), Voucher No becomes 45 (leading zeros lost), Amount stays text. Correct sequence: keep as text → split Dr/Cr suffix → clean digits → TransformColumnTypes with "en-IN" → Date 1 April 2025, Voucher "00045" (text), Amount 123456.

Edge cases & judgement calls

  • Error vs null: a failed conversion produces an error cell, not null. Count errors in a check query before removing them; silent Remove Errors hides data loss.
  • Excel serial dates in a column with mixed text dates: numbers like 45748 need Date.From(Number) while text needs locale parsing — handle with try.
  • Type of a merged/expanded column often reverts to any; re-type after expanding.
  • Data Model vs Excel table: Excel worksheet loads ignore some type nuances (a Currency column formats as number), but the Data Model and Power BI rely on types for aggregation and relationships.
  • Locale setting in options (File → Options → Regional Settings) affects all untyped conversions; explicit culture arguments make the query machine-independent.

Key takeaways

  • Turn off automatic type detection for recurring pipelines and type explicitly, once, after cleaning.
  • Identifiers (account codes, GSTIN, UTR, cheque no.) are text; amounts are Currency or number.
  • Always pass a culture ("en-IN") to type conversions of dates and formatted numbers.
  • Conversion changes values and can create errors; ascription only labels — use each where appropriate.
  • Floating-point residues make exact Dr = Cr tests fail; use fixed decimal or a tolerance.

Practice Questions

Q1. Choose the type [L1]

State the correct M type for each column of an ICICI bank CSV: Transaction Date, Value Date, Cheque Number, UTR/Reference, Description, Withdrawal (₹), Deposit (₹), Balance (₹), Branch Code ("0045"), and a computed IsMatched flag.

Q2. Diagnose a refresh failure [L2]

April's query worked. In May refresh fails with Expression.Error: The column 'Withdrawal Amt.' of the table wasn't found. and, separately, the Cheque No column shows 37 errors. Explain the root cause of each and the permanent fix, including the settings you would change.

💡 Hint: Look at what the auto-generated step captured from the April sample.

Q3. Locale test [L2]

A CSV contains the dates 05-04-2025, 13-04-2025 and 31-03-2026 as text. Describe what Table.TransformColumnTypes without a culture produces on (a) an en-US machine and (b) an en-IN machine, and write the step that gives the correct result regardless of machine.

Q4. Control total tolerance [L2]

Your TB has 18,450 lines with Debit and Credit typed as type number. List.Sum([Debit]) = List.Sum([Credit]) returns false although the Tally TB is balanced at ₹482,36,19,045.60. Explain why and write two alternative ways to make the check reliable.

Q5. Design a typing policy [L3]

Draft a one-page typing policy for a finance team's Power Query files covering: auto-detection settings, where in the pipeline typing happens, culture, identifier columns, amount precision, computed column ascription and how type errors are logged.
