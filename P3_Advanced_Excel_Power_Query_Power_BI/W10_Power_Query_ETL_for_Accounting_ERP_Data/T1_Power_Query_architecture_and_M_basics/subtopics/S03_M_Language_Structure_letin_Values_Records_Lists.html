Subtopic note

M Language Structure: let/in, Values, Records, Lists and each

Scope: M structure: let ... in, step references, records, lists, tables, each and _

Why it matters

The UI generates M for you, but every robust finance pipeline eventually needs hand-written M: a dynamic column list for unpivoting, a custom function per bank, a guard against a missing column, a parameterised as-of date. Reading M fluently also lets you review someone else's query in minutes rather than clicking through 40 steps. Coming from Java and SQL, the shift is that M is a functional, lazily evaluated expression language: there are no loops or mutable variables, every step is an immutable value, and the engine evaluates only what the final result needs.

Core notes

The let ... in expression

A query is a single expression. let binds names to expressions; in returns one of them (normally the last).

let
    Source        = Excel.Workbook(File.Contents(FilePath), null, true),
    TB            = Source{[Item="TB", Kind="Sheet"]}[Data],
    Promoted      = Table.PromoteHeaders(TB, [PromoteAllScalars=true]),
    NonBlank      = Table.SelectRows(Promoted, each [Particulars] <> null),
    Result        = NonBlank
in
    Result

Rules worth internalising:

  • Steps are separated by commas; the last step before in has no comma — the most common syntax error.
  • Names are case-sensitive (Source ≠ source), as are function names (Table.SelectRows, not table.selectrows).
  • Names with spaces need #"Changed Type" quoting.
  • Order in the text does not dictate evaluation; dependencies do. A step that nothing downstream references is never evaluated (lazy evaluation), which is why a broken unused step does not fail the refresh.
  • let expressions nest — a step can itself be a let ... in block, which is how you keep helper values local.

Step references

Each step usually references the previous one, but it may reference any earlier step or another query by name. Example: keep the raw source for a control total while cleaning:

RowCountRaw = Table.RowCount(TB),
...
Check = [Raw = RowCountRaw, Clean = Table.RowCount(Result)]

Referencing another query (stg_Bank) creates a dependency visible in Query Dependencies.

Primitive values and operators

Numbers, text ("Sales"), logical (true/false), null, dates #date(2026,3,31), datetimes #datetime(2026,3,31,23,59,0), durations #duration(30,0,0,0). Text concatenation uses &, not +: "FY" & Text.From(2026). Arithmetic with null returns null (null + 5 = null), which is why net-amount calculations use ?? (Topic 6). Comparisons are type-strict: "100" = 100 is false, not an error.

Records

A record is a set of named fields: [Code = "400100", Name = "Sales Domestic", Amount = 125000]. Access a field with Rec[Code]; optional access Rec[Code]? returns null instead of an error when the field is missing. Every row of a table, seen inside a row function, is a record — this is why [Amount] works inside each. Option arguments to library functions are also records: [Delimiter=",", Encoding=65001].

Lists

A list is an ordered sequence in braces: {"Apr-25", "May-25"}, {1..12}, {"0".."9"}. Access an item with zero-based {}: MyList{0}. A column of a table is a list: Table[Amount] returns the list of amounts, so List.Sum(TB[Debit]) is a Dr control total. Common list functions: List.Sum, List.Count, List.Distinct, List.Contains, List.Select, List.Transform, List.RemoveItems.

Dynamic column lists are built from lists — the heart of refresh-safe M:

MonthCols = List.RemoveItems(Table.ColumnNames(t), {"Account", "Department", "FY Total"})

Tables

A table is a list of records with a shared set of column names (and optional types). Ways to address it:

Expression Returns
t{0} First row as a record
t[Amount] Column as a list
t{0}[Amount] One cell
t{[Code="400100"]} The single row matching a key (error if 0 or >1 match)
Table.ColumnNames(t) List of column names

The navigation pattern Source{[Item="TB",Kind="Sheet"]}[Data] is exactly this: find the row of the navigation table whose Item and Kind match, then take its Data cell, which is itself a table. Nested tables in cells (after a Group By with All Rows, or a merge) are normal in M and are expanded later.

Functions, each and _

A function is written (x) => expression, e.g. (amt as number) as number => amt * -1. each is syntactic sugar for a one-parameter function whose parameter is named _:

\[ \texttt{each } [\text{Amount}] > 0 \;\equiv\; (\_) \Rightarrow \_[\text{Amount}] > 0 \]

Inside each, [Amount] is shorthand for _[Amount] because field access on the implicit _ can drop the underscore. Where the function receives a non-record (e.g. a single cell value in Table.TransformColumns), use _ directly: each Text.Trim(_).

Contexts and what _ is:

Function _ is
Table.SelectRows(t, each ...) the current row (record)
Table.AddColumn(t, "X", each ...) the current row (record)
Table.TransformColumns(t, {{"Name", each ...}}) the cell value
List.Transform(list, each ...) the list item
Table.Group(t, keys, {{"Total", each ...}}) the sub-table of the group

The last row is a classic trap: inside Group By, each List.Sum([Amount]) works because [Amount] on a table returns the column as a list.

Comments and error values

// and /* */ are comments. error "message" raises an error; try x otherwise y catches it (Topic 2).

Edge cases & judgement calls

  • each nested inside each makes the inner _ shadow the outer one. Write an explicit lambda for the outer function: (row) => List.Select(..., each _ > row[Limit]).
  • Key lookup t{[Code="X"]} errors if the key is duplicated — useful as an integrity check but dangerous in production. Use Table.SelectRows then {0}? when duplicates are tolerable.
  • Lazy evaluation and side effects: an unreferenced validation step never runs. Make checks a separate loaded query, or reference them in the output.
  • Performance of repeated references: referencing the same expensive step twice can evaluate it twice unless buffered (Topic s05/c06).
  • = is comparison, not assignment outside let; there is no ==.

Key takeaways

  • A query is one let ... in expression of immutable, lazily evaluated steps; commas separate steps, none before in.
  • Records [ ], lists { } and tables are the three structured values; a table row is a record and a column is a list.
  • each means (_) =>; [Col] inside it reads a field of _.
  • What _ represents depends on the calling function — row, cell, list item or group sub-table.
  • Dynamic lists from Table.ColumnNames and List.RemoveItems are the basis of refresh-safe code.
  • Use ? optional access and try ... otherwise to make code tolerant of missing fields.

Practice Questions

Q1. Fix the syntax [L1]

Identify every syntax error in this query and rewrite it correctly: let Source = Csv.Document(File.Contents(Path), [Delimiter=","]) Promoted = table.PromoteHeaders(Source), Filtered = Table.SelectRows(Promoted, each [Amount] <> null), in Filtered

Q2. What does it return? [L2]

Given a table TB with columns Code, Name, Debit, Credit and 3 rows: (400100, Sales, null, 500000), (500100, Purchases, 300000, null), (600100, Rent, 60000, null), state the value and type returned by each: (a) TB{1}; (b) TB[Debit]; (c) List.Sum(TB[Debit]); (d) TB{[Code=600100]}[Name]; (e) TB{0}[Debit] + 10.

💡 Hint: Remember how null behaves in arithmetic and in List.Sum.

Q3. Dynamic month list [L2]

A budget table has columns Account, Department, Apr-25 … Mar-26 and FY Total. Write a step that produces the list of month column names without hard-coding any month, and a second step that sums the April column only if it exists.

Q4. _ in different contexts [L2]

Write the M for (a) a filter keeping rows where Debit exceeds ₹1 lakh; (b) a transformation that upper-cases the Narration column; (c) a Group By on Ledger summing Amount. For each, state what _ refers to.

Q5. Interview: M vs Java [L3]

An interviewer with a Java background asks you to explain how a Power Query step list differs from a sequence of Java statements, covering mutability, evaluation order, loops and lambdas. Prepare a 2-minute answer with one finance example.
