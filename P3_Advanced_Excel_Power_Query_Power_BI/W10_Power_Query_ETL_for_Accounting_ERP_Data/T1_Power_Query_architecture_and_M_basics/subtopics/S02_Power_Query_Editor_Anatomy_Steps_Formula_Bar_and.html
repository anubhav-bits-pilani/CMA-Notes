Power Query Editor Anatomy: Steps, Formula Bar and Dependencies

Scope: Editor anatomy: Applied Steps, formula bar, Advanced Editor, Query Dependencies view

Why it matters

Power Query is often taught as a click-through tool, but a finance pipeline that runs every month for years must be auditable — a reviewer (or you, six months later) must be able to see exactly what was done to the Tally export, in what order, and what each output depends on. The editor gives you four lenses for that: the Applied Steps pane (the recipe), the formula bar (one step's M), the Advanced Editor (the whole query as code) and the Query Dependencies view (the lineage between queries and sources). Treat them the way an auditor treats a working paper file: steps are tick-marks, dependencies are cross-references.

Core notes

Layout of the editor

Area What it shows What you do there
Queries pane (left) All queries, grouped into folders; italics = connection only / load disabled Organise into groups such as 01 Parameters, 02 Staging, 03 Clean, 04 Output, 99 Checks
Data preview (centre) Result of the selected step, first 1,000 rows by default Inspect results, use column profiling
Query Settings (right) Query name, Properties, Applied Steps Rename, reorder, delete, insert steps
Formula bar M expression of the selected step Edit options directly (e.g. add a locale)
Ribbon Transformations that append a new step Home, Transform, Add Column, View

Turn on View → Formula Bar (hidden by default in Excel), and Column quality / Column distribution / Column profile for quick checks.

Applied Steps

Each step is a named variable in the query's let expression and takes the previous step as its input (usually — any step may reference any earlier step). Key behaviours:

  • Selecting a step shows the data as at that step; adding a transformation while an earlier step is selected inserts a step after it, with a warning that later steps may break.
  • The gear icon next to a step reopens its dialog (e.g. Split Column settings). Steps typed by hand have no gear.
  • Rename steps meaningfully (RemovedSubtotalRows, TypedAmounts), and use Properties → Description for a narrative note; descriptions show as tooltips, and as /// comments in M. Do this before handing the file over.
  • Delete Until End removes a step and everything after it — useful when rebuilding from a known-good point.
  • A yellow-triangle/warning icon on a step signals an error at that step; the preview shows the error message and, for row-level errors, an "errors" link.
  • Steps shown with a database icon/“View Native Query” enabled indicate folding (Topic s05).

Formula bar

The formula bar shows the M for the selected step, e.g.

= Table.SelectRows(#"Promoted Headers", each [Ledger] <> null and [Ledger] <> "Grand Total")

Note the #"..." syntax: identifiers with spaces or special characters (all UI-generated step names such as #"Changed Type") must be quoted this way. Editing here is the fastest way to add things the dialog does not expose: a culture argument to Table.TransformColumnTypes, MissingField.Ignore to a Table.RemoveColumns, or replacing a hard-coded list with a dynamic one.

Advanced Editor

Home → Advanced Editor shows the full let ... in expression. Use it to:

  • Read the whole pipeline in sequence and spot hard-coded values (paths, dates, column lists).
  • Paste a function or a reusable block from another file.
  • Add comments (// single line, /* ... */ block).
  • Convert a query into a function by adding (param as type) => before let.
  • Use Display Options (line numbers, word wrap) for review; the syntax checker at the bottom reports "No syntax errors have been detected" or the first error with a line position.

The Advanced Editor is not a debugger — it does not evaluate. Any typo surfaces as an Expression.SyntaxError when you click Done.

Query Dependencies view

View → Query Dependencies draws a diagram from data sources (files, folders, servers) through staging queries to outputs, showing each query's load destination. Use it to:

  • Confirm the layered pipeline: parameters → source/staging (connection only) → cleaned tables → outputs and checks.
  • Trace the impact of renaming a column in a staging query — every arrow out of it is a query that might break.
  • Spot duplicate source hits: two queries each reading the same 50 MB folder independently instead of referencing one staging query.
  • Spot sources that will need gateway credentials or privacy levels.

Illustration: a reviewable step list

# Step name M function Purpose
1 Source Excel.Workbook Read Tally TB export
2 TBSheet navigation {[Item="TB",Kind="Sheet"]}[Data] Pick sheet
3 SkippedReportHeader Table.Skip(..., each [Column1] <> "Particulars") Drop company name/period rows
4 PromotedHeaders Table.PromoteHeaders Use "Particulars", "Debit", "Credit" as headers
5 RemovedTotals Table.SelectRows Drop "Grand Total" and blanks
6 TypedColumns Table.TransformColumnTypes(..., "en-IN") Type amounts and dates with Indian locale

A reviewer reading only the step names understands the pipeline; that is the standard to aim for.

Edge cases & judgement calls

  • Inserting a step mid-query can break later steps that reference a column you just renamed or removed. Power Query warns once; it does not re-validate later steps until refresh.
  • Renaming a step in the Applied Steps pane updates references in that query automatically; renaming a query updates references in other queries in the same file, but not external references (another workbook or a DAX measure).
  • Preview vs refresh: the preview uses cached data and the top 1,000 rows. A step can look correct in the preview and fail at full refresh (e.g. a type error on row 40,000). Use Column profiling "based on entire data set" or a Keep Errors check query.
  • Excel vs Power BI editor: identical engine, slightly different ribbons. Excel's Query Dependencies diagram is less detailed and the formula bar is off by default.
  • Merged steps: Power Query sometimes merges consecutive identical operations (two Removed Columns steps) into one; do not be surprised when your step list compresses.

Key takeaways

  • Applied Steps are named variables of a let expression; name and describe them for auditability.
  • The formula bar edits one step and exposes options the dialogs hide (locales, MissingField, dynamic lists).
  • The Advanced Editor is the place to read, comment, parameterise and convert queries into functions.
  • Query Dependencies is your lineage map: use it before any rename and to enforce the staging → clean → output layering.
  • The preview shows only cached top rows; validate on the full data before trusting a step.

Practice Questions

Q1. Editor navigation [L1]

Describe where in the Power Query Editor you would (a) see the M for only the "Promoted Headers" step, (b) add a comment explaining why five rows are skipped, (c) find out which output queries depend on stg_BankHDFC, and (d) see that a step has generated row-level errors.

Q2. Rename impact [L2]

You rename the column Amt to Amount in the staging query stg_TB, which is referenced by TB_Clean, TB_Checks and BudgetVsActual. Explain what happens at the next refresh in each dependent query, how the Query Dependencies view helps you, and the safest sequence of edits.

💡 Hint: Renaming a column is different from renaming a step or query — only the latter are auto-updated.

Q3. Review a step list [L2]

A colleague's query has steps: Source, Navigation, Changed Type, Removed Top Rows, Promoted Headers, Changed Type1, Removed Bottom Rows, Filtered Rows, Changed Type2. Write a review note listing the risks you see from the names and order alone, and propose a renamed and reordered step list.

Q4. Turning a query into a function in the Advanced Editor [L3]

A query CleanHDFC begins let Source = Csv.Document(File.Contents("D:\Bank\HDFC_Apr.csv"), [Delimiter=","]), .... Describe the exact edits in the Advanced Editor to convert it into a function fxCleanHDFC that accepts a binary, and explain how its display in the Queries pane and Applied Steps changes after conversion.
