Roadmap topic: Power Query Architecture & M Basics: Connecting to CSV, Excel workbooks, folders, and SQL databases; understanding query folding and applied steps

Overview

Power Query is the ETL (extract, transform, load) engine shared by Excel, Power BI Desktop, Power BI Dataflows and Fabric Dataflows Gen2. Under every button sits M, a functional, lazily evaluated language in which a query is a single let ... in expression of named, immutable steps. For a finance professional this means the month-end chores you currently do by hand in Excel — deleting Tally report headers, retyping dates, pasting six bank files one below another, VLOOKUP-ing ledgers against bank lines — can be written once as a recipe and replayed on every refresh. The recipe is visible (Applied Steps), reviewable (Advanced Editor) and traceable (Query Dependencies), which suits an audit-trained mindset.

The architecture matters as much as the syntax. Connectors decide what work can be pushed to the source: database connectors (SQL Server, MySQL) support query folding, where your steps are translated into SQL and run on the server, whereas files (CSV, Excel, Folder, SharePoint) never fold. Types decide whether amounts sum and keys match; automatic type detection is a convenience that becomes a liability in recurring pipelines. Parameters and staging queries separate environment-specific values and source-specific cleaning from business logic. Load options decide where results land and how refresh behaves in Excel versus the Power BI Service. Privacy levels govern whether sources may be combined at all, and are behind the infamous Formula.Firewall errors.

Learning sequence: start with connectors (s01) and the editor (s02) to get data in and see the steps; learn M structure (s03) so you can read what the UI writes; then control types (s04) before anything else goes wrong; understand folding (s05) for database sources; design pipelines with parameters and staging (s06); choose load destinations and understand refresh (s07); and finally learn to fix firewall errors (s08) because every reconciliation combines sources. The concept notes give you the exact M patterns you will reuse for the rest of the phase: reading CSV and Excel robustly (c01, c02), SQL with and without native queries (c03, c04), each and _ (c05), the folding breakers (c06) and MySQL/Tally ODBC connectivity (c07).

For FP&A and reporting roles in India this topic is the foundation of the Week 10 exercise (bank reconciliation and multi-branch GL consolidation), the Week 11 data model and the Week 12 refresh/gateway setup. Interviewers for FP&A analyst and finance automation roles regularly ask "What is query folding?", "Reference vs Duplicate?" and "How would you make this refresh on someone else's machine?" — all answered here.

Related concepts to study

SQL equivalents from MySQL

SQL equivalents (WHERE, GROUP BY, JOIN, UNION) from your MySQL background

Your MySQL experience transfers almost one-to-one. WHERE is Table.SelectRows (Filter Rows); SELECT col1, col2 is Table.SelectColumns (Choose Columns); GROUP BY ... SUM() is Table.Group; JOIN is Table.NestedJoin + Table.ExpandTableColumn (Merge Queries) with join kinds matching LEFT, RIGHT, FULL, INNER plus the anti-joins SQL writes as LEFT JOIN ... WHERE b.key IS NULL; UNION ALL is Table.Combine (Append). Against a database these steps fold into exactly that SQL, so you can read View Native Query output like your own queries. Differences: Power Query keeps nested tables in cells after a merge, column names are case-sensitive, and Table.Distinct replaces UNION (without ALL) de-duplication.

Excel vs Power BI vs Dataflows Gen2

Power Query in Excel vs Power BI Desktop vs Dataflows Gen2 (Fabric)

The M engine is the same; the hosts differ. Excel Power Query loads to sheets or the Excel Data Model, refreshes on the desktop with per-user credentials and has no scheduling. Power BI Desktop loads to a VertiPaq model, adds folding indicators, query plans and Diagnostics, and publishes to the Service for scheduled refresh via gateways. Dataflows Gen2 in Microsoft Fabric run Power Query Online in the cloud, write outputs to destinations such as a Lakehouse or Warehouse, and let several reports share one cleaned staging layer — useful when five FP&A reports all need the same cleaned GL. Some connectors and functions differ by host (e.g. Excel.CurrentWorkbook exists only in Excel), so portable code avoids host-specific functions.

Week 11: loading into the Data Model

→ Week 11: loading clean tables into the Data Model / Power Pivot

Power Query output is the input to Week 11's star schema. Cleaned fact tables (GL lines, budget, bank) and dimensions (CoA, cost centre, calendar) load to the Data Model / Power Pivot, where relationships and DAX measures are defined. Decisions made now carry forward: correct types (dates as date, keys as text matching on both sides), long rather than wide facts, one row per grain, and staging queries left as connection only so that the model holds only what reports use. A poorly typed Power Query output becomes a broken relationship or a text column that cannot be summed in the model.

Week 12: gateway and scheduled refresh

→ Week 12: refresh through the on-premises data gateway and scheduled refresh

When the pipeline moves to the Power BI Service, every source must be reachable from the cloud. Cloud sources (SharePoint Online, OneDrive, Azure SQL) refresh directly. On-premises sources — a D:\Finance folder, an on-prem SQL Server, Tally ODBC on a branch PC — need an on-premises data gateway installed on a machine that can see them, with matching data source definitions, credentials and privacy levels. Parameters (s06) let you switch paths and servers between Desktop and Service, and folding (s05) is required for incremental refresh. Designs that ignore this in Week 10 have to be rebuilt in Week 12.

Java streams parallels

Functional parallels to Java streams/lambdas: List.Transform, List.Accumulate, List.Generate

M is functional, much like Java streams. List.Transform(list, each _ * 1.18) is list.stream().map(x -> x * 1.18); List.Select is filter; List.Sum is mapToDouble(...).sum(). List.Accumulate(list, seed, (state, current) => ...) is reduce — useful for applying a list of find-replace pairs to narrations or building a running balance. List.Generate(initial, condition, next, optional selector) resembles a for loop or Stream.iterate with a predicate — used for paging through an API or generating month-end dates from a start date until an end date. As with streams, there is no mutation: each call returns a new value, and evaluation is lazy.

Common pitfalls

Hard-coded absolute paths

Hard-coded absolute paths (C:\Users\...) break on another machine; use a parameter or a named cell

The UI writes the full path of the file you browsed to, such as C:\Users\ankit\Downloads\TB_Mar26.xlsx. It works for the author and fails for everyone else with DataSource.NotFound, and fails in the Power BI Service. People make the mistake because the first build is always a one-off test. Correct treatment: a typed text parameter (pFolderPath) or, in Excel, a named cell on a Control sheet, referenced by every source step; ideally a SharePoint/OneDrive location for team use. Detection in review: open the Advanced Editor of every source query and search for C:\, D:\ or Users\; Data source settings also lists every distinct path the file uses.

Auto Changed Type hard-codes column names

The auto "Changed Type" step hard-codes column names that may be missing in next month's file

Automatic type detection inserts Table.TransformColumnTypes listing every column from the sample file. Next month a bank renames "Withdrawal Amt." to "Withdrawal Amount", or a Tally export drops an empty column, and refresh fails with "The column ... wasn't found". It happens because the step is invisible until it fails. Correct treatment: turn off type detection for unstructured sources, delete the auto step, and type once after cleaning — with a dynamic column list where layouts vary and an explicit "en-IN" culture. Review check: any step named Changed Type immediately after Source or Promoted Headers is a red flag.

Renaming without tracing references

Renaming columns or steps without tracing downstream references leads to Expression.Error at refresh

Renaming a query or a step is propagated automatically within the file, but renaming a column in a staging query is not: every downstream step that refers to [Amt] breaks once it becomes [Amount], and DAX measures or Excel formulas pointing to the old name break too. People rename to tidy up, without checking dependants. Correct treatment: check Query Dependencies first, rename at the end of staging using a single explicit rename step, update dependants in the same session, and refresh all outputs before saving. Review check: refresh everything after any rename; search the M of dependent queries for the old name.

Assuming every source folds

Assuming every source folds, when CSV and Excel files never do

Users learn that "filter early" makes things fast and assume the same holds for a 400 MB CSV of SAP line items, or design incremental refresh on a folder of Excel files. File sources have no query engine; Power Query must read every byte, and View Native Query is always greyed out. Correct treatment: for large file-based data, reduce columns and rows as early as possible to cut memory, consider moving the data into a database or Dataflow/Lakehouse, and reserve folding-dependent designs (incremental refresh, DirectQuery) for database sources. Review check: list each query's source type; any performance or incremental-refresh claim on a file source should be challenged.

Practice Questions

Q1. Design a source layer for a multi-entity close [L3]

ABC Ltd (NSE-listed, FY ending 31 March) has: (i) three Tally companies whose TBs are exported monthly to .xlsx with sheet names that vary ("TB", "Trial Balance"); (ii) bank CSVs from HDFC and SBI, UTF-8, with quoted narrations containing commas; (iii) an on-prem SQL Server FinanceDW with a 35-million-row GLLines table for the SAP entity; (iv) a CoA mapping maintained in an Excel Table on SharePoint. The CFO wants a Power BI report refreshed daily in the Service. (a) Choose the connector and write the source M for each. (b) Design the parameter list and query layering with load settings. (c) Identify which steps can fold and which sources need a gateway. (d) State the privacy levels you would set and why.

Q2. Review a colleague's file [L2]

A colleague's Excel workbook has one query with these steps: Source = Csv.Document(File.Contents("C:\Users\neha\Desktop\bank_apr.csv"), [Delimiter=",", Columns=7, Encoding=1252, QuoteStyle=QuoteStyle.None]), Promoted Headers, Changed Type, Removed Top Rows (18), Removed Bottom Rows (3), Merged Queries with TallyBank (a SQL extract with a native query SELECT * FROM BankBook), Expanded, Added Index, Filtered Rows (Year = 2025). It is loaded to both a sheet and the Data Model. Write a structured review memo listing every issue, its consequence and the fix, grouped under connectors, types, folding, pipeline design and load settings.

💡 Hint: Work through the topic subtopics in order and test each step against them.

Q3. Folding and performance experiment [L2]

Using a SQL Server (or MySQL) table of at least 1 million GL rows, build two versions of the same summary query (by Account and Month for one FY): one where an index column is added first, one where it is added last. Record refresh time, the native query shown at each step, and Query Diagnostics output. Write a one-paragraph conclusion suitable for an internal wiki.

Q4. Firewall and parameter case [L2]

An Excel recon file reads the folder path from named cell rngPath, the as-of date from named cell rngAsOf, bank files from that folder, and the book ledger via Tally ODBC. On a colleague's machine refresh fails with "Formula.Firewall: Query 'Recon' (step 'Files') references other queries or steps, so it may not directly access a data source". Explain the cause, redesign the queries, and state what the colleague also needs installed and configured for the ODBC source.

Q5. M reading test [L1]

Explain in plain English what each line does, and identify what _ refers to on each line where it appears: Src = Excel.Workbook(File.Contents(pPath), null, true){[Item="Budget", Kind="Table"]}[Data], Cols = List.RemoveItems(Table.ColumnNames(Src), {"Account","Dept"}), Pos = Table.SelectRows(Src, each [#"Apr-25"] <> null), Up = Table.TransformColumns(Pos, {{"Dept", each Text.Upper(_), type text}}), Grp = Table.Group(Up, {"Dept"}, {{"Rows", each Table.RowCount(_), Int64.Type}}).
