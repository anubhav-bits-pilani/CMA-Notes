Key concept

Folding Breakers: Table.Buffer, Index Columns and Custom Functions

Concept: Table.Buffer, Table.AddIndexColumn and custom function calls usually break folding, so put them after foldable steps

Statement

For a foldable source, folding continues only while every step can be translated into the source's query language. Three common operations have no native translation on most relational connectors:

Operation Why it does not fold
Table.Buffer(t) Explicitly materialises the table in local memory — by design the opposite of folding
Table.AddIndexColumn(t, "Idx", 1, 1) Row numbering depends on an order the source does not guarantee; no generic SQL translation
Invoking a custom M function per row (each fxMap([Account])) Arbitrary M logic cannot be expressed in SQL

Rule: place them after all foldable steps (filters, column selection, group by, same-source joins), so that the expensive reduction happens at the source and the non-foldable step runs on the smallest possible table.

Explanation

Once folding stops, every later step is local even if foldable in principle (s05). So the position of a single breaker decides the volume transferred.

Table.Buffer reads the whole table into memory once and returns a stable copy. Benefits: repeated access (e.g. a table used in several merges or in a List.Contains lookup inside a row-by-row filter) does not re-evaluate the source each time; also it stabilises sort order before operations like Table.Distinct that keep the first occurrence. Costs: memory, loss of folding, and — with streaming sources — waiting for the full read. Use it on a small, already reduced lookup table referenced repeatedly, not on a 5-million-row fact.

Table.AddIndexColumn is needed for sequence numbers (duplicate-safe matching, Topic 5), row-position logic and stable IDs. Add it after grouping or filtering; if you need a server-side row number, use ROW_NUMBER() in a view or native query.

Custom functions (fxCleanBank, fxFYLabel) are evaluated by the mashup engine row by row or table by table. Even simple ones block folding. Where the logic is a simple conditional on database columns, a native if ... then ... else custom column may fold (as CASE WHEN); a function wrapper will not.

Other frequent breakers: Table.Transpose, Fill Down, culture-specific type conversions, text functions without SQL equivalents, merges with a different source.

Illustration

SQL table Receipts, 12 million rows; FY26 customer receipts above ₹10 lakh are 3,800 rows.

Order Folding stops at Rows transferred
Source → Table.Buffer → Filter FY26 → Filter Amount > 10,00,000 → Add Index Step 2 12,000,000
Source → Filter FY26 → Filter Amount > 10,00,000 → Add Index → Buffer Step 4 3,800

In the bank-reconciliation pipeline, the book ledger lookup is built from a SQL extract and then used in two anti-joins and a duplicate-check merge. Buffering it after its filters (current bank account, FY) means one read of a few thousand rows instead of three reads.

Connections

Applies s05 (folding) and s03 (functions). Connects to Topic 5 (buffering before repeated merges, index-based sequence numbers) and Topic 4 (custom functions over a folder — folding is irrelevant there because files never fold, but buffering still matters). The cross-cutting performance item for the week rests on this concept.

Practice Questions

Q1. Reorder the steps [L2]

A query: Source (SQL dbo.VendorPayments, 9 million rows) → Added Index → Invoked fxPANCheck on PAN → Filtered FY = 2026 → Filtered PaymentMode = "NEFT" → Removed Columns. Reorder the steps for performance and state where folding now stops.

Q2. Should you buffer? [L2]

For each case decide whether Table.Buffer helps and why: (a) a 2,000-row CoA mapping used in three merges; (b) a 6-million-row SQL GL fact before a single Group By; (c) a list of 400 book UTRs used inside Table.SelectRows(Bank, each List.Contains(BookUTRs, [UTR])); (d) a sorted table before Table.Distinct to keep the latest record.

💡 Hint: Buffering helps repeated access to small tables and order stability; it hurts when it stops folding on a large source.

Q3. Server-side alternative [L3]

You need a running sequence number per Amount value to make duplicate-safe keys for 4 million SQL ledger rows. Compare doing it with Table.Group + Table.AddIndexColumn in Power Query versus ROW_NUMBER() OVER (PARTITION BY Amount ORDER BY PostingDate) in a view, covering folding, refresh time and auditability.
