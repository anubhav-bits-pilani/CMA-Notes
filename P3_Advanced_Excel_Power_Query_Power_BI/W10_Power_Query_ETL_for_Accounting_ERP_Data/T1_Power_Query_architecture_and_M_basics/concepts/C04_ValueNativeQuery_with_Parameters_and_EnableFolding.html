Key concept

Value.NativeQuery with Parameters and EnableFolding

Concept: Value.NativeQuery(Source, "SELECT * FROM gl WHERE fy = @fy", [fy="FY26"], [EnableFolding=true])

Statement

Value.NativeQuery(target as any, query as text, optional parameters as any, optional options as record) runs a native query against a data source (target is usually the database returned by Sql.Database or another connector):

  • query: SQL text, with named placeholders such as @fy.
  • parameters: a record (or list) whose fields bind to placeholders — [fy="FY26"] binds @fy. Values are passed as parameters, not concatenated into SQL text.
  • options: [EnableFolding=true] asks the engine to treat the native query as a foldable subquery, so later steps can fold on top of it (supported on SQL Server, PostgreSQL, Snowflake, Databricks, Oracle and several others; connector support varies).

Explanation

Value.NativeQuery solves the two problems of the [Query=...] option of Sql.Database (c03).

1. Folding after native SQL. With EnableFolding=true, the engine wraps your SQL as a derived table: later filters and column selections become select ... from ( <your SQL> ) as [_] where .... This only works if your SQL is wrappable — a single SELECT without ORDER BY (unless with TOP), no stored procedure calls, no multiple statements. If the connector does not support the option, the call errors or simply does not fold.

2. Safe parameterisation. Building SQL by concatenation, e.g. "... WHERE fy = '" & pFY & "'", invites SQL injection and breaks on quotes, and every distinct text triggers a new native-query approval prompt. Bound parameters keep the SQL text constant, with values supplied separately; the engine handles quoting and types. Combined with a Power Query parameter: [fy = pFYLabel].

Conditions and caveats:

  • Placeholder syntax is source-specific: @name for SQL Server; other databases may differ.
  • Parameterisation with values from another query (not a simple parameter) can trigger Formula.Firewall partition errors (s08).
  • Native query permission must be granted (Data source settings or the "require user approval for new native database queries" option).
  • Check folding with View Native Query or the folding indicators on later steps.

Template:

let
    Source = Sql.Database(ServerName, "FinanceDW"),
    GL     = Value.NativeQuery(Source,
               "SELECT PostingDate, Account, CostCentre, Amount, FY FROM dbo.GL WHERE FY = @fy",
               [fy = pFYLabel],
               [EnableFolding = true]),
    IN01   = Table.SelectRows(GL, each [CostCentre] <> "ELIM"),
    ByAcct = Table.Group(IN01, {"Account"}, {{"Amount", each List.Sum([Amount]), type number}})
in
    ByAcct

With folding enabled, IN01 and ByAcct fold into an outer WHERE and GROUP BY around the native SQL.

Illustration

dbo.GL holds 30 million rows; FY26 is 3.1 million; after excluding cost centre ELIM and grouping by account there are 2,450 rows. Without EnableFolding, 3.1 million rows are transferred and grouped locally. With EnableFolding=true, 2,450 rows are transferred. Changing pFYLabel to "FY25" in the Power BI Service re-runs the same SQL text with a different bound value — no new approval prompt and no injection risk if someone types FY25' OR 1=1 --.

Connections

Extends c03 and s05 (folding) and s06 (parameters). Relevant to Week 12 (Service parameters and gateway refresh) and to the MySQL refresher — the bound-parameter idea mirrors prepared statements (PreparedStatement in Java JDBC).
