Key concept

MySQL.Database Connector and Odbc.DataSource for Tally

Concept: MySQL.Database("server", "db") needs the MySQL connector; for ODBC use Odbc.DataSource("dsn=TallyODBC")

Statement

  • MySQL.Database(server as text, database as text, optional options as record) connects natively to MySQL and returns a navigation table. It requires the MySQL Connector/NET (ADO.NET driver from Oracle, the version supported by your Power BI/Excel build) installed on the machine and on any gateway that refreshes it. Steps after navigation fold into MySQL SQL.
  • Odbc.DataSource(connectionString, optional options) connects through any ODBC driver configured on the machine; "dsn=TallyODBC" refers to a DSN defined in the Windows ODBC Data Source Administrator (64-bit for 64-bit Power BI/Excel). Odbc.Query(connectionString, "SELECT ...") sends native SQL through ODBC.

Explanation

MySQL: without the connector, Desktop shows "This connector requires one or more additional components to be installed". Options include [Query="..."] (same folding drawback as c03), CommandTimeout, and ReturnSingleDatabase. Many Indian SMEs run billing, POS or custom ERP systems on MySQL, so this connector gives FP&A direct access to sales registers. Use a read-only user on a reporting replica, not production.

ODBC: the generic route to systems without a native connector — Tally Prime/ERP 9, older ERPs, some cloud accounting tools. Key points:

  • Bitness: 32-bit DSNs are invisible to 64-bit Power BI; create the DSN in the 64-bit administrator (and on the gateway machine).
  • Tally ODBC: Tally acts as an ODBC server when running with ODBC enabled (F1 Help → Settings → Connectivity, default port 9000) and the company is open. The Tally ODBC driver exposes collections such as Ledger, Group, Voucher and Stock Item; field names follow Tally's internal method names (Name, Parent, ClosingBalance). In Tally's own SQL dialect each method name carries a dollar-sign prefix; the examples below show the names without the prefix for readability, so add it when you type the SQL.
  • Folding: ODBC folding depends on the driver's reported SQL capabilities. Tally's ODBC supports limited SQL, so treat it as mostly non-foldable; filter in the SQL text and keep extracts small.
  • Availability: Tally must be running and the company loaded for refresh; scheduled refresh needs a gateway on a machine where Tally runs. For unattended pipelines, scheduled XML/Excel exports or a third-party connector are often more reliable.
  • Sign convention: Tally closing balances via ODBC are typically signed (debit negative or positive depending on driver/version); verify against a known ledger before building Dr/Cr logic.

Illustration

Sales register from MySQL billing system:

let
    Source   = MySQL.Database("10.0.5.20:3306", "billing", [ReturnSingleDatabase=true]),
    Inv      = Source{[Schema="billing", Item="invoices"]}[Data],
    FY26     = Table.SelectRows(Inv, each [invoice_date] >= #date(2025,4,1) and [invoice_date] <= #date(2026,3,31)),
    Cols     = Table.SelectColumns(FY26, {"invoice_no","invoice_date","customer_gstin","taxable_value","igst","cgst","sgst"})
in
    Cols

Tally ledger balances via ODBC (DSN created as "TallyODBC" pointing to localhost:9000):

let
    Source = Odbc.Query("dsn=TallyODBC", "SELECT Name, Parent, ClosingBalance FROM Ledger"),
    Typed  = Table.TransformColumnTypes(Source, {{"ClosingBalance", type number}})
in
    Typed

Before trusting it, compare three ledgers' closing balances against Tally's own TB screen, including sign.
