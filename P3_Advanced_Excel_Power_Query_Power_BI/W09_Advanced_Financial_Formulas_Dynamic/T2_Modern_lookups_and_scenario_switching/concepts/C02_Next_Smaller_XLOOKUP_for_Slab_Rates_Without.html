Key concept

Next-Smaller XLOOKUP for Slab Rates Without Sorting

Concept: =XLOOKUP(Income, Slab[From], Slab[Rate], , -1): exact match or next smaller; data only needs sorting for binary search_mode

Statement

With match mode -1, XLOOKUP returns the rate of the row whose From value is the largest value not exceeding the income:

\[ \text{Rate}(I) = R_{j^*}, \qquad j^* = \arg\max_{j} \{\, F_j : F_j \le I \,\} \]

where \(I\) is the income looked up, \(F_j\) the From value of slab row \(j\), and \(R_j\) its rate. If no \(F_j \le I\) exists, the result is #N/A (the fourth argument is skipped, so the default not-found behaviour applies). With the default linear search modes (1 or -1) the rows may be in any order; only binary search modes (2, -2) require the From column to be sorted.

Explanation

The skipped argument. The double comma , , leaves if_not_found empty so that a value below the lowest From (for example a negative income) shows #N/A instead of a misleading default. For slab tables starting at 0, this only fires for genuinely invalid inputs.

No sort requirement — and why it matters. VLOOKUP with TRUE, MATCH with type 1 and LOOKUP all use a binary-search-like algorithm that assumes ascending order; on an unsorted table they return wrong rows without an error. XLOOKUP with -1 and linear search examines every row and keeps the best candidate, so a slab table someone re-ordered (e.g. sorted by rate, or with a new slab appended at the bottom) still returns the right rate. If you add search_mode 2 for speed, the sort requirement returns — and so does the silent-error risk.

Marginal vs average rate. The lookup returns the marginal slab rate. Progressive tax is BaseTax at From plus the marginal rate on the excess over From — the same -1 lookup pattern applied to the From and BaseTax columns. Multiplying income by the returned rate overstates tax.

Ties and duplicates. If two rows share the same From, linear search (mode 1) returns the first. Keep From values unique.

Boundary. An income exactly equal to a From value matches that row (exact match wins), so From values belong to the upper band.

Illustration

New-regime slabs, FY 2025-26 (Section 115BAC as amended by Finance Act 2025), deliberately stored out of order:

From Rate BaseTax
12,00,000 15% 60,000
0 0% 0
24,00,000 30% 3,00,000
4,00,000 5% 0
16,00,000 20% 1,20,000
8,00,000 10% 20,000
20,00,000 25% 2,00,000

For income ₹13,75,000: candidates with From ≤ income are 0, 4,00,000, 8,00,000 and 12,00,000; the largest is 12,00,000, so the rate is 15% and BaseTax ₹60,000. Tax before rebate and cess = 60,000 + 1,75,000 × 15% = ₹86,250. VLOOKUP(1375000, Slab, 2, TRUE) on this unsorted table would return an unreliable result.

Connections

Core formula of the approximate-match subtopic (tax slabs, TDS, commission tiers, depreciation bands) and of the search-mode rules in the XLOOKUP-arguments subtopic. It contrasts with the MATCH-defaults-to-approximate pitfall. In DCF and payroll models (Weeks 13–16) the same pattern drives tax-rate and slab lookups; in Power Query it is replaced by a merge plus a "between" condition or a sorted fill-down.

Practice Questions

Q1. Progressive tax with three lookups [L1]

Using the slab table above, write a formula (with or without LET) that returns tax before rebate and cess for income in B4. Then list the test incomes you would run to verify every band.

Q2. Unsorted table audit [L2]

An inherited payroll file uses VLOOKUP(Income, SlabTbl, 2, TRUE) and the HR team recently inserted the new ₹20–24 lakh slab at the bottom of the table. Explain which incomes are now likely to be mis-rated and why, and rewrite the formula so that row order no longer matters.

💡 Hint: Consider how an algorithm that assumes ascending order behaves when the last row is out of place.

Q3. Speed vs safety [L2]

A colleague proposes adding search_mode 2 to 25,000 slab lookups in an employee-level tax projection "for speed". Evaluate the proposal, including the size of the slab table, the actual performance gain and the control you would require if it is adopted.
