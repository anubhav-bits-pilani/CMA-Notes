Key concept

INDEX-MATCH-MATCH: The Version-Proof Two-Way Lookup

Concept: =INDEX(Data, MATCH($A5, Codes, 0), MATCH(C$4, Months, 0))

Statement

\[ \text{Result} = D_{r,c}, \qquad r = \text{MATCH}(a, \text{Codes}, 0), \qquad c = \text{MATCH}(h, \text{Months}, 0) \]

where \(a\) is the account code in column A of the current row, \(h\) the month header in row 4 of the current column, \(r\) the 1-based position of \(a\) within Codes, \(c\) the 1-based position of \(h\) within Months, and \(D_{r,c}\) the cell of Data at row \(r\), column \(c\). Match type 0 means exact match; if either key is absent, MATCH returns #N/A and so does the formula.

Explanation

Division of labour. MATCH answers "where?" and INDEX answers "what is there?". Separating the two makes the formula robust to inserted columns and rows (no hard-coded column index as in VLOOKUP), able to look left or up, and fast — each MATCH runs once per cell.

The 0 is not optional. MATCH's third argument defaults to 1 (approximate: largest value ≤ lookup value, assuming ascending order). On unsorted account codes or month headers, omitting 0 returns a plausible wrong position without any error. Reviewers should treat every MATCH without an explicit 0 (or -1/1 with a documented reason) as a defect.

Alignment. Codes must span exactly the rows of Data, and Months exactly its columns, starting at the same row/column. A header range that includes a label cell (A4) while Data starts in C means every column position is off by two.

Compatibility and auditability. This form works in every Excel version since the 1990s, which matters for files shared with subsidiaries, auditors or clients on older installations. It is also the form most reviewers recognise instantly.

Error handling. Wrap with IFNA (not IFERROR) when a missing key is a legitimate state: =IFNA(INDEX(…), 0) for "no budget line"; leave other errors visible.

Speed trick. On large grids, compute the row position once in a helper column (e.g. B5 =MATCH($A5, Codes, 0)) and the column position once in a helper row; the grid cells then become =INDEX(Data, $B5, C$3), which is extremely fast and makes position errors visible.

Illustration

Codes = Budget!A6:A8, Months = Budget!C4:E4, Data = Budget!C6:E8:

C (Apr) D (May) E (Jun)
6: 610100 82.0 82.0 86.5
7: 640500 21.0 21.0 21.0
8: 650200 6.4 7.1 5.8

For A5 = 640500 and C4 = 01-Jun-2025: row position 2, column position 3, result ₹21.0 lakh.

Now suppose the codes in the budget file are not sorted (650200, 610100, 640500 in rows 6–8) and the formula omits the 0 in the first MATCH. MATCH(640500, Codes) treats the list as ascending, and can stop at the wrong row — returning the 610100 row's value, ₹86.5 lakh, as "rent". No error is shown.

Connections

The legacy counterpart of the nested-XLOOKUP concept, covered in the two-way lookup subtopic; XMATCH (the modern MATCH subtopic) can replace both MATCHes. The match-type pitfall of this topic ("MATCH defaults to 1") is demonstrated directly. The helper-position technique also underpins fast INDEX-based scenario switches and the INDEX:INDEX dynamic ranges used for YTD windows.

Practice Questions

Q1. Build with helper positions [L1]

A 60-line × 12-month budget block is on sheet Bud. Design a report grid that uses a helper column of row positions and a helper row of column positions, and write the three formulas (row helper, column helper, grid cell).

Q2. Audit three variants [L2]

Explain what can go wrong with each: (a) =INDEX(Data, MATCH(A5, Codes, 0), MATCH(C4, Months)); (b) =INDEX(Data, MATCH(A5, Budget!A:A, 0), MATCH(C4, Months, 0)) where Data starts in row 6; (c) =IFERROR(INDEX(Data, MATCH(A5, Codes, 0), MATCH(C4, Months, 0)), 0).

💡 Hint: One is a match-type issue, one an alignment issue, and one an error-masking issue.

Q3. Interview comparison [L1]

"Why do many modellers still prefer INDEX-MATCH over XLOOKUP?" Give a balanced answer covering compatibility, performance, readability and the risks specific to each.
