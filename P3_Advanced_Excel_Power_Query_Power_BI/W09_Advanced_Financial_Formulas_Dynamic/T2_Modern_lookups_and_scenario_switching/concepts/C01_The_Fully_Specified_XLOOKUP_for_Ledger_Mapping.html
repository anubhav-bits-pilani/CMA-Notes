Key concept

The Fully Specified XLOOKUP for Ledger Mapping

Concept: =XLOOKUP(key, lookup_array, return_array, "Not mapped", 0, 1)

Statement

\[ \text{XLOOKUP}(k, L, R, f, 0, 1) = \begin{cases} R_{j^*} & \text{if } \exists\, j : L_j = k, \text{ with } j^* = \min\{\, j : L_j = k \,\} \\ f & \text{otherwise} \end{cases} \]

where \(k\) is the key (e.g. a TB ledger name), \(L\) the lookup array (mapping-table ledgers), \(R\) the return array (FS line, aligned with \(L\)), \(f\) the not-found value ("Not mapped"), match mode 0 means exact equality (case-insensitive for text), and search mode 1 means scanning from first to last so the first matching row \(j^*\) is returned.

Explanation

Why write the defaults explicitly. Match mode 0 and search mode 1 are XLOOKUP's defaults, so XLOOKUP(key, L, R, "Not mapped") behaves identically. Writing all six arguments in a mapping template documents intent — "exact, first match, flag misses" — and stops a later editor from "optimising" with binary search or approximate match without noticing what changes.

The not-found value as a control. "Not mapped" is deliberately a text flag, not 0 or blank:

  • It is visible in the TB and in any PivotTable of the mapped data.
  • It can be counted: =COUNTIF(TB[FSLine], "Not mapped") is a check cell that must be zero.
  • It flows into SUMIFS rollups as its own FS line, so its amount appears rather than vanishing: =SUMIFS(TB[Closing], TB[FSLine], "Not mapped").
  • It catches only the not-found case. A #REF! from a deleted mapping column still shows — unlike IFERROR(…,"Not mapped"), which would disguise a broken model as an unmapped ledger.

What "first match" implies. If the mapping table accidentally holds the same ledger twice with different FS lines, the first wins silently. Pair the formula with a duplicate check on the mapping table: =COUNTIF(Map[Ledger],[@Ledger])>1.

Exactness traps. Exact match is strict on content and type: "Rent " (trailing space) ≠ "Rent"; the number 410100 ≠ the text "410100"; non-breaking spaces (CHAR(160)) from web/PDF exports look like spaces but are not removed by TRIM. Clean keys at import (Power Query Trim/Clean, type setting) rather than inside every lookup.

Connections

This is the mapping step of the week's exercise (ledger → FS line → Schedule III line) and the unmapped-ledger check in the cross-cutting concepts. It applies the argument rules of the XLOOKUP-arguments subtopic and is the safer alternative to VLOOKUP covered under related concepts. The duplicate-key and trailing-space pitfalls of this topic are exactly the failure modes it is exposed to. At ETL scale (Week 10) the same mapping is a Power Query left-outer merge with null-checks.

Practice Questions

Q1. Mapping with control totals [L1]

Write the mapping formula for a TB Table with columns Ledger, Closing, and the three check cells (count of unmapped, net amount unmapped, absolute amount unmapped) you would place on the control sheet.

Q2. IFERROR vs the not-found argument [L2]

A reviewer replaced XLOOKUP([@Ledger], Map[Ledger], Map[FSLine], "Not mapped", 0, 1) with IFERROR(XLOOKUP([@Ledger], Map[Ledger], Map[FSLine]), "Not mapped") "for consistency". Describe a realistic sequence of events in which the IFERROR version produces a materially wrong draft balance sheet without anyone noticing, and how the original would have exposed it.

💡 Hint: Think about what happens to every row if the mapping Table's FSLine column is renamed or deleted.

Q3. Cleaning before mapping [L2]

A TB pasted from a PDF has 61 of 480 ledgers showing "Not mapped", although they look identical to mapping-table entries. Write formulas to test for trailing spaces, non-breaking spaces and number-versus-text mismatches, and describe the permanent fix.
