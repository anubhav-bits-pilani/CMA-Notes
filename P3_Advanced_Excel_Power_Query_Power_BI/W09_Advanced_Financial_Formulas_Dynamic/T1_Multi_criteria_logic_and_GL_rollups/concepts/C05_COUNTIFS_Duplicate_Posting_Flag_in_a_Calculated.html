Key concept

COUNTIFS Duplicate-Posting Flag in a Calculated Column

Concept: =COUNTIFS(GL[Voucher], [@Voucher], GL[Amount], [@Amount])>1 flags duplicate postings

Statement

For each row \(r\) of Table GL, the flag is

\[ \text{Dup}_r = \left( \sum_{i \in GL} \mathbf{1}\left[V_i = V_r\right] \times \mathbf{1}\left[A_i = A_r\right] \right) > 1 \]

where \(V\) is the voucher number, \(A\) the amount and \(\mathbf{1}[\cdot]\) the indicator function. The count always includes row \(r\) itself, so a value of 1 means "unique" and anything greater than 1 means at least one other row shares both the voucher number and the amount. The formula returns TRUE/FALSE.

Explanation

Calculated column. Entered once in a new column of the Table, it fills down for every row, and [@Voucher] / [@Amount] refer to the current row. When the next GL dump is pasted, new rows get the flag automatically.

Choosing the key. Duplicate detection is only as good as the key:

  • Voucher number alone flags every multi-line voucher (each Dr/Cr leg repeats the number). Adding Amount reduces this, but a JV with two identical ₹50,000 debit legs to different ledgers still flags — add GL[Account], [@Account] if lines legitimately repeat amounts.
  • Tally numbers restart per voucher type, so add GL[VchType], [@VchType]; multi-year dumps need FY too.
  • For purchase duplicates, the meaningful key is vendor GSTIN + supplier invoice number, not the internal voucher number.

Coercion trap. COUNTIFS treats numeric-looking text as numbers: vouchers "000123" and "123" are counted as the same, and identifiers longer than 15 digits are truncated in comparison. For such keys use SUMPRODUCT(--EXACT(GL[Voucher],[@Voucher]), --(GL[Amount]=[@Amount]))>1.

Performance. Each row's COUNTIFS scans the whole column, so n rows cost about \(n^2\) comparisons. Fine for 20,000 rows; on 2 lakh rows prefer a sort-and-compare helper or Power Query Group By.

Reporting. Summarise with =COUNTIFS(GL[Dup],TRUE) and =SUMIFS(GL[Amount],GL[Dup],TRUE) in the check block; list the rows with FILTER(GL, GL[Dup]) for investigation.

Illustration

Voucher VchType Account Amount (₹) Count Dup
PUR/0451 Purchase 510100 4,72,000 2 TRUE
PUR/0451 Purchase 510100 4,72,000 2 TRUE
JV/0102 Journal 640500 50,000 1 FALSE
JV/0102 Journal 230200 -50,000 1 FALSE

The PUR/0451 pair is a re-imported line — a genuine duplicate that would overstate purchases and GST input credit. The JV/0102 legs share the voucher number but differ in amount sign, so they are not flagged. Had the JV been a ₹50,000 debit to two expense ledgers, both legs would flag unless Account were added to the key.

Practice Questions

Q1. Strengthen the key [L1]

Rewrite the flag for a Tally Day Book export that spans FY25 and FY26 and contains columns FY, VchType, VchNo, Ledger and Amount, so that legitimate multi-line vouchers and voucher-number restarts are not flagged.

Q2. False positives and negatives [L2]

Give one realistic example each of (a) a false positive and (b) a false negative produced by the concept formula on a GL dump, and explain how you would adjust the key or the method for each.

💡 Hint: Consider identical legs within one voucher, and the same invoice booked under two different voucher numbers.

Q3. Scale problem [L2]

A 2.6 lakh-row GL Table takes over four minutes to recalculate after you add the duplicate flag column. Describe two alternative approaches that produce the same duplicate list faster, and the trade-offs of each.
