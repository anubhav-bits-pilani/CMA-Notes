Key concept

Range Criteria for Numeric Account Codes vs Wildcards on Text

Concept: Numeric account codes need range criteria (">=400000", "<500000"); wildcard "4*" only works on text codes

Statement

For an account-code column \(C\) and a series defined by leading digit \(d\) on a \(k\)-digit code, the numeric condition is

\[ d \times 10^{k-1} \le C_i < (d+1) \times 10^{k-1} \]

so for the 4-series on six-digit codes, \(400000 \le C_i < 500000\), written in SUMIFS as two criteria on the same column: ">=400000" and "<500000". The wildcard criterion "4*" is a text pattern: it matches only cells containing text that begins with "4". Cells holding the number 410100 never match it.

Explanation

Why wildcards ignore numbers. In the *IFS and *IF functions, a criterion containing * or ? triggers a text comparison. Numeric cells are not converted to text for that comparison, so they are excluded. The result is not an error but a silent zero — the most dangerous kind of wrong answer in a TB rollup.

Diagnosing the data type. Numbers align right by default and text left; =ISNUMBER(A2) and =COUNT(TB[Code]) vs =ROWS(TB[Code]) confirm it. ERP exports are frequently mixed: Tally and SAP dumps opened from CSV may hold codes as numbers, while copy-paste from PDF or web reports often yields text, sometimes with a leading apostrophe or trailing space.

Choosing a convention. Either:

  1. Keep codes numeric and use range criteria everywhere (">="&From, "<"&To with the bounds in a band table), or
  2. Convert codes to text consistently (Power Query type "Text", or TEXT(code,"0")) and use wildcards or LEFT tests.

Mixing the two in one model is the failure mode — a mapping table with numeric codes and a GL with text codes will also break XLOOKUP and COUNTIFS joins.

Range criteria are more precise. "4*" on text also matches "4", "40" and "4A-SUSP" — anything starting with 4. Range criteria on numbers enforce the code length implicitly. For sub-series, ranges are natural: 410000–419999 domestic revenue, 420000–429999 export revenue.

Cell-driven bounds.

=SUMIFS(TB[Closing], TB[Code], ">="&Band[@From], TB[Code], "<"&Band[@To])

Illustration

TB extract:

Code Type Closing (₹ lakh)
410100 number -820.0
410200 number -145.5
"420100" text -96.0
510100 number 512.0
  • SUMIFS(TB[Closing], TB[Code], "4*") → ₹-96.0 lakh (text row only).
  • SUMIFS(TB[Closing], TB[Code], ">=400000", TB[Code], "<500000") → ₹-965.5 lakh (numeric rows only; the text code fails numeric comparison).
  • True 4-series revenue is ₹-1,061.5 lakh. Neither formula is right until the data type is fixed — the real lesson is to standardise types before rolling up, and to reconcile the rollup total to the TB total.

Connections

Applies the criteria-syntax subtopic (wildcards and operators) and the text-stored-numbers pitfall of this topic. The same type discipline is needed for XLOOKUP keys in the lookups topic and for LEFT(GL[Account],1)="5" tests in SUMPRODUCT, which work on numbers because LEFT converts them to text. In Power Query (Week 10), setting the code column's data type once at import removes the problem upstream.

Practice Questions

Q1. Write the band criteria [L1]

Six-digit codes: 500000–549999 Direct costs, 550000–579999 Employee costs, 580000–589999 Finance costs, 590000–699999 Other expenses. Write SUMIFS formulas for each band using a band table with From and To columns, and state whether To should be inclusive or exclusive in your design.

Q2. Mixed-type TB [L2]

A 512-ledger TB has 47 codes stored as text. Write formulas that (a) count the text codes, (b) total their closing balances, and (c) produce a numeric helper column that converts every code to a number. Explain why you would rather fix the type in Power Query than in the helper column for a recurring monthly process.

💡 Hint: ISTEXT and VALUE are enough for (a) to (c).

Q3. Interview question [L1]

"Your SUMIFS for revenue returns zero, but filtering the TB on codes starting with 4 shows ₹820 crore. What are the possible reasons?" List at least three, with the test you would run for each.
