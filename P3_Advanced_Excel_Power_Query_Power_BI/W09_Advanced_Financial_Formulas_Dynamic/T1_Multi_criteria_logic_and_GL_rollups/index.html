Roadmap topic: Multi-Criteria Conditional Logic & Aggregation: Nested IF, IFS, SUMIFS, COUNTIFS, AVERAGEIFS, MAXIFS/MINIFS for multi-department GL rollups

Overview

Every finance deliverable built in Excel — the monthly MIS, the department cost report, the TB-to-Schedule III mapping, the actuals feed of a forecast — is an aggregation of transaction-level data under conditions. This topic is about doing that aggregation with formulas that are correct, complete and self-updating: classifying ledgers with IF/IFS/SWITCH, summing them with SUMIFS across department, cost centre, account group and date ranges, testing the data with COUNTIFS, and producing behavioural KPIs (average ticket, largest open payment, oldest open invoice) with AVERAGEIFS, MAXIFS and MINIFS.

For someone coming from audit and GL finalisation, the shift is from "I can filter Tally and get the number" to "I can build a grid that produces every number, every month, with no manual step, and proves its own completeness". Interviewers for FP&A and reporting roles test exactly this: a blank grid, a GL dump and a stopwatch. Model reviewers test it differently — they look for one consistent formula per block, inputs referenced rather than typed, and check cells that tie the output back to the source.

The subtopics form a sequence. Start with classification (s01), because a rollup needs a nature or group for each ledger. Then the core SUMIFS rollup (s02) and its grammar — criteria syntax (s05) and OR logic (s06). Before trusting any rollup, run COUNTIFS data-quality tests (s03), and extend the toolkit to averages and extremes (s04). Two structural skills make the whole thing robust and fast: Excel Tables so ranges grow with the data (s07), and mixed referencing so one formula fills a grid (s08). The seven key concepts are the exact formulas and behaviours you should be able to write from memory.

The topic connects forward to SUMPRODUCT (for conditions SUMIFS cannot express), XLOOKUP mapping (to attach FS lines to ledgers), dynamic arrays (to generate row and column headers), and later to DAX in Power BI, where the same rollup becomes a measure evaluated in filter context.

Related concepts to study

SUMPRODUCT for conditions SUMIFS cannot handle

SUMPRODUCT for criteria SUMIFS cannot handle, such as MONTH() or LEFT() on ranges → w9_t3

SUMIFS criteria ranges must be actual ranges, not computed arrays, so you cannot write SUMIFS(GL[Amount], MONTH(GL[Date]), 4) or test LEFT(GL[Account],1)="5". SUMPRODUCT accepts any array expression: SUMPRODUCT((MONTH(GL[Date])=4)*(LEFT(GL[Account],1)="5")*GL[Amount]). It also handles OR logic with overlapping conditions, case-sensitive matches via EXACT, and conditions comparing two columns of the same row (e.g. amount above that row's credit limit). The trade-off is speed: SUMPRODUCT evaluates every row for every cell and cannot use SUMIFS's internal optimisations, so it should be used for the conditions SUMIFS genuinely cannot express, not as a default. Topic 3 develops it fully.

PivotTables and GETPIVOTDATA as an independent check

PivotTables and GETPIVOTDATA as an independent cross-check of SUMIFS rollups

A PivotTable built on the same GL Table aggregates the data by an entirely different engine, so agreement between a SUMIFS grid and a pivot is strong evidence that the formulas are complete and correctly anchored. GETPIVOTDATA retrieves a specific value from a pivot by field names — =GETPIVOTDATA("Amount", Pivot!A3, "Dept", "Sales"), where A3 is any cell inside the pivot, — and keeps pointing at the right item even when the pivot layout changes. A practical control is a hidden check column: SUMIFS result minus GETPIVOTDATA result, which must be zero for every row. Remember that pivots need a refresh (Data → Refresh All) after new data is pasted; an un-refreshed pivot will disagree for the wrong reason. Pivots are also the quickest way to discover new departments or groups missing from the grid's row headers.

TB-to-Schedule III mapping and close rollups

→ Week 1–4: TB-to-Schedule III mapping and month-end close rollups

Weeks 1–4 established the classification rules: Ind AS 1 current/non-current, Schedule III Division II line items and note disclosures, and the month-end close sequence. This topic supplies the mechanics: a ledger-to-FS-line mapping table, an IFS or band-table nature classification, SUMIFS rollups from ledger to note line to face of the balance sheet and statement of profit and loss, and COUNTIFS checks that every ledger is mapped. The same rollup as a DAX CALCULATE measure

→ Week 11: the same rollup as DAX CALCULATE with filter arguments

In Power BI, the SUMIFS grid becomes a matrix visual and a measure such as Actual = SUM(GL[Amount]). The row (department), column (month) and slicer selections create filter context, so the measure needs no explicit criteria. When you need to override or add a filter — "Sales and Marketing only", "same period last year" — you use CALCULATE(SUM(GL[Amount]), GL[Dept] IN {"Sales","Marketing"}) or time-intelligence functions with a proper Date table. Understanding SUMIFS as "sum under a set of filters" makes CALCULATE intuitive: each SUMIFS criteria pair corresponds to a filter argument, and the date-range pair corresponds to a relationship to a Date table.

Department-wise budget vs actual MIS grids

→ Week 17–20: department-wise budget vs actual MIS grids

FP&A's monthly BvA pack is the same grid built twice — once on the actuals GL and once on the budget table (which is usually at a coarser grain: department × MIS line × month). The SUMIFS skills here let both grids share one row/column structure, so variance, variance %, and YTD columns are simple relative formulas. Weeks 17–20 add the analysis layer: price/volume/mix bridges, flexed budgets, rolling forecasts and commentary thresholds. The data-quality checks from this topic (unmapped ledgers, out-of-period postings) are what make variance commentary credible — an unexplained variance is often just a mis-mapped ledger.

Common pitfalls

Unequal ranges and SUMIF vs SUMIFS argument order

Unequal-size criteria ranges give #VALUE!; sum_range comes last in SUMIF but first in SUMIFS

The mistake. Writing SUMIFS(G2:G5000, D2:D4999, "Sales") — ranges of different sizes — returns #VALUE!. Converting a SUMIF to SUMIFS without reordering (SUMIF(range, criteria, sum_range) vs SUMIFS(sum_range, criteria_range, criteria)) either errors or sums the wrong column. SUMIF, by contrast, does not error on unequal sizes: it silently resizes sum_range to match range from its top-left cell, which can misalign rows.

Why it happens. Ranges typed by hand or extended by dragging; muscle memory from SUMIF.

Correct treatment and review. Use Table column references so all ranges are automatically identical; standardise on SUMIFS even for one criterion. In review, inspect the first argument of every sum formula and use Evaluate Formula on any #VALUE!.

Numbers stored as text in ERP exports

Numbers stored as text in ERP exports are silently left out of SUMIFS; check with ISNUMBER or convert with VALUE

The mistake. CSV and Excel exports from Tally, SAP or bank portals often hold amounts as text ("1,25,000.00", amounts with trailing "Dr", or numbers with leading apostrophes). SUMIFS ignores text in the sum range, so the total is understated with no error.

Why it happens. Indian digit grouping and Dr/Cr suffixes are text by nature; regional settings change decimal separators; people trust the green-triangle-free look of formatted cells.

Correct treatment and review. Check COUNT(GL[Amount]) against ROWS(GL[Amount]) and SUMPRODUCT(--ISTEXT(GL[Amount])); convert with VALUE, Text to Columns, Paste Special Multiply by 1, or — best for recurring dumps — a Power Query type change. Include a check cell that the dump's control total from the source system equals SUM(GL[Amount]).

Hard-coding month dates in criteria

Hard-coding month dates in criteria instead of pointing to header cells

The mistake. Formulas such as SUMIFS(GL[Amount], GL[Date], ">=01-04-2025", GL[Date], "<=30-04-2025") or with DATE(2025,4,1) typed inside every cell.

Why it happens. It works for the first month built, and copying a working cell feels safe.

Correct treatment and review. Every period bound must derive from a header cell (">="&C$3, "<="&EOMONTH(C$3,0)), and headers themselves from a single start-date input via EOMONTH/SEQUENCE. Typed date strings are also locale-dependent (dd-mm vs mm-dd). In review, use Ctrl+and Find (Ctrl+F) for"/20orDATE(` inside output formulas; a grid where columns differ only by typed dates is a red flag.

Mixing signed amounts with separate Dr/Cr columns

Mixing signed amounts and separate Dr/Cr columns, which doubles or nets totals by mistake

The mistake. Summing a Debit column and a Credit column as if both were positive (doubling movements), or adding a signed Amount column to a Debit column, or netting income (credit) against expenses when a gross figure was needed.

Why it happens. Tally and SAP exports give Debit and Credit columns; some sheets add a signed column later; different team members build different parts of the grid.

Correct treatment and review. Create one signed Amount = Debit − Credit column in the Table (or Power Query) and use it exclusively; flip signs only in presentation for credit-natured lines. The control is that SUM(GL[Amount]) for a complete GL, and SUM(TB[Closing]) for a TB, equals zero; a non-zero result immediately exposes a doubled or one-sided column.

Practice Questions

Q1. Month-end MIS build for a multi-branch distributor [L3]

Shree Ganesh Distributors Ltd (FY ending 31 March) exports a GL Day Book from Tally Prime each month with columns Date, VchType, VchNo, Ledger, Branch (MUM, PUN, NSK), Dept (Sales, Warehouse, Admin), Debit, Credit. A ledger master maps 230 ledgers to account codes (six-digit numeric) and 18 MIS groups. Required: (a) specify the Tables and calculated columns you would create, including a signed amount and a nature classification using IFS with a catch-all; (b) write the grid formula for MIS group × branch × month for April 2025 to March 2026, with month-start headers in row 4 and labels in columns A and B; (c) add check cells for TB nets to zero, unmapped ledgers, duplicate vouchers (keyed correctly for Tally) and postings outside the selected FY; (d) explain how the grid updates when the October Day Book is pasted.

Q2. Working-capital dashboard from AR and AP open items [L2]

Table AR has Customer, InvNo, InvDate, DueDate, Amount, Status; Table AP has Vendor, MSE (Y/N), InvNo, InvDate, Amount, Status. Report date: 31-Mar-2026. Build formulas for each customer row: count of open invoices, open amount, average open invoice, largest open invoice and oldest open due date with its age in days — all guarded against no-match cases. For each MSE vendor row: open amount older than 45 days and the oldest open invoice date. Explain which of your formulas would silently mislead if unguarded and why.

💡 Hint: Remember which functions return 0 and which return an error when nothing matches.

Q3. Debugging an inherited department cost report [L2]

You inherit a department cost report whose FY26 total (₹18.42 crore) is ₹74.6 lakh lower than the expense total in the signed-off TB. On inspection you find: some formulas use SUMIF with ranges ending at row 41,000 while the GL has 44,850 rows; the Marketing row uses =SUM(SUMIFS(…,GL[Ledger],{"*Digital*","*Ads*"})); account codes in the GL are a mix of numbers and text; and the February column criteria contain ">=01/02/2026". Explain how each issue affects the total (understatement, overstatement or locale risk), the order in which you would fix them, and the check cells you would add so the report can never again silently disagree with the TB.

Q4. Department OR lists and cost-centre drill-down [L2]

The CFO wants a "Commercial" cost line comprising departments Sales, Marketing and Key Accounts, by cost centre (12 cost centres) and month. Design (a) the assumptions-sheet list, (b) a single formula for one grid cell using that list with OR logic, (c) a cross-check of the grid against a PivotTable using GETPIVOTDATA, and (d) a COUNTIFS check that no GL posting for these departments has a blank cost centre. State one condition under which your OR formula would double count.

Q5. Timed interview exercise [L3]

In 20 minutes, from a 9,000-row GL (Date, Account, Dept, Amount — signed) and a 60-row account master (Account, Nature by code range, FS line), you must produce: a Nature column via IFS; an FS line × month grid for a selected department (dropdown in B1) and FY; a "Top line is income, shown positive" presentation; a row-consistency check; and a single "OK/ERRORS" master check. Describe your build sequence, keyboard shortcuts, the formula in the first grid cell and each check formula, and explain how you would demonstrate to the interviewer that the grid is complete.
