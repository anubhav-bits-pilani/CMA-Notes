Subtopic note

SUMIFS for Multi-Department GL Rollups by Group, Cost Centre and Month

Scope: SUMIFS across account group, department, cost centre and month-date ranges for multi-department GL rollups

Why it matters

The monthly MIS of most Indian companies is a grid: FS lines or account groups down the side, months (or departments) across the top, populated from a raw GL or day-book dump. SUMIFS is the workhorse that turns 50,000 voucher lines into that grid without a PivotTable refresh, without manual filtering and without copy-paste. Because it is non-volatile, fast and readable, it is the formula reviewers expect to see in close packs, department-wise cost reports, budget-vs-actual grids and the actuals feed of a forecast model.

Core notes

Syntax and logic

=SUMIFS(sum_range, criteria_range1, criteria1, [criteria_range2, criteria2], …)
  • sum_range comes first (unlike SUMIF, where it is last and optional).
  • Up to 127 range/criteria pairs. All criteria are combined with AND: a row is summed only if every criterion is met.
  • Every criteria_range must be the same size and shape as sum_range; otherwise #VALUE!.
  • Criteria are text strings evaluated like a filter: "Sales", ">=400000", "<>"&"", or a cell reference. Text matching is case-insensitive.
  • Non-numeric cells in sum_range (text, blanks) are ignored — which is why numbers stored as text silently disappear.

Source data shape

Rollups work on a flat, one-row-per-posting table. A typical GL Table GL exported from Tally (Day Book / Ledger Vouchers) or SAP (FBL3N) and cleaned:

Date Voucher Account AccGroup Dept CostCentre Amount
04-Apr-2025 JV/0012 640500 Rent Admin MUM-HO 3,50,000
15-Apr-2025 PUR/0450 510100 Raw material Plant PUN-P1 18,40,000
30-Apr-2025 SAL/0091 410100 Revenue Sales DEL-BR -42,75,000

Use a single signed Amount column (Dr positive, Cr negative) rather than separate Debit and Credit columns; one sum range keeps every formula uniform and lets the TB net to zero.

Building the rollup grid

Layout of the output sheet: account group in column A, department in column B, month-start dates in row 3 (C3, D3, …, formatted mmm-yy).

=SUMIFS(GL[Amount],
        GL[AccGroup], $A5,
        GL[Dept], $B5,
        GL[Date], ">="&C$3,
        GL[Date], "<="&EOMONTH(C$3,0))

Each line of the formula above holds one criteria pair, which is also how you should format long SUMIFS in the formula bar (Alt+Enter between arguments). Reading the mechanics:

  1. Account group criterion picks the FS line.
  2. Department criterion splits by department; add a GL[CostCentre] pair for a cost-centre view.
  3. Date range — the same GL[Date] column is used twice, once with ">=" the month start and once with "<=" the month end. This is the standard way to sum a period; Excel has no "between" operator inside SUMIFS.
  4. The $ placement lets one formula be copied across all months and down all group-department rows (see the mixed-referencing note).

If the dates carry time stamps (SAP posting timestamps, some bank feeds), use "<"&EOMONTH(C$3,0)+1 instead of "<="&EOMONTH(C$3,0) so postings at 15:30 on the last day are not lost.

Rolling up by levels

Rollup need Extra or changed criterion
Department total (all groups) drop the AccGroup pair
Cost centre within department add GL[CostCentre], $C5
All departments except Admin GL[Dept], "<>Admin"
Quarter (Q1 = Apr–Jun) start ">="&C$3, end "<="&EOMONTH(C$3,2)
Year-to-date start fixed at FY start cell, end at selected month end
Range of account codes GL[Account], ">=500000", GL[Account], "<600000"

A blank criterion cell is not "ignore this criterion": a criterion pointing at an empty cell matches only empty cells (in practice it usually returns 0). To make a filter optional, build the criterion as IF(B5="","*",B5) for text fields, or use separate formulas.

Worked illustration

GL extract for April 2025 (signed, ₹):

Date AccGroup Dept Amount
02-Apr Employee cost Sales 6,20,000
10-Apr Employee cost Admin 4,10,000
28-Apr Employee cost Sales 1,15,000
30-Apr Rent Sales 2,00,000
01-May Employee cost Sales 6,40,000

With A5 = "Employee cost", B5 = "Sales" and C3 = 01-Apr-2025, the formula sums rows 1 and 3 = ₹7,35,000. The 01-May row fails the <=30-Apr criterion, the Admin row fails Dept, and the Rent row fails AccGroup.

Controls around the grid

  • Completeness check: grand total of the grid for a month must equal SUMIFS(GL[Amount], GL[Date], ">="&C$3, GL[Date], "<="&EOMONTH(C$3,0)) for the P&L groups — any gap means a group or department is missing from the row headers.
  • Unmapped bucket: include an "Unassigned" department row fed by GL[Dept], "" or a COUNTIFS exception list.
  • Independent check: a PivotTable on the same Table should agree to the rupee.

Excel Table and Power BI angle

Pointing SUMIFS at Table columns (GL[Amount]) means the ranges auto-expand when next month's GL is pasted below. The same logic in Power BI is CALCULATE(SUM(GL[Amount]), …) with the filter coming from the matrix row/column context — the SUMIFS grid is effectively a hand-built DAX matrix.

Edge cases & judgement calls

  • Reversing entries across months. An accrual posted 31 March and reversed 1 April shows in two months; that is correct, but MIS users often expect "net" views — document it.
  • Back-dated postings after close. If the GL dump is re-pasted after a back-dated JV, the closed month changes. Freeze closed months (paste values to a locked "Actuals" tab) or reconcile to the signed-off TB.
  • Text dates. Dates exported as "30-04-2025" text are not numbers and fail date criteria silently. Test COUNT(GL[Date]) against ROWS(GL[Date]).
  • Sign of income. With signed amounts, revenue rolls up negative; flip the sign in the presentation layer (multiply by –1 for credit-natured groups) rather than in the data.
  • Performance. SUMIFS on 2–3 lakh rows × a 40 × 12 grid is fine; beyond about 5 lakh rows, aggregate in Power Query or the Data Model first.

Key takeaways

  • sum_range first, then up to 127 equal-sized criteria pairs combined with AND.
  • Sum a month with two criteria on the same date column: ">="&start and "<="&EOMONTH(start,0).
  • Use a single signed Amount column; flip signs for presentation, not in the data.
  • A criterion pointing at a blank cell matches blanks — it does not switch the filter off.
  • Mixed references (C$3 for month headers, $A5 for row labels) let one formula fill the whole grid.
  • Always prove completeness: grid total equals the GL total for the same period.

Practice Questions

Q1. Department-month grid formula [L1]

A Table GL has columns Date, Account, AccGroup, Dept, CostCentre, Amount (signed). Write the SUMIFS for cell D7 of a grid where A7 holds the account group, B7 the department, C7 the cost centre and D4 the month-start date, so that it copies across 12 months and down 60 rows without editing.

Q2. Quarter and YTD variants [L2]

Using the same layout, the FY starts 01-Apr-2025 (in a named cell FYStart) and the selected month-start is in SelMonth = 01-Nov-2025. Write (a) a quarter-to-date formula for Q3 (Oct–Dec) up to the selected month, and (b) a YTD formula. State the date criteria each one uses.

Q3. Grid does not tie to the GL [L2]

Your November 2025 grid totals ₹4,86,32,500 of expenses, but the GL contains ₹4,91,07,900 of expense-group postings dated November. List four possible causes and the formula you would write to locate each one.

💡 Hint: Think about missing row headers, text dates, time stamps and blank departments.

Q4. Optional department filter [L2]

Build a single formula that returns the expense group total for a selected department in cell H1, but returns the total across all departments when H1 is blank. Explain why simply pointing the Dept criterion at H1 does not work when H1 is blank.

Q5. Rollup design for a 6-plant manufacturer [L3]

A Pune-based auto-components company has 6 plants (cost centres), 4 departments per plant and 85 expense ledgers mapped to 14 MIS groups. Design the GL Table columns, the output grid layout (rows, columns, slicers or dropdowns) and the check cells for a monthly plant-wise cost report that updates when each month's Tally Day Book export is pasted. Justify whether you would use SUMIFS, a PivotTable or Power Pivot at this scale (about 60,000 rows a year).
