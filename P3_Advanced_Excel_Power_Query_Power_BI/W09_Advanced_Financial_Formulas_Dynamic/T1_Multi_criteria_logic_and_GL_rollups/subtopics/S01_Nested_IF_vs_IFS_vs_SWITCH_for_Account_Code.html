Subtopic note

Nested IF vs IFS vs SWITCH for Account-Code Classification

Scope: Nested IF vs IFS vs SWITCH for classifying account-code ranges into Asset / Liability / Income / Expense

Why it matters

Every TB-to-financial-statement build starts by tagging each ledger with its nature: Asset, Liability, Equity, Income or Expense. When the chart of accounts (CoA) is numbered by range — the common SAP/Oracle pattern, and increasingly the pattern Indian mid-market companies impose on Tally ledgers via an alias or code field — that tag can be derived by formula rather than typed. A formula-driven classification column is what lets a rollup survive new ledgers being opened mid-year: the new ledger gets a nature automatically, and anything outside the defined ranges is pushed into a visible "Check" bucket instead of being silently dropped.

In audit and close work the same logic flags misclassified postings (an expense code sitting in a balance-sheet group in Tally), and in FP&A models it drives sign conventions — income and liabilities are credit-natured, so the nature tag decides whether to flip the sign for presentation.

Core notes

The classification problem

Assume a six-digit numeric CoA:

Range Nature Typical Schedule III mapping
100000–199999 Asset PPE, inventories, trade receivables, cash
200000–299999 Liability Borrowings, trade payables, provisions
300000–399999 Equity Equity share capital, other equity
400000–499999 Income Revenue from operations, other income
500000–699999 Expense Cost of materials, employee benefits, finance costs, D&A, other expenses
anything else Check Suspense, typos, codes stored as text

Three formula families can do this: nested IF, IFS and SWITCH.

Nested IF

=IF(A2<200000,"Asset",
  IF(A2<300000,"Liability",
   IF(A2<400000,"Equity",
    IF(A2<500000,"Income",
     IF(A2<700000,"Expense","Check")))))

Mechanics: each IF tests one condition and passes control to the next IF in its value_if_false. Because the tests run top to bottom and stop at the first TRUE, you only need the upper bound of each band, provided the bands are tested in ascending order. Excel allows 64 nesting levels, but readability collapses after four or five.

Weaknesses: closing-bracket counting, the default being buried at the innermost level, and the temptation to write both bounds (AND(A2>=200000,A2<300000)) which doubles the edit points when a range changes. A code below 100000 (say a stray 9999) falls into "Asset" in the formula above — a lower-bound guard is needed if such codes are possible.

IFS

=IFS(A2<100000,"Check",
     A2<200000,"Asset",
     A2<300000,"Liability",
     A2<400000,"Equity",
     A2<500000,"Income",
     A2<700000,"Expense",
     TRUE,"Check")

IFS(test1, value1, test2, value2, …) evaluates pairs left to right and returns the value for the first TRUE test (up to 127 pairs). There is no default argument: if no test is TRUE, IFS returns #N/A. The idiom is to finish with TRUE, "Check" as the catch-all pair. IFS is flat, so adding a band is one extra pair, not one extra nesting level.

SWITCH

SWITCH(expression, value1, result1, …, [default]) compares one expression for exact equality against a list of values. It cannot test < or > directly. Two practitioner patterns make it work for ranges:

  1. Switch on a derived key — the first digit of the code:
=SWITCH(LEFT(A2,1),
  "1","Asset", "2","Liability", "3","Equity",
  "4","Income", "5","Expense", "6","Expense",
  "Check")

LEFT returns text, so the values must be quoted text. Alternatively =SWITCH(INT(A2/100000), 1,"Asset", 2,"Liability", …, "Check") keeps everything numeric.

  1. SWITCH(TRUE, …) — the expression is TRUE and each "value" is a logical test; the first test that equals TRUE wins. This mimics IFS but has a built-in default as the final odd argument.

Without a default, an unmatched SWITCH returns #N/A, just like IFS.

Comparison

Feature Nested IF IFS SWITCH
Range tests (<, >=) Yes Yes Only via SWITCH(TRUE,…) or a derived key
Default/else Innermost value_if_false None — add TRUE,"Check" Optional last argument
Unmatched result Whatever the last IF returns (FALSE if omitted) #N/A #N/A without default
Max conditions 64 levels 127 pairs 126 value/result pairs
Availability All versions Excel 2019 / Microsoft 365 Excel 2019 / Microsoft 365
Readability Poor beyond 4 levels Good Best for exact codes

The better-practice alternative: a band table

For more than five bands, or bands that management may change, the robust design is a small lookup table (From code, Nature) sorted ascending and an approximate lookup: =XLOOKUP(A2, Band[From], Band[Nature], "Check", -1). The thresholds then live in cells, are visible to reviewers, and can be changed without editing formulas. Formula logic (IF/IFS/SWITCH) is fine for stable, structural rules like CoA first digits; table logic is better for anything a business user owns.

Worked illustration

Code Nested IF IFS SWITCH on first digit
145010 (Trade receivables) Asset Asset Asset
230200 (TDS payable) Liability Liability Liability
410100 (Sales – domestic) Income Income Income
640500 (Rent) Expense Expense Expense
910000 (Suspense) Check Check Check
"410100" stored as text Check (text > any number) Check (TRUE catch-all) Income (LEFT works on text)

The last row is the important one: in Excel's comparison order, any text is greater than any number, so "410100"<200000 is FALSE throughout, and the nested IF and IFS fall through to "Check". SWITCH(LEFT(…)) classifies it "correctly" — and so hides the fact that the code is text, which will later break a numeric SUMIFS range criterion. Choose the behaviour you want, and add an explicit ISNUMBER test if codes come from an ERP export.

Edge cases & judgement calls

  • Contra and dual-nature ledgers. A bank OD appears in the asset range in many Tally setups but is a liability when overdrawn. Range logic classifies by code, not balance; balance-sign reclassification (Schedule III requires presenting OD under borrowings) is a separate step.
  • Equity vs liability. Many CoAs lump capital and reserves in the 2-series. Decide whether "Equity" is a separate nature — it matters for the TB check that Assets = Liabilities + Equity.
  • Codes with prefixes ("GL-410100") need VALUE(MID(…)) before numeric tests, or a text-based SWITCH.
  • Boundary errors. Writing <=200000 instead of <200000 pushes 200000 itself into the asset band. Test the exact boundary codes.
  • Version compatibility. IFS and SWITCH show #NAME? in Excel 2016 and earlier; for files circulated to plant or branch accountants on old versions, nested IF or a band table is safer.

Key takeaways

  • Nested IF and IFS both rely on ascending order and the first-TRUE rule, so only the upper bound of each band is needed.
  • IFS has no else: always end with TRUE,"Check" or it returns #N/A for unmatched codes.
  • SWITCH tests exact equality; use it on a derived key (first digit, INT(code/100000)) or as SWITCH(TRUE,…).
  • Text-stored codes compare greater than every number — they fall through range tests but pass through LEFT-based tests.
  • For business-owned thresholds, a band table with approximate XLOOKUP beats any hard-coded formula.
  • Always route unmatched codes to a visible "Check" category and count it.

Practice Questions

Q1. Rewrite a nested IF as IFS [L1]

A Tally export uses five-digit codes: 10000–19999 Assets, 20000–29999 Liabilities, 30000–39999 Income, 40000–49999 Expenses. A colleague wrote =IF(A2<20000,"Assets",IF(A2<30000,"Liabilities",IF(A2<40000,"Income","Expenses"))). Rewrite it as an IFS formula and as a SWITCH formula, both of which return "Check" for codes below 10000 or at/above 50000.

Q2. Diagnosing a classification failure [L2]

In a 1,200-ledger TB, 37 ledgers show "Check" under an IFS-based classification, yet their codes visually look like 410100–499999. The same ledgers show "Income" under a SWITCH on LEFT(code,1). Explain the likely cause, write a formula that counts how many codes in TB[Code] are stored as text, and state which classification result you would trust for the SUMIFS rollup and why.

💡 Hint: Think about how Excel orders text versus numbers in a comparison.

Q3. Boundary testing [L1]

List the exact test codes you would key into a check block to prove that a six-band classification formula (bands starting at 100000, 200000, 300000, 400000, 500000 and 700000 as "Check") handles every boundary correctly. Explain what result each test code should produce.

Q4. Formula vs table design choice [L3]

The FP&A head wants expense codes split further into "Direct", "Employee", "Finance" and "Other" based on ranges (500000–549999, 550000–579999, 580000–589999, 590000–699999), and expects the ranges to change when the CoA is restructured next year. Argue whether you would extend the IFS formula or build a band table, describe the table's columns and sort order, and write the lookup formula.

Q5. Dual-nature ledger [L2]

Ledger 120500 "HDFC Bank CC A/c" has a closing balance of ₹38.4 lakh credit at 31 March 2026. Your range-based classification tags it "Asset". Explain why this is wrong for Schedule III presentation and design an additional formula column that reclassifies bank ledgers with credit balances to "Liability – Short-term borrowings".
