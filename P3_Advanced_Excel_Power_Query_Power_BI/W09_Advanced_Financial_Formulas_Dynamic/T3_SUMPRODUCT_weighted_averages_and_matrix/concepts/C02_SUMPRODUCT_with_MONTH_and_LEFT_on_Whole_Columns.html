Key concept

SUMPRODUCT with MONTH and LEFT on Whole Columns

Concept: =SUMPRODUCT((MONTH(GL[Date])=4)*(LEFT(GL[Account],1)="5")*GL[Amount])

Statement

\[ \text{Result} = \sum_{i \in GL} \mathbf{1}\left[\text{month}(D_i) = 4\right] \times \mathbf{1}\left[\text{first character}(C_i) = \text{"5"}\right] \times A_i \]

where \(D_i\) is the posting date, \(C_i\) the account code, \(A_i\) the signed amount of GL row \(i\), and \(\mathbf{1}[\cdot]\) equals 1 when the condition is TRUE and 0 otherwise. The formula returns the total of all April postings — of any year — to accounts whose code begins with 5.

Explanation

Why SUMIFS cannot do this. SUMIFS criteria ranges must be worksheet ranges; MONTH(GL[Date]) and LEFT(GL[Account],1) are computed arrays, which SUMIFS does not accept. SUMPRODUCT evaluates any array expression.

Step by step.

  1. MONTH(GL[Date]) returns one month number per row; =4 turns it into TRUE/FALSE.
  2. LEFT(GL[Account],1) returns the first character as text — even when the code is a number, because LEFT converts it to text first. Hence the comparison with "5" in quotes; comparing with the number 5 would always be FALSE.
  3. The * operators coerce TRUE/FALSE to 1/0 and multiply: only rows meeting both conditions keep a 1.
  4. Multiplying by GL[Amount] keeps the amount on qualifying rows; SUMPRODUCT adds the single resulting array.

Conditions and traps.

  • Year is ignored. In a multi-year GL, April 2025 and April 2026 both qualify. Add *(YEAR(GL[Date])=2025) or replace the month test with a date range.
  • Blank dates are read as 0 (00-Jan-1900), so MONTH returns 1 — irrelevant for April, but blanks would count as January in a January formula.
  • Text dates that Excel cannot parse make MONTH return #VALUE! and the whole result errors.
  • Text amounts: in this * form, a non-numeric text amount on any row errors the formula; numeric text is coerced. (The comma form would silently treat text as 0.)
  • Codes with leading zeros stored as numbers have lost them; LEFT works on the stored value.
  • Performance: fine for a few check cells; for a 12-month × 30-line grid on lakhs of rows, add helper columns (FMonth, AccSeries) and use SUMIFS.

Microsoft 365. =SUM((MONTH(GL[Date])=4)*(LEFT(GL[Account],1)="5")*GL[Amount]) gives the same result natively.

Illustration

Date Account Amount (₹)
05-Apr-2025 510100 6,20,000
18-Apr-2025 410100 -18,40,000
28-Apr-2025 560200 95,000
02-May-2025 510100 5,80,000
11-Apr-2026 520400 1,10,000

Month test → {1;1;1;0;1}; first-digit test → {1;0;1;1;1}; product → {1;0;1;0;1}; × Amount → {6,20,000; 0; 95,000; 0; 1,10,000}. Result ₹8,25,000 — of which ₹1,10,000 is April 2026. If the report is "April FY26 (2025) expenses", the correct figure is ₹7,15,000.

Connections

The flagship example of the multi-condition boolean-sum subtopic, depending on the coercion subtopic. It is the SUMPRODUCT answer to the topic-1 related item on criteria SUMIFS cannot handle, and its performance trade-off is analysed in the SUMPRODUCT vs SUMIFS subtopic. In DAX (Week 11), the same logic is CALCULATE(SUM(GL[Amount]), MONTH(GL[Date])=4, LEFT(GL[Account],1)="5") or, better, a Date table column.
