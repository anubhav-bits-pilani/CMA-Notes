Key concept

Sorted Unique Account List for a Selected FY

Concept: =SORT(UNIQUE(FILTER(GL[Account], GL[FY]=H1)))

Statement

=SORT(UNIQUE(FILTER(GL[Account], GL[FY]=H1)))

Evaluated inside-out:

  1. FILTER(GL[Account], GL[FY]=H1) — the account code on every GL row whose FY equals the selection in H1 (e.g. "FY26"). Many duplicates.
  2. UNIQUE(…) — each distinct account once, in order of first appearance.
  3. SORT(…) — ascending order (default sort_index 1, sort_order 1).

The result is a vertical spill: the list of accounts that actually had postings in the selected financial year.

Explanation

This three-function nest is the standard way to build a dynamic row axis for a TB, P&L or ledger-scrutiny report. A hard-typed account list goes stale when new ledgers are opened; this list is derived from the data, so a ledger created mid-year appears the moment its first posting lands in the GL Table.

Why the order of nesting matters:

  • FILTER first reduces the data before de-duplication. UNIQUE(FILTER(…)) is correct; FILTER(UNIQUE(GL[Account]), …) fails because the include array (GL[FY]=H1) is the full GL height while the UNIQUE output is much shorter — #VALUE!.
  • SORT last sorts the short distinct list, which is cheaper than sorting the whole GL.

Practical points:

  • Missing if_empty: if H1 holds an FY with no postings (say "FY28"), FILTER returns #CALC!, and SORT/UNIQUE pass the error through. Add "No postings" as the third FILTER argument in production.
  • Numeric vs text codes: if Tally or SAP exported some account codes as text and others as numbers, SORT places numbers before text and UNIQUE treats 40010 and "40010" as different items. Normalise with VALUE or in Power Query.
  • Code vs name: build the axis on codes; fetch names with XLOOKUP(K2#, CoA[Code], CoA[Name]) beside the spill.
  • Statement order: ascending numeric order coincides with Schedule III order only if the chart of accounts was designed that way (e.g. 1xxxxx assets … 5xxxxx expenses). Otherwise sort by a mapping sort key with SORTBY.
  • FY column: the GL needs an FY field. Derive it with the FYEND LAMBDA (c06) or ="FY"&RIGHT(YEAR(Date)+(MONTH(Date)>=4),2) rather than relying on a typed column.

Downstream, the SUMIFS block references the axis as K2# (spill operator), so it resizes with the list.

Illustration

GL Table (extract), H1 = "FY26":

Date FY Account
12-Mar-25 FY25 510200
03-Apr-25 FY26 510200
03-Apr-25 FY26 400100
19-Jun-25 FY26 510200
02-Sep-25 FY26 530450
11-Jan-26 FY26 400100
  • FILTER → 510200, 400100, 510200, 530450, 400100
  • UNIQUE → 510200, 400100, 530450
  • SORT → 400100, 510200, 530450

Changing H1 to "FY25" returns 510200 only. When a new ledger 540900 (CSR expenditure, under Sec 135) gets its first FY26 posting, the list grows to four rows without edits.

Connections

Combines s02 (FILTER), s03 (UNIQUE) and s04 (SORT). The H1 selector is a Data Validation list (w9_t6), and the output feeds the P&L generator in the week's exercise as the UNIQUE FS-line/account axis × EOMONTH headers × SUMIFS. In Power BI the equivalent is VALUES(GL[Account]) filtered by a slicer (Week 11). In audit, the same list against the prior-year list (via a set difference with ISNA(XMATCH(...))) identifies new ledgers that need scrutiny.
