Key concept

Performance Analyzer to DAX Studio Server Timings

Concept: Performance Analyzer → Copy query → DAX Studio Server Timings to separate storage-engine from formula-engine time

Statement

Workflow:

  1. Power BI Desktop > View > Performance Analyzer > Start recording > Refresh visuals.
  2. Expand the slow visual > Copy query (the DAX query the visual sends to the engine).
  3. Open DAX Studio connected to the open Desktop model; paste the query.
  4. Enable Server Timings (and Clear cache then run), run the query.
  5. Read the split:

\[ T_{\text{total}} = T_{\text{FE}} + T_{\text{SE}} \]

where \(T_{\text{SE}}\) is storage-engine time (VertiPaq scans that retrieve and aggregate data, potentially multi-threaded and cached) and \(T_{\text{FE}}\) is formula-engine time (single-threaded evaluation of DAX logic that the storage engine cannot do, such as complex iterations, context transitions and row-by-row conditions). DAX Studio also shows the number of SE queries, SE CPU time, and cache hits.

Explanation

Performance Analyzer tells you which visual is slow and whether the time is in the DAX query or in rendering. Server Timings tells you why the query is slow:

Pattern Likely cause Typical fix
High SE time, few SE queries Large scans: big fact, high-cardinality columns Reduce model (s06), aggregations, filter earlier
High SE time, many SE queries Measure evaluated per row of a large iterator, generating a "callback" or many small scans Rewrite to set-based logic; avoid iterating high-cardinality columns
High FE time, low SE time Complex DAX evaluated row by row in the formula engine (nested IFs inside SUMX, FILTER over whole tables) Use variables, column filters in CALCULATE, pre-compute in Power Query
CallbackDataID in SE query text Storage engine calling back to the formula engine for each row (e.g. IF or DIVIDE inside an iterator) Move the condition outside the iterator or into a column

Practical notes:

  • Clear the cache before each timed run; otherwise warm-cache results look unrealistically fast. Compare cold and warm runs; users experience both.
  • Run several times and take the median.
  • Query Plan (logical/physical) in DAX Studio gives deeper detail when the timings are not enough.
  • The copied query includes the visual's filters (slicers, page filters) — test with realistic selections, e.g. FY2025-26 with all BUs, the CFO's default view.
  • Results from Desktop on a laptop are indicative; the Service under concurrent load may differ.

Illustration

The expense-page matrix (BU × cost centre, measure [Vendor Rank] and [Expense vs Budget %]) takes 3,400 ms in Performance Analyzer (DAX query 3,150 ms, visual display 250 ms). In DAX Studio with cold cache:

Run Total FE SE SE queries
Original 3,120 ms 2,640 ms (85%) 480 ms 1,212
After rewrite 410 ms 95 ms 315 ms 9

The original [Expense vs Budget %] iterated SUMX(GL, IF(RELATED(Budget...)...)) row by row, generating callbacks. Rewriting as DIVIDE([Expense] - [Budget Expense], [Budget Expense]) using two base measures moved the work to the storage engine.

Practice Questions

Q1. Reading timings [L1]

A query shows total 2,400 ms, FE 300 ms, SE 2,100 ms, 4 SE queries, no callbacks. What does this suggest about the cause, and which tool view would you use next?

Q2. Callback diagnosis [L2]

A measure Adj Expense = SUMX(GL, IF(GL[VoucherType] = "Journal", GL[Amount] * 0.98, GL[Amount])) is slow on a 40-million-row GL. Explain why DAX Studio would likely show CallbackDataID, and propose two faster formulations.

💡 Hint: Consider splitting the sum by voucher type with CALCULATE, or computing the adjusted amount in Power Query.

Q3. Performance test protocol [L2]

Write a short test protocol (steps, settings, number of runs, what to record) for measuring the three pages of the Executive Finance Pack before and after tuning, suitable for inclusion in the project documentation.
