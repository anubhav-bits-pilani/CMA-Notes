Key concept

Incremental Refresh Filter on RangeStart and RangeEnd

Concept: Incremental refresh filter: Table.SelectRows(GL, each [PostingDateTime] >= RangeStart and [PostingDateTime] < RangeEnd) (datetime parameters, foldable source)

Statement

let
    Source = Sql.Database("finsql.contoso.local", "FinanceDW"),
    GL     = Source{[Schema = "dbo", Item = "GL_Lines"]}[Data],
    Filtered =
        Table.SelectRows(
            GL,
            each [PostingDateTime] >= RangeStart and [PostingDateTime] < RangeEnd
        )
in
    Filtered
  • RangeStart, RangeEnd — Power Query parameters with these exact (case-sensitive) names and type Date/Time. The Service overwrites their values for each partition at refresh.
  • [PostingDateTime] — a datetime column on the fact.
  • >= on the start and < on the end — half-open interval, so each row belongs to exactly one partition.
  • Foldable source — the filter must translate into the source query (e.g. a SQL WHERE) for each partition to read only its slice.

For a partition \(p\) with bounds \([s_p, e_p)\), the rows loaded are:

\[ R_p = \{\, r \in \text{GL} : s_p \le t_r < e_p \,\} \]

where \(t_r\) is the posting datetime of row \(r\). Because partitions tile time without overlap, \(\sum_p \lvert R_p \rvert = \lvert \text{GL} \rvert\) within the archive window.

Explanation

The filter is what turns an ordinary import query into a partitionable one. After you define the policy (archive 5 years, refresh last 2 months) and publish, the Service creates year/quarter/month partitions, sets RangeStart and RangeEnd for each, and runs the query per partition. Only partitions inside the incremental window are reprocessed on later refreshes.

Conditions and pitfalls:

  • Type. Parameters must be Date/Time. If the column is a date, either filter a datetime column or convert: DateTime.From([PostingDate]) >= RangeStart — but conversions can stop folding on some sources. If the source uses integer keys (20260331), convert the parameter instead with a small function so the column stays native.
  • Both bounds inclusive (<= on the end) double-loads rows exactly at boundaries — e.g. a voucher at 01-04-2026 00:00 lands in March and April partitions, and the TB no longer balances by month (Topic 4 controls catch it).
  • Folding. Check with View Native Query on the filter step. Placing the filter early, directly after navigation, maximises folding; steps such as adding an index column or merging with a local Excel file before the filter break it.
  • Desktop behaviour. Desktop loads only rows between the parameters' current values; set them to a short recent range to keep the PBIX small.
  • Non-foldable sources (CSV folders) still work if you filter the file list by a period derived from the file name, but each partition re-reads folder metadata; acceptable for modest volumes.
  • One filter only. Apply RangeStart/RangeEnd filtering to the fact table(s) that need it; dimensions refresh in full.

Illustration

Policy: archive 6 years, incrementally refresh the last 2 months, refresh date 10 May 2026. Partitions refreshed: April 2026 \([\text{01-04-2026}, \text{01-05-2026})\) and May 2026 \([\text{01-05-2026}, \text{01-06-2026})\). A voucher posted 30-04-2026 23:59 is in April; one posted 01-05-2026 00:00 is in May. The SQL sent for April folds to: WHERE PostingDateTime >= '2026-04-01 00:00:00' AND PostingDateTime < '2026-05-01 00:00:00', reading 0.7 million rows instead of 64 million.

Practice Questions

Q1. Correcting a filter [L1]

A developer writes Table.SelectRows(GL, each [PostingDate] >= RangeStart and [PostingDate] <= RangeEnd), where PostingDate is of type date and the parameters are of type date. List every problem and write the corrected step.

Q2. Integer date key [L2]

The source fact has DateKey (integer, yyyymmdd) but no datetime column. Write an M function that converts a datetime parameter to the key, and the filter step that uses it, so that the filter still folds to SQL.

💡 Hint: Format the datetime as text in the yyyyMMdd pattern and convert to a number.

Q3. Boundary test [L2]

Describe a test, using DAX measures on the published model, that would prove no GL rows are duplicated or lost at partition boundaries after enabling incremental refresh.
