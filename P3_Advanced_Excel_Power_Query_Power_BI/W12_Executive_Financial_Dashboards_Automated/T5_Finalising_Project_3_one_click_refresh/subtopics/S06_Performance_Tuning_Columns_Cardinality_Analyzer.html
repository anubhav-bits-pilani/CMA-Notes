Subtopic note

Performance Tuning: Columns, Cardinality, Analyzer Tools

Scope: Performance tuning: removing unused columns, lowering cardinality, Performance Analyzer, VertiPaq Analyzer in DAX Studio

Why it matters

A CFO will tolerate a slow dashboard once. Visuals that take five seconds to render, a voucher drill-through that spins, or a refresh that runs into the morning review all erode trust in the pack. Most performance problems in finance models are not DAX cleverness problems; they are model-size problems — too many columns, high-cardinality columns that nobody uses, datetime stamps where dates suffice. The tools to diagnose them (Performance Analyzer, DAX Studio and VertiPaq Analyzer) are free and expected knowledge for a Power BI-heavy FP&A or reporting role.

Core notes

How VertiPaq stores data

The import engine (VertiPaq) stores each column separately, compressed with dictionary encoding (each distinct value stored once, rows hold an integer index) and run-length encoding. Consequences:

  • Column count matters: every column costs memory, even if no visual uses it.
  • Cardinality (number of distinct values) drives dictionary size and compression. A Narration text column with a different value on every row is very expensive; a VoucherType with eight values is nearly free.
  • Sort order affects run-length compression; the engine chooses it, but low-cardinality columns compress best.

1. Removing unused columns

Remove columns in Power Query (Choose Columns), not by hiding them in the model. Candidates in a GL extract: CreatedBy, AlteredOn, GUID, MasterID, duplicated descriptive columns (ledger name in GL when CoA has it), and source-system audit fields. Keep only keys, dates, amounts and the attributes the report uses. Narration is often needed for the voucher drill-through; keep it but consider truncating to 100 characters.

Rule of thumb: each fact column must answer "which visual, measure, relationship or control uses this?".

2. Lowering cardinality

Technique Example
Split datetime into date and time (or drop time) PostingDateTime → PostingDate (≈ 2,000 distinct values over 5 years instead of millions)
Round or fix decimals Amounts as Fixed decimal (Currency.Type, four decimal places) instead of floating decimal
Integer surrogate keys Replace text AccountCode "GL-4105-ADV" with an integer key in both GL and CoA
Move descriptive attributes to dimensions Vendor name in Vendor table, not repeated on each GL line
Disable Auto date/time Options > Data load > untick Auto date/time — removes a hidden date table per date column
Remove or bucket IDs Drop LineGUID; keep VoucherNo only if drill-through needs it
Pre-aggregate where detail is unnecessary Budget at Month × Ledger × Cost centre, not daily

Also avoid calculated columns on large facts when Power Query can create the column (better compression, no storage of intermediate results); and avoid bidirectional relationships and many-to-many where not needed, which slow queries rather than storage.

3. Performance Analyzer (in Desktop)

View > Performance Analyzer > Start recording > Refresh visuals. For each visual it lists:

  • DAX query — time for the engine to return results;
  • Visual display — rendering time in the browser/Desktop;
  • Other — waiting for other visuals or background work.

High DAX query time points to model or measure issues; high visual display time points to too many data points (a table of 50,000 voucher rows, a scatter with thousands of points). Use "Copy query" to take the DAX into DAX Studio (concept c05). Test with realistic slicer selections and clear the cache between tests (in Desktop, reopening the file or using the "Clear cache" feature in DAX Studio).

4. VertiPaq Analyzer in DAX Studio

DAX Studio (free, connects to an open Desktop model or an XMLA endpoint) > Advanced > View Metrics runs VertiPaq Analyzer. Key views:

  • Tables — total size, row count per table;
  • Columns — cardinality, total size, dictionary size, data size, percentage of database;
  • Relationships — referential-integrity violations (missing keys — useful as a completeness cross-check of Topic 4's unmapped-ledger control);
  • Partitions — useful with incremental refresh.

Sort columns by total size; the top five are usually the whole story. Metrics can be exported as a .vpax file to share or compare before/after.

Illustration

A Delhi NCR distribution company's model is 1.8 GB and refresh takes 70 minutes. VertiPaq Analyzer shows:

Column Cardinality Size % of model
GL[PostingDateTime] 38,400,000 610 MB 34%
GL[LineGUID] 42,100,000 540 MB 30%
GL[Narration] 18,900,000 310 MB 17%
GL[Amount] (decimal) 6,200,000 120 MB 7%
Others — 220 MB 12%

Actions: replace PostingDateTime with a date (cardinality ≈ 2,200), drop LineGUID, truncate narration to 80 characters, convert Amount to fixed decimal, disable Auto date/time. Result: 520 MB, refresh 24 minutes, P&L page query times from 2.8 s to 0.4 s.

Measure-level tuning (brief)

After the model is lean, tune slow measures: use variables to avoid repeated evaluation; prefer filter arguments on columns (CoA[FSLine] = "Revenue") over FILTER(ALL(GL), …) on the fact; avoid iterating the fact table with SUMX where SUM works; avoid IFERROR and heavy FORMAT in measures used in large tables; and pre-compute static classifications in Power Query.

Edge cases & judgement calls

  • Narration vs performance. Auditors and controllers want narration on the drill-through page. Keep it, but only in the fact used by drill-through, and make the detail page filter-required (Topic 2 pitfall on unfiltered voucher tables).
  • Fixed decimal precision stores four decimal places; fine for ₹ amounts, not for FX rates needing more precision.
  • Integer keys require mapping in both fact and dimension; keep the natural code as an attribute in the dimension for display and drill-through.
  • DirectQuery models are tuned differently (source indexes, aggregations); these notes assume Import.
  • Desktop vs Service. Desktop timings on a powerful laptop understate Service times under concurrency; test in the Service too.
  • Over-tuning. Don't drop a column a control depends on (e.g. Source.Name for per-file controls) — summarise it to a separate control table instead.

Key takeaways

  • VertiPaq compresses by column; size is driven by column count and cardinality.
  • Remove unused columns in Power Query, split or drop datetime, use fixed decimals and integer keys, and turn off Auto date/time.
  • Performance Analyzer separates DAX query time from visual display time per visual.
  • VertiPaq Analyzer in DAX Studio ranks columns by size and cardinality; the top few usually explain the problem.
  • Fix the model before the measures; then tune measures with variables and column filters.
  • Keep columns needed by drill-through and controls, but in their leanest form.

Practice Questions

Q1. Ranking reduction actions [L1]

A GL fact has these columns: VoucherNo (2.1m distinct), LineGUID (9.4m), PostingDateTime (8.7m), AccountCode (text, 900), CostCentre (text, 140), Narration (6.0m), Amount (decimal, 3.1m), CreatedBy (60). The table has 9.4 million rows. Rank the columns by likely size and propose an action for each.

💡 Hint: Think in terms of distinct values per column and whether any report element uses it.

Q2. Reading Performance Analyzer [L2]

On the expense page, Performance Analyzer shows: matrix by BU and cost centre — DAX query 2,950 ms, visual display 180 ms; voucher table — DAX query 410 ms, visual display 3,600 ms; card — DAX query 25 ms, other 3,100 ms. Interpret each and propose the next diagnostic or fix.

Q3. Before-and-after evidence [L2]

Describe how you would document the performance improvement of your model for the Project 3 submission, including the tools, the metrics captured before and after, and the file formats.

Q4. Trade-off case [L3]

The controller insists on keeping full narration, voucher-level GUIDs and the creation timestamp for forensic analysis, while the CFO wants sub-second executive pages. Propose a model design (one or two models, aggregation tables, column choices) that satisfies both, and explain the refresh and governance implications.
