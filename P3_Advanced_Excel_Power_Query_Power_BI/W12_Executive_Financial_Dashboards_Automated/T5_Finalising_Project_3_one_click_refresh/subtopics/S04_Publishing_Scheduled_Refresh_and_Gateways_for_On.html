Publishing, Scheduled Refresh and Gateways for On-Prem and Tally

Scope: Publishing to the Power BI Service: semantic model, scheduled refresh, standard vs personal gateway for on-prem/Tally

Why it matters

A pack that refreshes only on the developer's laptop is not a reporting system. Publishing to the Power BI Service separates the semantic model (data + measures, refreshed on a schedule) from the reports and Excel workbooks that consume it, so the CFO sees current numbers every morning without anyone opening Desktop. Whether that works depends on credentials, gateway setup for anything on-premises (Tally servers, network drives, SQL Server in the office), and refresh limits. These are exactly the details interviewers probe with "how does your dashboard refresh?".

Core notes

Publishing: what goes where

Publishing a PBIX from Desktop (Home > Publish, choose workspace) creates two items in the workspace:

  • a semantic model (formerly "dataset") — tables, relationships, measures, RLS roles, Power Query definitions and the imported data;
  • a report bound to it.

Subsequent reports can be "thin": built in Desktop with Get Data > Power BI semantic models (live connection), they contain only visuals. This lets several reports and the Excel cube pack share one model, which is the single source of truth for the pack. Republishing the same PBIX replaces both items (with a warning); keeping the model PBIX and report PBIXs separate avoids accidental overwrites of a shared model.

File size limits: the published PBIX must be within the workspace limit (1 GB on Pro/shared capacity; larger on Premium/Fabric with large semantic model storage format). Data volumes beyond this need incremental refresh (s05), model reduction (s06) or Fabric.

Configuring the semantic model in the Service

Semantic model > Settings:

  1. Data source credentials — for each source, set the authentication method (OAuth2 for SharePoint/OneDrive; Windows or Basic for gateway sources) and the privacy level (Organizational for internal finance sources).
  2. Gateway and cloud connections — map each on-premises source to a gateway data source; cloud sources need no gateway.
  3. Parameters — edit values such as SiteUrl (s02).
  4. Scheduled refresh — on/off, frequency (daily/weekly), time zone (choose "(UTC+05:30) Chennai, Kolkata, Mumbai, New Delhi"), times, and failure notification recipients (owner plus additional contacts).
  5. Refresh history — status, duration, errors.

Refresh limits (concept c02): up to 8 scheduled refreshes per day on shared capacity with Pro, up to 48 on Premium/Fabric capacity. Refresh time-outs are 2 hours on shared capacity and 5 hours on Premium per refresh. After repeated consecutive failures the Service disables the schedule, and models with no report views for two months have scheduled refresh paused — both reasons why an owner must watch failure emails (topic pitfall).

Schedule the refresh after the source files are final: if branch files arrive by 05:00 IST, schedule 06:30, with a second slot at 13:00 for late adjustments during close week.

Gateways

An on-premises data gateway is a Windows service that brokers queries from the Service to sources the cloud cannot reach directly (on-prem databases, file shares, local folders, ODBC sources). Two modes:

Feature Standard mode Personal mode
Users Shared; managed by gateway admins; data sources shared with users One user only
Refresh types Scheduled refresh, DirectQuery, live connection to SSAS, dataflows, paginated reports Import scheduled refresh only
Runs as Windows service (service account) App/service under the user's account
Recovery and clustering Supports clusters for high availability No
Governance Centrally visible, data sources and permissions managed Tied to an individual; hard to audit
Fit for Project 3 Production finance pack Personal prototypes only

Install the standard gateway on an always-on server (not a laptop), close to the data source, with a recovery key stored securely. Add the source under Manage connections and gateways, then map it in the model settings. Name an owner and a backup admin.

Tally Prime with a gateway

Tally exposes data through ODBC (Tally ODBC driver, default port 9000) and XML over HTTP on the same port. For Power BI:

  1. Tally must be running with the company loaded and ODBC enabled (F1 Help > Settings > Connectivity, or the Tally.ini setting), on a machine reachable by the gateway.
  2. Create an ODBC DSN for Tally on the gateway machine (the 32/64-bit driver must match the gateway's architecture — a common failure).
  3. In Desktop, Get Data > ODBC with the same DSN; query ledger, voucher or TB collections.
  4. In the Service, add an ODBC data source to the standard gateway with the identical connection string, and map it.

Practical risks: Tally closed overnight, a different company loaded, licence mode issues, and performance on large voucher collections. Many teams therefore schedule a Tally export (XML/CSV/Excel) to SharePoint and refresh in the cloud without a gateway (s01, c03). Third-party Tally connectors also exist; evaluate them for support and security.

Cloud vs on-prem in one model

A model combining SharePoint (cloud) and an on-prem SQL server must route the on-prem source through a gateway; the SharePoint source can refresh as a cloud connection if the tenant setting "Allow user's cloud data sources to refresh through this gateway cluster" is configured appropriately, or via its own cloud credentials. Privacy levels must be set for both; combining sources with different privacy levels can raise firewall errors only in the Service.

Illustration

A Kolkata FMCG company publishes Finance Pack.pbix to Finance – Prod. Sources: SharePoint /GL (cloud, OAuth), /Budget (cloud), and the HR cost table on an on-prem SQL Server (HRSQL01, via standard gateway GW-KOL-01). Scheduled refresh: 06:30 and 13:00 IST. On 3 April the 06:30 refresh fails: the gateway server was patched and restarted; the failure email to the owner prompts a manual refresh at 07:10 that succeeds. Refresh history records both.

Edge cases & judgement calls

  • Personal gateway in production. Works until the developer's account is disabled or the laptop sleeps — then the CFO pack stops. Avoid.
  • Credential expiry. OAuth tokens and passwords expire; use a service account where policy allows, and document renewal.
  • On-demand refresh limits. How manual "Refresh now" and REST API refreshes count against the 8-per-day shared capacity limit has been documented differently over time; check current Microsoft documentation before planning on extra manual refreshes during close. XMLA-based refreshes on Premium/Fabric are not bound by the scheduler's limit.
  • DirectQuery and live connections need no scheduled import refresh but require the gateway always on and add query latency; for month-end finance packs, Import is usually right.
  • Time-zone of the schedule is separate from M refresh stamps; set both to IST.
  • Dataflow dependency. If staging runs in a dataflow, the model refresh must be scheduled after the dataflow ends, or chained with Power Automate.

Key takeaways

  • Publishing creates a semantic model and a report; thin reports and Excel packs connect to the one model.
  • Configure credentials, privacy levels, gateway mapping, parameters and the refresh schedule (in IST) per model.
  • Pro allows 8 scheduled refreshes a day, Premium/Fabric 48; repeated failures and inactivity pause schedules.
  • Use a standard-mode gateway on an always-on server for on-prem sources; personal mode is for prototypes.
  • Tally via ODBC needs Tally running and a matching DSN on the gateway; scheduled exports to SharePoint are often more robust.
  • Name owners for the gateway, credentials and refresh failure emails.

Practice Questions

Q1. Choosing a gateway mode [L1]

A developer used a personal gateway on her laptop to refresh a pack reading a network share. Explain three risks of this setup for a production CFO pack and specify the replacement.

Q2. Tally refresh failing in the Service [L2]

Desktop refresh from Tally ODBC (DSN TallyODBC64_9000) works; the Service refresh through the standard gateway fails with "data source not found". List the configuration checks on the gateway machine and in the Service, in the order you would perform them.

💡 Hint: Compare the exact connection string and driver architecture in both environments.

Q3. Designing a refresh schedule [L2]

Branch files land in SharePoint by 05:00 IST on working days; late adjustment files arrive until 15:00 on the first five working days of each month. The workspace is on Pro. Design the scheduled refresh times, explain how you stay within limits, and specify failure notification recipients.

Q4. Hybrid source architecture [L3]

A company's pack needs SAP S/4HANA cloud extracts (exported to SharePoint), an on-prem SQL Server for payroll costs and Tally for one subsidiary. Design the publishing and refresh architecture (gateway, credentials, privacy levels, schedules), and identify three single points of failure and their mitigations.

Q5. Interview: semantic model vs report [L1]

Explain the difference between a semantic model and a report in the Power BI Service and why you publish the model separately from reports in a shared finance pack.
