Incremental Refresh with RangeStart and RangeEnd for GL History

Scope: Incremental refresh with RangeStart/RangeEnd for multi-year GL history

Why it matters

A GL with five years of voucher lines for a mid-size Indian group can easily reach 50–200 million rows. A full refresh reloads all of it every morning, although only the current month (and, during close, the previous one) changes. That wastes the refresh window, risks time-outs (2 hours on shared capacity), and burdens the source. Incremental refresh partitions the GL table by date so the Service reloads only recent partitions and keeps historical ones untouched. It is the standard answer to "how would your pack scale to ten years of GL?".

Core notes

Mechanics

  1. Create two parameters in Power Query, named exactly RangeStart and RangeEnd (case-sensitive), of type Date/Time, with current values bracketing a small range for Desktop (e.g. 01-04-2025 00:00 to 01-05-2025 00:00).
  2. Filter the fact on a date/time column: Table.SelectRows(GL, each [PostingDateTime] >= RangeStart and [PostingDateTime] < RangeEnd) (concept c01). One boundary inclusive, the other exclusive, so a row on a partition boundary is loaded exactly once.
  3. Define the policy in Desktop (right-click the table > Incremental refresh): - Archive data starting X years/months before refresh date (e.g. 5 years) — partitions kept but not refreshed; - Incrementally refresh data starting Y days/months before refresh date (e.g. 2 months) — partitions reloaded at each refresh; - optional: Get the latest data in real time with DirectQuery (hybrid table; Premium/Fabric); - optional: Only refresh complete days/months; - optional: Detect data changes using a column such as LastModified — a partition in the refresh window is reloaded only if the maximum of that column changed.
  4. Publish. The first Service refresh creates partitions (year, quarter, month granularity) and loads all history; later refreshes touch only the incremental window.

In Desktop, only the rows within the current RangeStart–RangeEnd values are loaded, keeping the PBIX small.

Incremental refresh is available with Pro as well as Premium/PPU/Fabric; real-time hybrid tables and some advanced options need Premium/Fabric.

Why folding matters

The filter must fold to the source, i.e. be translated into a source query (in SQL, WHERE PostingDateTime >= @start AND PostingDateTime < @end). Then each partition refresh fetches only its rows. If the filter does not fold, the mashup engine reads the whole source for every partition, which can make incremental refresh slower than a full refresh. Check folding with right-click step > View Native Query (enabled when folding occurs) or the query-folding indicators in Power Query Online.

Sources that fold: SQL Server, Azure SQL, Synapse, Snowflake, many ODBC/OData sources (partially), Fabric Lakehouse/Warehouse SQL endpoints. Sources that do not: CSV, Excel, SharePoint folders, web pages.

Incremental refresh over a folder of files

A month-per-file SharePoint folder does not fold, but you can still benefit:

  • filter the file list (not the rows) on a date derived from the file name or Date created, using RangeStart and RangeEnd, so each partition opens only the files for its period;
  • ensure each file belongs to exactly one partition (a file dated by its name 2026-03 maps to 01-03-2026);
  • beware that Date modified changes when a file is corrected, which can move a file between partitions if used as the filter — prefer the period encoded in the file name, converted to a datetime.

Microsoft documents this pattern as supported but not optimal; for large history, land files in a Lakehouse or SQL staging table that folds.

Datetime parameters and date keys

The parameters must be Date/Time even if the column is a date. Options:

  • If the GL column is a date, convert it to datetime in the filter: DateTime.From([PostingDate]) >= RangeStart. This may break folding on some sources; better to filter on a native datetime column.
  • If the source has an integer date key (20260331), write a function converting RangeStart to a key: Number.From(DateTime.ToText(RangeStart, "yyyyMMdd")) and filter [DateKey] >= fxKey(RangeStart); this folds on SQL sources.

Choosing the policy for a finance GL

Choice Typical setting Reason
Archive period 5–8 years Trend analysis; Sec 128(5) requires books for 8 FYs (retention is the ERP's job, but analytics often want comparable history)
Incremental window 2–3 months Current month plus prior month(s) receiving close adjustments and audit entries
Complete periods only Off for finance You want the current, partial month
Detect data changes On if a reliable LastModified column exists Avoids reloading unchanged months

Post-close adjustments to older periods (e.g. an audit adjustment to Q4 posted in May) fall outside a two-month window; either widen the window during audit, or run a targeted partition refresh via the XMLA endpoint (Premium) or a full refresh.

Illustration

GL with 72 million rows for FY2019-20 to FY2025-26 on an Azure SQL source. Full refresh: 54 minutes. Policy: archive 7 years, refresh last 2 months, detect changes on LastModified. After the initial load, the daily refresh loads about 1.4 million rows (April and May 2026) in 3 minutes; the 6:30 IST schedule completes before the CFO's 09:00 review.

Edge cases & judgement calls

  • No PBIX download. After incremental refresh is applied in the Service, the model can no longer be downloaded as a PBIX; changes need PBIP/Git plus deployment, or XMLA tools (Tabular Editor). Plan change control (Topic 4 s07).
  • Republishing a model with a changed policy may trigger re-partitioning and a full reload.
  • Boundary errors. Using <= on both sides duplicates boundary rows; using a date column with a datetime parameter without conversion can drop the last day.
  • Time zone. RangeStart/RangeEnd are evaluated in UTC in the Service unless the policy's refresh time zone is set; for daily partitions, an IST/UTC mismatch can shift a partition boundary by a day.
  • Dimension tables should not be incremental; refresh them fully.
  • Controls with incremental refresh. Per-file and row-count controls (Topic 4) cover only reloaded partitions; keep model-wide DAX controls (Dr = Cr by month) to test history too.

Key takeaways

  • Incremental refresh partitions a fact table by date and reloads only recent partitions.
  • Parameters must be named RangeStart and RangeEnd, typed Date/Time, with one inclusive and one exclusive bound.
  • The filter must fold to the source for real gains; folders of CSVs do not fold.
  • For finance, archive several years, refresh 2–3 months, and widen the window during audit adjustments.
  • Once applied, the model cannot be downloaded as PBIX; plan change management accordingly.
  • Keep model-wide controls because file-level controls only see refreshed partitions.

Practice Questions

Q1. Writing the filter [L1]

A GL table has a PostingDate column of type date and a CreatedAt column of type datetime. Write the incremental refresh filter step using RangeStart and RangeEnd, explain which column you would use and why, and state the parameter types.

Q2. Designing the policy [L2]

A company with GL history from FY2018-19 posts audit adjustments to the prior FY until 31 May each year. Daily refresh must complete within 30 minutes. Propose the archive and incremental windows and the change-detection setting, and describe what you would do on 15 May when an audit entry is posted to February.

💡 Hint: Consider temporarily widening the window versus refreshing a specific partition.

Q3. Folding check [L2]

After configuring incremental refresh on a SQL source, the first Service refresh takes 3 hours instead of 50 minutes for a full refresh. List the likely causes and how you would confirm whether the filter folds.

Q4. Folder-based incremental refresh [L3]

Your source is a SharePoint folder with one CSV per branch per month for six years (864 files). Design an incremental refresh approach (which column to filter, how to derive it, partition mapping), and argue whether it is worth it compared with moving the files into a Lakehouse.
