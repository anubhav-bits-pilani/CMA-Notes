Subtopic note

Parameters for Folder Path, As-of Date, FY Start and Environment

Scope: Parameters for folder path, as-of date and FY start; switching between Dev and Prod sources

Why it matters

Hard-coded values are the enemy of one-click refresh. A folder URL typed into five queries, an as-of date buried in a filter step, and an April FY start written into the Date table formula all mean that moving the pack to a new company, a new year or a production site requires editing M code — which is where errors and broken refreshes come from. Power Query parameters make these values explicit, editable without opening the query, and swappable per environment by deployment rules. For an FP&A team, this is what turns a one-off build into a template (s07).

Core notes

Creating parameters

Home > Manage Parameters > New. Each parameter has a name, type, suggested values (Any, List, Query) and a current value. Required, well-typed parameters are best practice. For the pack:

Parameter Type Example Used by
SiteUrl Text https://contoso.sharepoint.com/sites/Finance All SharePoint source queries
GLFolderPath Text https://contoso.sharepoint.com/sites/Finance/Shared Documents/GL/ GL file filter
AsOfDate Date 31-03-2026 Filters, last closed month, control measures
FYStartMonth Decimal/Whole number 4 Date table FY columns
Environment Text (List: DEV, TEST, PROD) PROD Banner text, source selection
RangeStart, RangeEnd Date/Time — Incremental refresh (s05)

Parameters are queries returning a value; they appear in the model only if loaded (usually keep them unloaded, except AsOfDate and Environment, which you may load to a one-row table for DAX use).

Folder path parameter

let
    Source  = SharePoint.Files(SiteUrl, [ApiVersion = 15]),
    GLFiles = Table.SelectRows(Source, each [Folder Path] = GLFolderPath and [Extension] = ".csv")
in
    GLFiles

Using the parameter directly as the connector argument keeps the data source static from the Service's point of view: Power BI can determine at publish time which site it must authenticate against. If you instead build the URL from values computed in another query (e.g. reading the site name from a config file), the Service may reject the model with a "dynamic data source" error and refuse scheduled refresh. Parameters and simple text concatenation of parameters are fine; query-derived source paths are not.

As-of date parameter

AsOfDate defines the reporting period, independent of today's date. Uses:

  • filter out future-dated postings: Table.SelectRows(GL, each [PostingDate] <= AsOfDate);
  • define "last closed month" for completeness checks and default page titles;
  • drive DAX: load it to a table Settings and create As Of = MAX(Settings[AsOfDate]), then Is Closed Period = MAX('Date'[Date]) <= [As Of].

This makes reruns reproducible: setting AsOfDate to 31-12-2025 regenerates the Q3 pack as presented, which is useful when the auditor asks to re-perform. Do not use DateTime.LocalNow() for this; "today" changes and differs between Desktop and Service (UTC).

FY start parameter

Indian companies use April–March, but subsidiaries of foreign groups often report January–December for group purposes. A parameter feeding the Date table makes the model reusable:

FY = if Date.Month([Date]) >= FYStartMonth
     then "FY" & Text.From(Date.Year([Date])) & "-" & Text.End(Text.From(Date.Year([Date]) + 1), 2)
     else "FY" & Text.From(Date.Year([Date]) - 1) & "-" & Text.End(Text.From(Date.Year([Date])), 2),
FiscalMonthNo = Number.Mod(Date.Month([Date]) - FYStartMonth, 12) + 1

For FYStartMonth = 4, 15 May 2025 gives FY2025-26 and fiscal month 2. (For a January start the FY label logic should be simplified to the calendar year; handle this explicitly.) DAX time intelligence must be consistent: TOTALYTD with year-end "31/3", or better, fiscal columns in the Date table and measures that use them.

Switching Dev and Prod sources

Three mechanisms, from simplest to most governed:

  1. Edit parameters in Desktop (Transform data > Edit parameters) and republish. Simple, error-prone.
  2. Edit parameters in the Service — semantic model settings > Parameters; change SiteUrl from the Dev to the Prod site, then refresh (credentials for the new site must be set). No republish needed.
  3. Deployment pipeline rules (Premium/PPU/Fabric) — parameter rules per stage set SiteUrl and Environment automatically when content is deployed from Dev to Test to Prod (Topic 4 s07).

Display the environment on every page with a measure: IF([Env] <> "PROD", "TEST DATA – " & [Env], "") in a red banner, so nobody mistakes a Test pack for the real one.

Illustration

A group with two companies reuses one template:

Parameter Company A (India) Company B (Singapore sub)
SiteUrl .../sites/FinanceIN .../sites/FinanceSG
FYStartMonth 4 1
AsOfDate 31-03-2026 31-12-2025

Opening the .pbit template prompts for these values; the same queries, model and measures produce both packs.

Edge cases & judgement calls

  • Parameter types. A Text parameter holding a date breaks comparisons; type parameters correctly. Incremental refresh requires RangeStart/RangeEnd to be Date/Time exactly.
  • Trailing slashes and case in folder paths cause silent empty results; compare with Text.Lower and standardise.
  • Credentials per source. Switching SiteUrl to a new site means a new data source in the Service requiring its own OAuth credentials.
  • Excel parameters. In Excel Power Query, a common pattern reads parameters from a named range (Excel.CurrentWorkbook(){[Name="pFolder"]}[Content]{0}[Column1]) so users change a cell; this does not apply to Service refresh.
  • Privacy levels. Reading a parameter from an Excel table and combining it with a SharePoint source can trigger Formula.Firewall errors (see topic pitfalls); native parameters avoid this.
  • As-of vs refresh. The as-of date controls which data is reported, not when refresh runs; keep both visible.

Key takeaways

  • Parameterise every value that changes between companies, environments or periods: site/folder, as-of date, FY start, environment.
  • Use parameters directly in connector arguments to keep data sources static for Service refresh.
  • An as-of date makes packs reproducible and filters future-dated entries.
  • A FY-start parameter in the Date table makes the model reusable across April and January year-ends.
  • Switch Dev/Prod via Service parameter settings or, better, deployment-pipeline parameter rules.
  • Show a visible environment banner on non-production packs.

Practice Questions

Q1. Parameterising a hard-coded query [L1]

Rewrite this query using parameters for the site and folder: SharePoint.Files("https://contoso.sharepoint.com/sites/FinanceDev", [ApiVersion = 15]) followed by a filter on [Folder Path] = "https://contoso.sharepoint.com/sites/FinanceDev/Shared Documents/GL/". List the parameters you create with their types.

Q2. FY columns for two year-ends [L2]

Write M expressions for FY label, fiscal month number and fiscal quarter that work for FYStartMonth = 4 (April) and FYStartMonth = 1 (January). State the outputs for 15-Feb-2026 under each setting.

💡 Hint: Use Number.Mod for month and quarter, and branch the label logic when the start month is 1.

Q3. Dynamic data source error [L2]

A developer reads the SharePoint site URL from a Config.xlsx table and passes it to SharePoint.Files. Desktop refresh works; after publishing, the Service says the model cannot be refreshed because it uses a dynamic data source. Explain the cause and give two fixes.

Q4. Reproducing the Q3 pack [L3]

The auditor asks you to regenerate the Q3 FY2025-26 pack exactly as presented to the board on 28 January 2026, although the model now holds data to 31 March 2026 and two ledgers have since been remapped. Explain which parameters, data and versioned artefacts you would need, and the limits of what parameters alone can reproduce.
