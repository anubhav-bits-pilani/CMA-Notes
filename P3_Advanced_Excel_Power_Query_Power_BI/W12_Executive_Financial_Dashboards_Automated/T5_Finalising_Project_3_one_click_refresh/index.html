Roadmap topic: Finalizing Project 3: End-to-end automated Excel + Power Query + Power BI reporting system ready for one-click refresh

Overview

This topic converts the pieces built over Weeks 10–12 — folder pipelines, the star-schema model and measure library, the three-page executive pack, the Excel cube board pack and the control page — into a system that runs without its builder. The test is the Week 12 Saturday validation: drop a new month's raw CSV into the source folder, trigger one refresh, and show that every measure, visual, cube formula and control updates cleanly. Passing it requires decisions about architecture, parameters, refresh mechanics, publishing and gateways, scale, performance, packaging and distribution.

For FP&A and reporting roles in India, this is where many candidates' portfolios fall short: dashboards that look good in Desktop but break in the Service because of a local file path, a privacy-level conflict or a personal gateway. Being able to explain lineage from SharePoint to the CFO's phone, why the refresh stamp is in IST, how incremental refresh keeps seven years of GL manageable, and how the Excel board pack reads the same certified model is the practical evidence employers look for when they ask for "Power BI and automation" alongside "month-end MIS".

The learning sequence follows the data. Start with the end-to-end architecture (s01) and parameters (s02) that make sources and periods configurable. Then the two refresh paths: Excel orchestration (s03) and publishing with scheduled refresh and gateways (s04). Scale with incremental refresh (s05) and performance tuning (s06). Finish with packaging (s07) and distribution (s08). Concepts c01–c05 are the exact M filter, the refresh limits, the SharePoint connector, the one-click macro or flow, and the DAX Studio diagnostic workflow.

Related concepts to study

Feeding the 3-statement model

→ Week 13–16: feeding model actuals into the 3-statement model

The certified semantic model becomes the actuals source for the 3-statement model in Weeks 13–16. Rather than pasting TB exports into the model's actuals tab, connect the Excel model to the semantic model with cube formulas or a Power Query query against the model (Analyze in Excel), pulling FS-line actuals by month in Schedule III structure. The historical columns then refresh with the pack, and the 3-statement model's balance check inherits the BS check of Topic 4. Design the FS-line keys and sign conventions now so that P&L, BS and cash-flow lines map one-to-one into the model's line items, and keep the as-of date parameter aligned with the model's last actual month.

Monthly MIS and rolling forecast

→ Week 17–20: monthly MIS cycle and rolling-forecast refresh

The one-click pack is the engine of the monthly MIS cycle in Weeks 17–20: close on working day 3, refresh and controls on day 4, variance commentary on day 5, board pack on day 7. The same architecture extends to rolling forecasts: add a /Forecast/ folder with versioned forecast files (e.g. RF_2026-05_v2.xlsx), a Scenario or Version dimension, and measures comparing Actual, Budget and latest forecast. Parameters (as-of date) drive the actual/forecast split month. Incremental refresh is usually unnecessary for forecasts (small), but version control and naming conventions matter even more because forecasts are revised.

Capstone and interview walk-through

→ Week 23–24: capstone and walking interviewers through Project 3

In Weeks 23–24 you present Project 3 as a portfolio piece. Prepare a 5-minute walk-through: the business question, the architecture diagram (s01), a live refresh with a new month file, the control page showing every check passing, a drill from an EBITDA variance to vouchers, the Excel board pack updating from the same model, and the governance (RLS, certification, Git). Bring the .pbit template with synthetic data and the documentation pack (s07). Expect follow-ups on gateways, incremental refresh, refresh limits, and how you would scale or hand over — the topics of this week.

Microsoft Fabric for scale

Microsoft Fabric (Dataflows Gen2, Lakehouse, Direct Lake) as the path to larger scale

When a folder-of-CSVs pipeline outgrows Power BI import refresh, Microsoft Fabric provides the next layer. Dataflows Gen2 run Power Query online and write output to a destination such as a Lakehouse; the Lakehouse stores data as Delta/Parquet tables in OneLake; notebooks or pipelines can automate ingestion. Semantic models in Direct Lake mode read the Delta tables directly without a scheduled import refresh, combining import-like speed with near-real-time freshness (with fallbacks to DirectQuery in some conditions). Fabric requires an F capacity (or trial); the skills — Power Query, star schemas, DAX measures — carry over unchanged, which is why this week's design is Fabric-ready.

PBIP and Git

Power BI Project (PBIP) format with Git for version control and diffing

Saving the pack as a PBIP stores the semantic model (TMDL or model.bim) and report definition as text files that Git can version and diff. For Project 3, initialise a repository, commit the PBIP with a .gitignore that excludes the local data cache, and tag releases (v1.0 at submission). Pull-request reviews show measure and query changes line by line, which supports the change-control discipline of Topic 4 s07. Fabric workspaces can sync directly with Azure DevOps or GitHub repositories, so main can be the deployed version. Keep CSV mapping files and sample data in the repo too; never commit credentials.

Common pitfalls

Local file paths

Local file paths in queries, which stop Service refresh unless a gateway is set up

The pack is built on a laptop with Folder.Files("C:\Users\…\OneDrive – Contoso\GL") or a mapped network drive. Desktop refresh works, so the problem stays hidden until publishing, when the Service reports that a gateway is required. People make the mistake because the OneDrive sync folder looks like a cloud source. Correct treatment: use SharePoint.Files or SharePoint.Contents with the site URL (c03), parameterised (s02); use a standard gateway only for genuinely on-prem sources. Detect it in review by searching the M code (Advanced Editor or the PBIP files) for Folder.Files, File.Contents and drive letters, and by checking the Service's data source settings for gateway requirements.

Formula.Firewall after publishing

Privacy-level (Formula.Firewall) conflicts that only appear after publishing

Power Query's privacy firewall stops data from one source being sent to another of a different privacy level, raising "Formula.Firewall: Query … references other queries or steps, so it may not directly access a data source". In Desktop, privacy may be set to ignore for the file or levels may differ from what the Service uses, so the error appears only after publishing or on another user's machine. Typical cause: a query reads a parameter value from an Excel table and uses it inside a SharePoint call, or merges SharePoint data with a web API. Correct treatment: set consistent privacy levels (Organizational) for all internal sources in Desktop and in the Service's data source settings, use native Power Query parameters rather than values read from another source, and restructure queries so data-source access and combination happen in separate staging queries. Detect by testing a refresh in the Service before the demo.

Untested new-month refresh

Not testing refresh with a genuinely new, messy month file before the demo

The pack is demonstrated with the same clean files it was built on. A real new month brings a renamed column, a new ledger, a branch file with an extra header line, a date in dd-mm-yyyy text, a duplicate file, or an empty file. The Saturday validation is designed to expose this. Correct treatment: create a deliberately messy test file (extra column, new ledger, text amounts with commas, wrong-period vouchers), drop it into a Test folder, run the full refresh and confirm that the pipeline either handles it or surfaces it on the control page (unmapped count, per-file controls, missing months) rather than failing silently or crashing. Keep these files as a regression test set.

No refresh owner

Ignoring refresh-failure emails, and no owner for gateway and refresh credentials

Failure notifications go to the developer who published the model; after a few weeks they are filtered to a folder or the developer moves on. The schedule is disabled after consecutive failures and the CFO sees stale numbers, with a correct-looking but old refresh stamp. Correct treatment: name a refresh owner and a backup; send failure emails to a shared finance-systems mailbox or Teams channel; document gateway admins, recovery keys and credential owners; use service accounts where policy allows; and put a "data lag" control (Topic 4 s04) on the cover page. Detect by checking refresh history and credential owners monthly as part of the close checklist.

Practice Questions

Q1. Saturday validation dry run [L3]

The Project 3 pack reads 14 branch GL files per month from SharePoint, a CoA mapping, a budget file and ERP control totals; it is published to a Pro workspace with scheduled refresh at 06:30 IST, and the Excel board pack connects to the published model with 260 cube formulas. You receive the May 2026 files, one of which (GL_KOL_2026-05.csv) has an extra "Branch Remarks" column, amounts formatted as text with commas, and two new ledgers.

(a) List, in order, every step from dropping the files to confirming success in both Power BI and Excel. (b) For each anomaly in the Kolkata file, state whether your pipeline should handle it silently, flag it on the control page, or fail, and how. (c) Specify the evidence (screenshots, control results, stamps) you would present to the examiner.

Q2. From laptop to Service [L2]

A colleague's pack works in Desktop but cannot be scheduled in the Service. Its sources are: Folder.Files("C:\Users\amit\OneDrive - Contoso\Finance\GL"), an Excel file on \\fs01\finance\Budget.xlsx, and Tally ODBC on the accounts server. It also reads the FY start month from a Config.xlsx table.

(a) Identify every issue preventing or risking Service refresh, including privacy-level and dynamic-source risks. (b) Redesign the sources, parameters and gateway setup. (c) Write the replacement source step for the GL query.

💡 Hint: Separate cloud-reachable sources from genuinely on-prem ones before deciding on a gateway.

Q3. Scaling to seven years [L2]

The GL has grown to 85 million rows (FY2019-20 to FY2025-26) in an Azure SQL staging database; full refresh takes 2 hours 10 minutes on Pro and has started timing out. VertiPaq Analyzer shows PostingDateTime (31% of model), LineGUID (24%) and Narration (19%) as the largest columns.

(a) Design the incremental refresh policy and write the filter step. (b) Propose model reductions with their expected effects, and explain how you would prove the improvement. (c) Explain how change control must adapt once incremental refresh is applied in the Service.

Q4. Packaging and distribution plan [L3]

You are handing Project 3 to the finance-systems team of an NSE-listed company with Pro licences for 30 finance users, eight BU heads without licences, and a board that receives PDF packs.

(a) List the release package contents and the purpose of each artefact. (b) Design distribution for each audience (App audiences, subscriptions, exports, Teams), addressing licensing and UPSI restrictions in the results quiet period. (c) Draft the refresh-ownership section of the handover note, covering schedules, gateway, credentials and failure handling.
