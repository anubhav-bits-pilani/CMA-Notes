Key concept

IST Last-Refresh Table in Power Query

Concept: Last refresh table in M: #table(type table [LastRefresh = datetimezone], {{DateTimeZone.SwitchZone(DateTimeZone.UtcNow(), 5, 30)}})

Statement

let
    LastRefresh =
        #table(
            type table [LastRefresh = datetimezone],
            {{ DateTimeZone.SwitchZone(DateTimeZone.UtcNow(), 5, 30) }}
        )
in
    LastRefresh
  • #table(type, rows) — constructs a table literal; the type table [LastRefresh = datetimezone] defines one column of type datetimezone; {{ … }} is a list containing one row, which is a list containing one value.
  • DateTimeZone.UtcNow() — current date-time in UTC, with offset +00:00, evaluated when the query runs.
  • DateTimeZone.SwitchZone(dtz, 5, 30) — re-expresses the same instant in the zone UTC+05:30 (IST): the clock time changes, the instant does not.

Explanation

Power BI has no DAX function for "model last refreshed", so the usual solution is a one-row table evaluated during every refresh. The choice of function matters:

Function In Desktop (IST laptop) In Power BI Service
DateTime.LocalNow() IST UTC (servers run on UTC) — 5h30m early
DateTimeZone.LocalNow() IST, offset +05:30 UTC, offset +00:00
DateTimeZone.UtcNow() + SwitchZone(5, 30) IST IST

Only the last is correct in both environments. India has no daylight saving, so a fixed offset is reliable; for zones with DST, keep UTC and label it, or convert in a dataflow with a zone table.

Model and display:

  • Load the query to the model (table Refresh Info). The model has no true datetimezone type, so the column is stored as date/time on load. To remove any ambiguity about how the offset is handled, add a final step Table.TransformColumns(LastRefresh, {{"LastRefresh", DateTimeZone.RemoveZone, type datetime}}), so the model receives a plain datetime holding the IST clock time.
  • Display with a measure: "Refreshed " & FORMAT(MAX('Refresh Info'[LastRefresh]), "dd-mmm-yyyy hh:mm") & " IST".
  • Keep "Include in report refresh" ticked; a disabled query keeps the old stamp.
  • With an on-premises gateway, the M runs on the gateway machine; UtcNow is still correct, whereas LocalNow would depend on that server's clock setting.
  • The stamp records when this query ran. In a model that refreshes some tables separately (enhanced refresh, incremental partitions), it is a model-level stamp, not proof each table refreshed.
  • In Excel, the same query loaded to a cell gives the workbook's refresh time for the board pack cover.

Illustration

Scheduled refresh in the Service is set for 06:30 IST, which is 01:00 UTC. The refresh completes at 01:04 UTC.

  • DateTime.LocalNow() stamp: 07-Apr-2026 01:04 — reads as though the pack refreshed after midnight, before the branch files dropped at 05:00 IST.
  • DateTimeZone.SwitchZone(DateTimeZone.UtcNow(), 5, 30) stamp: 07-Apr-2026 06:34 +05:30 — correct.

Connections

  • s04 (refresh metadata) combines this stamp with the latest GL posting date and the file list.
  • Topic pitfall: DateTime.LocalNow() returns UTC in the Service.
  • Topic 5 (one-click refresh): the stamp is the first thing to check in the Saturday validation after Refresh All.
  • Week 10 pipelines: the same table pattern can stamp each consolidation run.

Practice Questions

Q1. Fixing a stamp [L1]

A pack's footer reads "Refreshed 12-Jan-2026 02:15" for a refresh scheduled at 07:45 IST. Identify the function probably used and rewrite the query correctly.

Q2. Multi-country group [L2]

A group reports from India (IST) and Dubai (UTC+04:00). Design the refresh-metadata table and display measure so that viewers in both countries interpret the stamp correctly.

💡 Hint: Store one canonical instant and decide whether to convert at load or at display.

Q3. Stamp did not change [L2]

The Service shows a successful refresh at 06:30 IST today, but the footer still shows yesterday's time. List three possible reasons.
