Subtopic note

GL-to-Dashboard Tie-Out Against Source TB Control Totals

Scope: GL-to-dashboard tie-out: dashboard P&L totals vs source TB control totals for each period

Why it matters

The internal checks in s01 prove that the loaded data is self-consistent. They do not prove that it matches the books of account. A GL extract can be perfectly balanced yet incomplete (a voucher type filtered out in the Tally export), duplicated (the same month file dropped twice and both balanced), or stale (last month's file overwritten). The only way to prove agreement with the books is an independent control total — a trial balance or P&L summary produced directly by the accounting system and compared, period by period, to what the dashboard shows.

This is the same logic as an auditor's "agree the financial statements to the TB and the TB to the ledger". For an FP&A team it is the difference between a CFO who trusts the pack and one who asks finance to re-cut every number in Excel. Statutory auditors increasingly ask for this reconciliation when management information feeds the quarterly results under SEBI LODR Reg 33.

Core notes

What the control-total source should be

The control file must be produced independently of the GL extract — ideally a different report from the ERP:

ERP GL extract (model data) Control total (independent)
Tally Prime Day Book / Ledger vouchers export (XML/ODBC/CSV) Trial Balance or P&L report exported for each month (Gateway of Tally > Display > Trial Balance with period set)
SAP S/4HANA ACDOCA / FBL3N line items Balance-sheet / P&L report (F.01 or financial statement version) or FAGLB03 period balances
Oracle / Dynamics GL journal lines Period trial balance

A practical structure is a small table, TB_Control, at grain Company × Month × Control line, with columns such as CompanyCode, MonthKey (e.g. 202603), ControlLine (Revenue from operations, Other income, Total expenses, PBT, Total assets) and Amount. It is loaded from a separate folder (/Controls/) that the accountant populates at close. If the ERP TB has ledger-level rows, aggregate it through the same CoA mapping, or better, keep both: a ledger-level TB tie-out catches mapping-independent differences, and a line-level tie-out checks the presentation.

Modelling the control table

TB_Control is a fact table. Relate it to the shared Date dimension through a month-level key (one row per 'Date'[MonthKey] is not unique in the Date table, so either create a relationship from TB_Control[MonthEndDate] to 'Date'[Date], or use a separate Month dimension). Relate it to Company too. Do not relate it to CoA unless it is at ledger grain.

Dashboard Revenue =
CALCULATE ( - SUM ( GL[Amount] ), CoA[FSLine] = "Revenue from operations" )

Control Revenue =
CALCULATE ( SUM ( TB_Control[Amount] ), TB_Control[ControlLine] = "Revenue from operations" )

Tie-out Diff Revenue = [Dashboard Revenue] - [Control Revenue]

Tie-out Status Revenue =
SWITCH (
    TRUE (),
    ISBLANK ( [Control Revenue] ), "NO CONTROL",
    ABS ( [Tie-out Diff Revenue] ) < 1, "PASS",
    "FAIL"
)

The "NO CONTROL" state matters: a missing control file is itself a control failure and must not silently show PASS (a blank difference would otherwise evaluate as zero in ABS).

Generalising with a disconnected control-line table

Rather than one measure per line, build a small table ControlLines (Revenue, Other income, Employee benefits, Finance costs, Depreciation, Other expenses, PBT, Total assets, Total equity) and a single SWITCH measure that returns the dashboard value for the current line:

Dashboard Value =
SWITCH (
    SELECTEDVALUE ( ControlLines[Line] ),
    "Revenue from operations", [Revenue],
    "Other income",            [Other Income],
    "Profit before tax",       [PBT],
    "Total assets",            [Total Assets],
    BLANK ()
)

A matrix of ControlLines[Line] on rows and 'Date'[Month] on columns with [Tie-out Diff] in values gives the full period-by-line reconciliation grid in one visual. Crucially, the dashboard measures inside the SWITCH must be the same measures used on executive pages; if the P&L page uses [Revenue], the tie-out must use [Revenue], not a separately written formula, otherwise you are testing a copy.

Each period, not only the year

Tie out every month of the FY (and, for balance-sheet lines, every month-end). The reasons:

  • monthly errors offset — a February invoice back-dated into January shows zero at YTD level;
  • the CFO consumes monthly variance, so a misallocated month is a reporting error even if YTD agrees;
  • after a mid-year CoA remap, prior months may change; per-period tie-out shows exactly which months moved.

Illustration

Hyderabad-based pharma company, Q4 FY2025-26, Revenue from operations (₹):

Month Dashboard Tally P&L control Diff Status
Jan-26 142,35,60,400 142,35,60,400 0 PASS
Feb-26 128,90,14,250 129,02,64,250 −12,50,000 FAIL
Mar-26 165,48,20,000 165,35,70,000 +12,50,000 FAIL
Q4 436,73,94,650 436,73,94,650 0 PASS

Q4 ties, but Feb and Mar fail by equal and opposite amounts. Investigation shows a ₹12.5 lakh sales invoice was dated 28-Feb in Tally but the GL extract used the entry date (2-Mar) instead of the voucher date. The fix is in Power Query (use the voucher date column), not in the dashboard.

Reconciling items and documentation

Some differences are legitimate and permanent — for example, the dashboard presents revenue net of a management-only reclassification, or excludes a dormant company. Do not hide these by adjusting tolerance. Instead, hold them in a Recon_Items table (Company, Month, Line, Amount, Reason, Approved by) and compute Unexplained Diff = [Tie-out Diff] - [Reconciling Items]. The status keys off the unexplained difference. This mirrors a bank reconciliation: every difference is either explained and approved, or a failure.

Excel version

In an Excel cube pack (Topic 3), the same check sits beside the board-pack layout: =CUBEVALUE(conn,"[Measures].[Tie-out Diff]",Slicer_FY,"[ControlLines].[Line].&[Profit before tax]"), with a conditional format that turns the cell red when its absolute value is at least 1.

Edge cases & judgement calls

  • Sign conventions. ERP TB exports often show credits as positive in a "Credit" column; the dashboard shows revenue as positive. Normalise signs in Power Query, and document the convention in the measure description.
  • Timing of the control file. If the TB is exported before late adjustments (provisions posted on day 5 of close), the tie-out will fail legitimately. Store an export timestamp in TB_Control and require re-export after final close.
  • Rounding at line level. ERP reports sometimes round each line to the rupee; summing rounded lines differs from rounding the total. Use a tolerance of ₹1 per line, or tie out at ledger level unrounded.
  • Closed versus open periods. Current-month figures move daily. Show the tie-out status for closed periods only, or label open periods "PROVISIONAL".
  • Restated prior periods. If prior-year comparatives are restated under Ind AS 8 for a prior-period error, the control file for those months must also be restated, otherwise PY tie-outs fail.
  • Circularity. Never derive TB_Control from the same GL extract; that tests nothing.

Key takeaways

  • A tie-out compares the dashboard to an independent ERP report, not to the model's own data.
  • Model the control totals as a small fact table at Company × Month × Line grain, sharing the Date and Company dimensions.
  • Use the same production measures inside the tie-out; testing a copy proves nothing.
  • Reconcile every period; YTD agreement can hide offsetting monthly errors.
  • Treat a missing control file as a failure ("NO CONTROL"), not as a pass.
  • Explain legitimate differences in an approved reconciling-items table rather than loosening tolerance.

Practice Questions

Q1. Designing the control table [L1]

Specify the columns, grain and relationships of a TB_Control table for a group of two companies (Tally and SAP), covering Revenue from operations, Total expenses, PBT, Total assets and Total equity for every month of FY2025-26. State which dimension tables it should and should not be related to, and why.

Q2. Blank control values [L2]

Your tie-out measure is IF(ABS([Dashboard PBT] - [Control PBT]) < 1, "PASS", "FAIL"). For May 2025 the accountant has not yet uploaded the control file, and the dashboard PBT is ₹0.40 (a rounding residue). What does the measure return and why is this dangerous? Rewrite the measure to distinguish PASS, FAIL and NO CONTROL.

Q3. Investigating an offsetting difference [L2]

The dashboard shows Employee benefits expense for Q1 FY2025-26 of ₹48.62 crore, which agrees to the SAP control total. Monthly differences are April −₹1,85,000, May +₹1,85,000, June 0. List the investigation steps you would perform and the likely root causes, distinguishing data-extraction issues from mapping issues.

💡 Hint: Compare the date fields available in the extract and check whether the same accounts appear in both months.

Q4. Reconciling items workflow [L3]

Management reports revenue excluding ₹2.1 crore per month of scrap sales, which the statutory P&L includes in Revenue from operations (Schedule III "Other operating revenue"). Design the reconciling-items table, the DAX measures and the approval process so that the tie-out still shows PASS while the reclassification remains visible and auditable.

Q5. Interview: why not tie out only the grand total? [L1]

Explain to a non-technical CFO, in four or five sentences, why the pack ties out every month and every major P&L line rather than only annual PAT.
