Subtopic note

Change Control: PBIP in Git, Measure Docs, Deployment Pipelines

Scope: Change control: PBIP files in Git, measure documentation, deployment pipelines (Dev/Test/Prod)

Why it matters

A finance pack is a piece of software that computes reported numbers. Changing a measure, a mapping or a filter changes what the CFO sees, so it needs the same discipline as a change to an ERP configuration: a record of what changed, who changed it, why, who approved it, and a way to test before production. Auditors testing ITGCs call this change management. Without it, the classic failure is "someone edited the PBIX on their laptop, published over production, and EBITDA for last quarter moved by ₹2 crore — nobody knows why". The Companies (Accounts) Rules' audit-trail requirement (edit log for books of account, applicable from FY2023-24) covers the accounting software itself, not your BI layer, but the same principle — every change traceable — is what reviewers expect of reporting tools that sit on top of the books.

Core notes

1. PBIP files in Git

A PBIX is a binary zip: two versions cannot be meaningfully compared. The Power BI Project (PBIP) format (File > Save as > Power BI project) saves the same content as a folder of text files:

Item Content
Pack.pbip Pointer file that opens the project in Desktop
Pack.SemanticModel/ The model definition — in TMDL (Tabular Model Definition Language) or model.bim JSON: tables, columns, measures, relationships, roles, Power Query expressions
Pack.Report/ Report definition (legacy report.json or the newer PBIR folder format with one file per page/visual)
.pbi/cache.abf Local data cache — excluded from Git via the generated .gitignore

Because measures are plain text, a Git diff shows exactly that EBITDA changed from [Revenue] - [Operating Costs] to [Revenue] - [Operating Costs] - [Other Opex]. Typical workflow:

  1. Developer creates a branch (feature/add-ebitda-margin-pp).
  2. Edits in Desktop, saves PBIP, commits with a message referencing the change request.
  3. Opens a pull request; reviewer (the reporting lead) reviews the TMDL diff and the control-page results.
  4. Merge to main; main is synced to the Dev workspace through Fabric Git integration (Azure DevOps or GitHub) or deployed by a CI pipeline.

PBIP, TMDL and the PBIR report format have been moving from preview towards general availability since 2023, in stages; check their status (and any preview-feature switches) in your Desktop version before standardising.

2. Measure documentation

Every production measure needs, at minimum: name, business definition, DAX, format, owner, and which control or source it ties to. Store as much as possible inside the model so it travels with it:

  • Description property on each measure (shows as a tooltip in the Fields pane and in Excel's field list).
  • Display folders (Controls, P&L\Base, P&L\Variance, Time intelligence) to make the library navigable.
  • A generated data dictionary: the DAX function INFO.VIEW.MEASURES() (or INFO.MEASURES()), available in recent Desktop versions, returns measures with expressions and descriptions — query it in DAX query view and copy to the user guide. In DAX Studio, the DMV $SYSTEM.TMSCHEMA_MEASURES does the same for older versions. Tabular Editor can also export documentation and apply naming checks via its Best Practice Analyzer.

A minimal dictionary entry:

Measure Definition DAX (summary) Format Ties to
EBITDA PBT + finance costs + D&A − other income (per company's KPI definition) [PBT] + [Finance Costs] + [D&A] - [Other Income] ₹ Cr, 2 dp ERP P&L via C05
Dr Cr Diff Debits minus credits, account filters removed SUM(GL[Debit]) - SUM(GL[Credit]) ₹, 2 dp Control C01

Note the definition column: EBITDA is a non-GAAP measure; whether other income is excluded is a company policy, and SEBI and auditors expect it to be applied consistently with what is disclosed in results presentations.

3. Deployment pipelines (Dev → Test → Prod)

Power BI/Fabric deployment pipelines move content between workspaces assigned to stages (default three: Development, Test, Production; up to ten stages are configurable). Steps:

  1. Create the pipeline, assign a workspace to each stage. Workspaces must be on Premium, Premium Per User or Fabric capacity.
  2. Developer publishes to Dev. Compare view shows differences between stages (new, different, same).
  3. Deploy to Test. Set deployment rules per stage: data source rules (Test points at the UAT SharePoint folder) and parameter rules (e.g. FolderPath, Environment = "TEST"). Rules apply after deployment so the same definition targets different sources.
  4. Test: refresh, check the control page, compare totals with the previous Prod version, user acceptance by the reporting lead.
  5. Deploy to Prod — permissions can be restricted so only the reporting lead or IT can deploy to Production. Deployment history records who deployed what and when.

Deploying a semantic model replaces metadata but keeps data in the target (a refresh is needed only if the change requires it); RLS role memberships and credentials in the target stage are not overwritten.

Without Premium, a manual equivalent is three workspaces (Dev/Test/Prod) and a documented publish procedure — weaker but better than publishing straight to production.

4. The change log

Tie it together with a change register (SharePoint list or Jira): ID, description, requested by, approved by, branch/commit, deployment date, controls result before and after. For material changes (e.g. remapping a ledger from Other expenses to Cost of materials consumed), record the effect on each reported line for prior periods, because the CFO may have already presented those numbers.

Illustration

Change request CR-047: "Reclassify freight-inward ledgers (5 ledgers, ₹6.4 crore YTD) from Other expenses to Cost of materials consumed per Schedule III". The mapping change is a CSV edit in the CoA file (data, not model), so Git holds the CoA mapping file too. The PR shows the five rows changed; Test-stage refresh shows Other expenses down ₹6.4 crore, COGS up ₹6.4 crore, PBT unchanged, all controls PASS. The reporting lead approves; deployment to Prod at 18:00 after the daily refresh; the CFO is told that gross margin for April–September is restated by 1.1 pp.

Edge cases & judgement calls

  • Mapping tables are code too. CoA mappings and control tolerances drive numbers; version them in Git (CSV) or a SharePoint list with version history.
  • Hotfixes. An urgent fix during close still goes through Git; allow an expedited approval but no direct edits in Prod.
  • Report-only changes (layout, colours) carry lower risk; you may skip Test for them, but document the policy.
  • Large models cannot be downloaded as PBIX once incremental refresh is applied in the Service; PBIP plus deployment pipelines (or XMLA-based tools) is then the only practical change path.
  • Excel cube packs depend on measure names; renaming a measure breaks every CUBEVALUE referencing it. Treat names as an interface and avoid renames, or search the workbooks first.
  • Secrets (connection strings, keys) never go into Git.

Key takeaways

  • Save the pack as PBIP so measures, queries and report definitions are diffable text in Git.
  • Review changes by pull request with the control-page results as evidence.
  • Document measures inside the model (descriptions, display folders) and generate a dictionary from it.
  • Use deployment pipelines with stage-specific rules for data sources and parameters; restrict Prod deployment.
  • Keep mapping tables under version control, because they change numbers as much as DAX does.
  • Record material changes and their effect on previously reported figures.

Practice Questions

Q1. PBIX vs PBIP [L1]

Explain to a finance manager why the team is moving from emailing PBIX files to a PBIP project in Git, naming the folders in a PBIP project and what each contains.

Q2. Deployment rules [L2]

Your Dev workspace reads https://contoso.sharepoint.com/sites/FinanceDev/GL/, Test reads .../FinanceUAT/GL/ and Prod reads .../Finance/GL/. The model has parameters SiteUrl and Environment. Describe the pipeline stages, the rules you would configure and the checks to perform before deploying to Prod.

💡 Hint: Think about which rule type applies to parameters and what must be refreshed after deployment.

Q3. Change request evidence [L2]

A change redefines EBITDA to exclude ₹1.2 crore per quarter of foreign-exchange gains previously in Other income. List the artefacts (diff, control results, dictionary update, communication) that should be attached to the change request, and the numbers you would report as the impact on Q1–Q3 FY2025-26.

Q4. Designing change control without Premium [L3]

A mid-size listed company has Power BI Pro only and two BI developers. Design a practical change-control process covering Git, workspaces, approval, documentation and audit evidence, and identify which risks remain compared with deployment pipelines.

Q5. Interview: measure names as an interface [L1]

Why might renaming [Actual] to [Actual ₹] break things outside Power BI, and how would you find out before you do it?
