Subtopic note

Long-Format Version Storage Instead of Sheet-per-Version

Scope: Long-format data layout with Version and Scenario columns instead of separate sheets per version

Why it matters

The single most common reason forecast models break at the second or third reforecast is that versions were stored as separate sheets. Every new cycle means copying a tab, re-pointing summary links, and hoping nobody edited a formula in one copy but not the other. A long-format ("tidy" or "database-style") table removes all of that: a new version is simply more rows. The same structure feeds SUMIFS, XLOOKUP, PivotTables, Power Query and Power BI without modification, and it mirrors how every EPM system (EPBCS, Anaplan, Adaptive) stores data internally as cells addressed by dimension members. When an auditor or CFO asks for "Q1 Fcst EBITDA by BU by month", the answer is a filter, not a hunt across tabs.

Core notes

Wide vs long

A wide layout puts months (or versions) across columns:

Account Apr-25 May-25 … Mar-26
Revenue 120 118 … 140

Repeat that block on a sheet per version and per scenario, and you have the sheet-per-version anti-pattern.

A long layout has one row per data point, with every dimension as a column:

Version Scenario Entity Account Month Amount
BUD Base Foods 4000 Revenue 30-Apr-2025 120.0
BUD Base Foods 4000 Revenue 31-May-2025 118.0
Q1F Base Foods 4000 Revenue 30-Apr-2025 116.4
Q1F Downside Foods 4000 Revenue 31-Jul-2025 109.0
ACT NA Foods 4000 Revenue 30-Apr-2025 116.4

Design rules:

  1. One fact per row: Version × Scenario × Entity × Account × Month (plus optional Product, Cost centre, Currency) → Amount. The combination of dimension columns is the primary key; it must be unique.
  2. Month stored as a true month-end date (use EOMONTH), not text "Apr-25" or a period number. This lets the rolling timeline headers (Topic 1) match directly.
  3. Account stored as code, with a separate mapping table to reporting lines (Revenue, COGS, Gross margin, Opex, EBITDA). Mapping changes are then a mapping-table change, not a data change.
  4. Signs consistent: decide once whether costs are stored positive or negative and document it.
  5. Actuals as just another version (ACT) so the same lookup retrieves actual or forecast by changing one criterion.
  6. A Version master table (dimension table) holds metadata per version: cut-off date, status (Working/Submitted/Locked), submitted by, timestamp, FX rate set, mapping version, approved by. The fact table references the version code only.

Implementing in Excel

Convert the range to an Excel Table (Ctrl+T) named Fact. Retrieval on the report sheet:

=SUMIFS(Fact[Amount], Fact[Version], SelVer, Fact[Scenario], SelScen,
        Fact[Entity], $B$2, Fact[Account], $A7, Fact[Month], D$5)

Because it is a Table, new rows appended at the bottom are automatically included; no ranges need extending. For a comparison column, the same formula with CmpVer instead of SelVer returns the comparison version.

Row-count sanity: 3 entities × 40 accounts × 12 months = 1,440 rows per version-scenario. Budget, Q1F and Q2F each with 3 scenarios plus 12 months of actuals → (3 × 3 + 1) × 1,440 = 14,400 rows — trivial for Excel (limit 1,048,576 rows) and fast with SUMIFS. At finer grain (cost centre × SKU) row counts climb into hundreds of thousands, at which point Power Pivot / Power BI or a database is the right home.

Loading data

  • Forecast input sheets remain wide (users like months across) but are converted to long on submission — by Power Query's Unpivot Other Columns, or by a staging block of formulas — and appended to Fact with the version and scenario stamped.
  • Actuals come from the ERP trial-balance extract (Tally, SAP, Oracle) refreshed via Power Query (Week 10), mapped to account codes and loaded as Version = ACT.
  • Snapshots are appended, never edited; replacement of a version is done by deleting all rows for that version code and re-loading only while the version status is Working (see s04).

Pivot and BI readiness

A long table can be dropped straight into a PivotTable (Version in columns, Account in rows), into Power Pivot with a Version dimension, or into Power BI with slicers (Week 11). Wide sheet-per-version data cannot be used this way without first being unpivoted.

Worked illustration: adding Q2 Fcst

Sheet-per-version approach: copy "Q1 Fcst" tab, rename to "Q2 Fcst", overwrite inputs, re-link 40 × 3 summary cells, update the variance sheet, check every chart series. Roughly 2–3 hours and error-prone.

Long-format approach: users complete the input template; Power Query unpivots it, stamps Version = Q2F, Scenario = Base; Refresh appends 1,440 rows; set SelVer drop-down to Q2F. Report, variance columns and charts update. Roughly 10 minutes, with no formula edits.

Edge cases & judgement calls

  • Mixed granularity. Budget may be at cost-centre level while forecasts are at BU level (Topic 1, s06). Store each at its natural grain with a blank or "ALL" member for the missing dimension, and ensure report formulas aggregate to the common level; otherwise SUMIFS on cost centre returns zero for forecast versions.
  • Calculated lines. Store only input/base accounts in the fact table; compute Gross margin, EBITDA and ratios in the report or measure layer. Storing subtotals invites double-counting when a user sums the column.
  • Driver data. Drivers (stores, footfall, ATV, headcount) can live in the same table with Account = driver code and a "Type" column (Financial/Driver), or in a parallel driver fact table with the same keys. Keep units in the Account master.
  • Duplicate keys. If the same key appears twice (e.g., a version loaded twice), SUMIFS silently doubles the figure while XLOOKUP returns only the first match. Add a check: COUNTIFS on the key columns must be 1 for every row, and the version total must reconcile to the submission file.
  • Performance. Thousands of SUMIFS over a 200,000-row table can slow recalculation. Mitigate by pre-aggregating in Power Query, using a PivotTable/GETPIVOTDATA report, or moving to the Data Model.
  • Currency. If entities report in different currencies, store both local currency and reporting currency amounts, or a Currency column with an FX table per version, so that constant-currency comparison is possible (topic pitfall on FX normalisation).

Key takeaways

  • Store every version and scenario in one long table: Version × Scenario × Entity × Account × Month → Amount.
  • A new version is appended rows, not a copied sheet; report formulas never change.
  • Use true month-end dates, account codes with a mapping table, and a Version master table for metadata.
  • Treat actuals as Version = ACT so one lookup pattern serves actual and forecast.
  • Store base accounts only; compute subtotals in the report layer to avoid double counting.
  • Add key-uniqueness and version-total checks because SUMIFS silently aggregates duplicates.

Practice Questions

Q1. Converting a wide workbook [L2]

You inherit a workbook with tabs BUD, Q1F and Q1F_DS, each with 35 accounts in rows and 12 months (Apr-25 to Mar-26) in columns for a single entity. (a) Describe the Power Query steps to convert all three into one long table with Version, Scenario, Account, Month (as month-end date) and Amount columns. (b) State how many rows the final table will have. (c) Write the formula that returns Q1F Base gross margin for October 2025 if Revenue is account 4000 and COGS accounts are 5000–5099 (stored positive).

💡 Hint: Gross margin can be built with two SUMIFS calls, the second using ">=" and "<=" criteria on a numeric account column.

Q2. Designing the version master table [L2]

Design a Version master table for an NSE-listed pharma company that maintains Budget, quarterly forecasts and monthly LEs with three scenarios. List at least eight columns, the data type of each, and explain how the report sheet would use the Status and Cut-off columns.

Q3. Duplicate-key failure [L2]

After a refresh, Q2F Base revenue for "Exports" in November 2025 shows ₹48.6 crore in the report, while the submitted template shows ₹24.3 crore. (a) Explain the most likely cause. (b) Write a COUNTIFS-based check column and a summary check cell that would flag the problem. (c) Explain why an XLOOKUP retrieval would have shown a different (but still unsafe) result.

Q4. Grain mismatch [L3]

The Budget is stored at 120 cost centres; Q1F and Q2F are forecast at 8 BUs. The report sheet currently filters Fact[CostCentre] and shows zero for Q1F. Propose two alternative designs to make Budget, Q1F and Q2F comparable at BU level, and evaluate each for auditability, performance and effort.
