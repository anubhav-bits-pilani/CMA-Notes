Subtopic note

Versions vs Scenarios: Time Snapshots vs Alternative Assumptions

Scope: Version vs scenario: versions are time snapshots (Budget, Q1 Fcst 3+9, Q2 Fcst 6+6, Q3 Fcst 9+3); scenarios are alternative assumptions (base/upside/downside)

Why it matters

Every planning number in a company answers two questions: when was this view formed, and under which assumptions? A version answers the first; a scenario answers the second. If the model does not separate them, the FP&A team cannot answer basic Audit Committee questions such as "what did we believe in July about H2 margin?" or "how bad is the downside today compared with the downside we showed in the Budget?". In Indian listed companies this matters beyond internal management: Ind AS 36 value-in-use calculations must be based on the most recent budgets/forecasts approved by management, Ind AS 116 and Ind AS 109 expected-credit-loss models use forward-looking scenarios, and SEBI LODR Regulation 30 disclosure decisions (for example, whether a material change in outlook must be disclosed) depend on which version of the forecast was in force when.

In EPM systems (s07) Version and Scenario are literally two separate dimensions. Learning to think in those two axes in Excel makes the later migration trivial.

Core notes

Versions: time snapshots

A version is the organisation's official view of the full year (or rolling horizon) as at a particular cut-off date. For an Indian FY (April–March) the standard family is:

Version Prepared Actual months Forecast months Typical use
Budget / AOP Jan–Mar of prior FY 0 12 (Apr–Mar) Board-approved target, incentive baseline
Q1 Fcst (3+9) After June close (July) Apr–Jun Jul–Mar First reforecast; Q1 results context
Q2 Fcst (6+6) After September close (October) Apr–Sep Oct–Mar H1 review; festive season locked in
Q3 Fcst (9+3) After December close (January) Apr–Dec Jan–Mar Year-end landing, tax and bonus provisioning; often feeds next year's Budget

Some companies add monthly LEs (1+11, 2+10, …) or a "Flash" version for the current month. Key properties of a version:

  • It has a cut-off date — the last closed actual month — and therefore a fixed split of actual and forecast months.
  • It has an owner and a submission date; once submitted it is frozen (see c04 and s04).
  • It is one official number per account per month — the version itself is not "an alternative"; it is the then-current best estimate.
  • Versions are compared with each other to show how the view evolved (s05, c03).

Scenarios: alternative assumption sets

A scenario is an internally consistent set of assumptions that produces an alternative outcome at the same cut-off date. The usual trio:

  • Base — the most likely outcome; this is what becomes "the forecast" for that version.
  • Upside — favourable but plausible: faster ramp-up of new stores, better monsoon-driven rural demand, softer input prices.
  • Downside — adverse but plausible: delayed product launch, commodity spike, INR depreciation for an importer.

Many companies add a Stress / Severe case (s06) and sometimes management-defined cases (e.g., "Plant 3 delayed"). Scenarios are not probability-weighted in the base view; probability weighting is the job of the risks-and-opportunities overlay in the LE (Topic 2), though some companies attach indicative probabilities to Upside/Downside for the Board.

The two-axis grid

Combining the axes gives a matrix of datasets:

Base Upside Downside
Budget ✓ (approved) ✓ ✓
Q1 Fcst 3+9 ✓ (official) ✓ ✓
Q2 Fcst 6+6 ✓ (official) ✓ ✓
Q3 Fcst 9+3 ✓ (official) optional optional

Important mechanics:

  1. Actuals are scenario-independent. In the Q2 Fcst, April–September actuals are identical in Base, Upside and Downside; only October–March differ. If the actual months differ between scenarios, the model is broken.
  2. Each version usually has exactly one "official" scenario (Base) that is reported as the forecast. Upside and Downside are context.
  3. Scenario names should mean the same thing across versions. "Downside" in Budget and "Downside" in Q2 Fcst may contain different assumptions (the world changed), but both should represent the same severity level (e.g., roughly 1-in-5 adverse).
  4. Actual itself is often stored as a version (Version = "Actual", Scenario = "NA" or "Base") so that one long-format table holds everything (s02).

Worked illustration

Konkan Retail Ltd, FY26 revenue (₹ crore):

Version Scenario Apr–Sep Oct–Mar Full year
Budget Base 1,150 1,450 2,600
Q2 Fcst 6+6 Base 1,092 (actual) 1,418 2,510
Q2 Fcst 6+6 Upside 1,092 (actual) 1,520 2,612
Q2 Fcst 6+6 Downside 1,092 (actual) 1,300 2,392

Reading across versions (Budget Base → Q2 Base) gives the forecast evolution: −₹90 crore, of which −₹58 crore is H1 actualisation and −₹32 crore is the revised H2 view. Reading across scenarios within Q2 gives the current range of outcomes: ₹2,392–2,612 crore. These are two different questions and must never be mixed — for example, comparing Q2 Downside with Budget Base and calling the −₹208 crore "forecast deterioration" overstates the change in the official view.

Naming taxonomy

Use a controlled naming convention so the version is self-describing:

FY26_Q2F_6+6_Base, FY26_BUD_0+12_Downside, FY26_Q3F_9+3_Base

Store the components as separate columns (FY, Version code, Actual months, Scenario) rather than relying on a parsed string; the string is just a display label.

Edge cases & judgement calls

  • Re-budgeting mid-year. After a major shock (e.g., a COVID-type disruption or an acquisition), the Board may approve a "Revised Budget". Treat it as a new version with its own approval record; never overwrite the original Budget, which remains the incentive and Board-target baseline unless the compensation committee explicitly re-bases.
  • Rolling 12-month horizons. In a true rolling forecast, the Q2 version may extend to September of next FY. The version still has one cut-off; its horizon simply crosses the FY boundary. Store the month-end date, not "Month 1…12".
  • Scenario becoming base. If the Downside materialises, next cycle's Base may look like last cycle's Downside. That is a change of view captured as a version movement, not a relabelling of the old scenario.
  • Monthly LE vs quarterly forecast. If the company produces monthly LEs but only quarterly Board forecasts, decide which versions are "official" (locked and stored permanently) and which are "working" (overwritten). Keep at least the quarter-end versions permanently.
  • Acquisitions and demergers. A version prepared before an acquisition excludes the target; later versions include it. Comparisons need a like-for-like flag (see the normalisation pitfall in topic.md).

Key takeaways

  • Version = when the view was formed (cut-off date, frozen once submitted); scenario = which assumptions were used at that date.
  • Indian FY version family: Budget (0+12), Q1 Fcst 3+9, Q2 Fcst 6+6, Q3 Fcst 9+3, optionally monthly LEs.
  • Actual months are identical across scenarios within a version; only forecast months differ.
  • Each version has one official scenario (usually Base) that is reported as "the forecast".
  • Compare versions to explain evolution; compare scenarios to show range — never mix them in one bar.
  • Store Version, Scenario, cut-off and timestamp as separate fields, not as sheet names.

Practice Questions

Q1. Classifying datasets [L1]

Classify each of the following as a version, a scenario, or a version–scenario combination, and state its cut-off month: (a) FY26 AOP approved by the Board on 20 March 2025; (b) "Monsoon failure case" prepared with the July reforecast; (c) the January 2026 forecast used for advance-tax estimation; (d) "Revised Budget" approved after an acquisition closes on 1 August 2025; (e) "Upside" prepared with the Budget.

Q2. Identifying a broken scenario structure [L2]

In a Q2 Fcst (6+6) workbook for FY26, Base shows April–September revenue of ₹842 crore, while Downside shows ₹826 crore for the same months, and Upside shows ₹842 crore. Full-year revenue is ₹1,760 crore (Base), ₹1,690 crore (Downside) and ₹1,830 crore (Upside). (a) What is wrong with the structure? (b) Compute the correct H2 range across scenarios assuming H2 figures are unchanged. (c) Describe a model check that would catch this automatically.

💡 Hint: Actual months must be scenario-independent; build a check that differences actual-flagged months across scenarios.

Q3. Designing a version calendar [L2]

A Chennai-based B2B SaaS company with an April–March FY wants quarterly reforecasts and a rolling 18-month view. Draft the version calendar for FY26: version names, cut-off dates, submission deadlines, actual/forecast month split, horizon end date and which versions carry Upside/Downside scenarios. Justify any version you choose not to keep permanently.

Q4. Interview: explaining the difference [L1]

An interviewer asks: "Our Board pack shows Budget, Q2 Forecast and a Downside. The Downside is ₹120 crore below Budget. Is that our forecast deterioration?" Prepare a two-minute answer explaining versions vs scenarios using the numbers given, and state what additional figure you would need to answer the question precisely.
