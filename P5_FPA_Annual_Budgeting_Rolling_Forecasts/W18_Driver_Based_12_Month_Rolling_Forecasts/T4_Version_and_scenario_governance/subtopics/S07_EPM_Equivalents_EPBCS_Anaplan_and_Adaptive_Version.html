EPM Equivalents: EPBCS, Anaplan and Adaptive Version Handling

Scope: EPM equivalents: Scenario/Version dimensions in Oracle EPBCS, Anaplan version list, Adaptive versions with lock

Why it matters

Most large Indian corporates and MNC captives (GCCs in Bengaluru, Hyderabad, Pune) run planning on an enterprise performance management (EPM) platform: Oracle EPM Cloud Planning (EPBCS), Anaplan or Workday Adaptive Planning are the most common, with SAP Analytics Cloud and OneStream also present. FP&A job descriptions routinely list one of them. The good news is that the governance concepts in this topic — separate version and scenario axes, long-format storage, locking, comparison — are built into these tools as first-class objects. An analyst who understands why Excel needs a Version column and a lock procedure will configure and use EPM versions correctly; one who only knows the menus will reproduce the sheet-per-version mess inside a much more expensive tool.

Core notes

Common principle: multidimensional cells

All three platforms store data as cells addressed by dimension members — conceptually identical to the long-format table of s02. Each cell is an intersection such as Scenario = Forecast, Version = Working, Entity = Foods, Account = Revenue, Period = Oct, Year = FY26 → Amount. Reports, forms and dashboards are views over that cube. Adding a version adds members, not sheets.

Oracle EPM Cloud Planning (EPBCS / PBCS)

EPBCS ships with two separate dimensions that map exactly onto the version–scenario distinction — though with Oracle's naming, which reverses the intuitive labels:

  • Scenario dimension — the type/purpose of the plan: Actual, Plan (Budget), Forecast, often extended with Q1 Fcst, Q2 Fcst, Rolling Forecast. Each Scenario member has a start year/period and end year/period defining its valid time range, and an exchange-rate table assignment. In Oracle terms, what this note calls a "version" (time snapshot) is usually a Scenario member.
  • Version dimension — the iteration or case within a scenario: Working, Final, Base, Best case, Worst case, Version 1…n. Members are typed bottom-up (data entered at level-0 entities) or target (top-down data entry at parent levels). In Oracle terms, Base/Upside/Downside often sit in Version.

Key governance features:

  • Approvals / Task Manager (Planning Units / approval units): each Entity × Scenario × Version combination is an approval unit with a workflow state — Not Started, Under Review, Signed Off, Approved. Once Approved, the owner loses write access: this is the lock.
  • Scenario start/end period and valid intersections prevent data entry outside the version's forecast window (e.g., Q2 Fcst actuals months are read-only, mirroring Topic 1's actual/forecast flag).
  • Copy Data / Copy Version — copies Working to Final, or Q1 Fcst to Q2 Fcst as a starting point; equivalent to the copy-as-values snapshot.
  • Rolling forecast feature: forecast range set by substitution variables (&CurMonth, &CurYear), advanced each close by an administrator — the EPM version of the single cutoff switch.
  • Audit trail of data changes and approval actions.

Anaplan

Anaplan has a native Versions list (a special system list) configured in model settings:

  • Typical members: Actual, Budget, Forecast, plus additional forecast snapshots (Q1 Fcst, Q2 Fcst) and scenario-style members if desired.
  • Each version has a Current flag (one version is designated current), an Actual flag (one version is designated actual), Edit From / Edit To settings that restrict the time periods in which data can be entered — setting Edit From after the last closed month locks actual months, and setting Edit To before Edit From (or removing edit rights) freezes the whole version.
  • Switchover date per version: periods before switchover take values from the Actual version and periods after from the version itself — directly implementing the actual/forecast blend (3+9, 6+6) without formulas.
  • Formula scope — formulas can apply to all versions, actual only, or current only; e.g., the forecast driver logic runs in the Forecast version but actuals are imported.
  • PREVIOUS, CURRENTVERSION() and ACTUALVERSION() functions support comparisons (e.g., Revenue[SELECT: Versions.Budget]).
  • Many Anaplan builders model scenarios as a separate custom list (Base/Upside/Downside) dimensioning the driver modules, leaving the native Versions list for time snapshots — preserving the two-axis distinction of s01.
  • Archiving prior forecasts is often done by copying the current forecast into a snapshot version via an action/process, then restricting edit rights; alternatively by exporting to a data hub model.

Workday Adaptive Planning

Adaptive uses a single Versions hierarchy (Admin → Versions) containing:

  • Actuals version (data loaded from the ERP; can be locked by period).
  • Plan versions: Budget FY26, Q1 Fcst, Q2 Fcst, and scenario copies (Q2 Fcst Downside) — organised in folders.
  • Version properties: start and end period, actuals-overlay / "Actuals through" setting so that a forecast version displays actuals up to the cutoff and plan thereafter, and which sheets/levels are editable.
  • Lock version — a version-level setting that makes the version read-only for all users (admin can unlock with audit). This is the direct equivalent of c04's freeze rule.
  • Copy version — creates Q2 Fcst from Q1 Fcst (including or excluding data), the typical start of each cycle.
  • Default version setting — the version users see by default (the "working" one).
  • Comparisons via report columns that reference different versions, and Version-to-version variance columns.

Because Adaptive puts versions and scenarios in one list, naming discipline (s04) is essential: FY26 Q2 Fcst – Base, FY26 Q2 Fcst – Downside, grouped under a FY26 Q2 Fcst folder.

Edge cases & judgement calls

  • Terminology clash. Oracle's "Scenario" = time snapshot and "Version" = iteration/case is the reverse of how many finance teams speak. Agree a glossary on day one of an implementation.
  • Version proliferation. EPM makes copying versions cheap, so dozens accumulate (Q2 Fcst v1…v7). Cap versions, archive superseded ones, and keep only official quarterly snapshots permanently.
  • Locking granularity. In EPBCS, an approval lock is per approval unit; a BU can be locked while another is still open. Ensure the whole version is locked before it is used for accuracy tracking or Board reporting.
  • Admin overrides. Administrators can usually unlock versions; the audit trail must be reviewed periodically, and unlocks should require a ticket or change-log entry.
  • Integration with Excel. Users still pull data into Excel via Smart View (Oracle), the Anaplan Excel add-in or Adaptive OfficeConnect; ensure the version member is explicit in every retrieval sheet so a "Working" pull is not mistaken for a locked version.
  • Rolling forecast configuration. Rolling horizons crossing the FY boundary need Year and Period dimensions (EPBCS) or a continuous timescale (Anaplan) configured to span 18–24 months.

Key takeaways

  • All major EPM tools store data as dimensioned cells — the same idea as a long-format Version × Scenario table.
  • Oracle EPBCS: Scenario dimension (plan type/time snapshot) + Version dimension (Working/Final/cases); approvals provide the lock.
  • Anaplan: native Versions list with Current/Actual flags, switchover and Edit From/To; scenarios usually as a custom list.
  • Adaptive: single Versions hierarchy with actuals overlay, copy version and a version-level lock.
  • Governance still depends on naming, version caps, audit-trail review and a clear glossary.

Practice Questions

Q1. Configure versions in EPBCS [L2]

An Indian conglomerate on EPBCS needs Actual, Budget FY26, Q1 Fcst (3+9), Q2 Fcst (6+6) and Q3 Fcst (9+3), each with Base and Downside cases, and an 18-month rolling forecast. Specify the Scenario and Version dimension members, the start/end periods for each Scenario member, how actual months become read-only, and how Q1 Fcst is locked after Board approval.

Q2. Anaplan switchover and edit settings [L2]

In Anaplan, the FY26 timescale is April 2025–March 2026. For the Q2 Fcst version, state the appropriate switchover period, Edit From and Edit To settings during the submission window, and the settings after lock. Explain what values the model shows for August 2025 and for November 2025 in the Q2 Fcst version.

💡 Hint: Switchover controls where actuals stop and forecast starts; edit settings control what users may type into.

Q3. Adaptive Planning version clean-up [L2]

An Adaptive Planning instance has 27 versions, including "Q2 Fcst", "Q2 Fcst new", "Q2 Fcst CFO", "Q2 Fcst final", "Q2 Downside" and "Q2 Downside v2". Propose a folder structure, naming convention, locking status and archival rule, and explain how you would identify which version the Board actually saw.

Q4. Interview: Excel to EPM translation [L3]

An interviewer asks: "In your Excel model you had Version and Scenario columns, a cutoff cell and a lock procedure. How would each translate into Anaplan and into Oracle EPBCS, and what new governance risks does EPM introduce?" Prepare a structured answer.
