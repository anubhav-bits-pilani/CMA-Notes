Key concept

Scenario Invariance: A Linked Model Balances for Any Input

Concept: Scenario invariance: a correctly linked model balances for any input, not just Base

Statement

Let \( \mathbf{x} \) be any vector of inputs (growth, margins, capex, working capital days, financing assumptions, scenario switch, stress shocks) within the model's valid domain. A model is scenario-invariant if:

\[ \text{BS check}_t(\mathbf{x}) = 0 \quad \text{for all forecast years } t \text{ and all valid } \mathbf{x} \]

The balance is a property of the model's structure (its links), not of any particular set of inputs. Conversely, if there exists any valid \( \mathbf{x} \) with \( \text{BS check}_t(\mathbf{x}) \neq 0 \), the model has a structural error, even if it balances in Base.

Explanation

Double-entry is an identity. If every BS movement is linked to a CFS line or a non-cash counterpart, the accounting equation holds whatever the numbers are. Inputs change the size of the flows, not whether each flow has a counterpart. So a model that balances only in some cases is not "mostly right". It contains an error that happens to be zero, or to cancel out, for those inputs.

How a structural error hides in Base:

  • Dormant logic: the error sits in a branch that is not exercised. Revolver draws, tax loss utilisation, dividend floors, DTA recognition and WC release all equal zero in a growing, profitable Base case.
  • Coincidental hardcodes: a typed number equals the Base formula result (Topic 4 s06).
  • Offsetting errors: two errors of +5 and −5 cancel in Base but diverge under another scenario.
  • Direction-blind formulas: ABS or MAX(0, …) on movements gives correct results only while the movement is in one direction.

Invariance testing therefore needs inputs that activate every branch: losses, revolver draws, WC decreases, capex spikes and zero growth. That is why stress tests (s02–s05) go beyond plausible scenarios.

Invariance concerns the balance check and other integrity checks (cash check, convergence). It does not require business outcomes to be good. Negative cash and covenant breaches are valid results. It also does not prove the model is economically right. A model with a wrong tax rate is still invariant. Invariance is necessary for correctness, not sufficient.

"Valid domain" matters. Growth below −100% (negative revenue) or negative days are outside it. Use input validation to define the domain, then require invariance everywhere inside it.

Illustration

Ravi Engineering Ltd: three tests of the same model.

Test Inputs Max abs BS check
Base Growth 12%, margin 15% 0.000
Bear Growth −8%, margin 9% 0.000
Extreme Growth −35%, margin −2%, capex 3× 18.40

Base and Bear pass. The extreme case fails, so the model is not invariant. Investigation: the extreme case is the first to produce a tax loss. The loss corkscrew credits the DTA on the BS, but the CFS deducts total tax, including the deferred credit, instead of only cash tax. That creates a difference equal to the deferred tax credit (18.40). The error exists in the structure and was dormant in Base and Bear because both had positive PBT. After the fix all three tests show 0.000, and a one-variable data table of growth from −60% to +40% shows a zero check in every row.

Connections

This principle is the purpose of the whole topic. It justifies s01 (toggling scenarios), s02 (extreme inputs) and the data table approach in c04, where every breaking point is valid only if invariance holds at that input. It links back to Topic 4 diagnostics (dormant-branch errors show up as Bear-only or extreme-only imbalances) and forward to Week 16, where valuation sensitivities rely on a model that balances across the grid. It is also the basis of the week's checklist item: show check = 0 across 5 years in Base, Bull, Bear and extreme inputs.

Practice Questions

Q1. Explain invariance [L1]

In three or four sentences, explain to a junior analyst why "it balances in Base" does not prove a model is correctly linked. Give two concrete examples of errors that are invisible in a profitable, growing Base case.

Q2. Designing an invariance test suite [L2]

Design a minimum set of six input configurations that together activate every conditional branch in a model containing a revolver with limit, tax loss corkscrew with DTA switch, dividend floor and cash cap, WC days drivers, CWIP capitalisation and a cash sweep on term debt. For each configuration, state which branch it activates and what output you would check.

💡 Hint: Map each MAX, MIN and IF in the model to an input that flips it.

Q3. Offsetting errors [L2]

A model has two errors: the ESOP charge (₹6 crore a year) is not added back in CFO, and the ΔDTL add-back is entered twice. In Base, ΔDTL is exactly ₹6 crore a year. In Bear, ΔDTL is ₹2 crore a year. (a) Compute the BS check in each case for FY26E–FY28E. (b) Explain how this shows the value of scenario invariance testing. (c) State how the reconciliation block from Topic 4 would expose both errors even in Base.
