Subtopic note

Separating Inputs, Calculations and Outputs

Scope: Strict separation of inputs, calculations and outputs; calculations flow left-to-right and top-to-bottom

Why it matters

Almost every model error found in Big 4 model reviews falls into one of three families: a hardcoded number sitting where a formula should be, a formula referring to the wrong cell, or an output that was typed over. Separation of inputs, calculations and outputs attacks all three. If every hardcode lives in an input zone, a reviewer can audit every assumption in one place; if calculations never contain typed numbers, a formula error is a logic error and not a hidden override; if outputs only display, nobody "fixes" a number on the dashboard. For FP&A roles, the same discipline is what lets a budget model be re-run each month by someone other than the original builder.

Core notes

Definitions

Zone What it contains What it must never contain
Inputs Hardcoded numbers, text choices, dates, switches; each with label, units, source Formulas (except simple input-side aids such as a sum check of an input table)
Calculations Formulas only, referencing inputs, historicals and other calculations Typed numbers (other than structural constants like 0, 1, 12 months, 100%)
Outputs Links and presentation formulas (ratios, charts, summary tables) New logic that other calculations depend on; typed numbers

The separation can be at tab level (an Inputs tab, calc tabs, an Outputs tab) or at block level within a tab (an input block at the top of the Revenue tab, calcs below). The FAST Standard prefers inputs on dedicated input sheets; the ICAEW Code accepts either provided it is consistent and visibly flagged (blue font, input fill — topic t2).

Why hardcodes in calculations are dangerous

=C12*1.12 embeds a 12% growth rate that does not appear on the Inputs tab, cannot be flexed by the scenario switch, and is invisible to Go To Special → Constants (which selects only cells that are constants, not formulas containing constants). The correct structure is:

Inputs!F20   = 12.0%          (blue, labelled "Zudio revenue/sq ft growth, %", source: FY25 concall)
Revenue!F12  = E12*(1+Inputs!F20)

Better still, pull the input into the Revenue tab once (green link) and reference it locally (topic t2, c04).

Flow direction: left-to-right and top-to-bottom

Within a sheet, a formula should refer to cells above it or to its left. Time runs left to right (FY21A in column H, FY30E in column Q). Logic runs top to bottom: drivers at the top, intermediate calculations in the middle, the result that leaves the sheet at the bottom.

Exceptions arise naturally:

  • Prior-period references (=G15+H10-H11) look left — compliant.
  • Totals placed above detail (a common presentation habit) look downward — avoid in calc sheets; put totals below detail.
  • Corkscrews (opening + additions − deductions = closing; next opening = prior closing) are the canonical compliant pattern.

A flow-compliant sheet can be audited by reading it like a book. When a formula refers downward or rightward, the reader must hold the unresolved reference in their head, and that is where errors hide.

Illustration: Pidilite Consumer & Bazaar revenue block

Row Label Units Const FY25A FY26E FY27E
5 UVG (input link) % 9.0% 10.0%
6 Price/mix (input link) % 2.0% 3.0%
7 Revenue ₹ crore 10,500 =G7*(1+H5)*(1+H6) …

FY26E revenue = ₹10,500 × 1.09 × 1.02 = ₹11,673.9 crore. Rows 5–6 are green links from Inputs; row 7 is black calculation, FY25A is a green link from Historicals. Every reference in H7 points up or left.

Outputs: display, never compute

An Outputs tab may contain ratios (=EBITDA/Revenue) and formatting formulas, but nothing upstream should depend on it. If the DCF uses an EBITDA margin computed on the Outputs tab, the dependency now runs from calc → output → calc, breaking the zone logic. Compute anything the model uses inside the calc zone; outputs merely re-display.

Implementation steps

  1. Create the Inputs tab with sections mirroring the calc tabs (Timeline, Revenue, Costs, WC, Capex, Financing, Tax, Valuation).
  2. Every input row: label, units, constant column (for scalars) or timeline values (for time series), source, comment.
  3. On each calc tab, link the needed inputs into a small block at the top (green), then calculate below.
  4. Run Go To Special → Constants on each calc tab; the only selected cells should be historical actuals (if hosted there) and nothing else.
  5. Lock output tabs with sheet protection (no password, or a documented one) to prevent overtyping.

Excel and Power BI parallels

In Power BI the same philosophy appears as Power Query (inputs/ingestion), the data model and DAX measures (calculations), and report pages (outputs). A DAX measure that hardcodes * 1.12 has exactly the same defect as an Excel formula.

Edge cases & judgement calls

  • Historical actuals. They are hardcoded but are not assumptions. Keep them on the Historicals tab (input zone, blue) and link into calc tabs; do not type them into calc rows.
  • Structural constants. Dividing by 12 months, 365 days or 100 is acceptable inside formulas if the meaning is obvious; days-in-year conventions (365 vs 360) are better as a named input.
  • Overrides. Management sometimes insists on a specific FY26E number. Build an explicit override row on Inputs with a flag (=IF(Override_Flag=1,Override,Calculated)), never type over a formula (topic t2 pitfalls).
  • Small models. For a one-page sensitivity, inputs at the top of the same sheet are fine — the separation is logical, not necessarily physical.
  • Iterative calcs. A circular interest calculation may refer to a closing balance below it; contain it inside the Debt tab with a circuit breaker.

Key takeaways

  • Every hardcode lives in an input zone, labelled with units and source.
  • Calculation cells contain formulas only; Go To Special → Constants on a calc sheet should select nothing unintended.
  • Formulas refer up and to the left; totals sit below detail; corkscrews are the default pattern.
  • Outputs display but are never used as a source for calculations.
  • Overrides are explicit, flagged inputs, never typed over formulas.
  • The same separation applies in Power BI: ingestion, measures, visuals.

Practice Questions

Q1. Classify the cells [L1]

Classify each as input, calculation or output and state whether it is correctly placed: (a) FY25A revenue of ₹14,603 crore typed into the 3-Statement tab; (b) =E12*1.12 on the Revenue tab; (c) a chart of EBITDA margin on the Dashboard; (d) tax rate 25.168% typed on Inputs with source "Sec 115BAA"; (e) =Dashboard!F10*Inputs!F5 on the DCF tab.

Q2. Refactor a block [L2]

A Revenue tab shows: row 10 stores (typed 300, 360, 430, 510, 600 for FY26E–FY30E); row 11 area per store typed as 0.011 mn sq ft in every year; row 12 revenue =H10*H11*21000/100. Redesign the block and the matching Inputs section so that no hardcode remains in the calc tab and units are explicit.

💡 Hint: The 21000 and /100 hide both a driver and a unit conversion — separate them.

Q3. Flow audit [L2]

On a WC tab, row 30 (closing receivables) is =H45*Inputs!$F$40/365 where row 45 is revenue linked from the P&L, and row 25 (change in receivables) is =H30-G30. Identify the flow violations, explain why they matter, and propose a reordered layout.

Q4. Management override policy [L3]

The CFO of an NSE-listed FMCG company wants FY26E advertising spend fixed at ₹620 crore (board-approved budget) while the model computes A&P as 11% of revenue. Design the override mechanism, the documentation on Inputs, and the check that alerts a reviewer that an override is active.
