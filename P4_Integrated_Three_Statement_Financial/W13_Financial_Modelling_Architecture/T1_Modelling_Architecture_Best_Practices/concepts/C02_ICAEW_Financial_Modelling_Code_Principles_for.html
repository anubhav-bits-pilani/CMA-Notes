Key concept

ICAEW Financial Modelling Code: Principles for Reliable Models

Concept: ICAEW Financial Modelling Code: separate inputs/calculations/outputs, consistent layout, documented assumptions, built-in checks, designed for the end user

Statement

The ICAEW Financial Modelling Code (Institute of Chartered Accountants in England and Wales, first issued 2018) is a principles-based framework for building and reviewing spreadsheet models. Its central requirements:

  1. Separate inputs, calculations and outputs so that assumptions can be found, changed and audited.
  2. Consistent layout — the same structure, timeline, column usage and formatting across sheets.
  3. Documented assumptions — every input has a description, units and source.
  4. Built-in checks — integrity checks summarised so the user knows the model is working.
  5. Designed for the end user — the model answers the user's question, at the right level of detail, in a form they can use and understand.

Explanation

Where FAST (c01) is a detailed rulebook, the ICAEW Code is a set of principles organised around the modelling lifecycle: planning (define purpose, users, outputs before building), structure (input–calculation–output separation, workbook map), building (consistent formulas, avoiding complexity), checking (integrity checks, peer review, testing) and communicating (outputs, documentation, version control). It explicitly allows different house styles provided they are applied consistently and the model is transparent to a reasonably competent user.

Key implications:

  • End-user design means starting from the outputs: an investment committee needs EV, implied share price, scenario comparison and key ratios; a lender needs DSCR and covenant headroom; an FP&A pack needs variance to budget. Planning these first avoids building detail nobody uses.
  • Documented assumptions is more than a source column. It means rationale ("Zudio revenue/sq ft +6% p.a. — below FY23–FY25 LFL of 8–10% given cannibalisation") and an owner. This is the assumption log of the week's cross-cutting concepts.
  • Built-in checks includes both arithmetic checks (balance, cash) and reasonableness checks (margins within historical ranges, utilisation ≤ 90%).
  • Review is part of the Code: a model should be reviewed by someone other than the builder before reliance, proportionate to its risk.

For Indian practitioners the Code is a useful reference when an audit committee or Ind AS 36 impairment review asks "what standard was this model built to?". Big 4 model-assurance reviews in India commonly cite the ICAEW Code or FAST.

Illustration

An FP&A team building Pidilite's FY27 budget applies the Code:

Code principle Implementation
Plan for the user Outputs agreed first: monthly P&L by segment, EBITDA bridge vs FY26, cash flow, capex
Separate I/C/O Inputs tab per segment; calc tabs; Board pack tab
Consistent layout Monthly timeline Apr-26 to Mar-27 in identical columns on every calc tab
Documented assumptions UVG 9% (Consumer & Bazaar), source: management plan; VAM ₹1,050/kg base, source: procurement
Built-in checks Monthly totals = annual; BS balances; cash check; gross margin within 50–56% band
Review Independent review by corporate finance; Inquire comparison vs prior version

Practice Questions

Q1. Code vs FAST [L1]

Explain two ways the ICAEW Code differs in approach from the FAST Standard and one area where they give identical guidance.

Q2. Planning document [L2]

Before building a 5-year Trent model for an IC, draft the one-page planning note the ICAEW Code envisages: purpose, users, key outputs, level of detail, key risks, timeline, review arrangements.

Q3. Reasonableness checks [L2]

Beyond the balance and cash checks, design five reasonableness checks for a Pidilite forecast model (e.g., gross margin band, capex/sales range), stating the threshold and source of each threshold.

💡 Hint: Base thresholds on the historical ratio ranges derived in topic t3 and on physical limits such as utilisation.
