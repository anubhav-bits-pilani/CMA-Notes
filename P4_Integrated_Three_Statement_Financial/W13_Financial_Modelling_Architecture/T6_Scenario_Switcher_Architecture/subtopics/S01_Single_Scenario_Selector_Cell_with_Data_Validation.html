Subtopic note

Single Scenario Selector Cell with Data-Validation Dropdown

Scope: Single selector cell with data-validation dropdown (1 = Base, 2 = Bull, 3 = Bear) on Cover/Inputs

Why it matters

A model that supports scenarios must make it impossible to be ambiguous about which scenario is running. In investment committees, lender presentations and board budget reviews, the first question about any output page is "which case is this?" — and the most embarrassing error in practice is a model emailed with the Bear case live while everyone reads it as Base. The single selector cell is the control point that prevents this: one cell, in one place, validated to accept only defined values, named so every formula refers to it the same way, and displayed prominently on the Cover. Everything else in scenario architecture (driver blocks, live rows, output capture) depends on this one cell being unique and reliable.

Core notes

Design of the selector

Design element Rule Reason
Location One cell on the Cover or at the top of the Inputs/Assumptions sheet Visible on opening; one control point
Content Integer code: 1 = Base, 2 = Bull, 3 = Bear Integers feed CHOOSE/INDEX directly; no text matching
Name Named range Scenario (workbook scope) Every formula reads the same cell; auditable via Name Manager
Validation Data → Data Validation → List or whole number 1–3 Prevents 4, 2.5, blank or text
Label Adjacent cell shows the scenario name via INDEX User sees "Bear", not just "3"
Formatting Blue input font, distinctive input fill, border Colour convention (w13 t2): hardcoded input
Protection Only this cell (and other inputs) unlocked on the Cover Prevents overwriting labels or formulas

Integer codes are preferred over text ("Base", "Bull", "Bear") because selection functions use positions; a text selector requires a MATCH step and fails silently on a typo or trailing space.

Building the dropdown

  1. Create a small scenario list on the Inputs sheet (or a Lists sheet):
Code Scenario name
1 Base
2 Bull
3 Bear
  1. Name the code column Scenario_Codes and the name column Scenario_Names.
  2. Select the selector cell, Data → Data Validation → Allow: List → Source: =Scenario_Codes. Tick "In-cell dropdown". Add an Input Message ("Select 1 = Base, 2 = Bull, 3 = Bear") and an Error Alert of style Stop.
  3. Name the cell Scenario (Formulas → Define Name, scope Workbook).
  4. Next to it, the label: =INDEX(Scenario_Names, Scenario).

An alternative is a list validation on the names with a hidden helper =MATCH(Selected_Name, Scenario_Names, 0) producing the code. This is friendlier for non-modellers but adds a step; whichever is chosen, the code cell is what calculations reference.

Data validation can be bypassed by pasting values into the cell. Add a check on the Checks sheet:

Scenario_Check = --OR(Scenario<1, Scenario>COUNTA(Scenario_Names), Scenario<>INT(Scenario))

which feeds the master check on the Cover (w13 t1 c04).

Where to put it — Cover vs Inputs

  • Cover — maximum visibility; the scenario is the first thing anyone sees; works well with a master check and a version stamp next to it. Recommended for models circulated to non-builders.
  • Inputs/Assumptions top — keeps all inputs on one sheet (cleaner FAST/ICAEW separation); the Cover then displays the scenario via a link (=Scenario and the label), formatted as a link (green), not as an input.

Never have two input cells that both look like selectors. If the Cover displays the scenario, the displayed cell must be a formula, not a second input.

Additional controls next to the selector

The selector often sits in a small control panel with related switches, each with its own named cell:

Switch Name Values
Scenario Scenario 1/2/3
Circularity breaker Circ 0/1 (Week 15)
Units display Units_Div 1 (₹ crore) or 100 (₹ '00 crore) — display only
Lease treatment memo IndAS116_View 1 = post, 2 = pre (output memo only)

Keep the scenario switch distinct from sensitivity inputs (Week 16) — scenarios swap coherent driver sets; sensitivities flex one or two variables.

Five-case extensions

Some models need more than three cases (Base, Bull, Bear, Management case, Lender/Downside). The architecture generalises: extend Scenario_Codes to 1–5, add rows to each driver block (s02), and validation and CHOOSE/INDEX selection extend naturally. Keep the code order fixed once outputs have been circulated, because changing the meaning of "2" silently changes every downstream number.

Edge cases & judgement calls

  • Data tables and the selector. A data table that loops the scenario must be on the same sheet as the selector cell (Excel requires the row/column input cell to be on the data-table sheet) — a reason some builders put the selector on the Cover alongside the scenario summary (s06).
  • Calculation mode. If the workbook is in "Automatic except data tables", changing the selector updates the model but not the summary table until F9; label this on the Cover.
  • Macros. VBA buttons that set the scenario are acceptable for convenience, but the selector cell must remain the single source; never let macros write driver values directly.
  • Version stamping. Record the scenario active at save time in the file name or a "Saved with scenario" cell — combined with a pre-circulation check that the Base case is active (topic pitfall).
  • Power BI and dashboards. If outputs feed Power BI, export all three cases rather than the live case alone, otherwise the dashboard reflects whichever case was last selected.

Key takeaways

  • One selector cell, named Scenario, holding an integer code with data validation.
  • Show the scenario name next to it with INDEX; colour it as an input and unlock only that cell.
  • Integer codes avoid text-matching errors and feed CHOOSE/INDEX directly.
  • Add a check that catches invalid values pasted over validation.
  • If the selector sits on Inputs, the Cover displays it by formula — never a second input.
  • Keep code meanings fixed once outputs are circulated; extend to more cases by adding codes.

Practice Questions

Q1. Build the selector [L1]

Write step-by-step instructions to create a scenario selector on a Cover sheet with codes 1–3, a dropdown, an error alert, a workbook-scoped name and a label cell showing the scenario name. Include the exact formula for the label.

Q2. Validation bypass check [L2]

A user pastes "Bull" (text) into the selector cell, bypassing data validation. Describe what happens to CHOOSE-based live rows, write a check formula that flags the problem, and explain how it reaches the master check on the Cover.

💡 Hint: Test for non-numeric, out-of-range and non-integer values in one expression.

Q3. Cover vs Inputs placement [L2]

Your model will be used by a lender's credit team who will only flip scenarios and print outputs. Recommend where to place the selector and what to place next to it, and justify the choice against FAST/ICAEW separation principles.

Q4. Extending to five cases [L3]

A private-equity client wants Base, Bull, Bear, Management and Lender cases. Specify every change needed to the selector, lists, driver blocks, label formulas and summary table, and the risks of re-ordering the codes after outputs have been shared.
