Roadmap topic: Scenario Switcher Architecture: Building Base, Bull, and Bear case driver blocks controlled via a single scenario selector cell

Overview

Every forecast is wrong; the useful question is how wrong it could be and what would happen if it were. Scenario analysis answers that by running the whole model under a small number of coherent alternative worlds — typically Base, Bull and Bear — and comparing the results. For the model to support this reliably, scenarios must be an architectural feature, not an afterthought: one selector cell controls the case; driver blocks on the Assumptions sheet hold each case's values; one Live row per driver feeds the calculations; outputs are captured side by side and labelled so no one misreads which case they are looking at. Built this way, flipping from Base to Bear is a single keystroke, every schedule responds (revenue, costs, capex, working capital, debt, valuation), and a reviewer can see exactly what differs between cases.

In the target roles this is routine. Sell-side and buy-side analysts present Bull/Base/Bear price targets; transaction services and lenders run management, base and downside cases through acquisition and project-finance models; FP&A teams maintain budget, stretch and downside versions and update them through rolling forecasts. Model reviewers check the switch mechanics first — scattered IF(Scenario=…) logic, volatile OFFSET switches and data tables pointing at another sheet's switch are standard audit findings. The architecture also pays off later in this phase: Week 15 stress tests run through the same switch, and Week 16 contrasts scenarios with sensitivity grids.

The learning sequence follows the data flow. Set up the single selector with data validation (s01) and the one-switch rule (c02). Build driver blocks with Base/Bull/Bear rows and a Live row (s02, c01) using non-volatile selection functions (s03). Decide which drivers to flex across the chain from demand to cash (s04) and tie them together with coherent narratives rather than single-variable tweaks (s05), checking internal consistency of growth, capex, NWC and funding (c05). Finally, capture outputs in a scenario summary (s06, c03) and label every output page and document each case (s07, c04).

Related concepts to study

Week 15: Stress testing through the switch

→ Week 15 (w15_t5): stress testing runs through this switch

In Week 15 the integrated model gains a debt schedule, revolver and minimum cash logic, and stress tests ask how far operating drivers can deteriorate before covenants break or the revolver limit is exhausted. Those stress cases should be additional codes on the same selector (e.g., 4 = Lender stress) with their own driver-block rows, not a parallel set of overrides. Because the switch architecture already flexes volume, margins, capex and NWC days coherently, stress tests inherit those links; what changes is severity and, sometimes, deliberate combination of adverse moves beyond a single narrative. Build the selector and blocks now so they extend cleanly.

Week 16: Sensitivity grids vs scenarios

→ Week 16 (w16_t5): sensitivity grids vs scenarios

Week 16 introduces sensitivity analysis — one- and two-variable data tables over WACC, terminal growth, exit multiples or single operating drivers — and tornado charts ranking driver impact. Sensitivities and scenarios answer different questions: a sensitivity isolates how much value depends on one variable with everything else held constant; a scenario shows the outcome of a coherent alternative world. They combine usefully (a Scenario × WACC grid), and the tornado helps choose which drivers to flex in scenarios (s04). Keep the mechanisms separate in the model: sensitivity inputs are not scenario codes, and sensitivity data tables must also sit on the sheet of their input cells.

Phase 5: Budget versions and rolling forecast scenarios

→ Phase 5 (W17–20): budget versions and rolling forecast scenarios

FP&A uses the same architecture with different vocabulary: Budget, Stretch and Downside versions; Reforecast Q1, Q2; management and board cases. Driver blocks hold the version assumptions (volume, price, headcount, increments, opex inflation), and a version selector drives the plan. Rolling forecasts update the Base drivers each quarter as actuals land, often keeping Bull/Bear as deltas around the latest Base (s02 base-plus-delta style). Version labelling and a change log become critical when the board approves one version and management reports against another. The discipline learned here transfers directly to planning tools and Excel-based budget models.

Phase 3: Power BI what-if parameters

→ Phase 3 (W9–12): Power BI what-if parameters as the reporting analogue

In Power BI, a what-if parameter creates a disconnected table of values and a measure returning the selected value (via SELECTEDVALUE), exposed through a slicer; measures then use the parameter to recompute results — the reporting analogue of the selector cell and Live row. A scenario dimension table (Base, Bull, Bear) with driver values by year, filtered by a slicer, mirrors the driver block. Two cautions from this topic carry over: show the selected scenario visibly on every report page (a card), and avoid embedding scenario logic in many separate measures — centralise it in one driver measure that others reference.

Common pitfalls

Scenario IFs scattered across calculation sheets

Scenario IF statements scattered across calculation sheets

The mistake: formulas such as =IF(Scenario=3, Revenue*0.9, Revenue) on the revenue sheet, a separate capex IF on the PPE sheet, and a days IF on the working capital sheet. It happens because adding an IF in place is faster than adding a driver row. It hides assumptions, breaks row consistency, and makes cases incoherent and unauditable. The correct treatment is the one-switch rule (c02): every case difference is a value in a driver block; calculations reference Live rows only. Detect it by searching formulas for "Scenario" (Find in formulas, or Trace Dependents from the selector): every hit outside the Assumptions Live rows, labels, checks and summary table is a finding.

Bear case that cuts revenue only

Bear case cuts revenue but leaves costs, capex and NWC days unchanged

The mistake: the Bear case lowers a revenue growth rate while COGS, staff, opex, capex and working-capital days stay at Base. It happens when the model's costs are % of revenue (so they fall pro rata, preserving margins) or when only the revenue block has scenario rows. The result is a Bear case with unchanged margins, too much capex and unrealistically good cash conversion — or, conversely, costs that do not respond to lower volume at all. The correct treatment is to flex the full driver set coherently (s04, s05) on a driver-based cost structure (Topic 5), including NWC days and capex timing, and to check consistency (c05). Detect it by comparing Bear vs Base on margin, capex ÷ revenue and NWC days in the scenario summary.

Data table on a different sheet from the switch

Data table on one sheet pointing at a switch on another sheet (Excel disallows it)

The mistake: building the scenario summary data table on an Outputs sheet while the Scenario cell sits on Inputs. Excel rejects it ("Input cell reference is not valid"), and builders then work around it with fragile links — for example, making the Inputs selector a formula pointing at an Outputs cell, which creates two apparent switches, or pasting static values. The correct treatment is to place the data table on the same sheet as the selector (often both on the Cover), or to move the selector to the sheet hosting the summary, keeping one input cell (s01, s06, c03). Detect it by checking that the selector is a blue hardcoded input (not a formula) and that the summary table is a genuine {=TABLE(...)} on that sheet.

File circulated with Bull or Bear active

File saved and circulated with Bear/Bull left active

The mistake: the analyst finishes testing the Bear case, saves and emails the file; recipients read Bear outputs as Base. It happens under time pressure, especially when headers are typed rather than formula-driven. The correct treatment: live scenario headers on every output page (c04), a visible "non-Base case active" flag on the Cover with conditional formatting, a pre-circulation checklist (selector = 1, master check = 0, data tables refreshed), and optionally a file-name convention that includes the active case. Detect it by opening the file and reading the Cover flag and headers before using any number; in review, check the selector value of every file version circulated.

Practice Questions

Q1. Build the switch for a Trent model [L3]

You are building the Week 13 exercise model for Trent. (a) Specify the selector cell, name list, validation and Cover display. (b) Design driver blocks for Zudio and Westside store additions, LFL, gross margin, store staff increment, fit-out capex per sq ft, inventory days and payable days, with illustrative Base/Bull/Bear values for FY26E–FY30E and a written narrative for each case. (c) Write the Live row formula and the integrity check for one block. (d) Lay out the scenario summary data table, naming its sheet and outputs. (e) Describe the checks that feed the master flag on the Cover.

💡 Hint: Decide first where the selector lives, because the summary data table must share its sheet.

Q2. Refactor a legacy model [L2]

A Pidilite model inherited from a colleague has: an OFFSET-based scenario switch on Inputs; IF(Scenario=3,…) haircuts on revenue and gross margin in the P&L; a separate "Capex case" dropdown on the PPE sheet; a scenario summary pasted as values dated four months ago; and typed "Base case" headers on outputs. List every finding with its risk, and set out a step-by-step refactoring plan, including how you would reconcile outputs before and after for each case.

Q3. Coherent Bear case with funding consequences [L3]

For a retailer with FY27E Base revenue ₹24,000 crore, EBITDA ₹3,900 crore, capex ₹1,450 crore, DIO 65, DPO 60, DSO 5, opening cash ₹900 crore, minimum cash ₹300 crore and a ₹1,000 crore revolver at 9.5%: (a) write a demand-slowdown Bear narrative; (b) set Bear values for LFL, store adds, gross margin, A&P %, capex, DIO and DPO; (c) estimate Bear EBITDA, change in NWC, pre-financing FCF and revolver draw with stated assumptions for COGS and tax; (d) explain which management responses you included and why; (e) list the consistency checks the Bear case passes.

Q4. Interview — scenarios vs sensitivities and controls [L2]

An interviewer asks: "How do you build scenarios in a model, how are they different from sensitivities, and how do you make sure nobody misreads which case they are looking at?" Prepare a structured three-minute answer covering the selector, driver blocks, selection functions, narratives, output capture and labelling controls.
