Subtopic note

Formula Engine: SUMIFS, XLOOKUP, DAX and Dynamic Arrays

Scope: Formula engine: SUMIFS/XLOOKUP or Power Pivot/DAX from TB extract to BS, P&L, SOCIE and notes; dynamic arrays for note tables

Why it matters

The formula engine is the layer that turns "TB + mapping" into statements. Done well, it is transparent (every number traces back to accounts), robust (new accounts and adjustments flow without editing formulas) and fast to review. Done badly, it is a maze of hard-coded cell references, pasted values and manual overrides that breaks every time the TB extract changes shape. Reviewers and auditors increasingly ask for a walkthrough of the engine, and in FP&A the same engine converts historical actuals into model templates. Two implementation families exist: worksheet formulas (SUMIFS/XLOOKUP and dynamic arrays) and the data model (Power Query + Power Pivot/DAX or Power BI). Both should follow the same design.

Core notes

1. Data flow

  1. TB extract (Power Query from ERP export/CSV): Entity, Account, Description, Debit, Credit, Closing balance (debits positive, credits negative), Period.
  2. Mapping table (s02): Account → Line ID, Note, Sub-note, C/NC, CF tag, DT category, Sign.
  3. Adjustment layer (s04): entries with reference, account, amount.
  4. Final TB = TB + adjustments, merged with mapping (Power Query merge or XLOOKUP columns).
  5. Outputs: BS, P&L, SOCIE, notes, CF, checks — each pulling from the final TB by attribute.

The rule: outputs reference attributes, never accounts or cells in the TB. A new account mapped to an existing line appears automatically.

2. Worksheet engine — SUMIFS and XLOOKUP

Structured tables: FinalTB (Account, Bal, Line, Note, SubNote, CNC, CFTag, Sign, Year); statement rows hold a Line ID in column B.

Mapping attributes onto the TB:

=XLOOKUP([@Account], Map[Account], Map[Line], "UNMAPPED")

Face line value (current year), with display sign so liabilities and income show positive:

=SUMIFS(FinalTB[Bal], FinalTB[Line], B12, FinalTB[Year], CurYear) * XLOOKUP(B12, Lines[LineID], Lines[DisplaySign])

Note sub-row:

=SUMIFS(FinalTB[Bal], FinalTB[SubNote], B30, FinalTB[Year], CurYear) * -1

Use a Lines table holding each Line ID's caption, order, display sign and parent so subtotals are SUMIFS on the parent attribute rather than hand-built additions. Avoid SUMPRODUCT over entire columns for speed; avoid INDIRECT/OFFSET (volatile and untraceable).

3. Dynamic arrays for note tables

Notes with a variable number of rows (e.g., borrowings by lender, investments by scrip, related-party balances by party) suit dynamic arrays:

=LET(
  t, FILTER(FinalTB[[Description]:[Bal]], (FinalTB[Note]="N15")*(FinalTB[Year]=CurYear)),
  g, GROUPBY(CHOOSECOLS(t,1), CHOOSECOLS(t,2)*-1, SUM, 0, 1),
  g)

GROUPBY/PIVOTBY are available in current Microsoft 365 builds; where not available use UNIQUE on the description plus SUMIFS against the spilled range (=SUMIFS(FinalTB[Bal], FinalTB[Description], E5#, FinalTB[Note], "N15")). SORTBY orders rows; VSTACK appends a total row. Spilled ranges referenced with # keep the note and its total in sync.

4. SOCIE

The statement of changes in equity is generated from equity accounts mapped with a movement type attribute in a sub-ledger of equity movements (opening, profit for the year, OCI items, dividends, transfers to reserves, share issues, buy-backs). Profit for the year in SOCIE is linked to the P&L output, not to the retained earnings account movement — that comparison is the integrity check (c03).

5. Data model engine — Power Pivot / DAX

Model: FinalTB fact table related to Map (Account) and Lines (LineID), Calendar (Period). Measures:

Balance := SUM ( FinalTB[Bal] )

Line Value :=
VAR s = SELECTEDVALUE ( Lines[DisplaySign], 1 )
RETURN [Balance] * s

Line Value PY :=
CALCULATE ( [Line Value], SAMEPERIODLASTYEAR ( 'Calendar'[Date] ) )

Unmapped Count :=
COUNTROWS ( FILTER ( FinalTB, ISBLANK ( RELATED ( Map[Line] ) ) ) )

A matrix visual with Lines[Caption] on rows (sorted by Lines[Order]) and the measures in columns renders the BS/P&L; Excel CUBEVALUE formulas can place model values into a fixed Schedule III layout when exact formatting is needed. Balances are snapshots, so for balance sheet lines use period-end filtering (LASTDATE / closing balance in the extract) rather than summing movements across periods.

6. Choosing between them

Factor SUMIFS/XLOOKUP Power Pivot/DAX
Transparency to auditors High — formulas visible per cell Medium — measures need documentation
Volume (multi-entity, monthly history) Slows beyond ~100k rows Scales to millions
Fixed-format Schedule III layout Natural Needs CUBE functions or report layout
Multi-period, multi-entity slicing Manual Native
Skills needed Excel Power Query, DAX

Many teams use Power Query for extract and merge, a worksheet engine for statutory statements, and Power BI for management and flux dashboards — all off the same final TB.

Illustration

Final TB lines mapped to BS.CL.FL.TP (trade payables): 520000 MSME (₹(4,20,00,000)), 521000 Others (₹(18,65,00,000)), 521500 Accrued GRNI (mapped to other financial liabilities, not TP). SUMIFS on Line "BS.CL.FL.TP" returns −22,85,00,000; display sign −1 gives ₹22,85,00,000 (₹22.85 crore) on the face. A new account 520100 "MSME – capital creditors" mapped to BS.CL.FL.TP and sub-note N18.1 is picked up by both the face and Note 18 next close without any formula change.

Edge cases & judgement calls

  • Sign handling in one place only — either the Lines display sign or the mapping — never both, or liabilities appear negative (topic pitfall).
  • Rounding after aggregation, not per account (s07, c04) — otherwise totals do not cast.
  • Prior-year columns must use the current mapping applied to prior-year TB, or regrouped comparatives will not be consistent (s07).
  • Circularity: current tax depends on PBT, which depends on the final TB; keep tax computations in a schedule that posts to the adjustment layer rather than formulas referencing the FS.
  • Performance: whole-column references in SUMIFS on large tables slow recalculation; structured references keep ranges tight.
  • Manual overrides in output cells are prohibited; use the adjustment layer (s04) — a check comparing each output cell's formula status (e.g., ISFORMULA) can detect hard-codes.

Key takeaways

  • Outputs reference mapping attributes, never TB rows or cells, so new accounts and adjustments flow automatically.
  • SUMIFS + XLOOKUP on structured tables is transparent and suits fixed Schedule III layouts; DAX scales for multi-entity, multi-period work.
  • Dynamic arrays (FILTER, GROUPBY, UNIQUE, SORTBY, VSTACK) generate variable-length note tables.
  • SOCIE profit links to the P&L output so it can be checked against retained earnings.
  • Keep sign, rounding and tax logic in single, documented places.

Practice Questions

Q1. Write the face formulas [L1]

Given structured tables FinalTB (Account, Bal, Line, Year) and Lines (LineID, Caption, DisplaySign), write formulas for current-year and prior-year values of the line "BS.CA.FA.TR" (trade receivables) and a subtotal for "Total current assets" using a Parent attribute.

Q2. Dynamic note table [L2]

Write a dynamic-array formula that produces the borrowings note: lender-wise list of term loans (from accounts mapped to sub-note N15.1) with current-year and prior-year balances shown positive, sorted by current-year balance descending, with a total row. State the fallback approach if GROUPBY is unavailable.

💡 Hint: Build the unique list first, then calculate each column against the spilled range.

Q3. DAX model [L2]

Design a Power Pivot model (tables, relationships, measures) that produces the Schedule III P&L for three entities and 24 months, with a measure for unmapped accounts and a measure for the BS check. Explain how you would handle closing balances for BS lines versus movements for P&L lines.

Q4. Engine audit [L3]

You inherit a reporting workbook in which 30% of BS cells reference specific TB rows (e.g., =TB!F214) and some are hard-coded. Describe how you would detect these, re-engineer the workbook to an attribute-driven engine without disrupting the quarter-end close, and evidence that the new engine reproduces the last audited FS.
