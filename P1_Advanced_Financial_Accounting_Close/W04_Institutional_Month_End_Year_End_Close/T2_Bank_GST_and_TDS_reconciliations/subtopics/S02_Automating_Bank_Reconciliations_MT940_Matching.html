Subtopic note

Automating Bank Reconciliations: MT940, Matching Rules and Ageing

Scope: Automation: MT940/CSV statement import, rule-based matching, Power Query, unmatched-item ageing

Why it matters

A company with 25 bank accounts and 40,000 monthly bank lines cannot reconcile manually within a T+4 window. Automation shifts effort from ticking to investigating exceptions: statements are imported in a structured format, matched to the GL by deterministic rules, and only unmatched items reach a human, with ageing that drives escalation. Auditors increasingly rely on automated recs as evidence for IFC, provided the matching rules are controlled and the completeness of imported data is proven. For a CMA with SQL and Power Query exposure, this is a natural place to demonstrate automation value in a controller or FP&A role.

Core notes

Statement formats

  • MT940 (SWIFT customer statement message): a tagged text format. Key tags: :20: transaction reference, :25: account identification, :28C: statement number, :60F: opening balance (D/C mark, date, currency, amount), :61: statement line (value date, entry date, D/C, amount, transaction type, references), :86: information to account owner (narrative, often containing UTR, cheque number or remitter name), :62F: closing balance. MT942 is the intraday equivalent.
  • ISO 20022 camt.053: XML bank-to-customer statement, increasingly offered by Indian banks for host-to-host connectivity; richer structured remittance data.
  • CSV/Excel from net banking: most common for smaller entities; column layouts differ by bank and change without notice, so the import must validate headers.

Completeness control: for each statement import, check that opening balance = prior closing balance, that \(\text{Opening} + \sum \text{Credits} - \sum \text{Debits} = \text{Closing}\), and that statement numbers are sequential. An import that fails these checks must not be reconciled.

Rule-based matching

Matching runs in passes from strictest to loosest, each pass removing matched items from the pool:

Pass Rule Typical items Confidence
1 Exact reference (UTR/cheque number/payment run ID) + exact amount Vendor payments, cheques High — auto-clear
2 Exact amount + date within ±3 days + same counterparty Customer receipts High — auto-clear
3 One-to-many / many-to-one: sum of book items = bank item with common reference Bulk payment files, batched card settlements Medium — auto-propose, reviewer approves
4 Narrative rules: text contains "CHGS", "GST ON CHGS", "INT CR", "NEFT RTN" Bank charges, interest, returns Auto-post bank-only item via template
5 Tolerance match: amount within ₹10 or 0.1%, same reference FX short-receipts, rounding Medium — reviewer approves
— Unmatched Everything else Manual investigation and ageing

Rules are controlled objects: changes require approval and testing, since a loose rule (e.g., amount-only matching) can clear unrelated items and hide errors.

Power Query implementation

A practical workflow in Excel/Power BI:

  1. Import: Folder connector pointing to the statements folder; combine files; for MT940, parse lines by tag using Text.StartsWith and split :61: lines into value date, D/C mark and amount.
  2. Normalise: convert amounts to signed numbers (credits positive for bank, debits negative), trim and upper-case narratives, extract UTR (e.g., 22-character NEFT/RTGS references) with Text.Middle or Text.Select.
  3. Load GL: bank GL lines from the ERP extract, with the same signed convention (receipts positive).
  4. Merge for pass 1: inner join on Reference and Amount; the anti-joins (left anti, right anti) produce unmatched lists for the next pass.
  5. Pass 2: join on Amount and Counterparty, then filter on date difference ≤ 3 days.
  6. Output: matched register, unmatched bank items, unmatched book items, with an ageing column.
let
    Bank   = Excel.CurrentWorkbook(){[Name="BankLines"]}[Content],
    GL     = Excel.CurrentWorkbook(){[Name="GLLines"]}[Content],
    P1     = Table.NestedJoin(Bank, {"UTR","Amount"}, GL, {"UTR","Amount"}, "GLMatch", JoinKind.LeftAnti),
    Aged   = Table.AddColumn(P1, "AgeDays", each Duration.Days(#date(2027,3,31) - [ValueDate]), Int64.Type),
    Bucket = Table.AddColumn(Aged, "Bucket", each if [AgeDays] <= 30 then "0-30" else if [AgeDays] <= 60 then "31-60" else if [AgeDays] <= 90 then "61-90" else ">90", type text)
in
    Bucket

In Excel, a quick check on whether each bank line has a GL partner:

=XLOOKUP([@UTR]&"|"&TEXT([@Amount],"0.00"), GL[UTR]&"|"&TEXT(GL[Amount],"0.00"), GL[DocNo], "UNMATCHED")

Unmatched-item ageing

Ageing is computed from the transaction date of each unmatched item to the reconciliation date, on a gross (item-by-item) basis — never on the net difference (topic pitfall 4). Standard buckets: 0–30, 31–60, 61–90, over 90 days. Treatment:

Unmatched type Typical cause Action Escalation
Bank credit, no book entry Unidentified customer receipt Post to unidentified receipts (Topic 4), contact bank for remitter details > 30 days: controller
Bank debit, no book entry Charges, direct debits, fraud Book or dispute with bank Any unknown debit: immediate
Book receipt, not in bank Deposit in transit or fictitious receipt Verify with bank deposit slip > 7 days: investigate
Book payment, not in bank Unpresented cheque Cheques stale after three months — reverse to liability > 90 days: write back to vendor liability

Illustration: on 31 March, unmatched bank credits total ₹1.84 crore across 63 items: ₹1.21 crore (0–30 days), ₹0.38 crore (31–60), ₹0.17 crore (61–90), ₹0.08 crore (>90). The >60-day items (₹0.25 crore) require controller approval to remain open, and the >90-day items are reviewed for refund to the remitter or recognition per policy.

Edge cases & judgement calls

  • Value date vs entry date: use value date for interest and cash-pooling purposes, entry date for reconciliation consistency; document the choice.
  • Bulk payment files: a single bank debit for 300 salary credits must be matched to the payroll batch total, with rejected credits (account closed) returning as separate credits.
  • Payment gateway settlements: gross sales, MDR, GST on MDR and refunds net into a single credit; match against the gateway settlement report first, then to the bank.
  • Format changes: a bank silently changing CSV column order can shift amounts into the wrong field; header validation and control totals catch this.
  • Rule drift: if auto-match rates fall sharply, investigate customer reference behaviour or a broken parser rather than loosening rules.

Key takeaways

  • Import structured statements (MT940/camt.053/CSV) with balance and sequence completeness checks.
  • Match in passes from strict to loose; treat matching rules as controlled configuration.
  • Power Query merges and anti-joins implement passes; XLOOKUP on composite keys gives quick checks.
  • Age unmatched items gross, by type, with defined escalation and resolution actions.
  • Automation is evidence for IFC only if import completeness and rule changes are controlled.

Practice Questions

Q1. MT940 parsing [L1]

Explain the purpose of tags :60F:, :61:, :86: and :62F: in an MT940 statement and describe the completeness checks you would perform before reconciling.

Q2. Matching design [L2]

A company receives 9,000 customer receipts a month via NEFT, UPI collections and a payment gateway. Design a five-pass matching logic with keys, tolerances and auto-clear/approve settings, and explain the controls over rule changes.

💡 Hint: Treat the payment gateway as a separate sub-reconciliation before matching to bank.

Q3. Power Query build [L3]

Build specification: from a folder of daily CSV statements (columns Date, Narration, ChqRef, Debit, Credit, Balance) and a GL extract (DocNo, PostingDate, Reference, Amount), produce matched, unmatched-bank and unmatched-book tables with ageing buckets. Specify each query step, merge kind and the validation that daily balances roll forward.

Q4. Ageing analysis [L2]

Unmatched items at 31 March: bank credits — 14 items, ₹42 lakh (all ≤ 30 days), 6 items ₹19 lakh (45–80 days), 3 items ₹7 lakh (> 120 days); book payments not in bank — 22 cheques, ₹31 lakh, of which 5 cheques of ₹6.4 lakh are older than 3 months. State the actions, entries (if any) and escalations for each group.
